## 1. Core Concept: The Three Pillars

For SC-200, always remember this triad:

| Product | Role |
|---|---|
| Microsoft Defender for Endpoint (MDE) | Detects threats |
| Microsoft Intune | Manages devices |
| Microsoft Entra ID | Controls access |

> Exam Tip: If a question describes "detect, evaluate, block," map it to MDE, then Intune, then Entra ID.

---

## 2. Microsoft Defender for Endpoint (MDE)

- MDE = Endpoint detection and response (EDR) service.
- Protects: Windows, Linux, macOS, Servers.
- Detects: Malware, ransomware, suspicious processes.
- Role in chain: The Detector - flags device risk (e.g., "Risk level: High").

### SC-200 Exam Tips
- MDE is the first responder in most attack scenarios (malware, USB, or email-triggered).
- MDE risk signals feed directly into Intune Compliance Policies.
- Know MDE covers multi-OS, not just Windows.

---

## 3. Microsoft Defender for Office 365 (MDO)

Protects:
- Exchange Online (Email)
- Microsoft Teams
- SharePoint Online
- OneDrive
- Microsoft 365 collaboration tools

Detects:
- Phishing
- Malicious links
- Malicious attachments

> Think of MDO as Microsoft's email and collaboration security solution.

### SC-200 Exam Tips
- MDO covers the email and collaboration layer, not endpoints.
- In an XDR investigation, MDO is usually the entry point (initial phishing vector).
- MDO can act on Defender XDR instructions (e.g., search all mailboxes, remove malicious file).

---

## 4. Microsoft Intune

Definition: Cloud-based endpoint (device) management solution.

Manages:
- Windows, macOS, Android, iPhones/iPads

Capabilities:
- Deploy applications
- Push security policies
- Enforce BitLocker encryption
- Configure Windows settings
- Manage BYOD devices
- Check device compliance
- Wipe lost or stolen devices

Compliance Example:
- Policy: laptops must have antivirus enabled, BitLocker enabled, and a screen lock.
- Intune checks every device.
- Non-conforming device is marked Noncompliant.
- Intune reports this status to Entra ID.

> Intune is the bridge: it doesn't hunt malware (that's MDE's job), but it listens to MDE's risk signal and converts it into a compliance verdict.

### SC-200 Exam Tips
- Intune uses Compliance Policies to evaluate device health.
- Intune itself does not block access - it only marks devices Noncompliant; Entra ID enforces the block via Conditional Access.
- Know the flow: MDE detects, then Intune marks Noncompliant, then Entra ID blocks.

---

## 5. Microsoft Entra ID

Definition: Microsoft's Identity and Access Management (IAM) service (formerly Azure AD).

Manages:
- User accounts, Groups
- Authentication
- Single Sign-On (SSO)
- Multi-Factor Authentication (MFA)
- Conditional Access

Main job: Verifies who you are (Authentication) and decides what you can access (Authorization).

Decision logic on login (Outlook, Teams, SharePoint, Azure Portal):
- Allow?
- Deny?
- Require MFA?
- Require compliant device?

> Entra ID is the Enforcer. Conditional Access = "if-then" rules, e.g., If accessing corporate email, then device must be compliant.

### SC-200 Exam Tips
- Conditional Access is the enforcement mechanism - memorize this term.
- Entra ID Protection (identity-specific) detects impossible travel, risky sign-ins, and compromised accounts.
- Entra ID is the final gate in the Zero Trust chain.

## 6. Zero Trust Chain Reaction (MDE, Intune, Entra ID)

This is a classic SC-200 scenario question.

| Role | Product | Action |
|---|---|---|
| The Detector | MDE | Detects infected device, flags "Risk level: High" |
| The Evaluator | Intune | Applies compliance policy, marks device Noncompliant |
| The Enforcer | Entra ID | Conditional Access triggers, Access Denied to Office/Teams/company apps |

Result: The compromised device is automatically quarantined from the network, without manual IT intervention. This is Zero Trust security architecture in action.

### SC-200 Exam Tips
- This exact chain (Detect, Evaluate, Enforce) is a favorite scenario-based question pattern.
- Key phrase to recognize: "automatically... without a human admin" points to Zero Trust automation.
- Remember which product performs which verb: Detect = MDE, Evaluate = Intune, Enforce = Entra ID.

## 7. Microsoft Graph and Security Graph

### Microsoft Graph
- Microsoft has hundreds of services (Outlook, Teams, SharePoint, OneDrive, Entra ID, Intune, Defender XDR, Defender for Identity, Defender for Cloud).
- Normally each has its own separate API.
- Microsoft Graph is a single unified endpoint/doorway to access data from all Microsoft 365, Windows, and Enterprise Mobility + Security services.

| Without Graph | With Graph |
|---|---|
| Teams API, Outlook API, Entra API, Intune API (many doors) | Microsoft Graph API (one door) |

### Security Graph
- The security-focused subset of Microsoft Graph.
- Aggregates data from: Defender products, Entra ID, Intune, Azure security services, Microsoft security partners.
- Presents it via a common interface - the "Security Brain."

Diagram logic:
```
Microsoft 365   \
                  \
Azure ----------> Microsoft Graph Security API
                  /
Microsoft Partners /
```
Applications query the Graph Security API instead of querying every product individually.

Why it matters (phishing example):
- Without Security Graph: manually check Outlook, Defender, Entra, Intune, Azure separately (slow).
- With Security Graph: one query retrieves data from all services (fast investigation).

### SC-200 Exam Tips
- Microsoft Graph is the general unified API for all Microsoft services.
- Security Graph / Graph Security API is the security-specific subset used for investigations.
- Know the value proposition: fewer queries, faster investigation, single interface.

## 8. Microsoft Defender XDR

Definition: A platform combining multiple Microsoft security products into one investigation and response system.

Problem it solves: Instead of separately investigating email, endpoint, identity, and cloud attacks, Defender XDR merges everything into one incident.

Without XDR:
```
MDE -> Alert #1
MDO -> Alert #2
MDI -> Alert #3
Defender for Cloud Apps -> Alert #4
```
SOC analyst sees 4 disconnected alerts.

With XDR:
```
Phishing Email -> Malware Executed -> Credential Stolen -> Suspicious Login -> Cloud Access
```
All correlated into Incident #123 - one incident, one investigation, one timeline.

> Exam answer trigger: "Which solution correlates alerts across endpoints, email, identities, and cloud apps into a single incident?" Answer: Microsoft Defender XDR.

### SC-200 Exam Tips
- Defender XDR does not replace MDE/MDO/MDI/Defender for Cloud Apps - it correlates their signals.
- Core value = correlation, not detection.
- Memorize the phishing to malware to credential theft to risky login kill-chain example.

## 9. Products Feeding Defender XDR

| Product | Protects | Detects |
|---|---|---|
| Defender for Endpoint (MDE) | Windows, Linux, macOS, Servers | Malware, ransomware, suspicious processes |
| Defender for Office 365 (MDO) | Exchange, Outlook, Teams, SharePoint, OneDrive | Phishing, malicious links/attachments |
| Defender for Identity (MDI) | Active Directory | Pass-the-Hash, Kerberoasting, lateral movement, credential theft |
| Defender for Cloud Apps | Cloud/SaaS apps (Salesforce, Box, Dropbox) | Risky SaaS activity |
| Entra ID Protection | User identities | Impossible travel, risky sign-ins, compromised accounts |

Why XDR is powerful - shared signals example:

1. MDO detects phishing - malware.docx sent to user@company.com
2. User opens file - MDE detects powershell.exe downloading malware
3. MDI detects Pass-the-Hash (credential theft)
4. Entra ID detects risky login from unusual location (e.g., Russia)

Instead of 4 separate alerts, Defender XDR builds one incident: "Phishing led to endpoint compromise, which led to credential theft, which led to account compromise."

### SC-200 Exam Tips
- Memorize which product detects which attack type (table above is a common exam matching question).
- MDI is identity/AD-focused, detects Pass-the-Hash and Kerberoasting (common exam keywords).
- Defender for Cloud Apps is not the same as Defender for Cloud (workloads) - don't confuse them (see comparison table in section 13).

## 10. Automatic Response and Self-Healing

Automatic Response Example:
- MDE finds malware (evil.exe) on a device.
- MDE shares info with Defender XDR.
- Defender XDR instructs MDO: search all mailboxes, remove evil.exe.
- Result: every mailbox is cleaned automatically.

Second Example - Device Compromise:
- Device Risk = High.
- Defender XDR triggers:
  - Device Isolation (via MDE)
  - User Access Blocked (via Entra ID + Intune)

Self-Healing (Microsoft's term for automated remediation):

| Trigger | Automated Action |
|---|---|
| Compromised Mailbox | Remove malicious emails |
| Compromised Device | Quarantine malware |
| Compromised Account | Force password reset |

### SC-200 Exam Tips
- "Self-healing" is Microsoft's official term - likely appears as exam vocabulary.
- Automated response actions span multiple products simultaneously (MDE + MDO + Entra ID + Intune).
- Know real examples: mailbox cleanup, device isolation, forced password reset.

## 11. Threat Hunting and KQL

- Defender XDR stores security data that analysts search using KQL (Kusto Query Language).
- This activity is called Advanced Hunting - a major SC-200 topic.

Example KQL query:
```kql
DeviceProcessEvents
| where FileName == "powershell.exe"
```

### SC-200 Exam Tips
- Advanced Hunting = KQL queries against Defender XDR data.
- Know basic KQL syntax structure: TableName | where Column == "Value".
- Common tables to recognize: DeviceProcessEvents, DeviceNetworkEvents, DeviceFileEvents, EmailEvents (know the naming pattern).

## 12. Single Pane of Glass and Incident Correlation

Single Pane of Glass = one unified portal instead of separate portals per product.

| Without XDR | With XDR |
|---|---|
| Portal 1 - Endpoint | |
| Portal 2 - Email | Microsoft Defender Portal (one place for everything) |
| Portal 3 - Identity | |
| Portal 4 - Cloud | |

Combined Incident Queue:

| Without XDR | With XDR |
|---|---|
| 100 alerts | 20 incidents (related alerts grouped) |

> This reduces alert fatigue - a key SOC efficiency concept.

### SC-200 Exam Tips
- Single pane of glass = one portal, unified visibility.
- Grouping alerts into incidents reduces alert fatigue - likely exam phrase to recognize.
- The portal name to remember: Microsoft Defender Portal.

## 14. SC-200 Last Minute Revision

### One-Page Cheat Sheet

The Golden Triad
> MDE detects, Intune manages/evaluates, Entra ID controls access.

The Zero Trust Chain
> Detector (MDE) -> Evaluator (Intune) -> Enforcer (Entra ID)
> Result: automatic quarantine, no human intervention needed.

Graph Hierarchy
> Microsoft Graph (all M365/Windows/EMS data) contains Security Graph / Graph Security API (security-only subset).

XDR Value
> Defender XDR doesn't detect - it correlates. Many alerts become few incidents.

### Quick-Reference Table: Who Protects What

| Product | Protects | Key Detection |
|---|---|---|
| MDE | Endpoints (Win/Linux/macOS/Servers) | Malware, ransomware |
| MDO | Email and Collaboration (Exchange/Teams/SharePoint/OneDrive) | Phishing, malicious attachments |
| MDI | Active Directory | Pass-the-Hash, Kerberoasting, lateral movement |
| Defender for Cloud Apps | SaaS apps | Risky cloud app activity |
| Entra ID Protection | User identities | Impossible travel, risky sign-ins |
| Defender for Cloud | Azure/AWS/GCP workloads | Cloud misconfigurations |
| Defender XDR | All of the above | Correlated multi-stage incidents |

### Frequently Confused Concepts

| Term A | Term B | Difference |
|---|---|---|
| Defender for Cloud Apps | Defender for Cloud | SaaS/CASB vs. cloud workload (IaaS/PaaS) protection |
| Microsoft Graph | Security Graph | General API vs. security-only subset |
| Intune | Entra ID | Intune = device compliance evaluator; Entra ID = access enforcer |
| Alert | Incident | Alert = single signal; Incident = correlated group of related alerts |
| Compliant/Noncompliant | Allow/Deny | Compliance = Intune's device verdict; Allow/Deny = Entra ID's access verdict |

### Key Terminology to Memorize

- Zero Trust - never trust, always verify; automated enforcement across signals.
- Conditional Access - Entra ID's "if-then" access rule engine.
- Compliance Policy - Intune's rule set defining a "healthy" device.
- Self-Healing - automated remediation (mailbox cleanup, device quarantine, password reset).
- Advanced Hunting - proactive KQL-based threat hunting in Defender XDR.
- Single Pane of Glass - unified portal (Microsoft Defender Portal).
- Alert Fatigue - problem solved by grouping alerts into fewer incidents.

### Essential KQL Syntax

```kql
TableName
| where ColumnName == "Value"
```

Example:
```kql
DeviceProcessEvents
| where FileName == "powershell.exe"
```

> Exam Tip: KQL queries always start with a table name, followed by pipe (|) operators like where, project, summarize.

### Final Memory Hooks

- "Detect, Evaluate, Enforce" = MDE, Intune, Entra ID
- "One door" = Microsoft Graph
- "Security Brain" = Security Graph
- "One incident from many alerts" = Defender XDR
- "Self-healing" = automated remediation
- "KQL + Advanced Hunting" = threat hunting in Defender XDR
