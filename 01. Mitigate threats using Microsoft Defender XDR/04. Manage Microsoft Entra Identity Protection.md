## Overview: What Identity Protection Is and Why It Matters

**Microsoft Entra ID Identity Protection** is a cloud based service that continuously monitors sign-in activity, detects suspicious behavior, calculates a risk score, and can automatically protect accounts. It works closely with **Conditional Access**, **Microsoft Sentinel**, and **Microsoft Defender XDR**.

Without Identity Protection, a stolen password is enough for an attacker to log in successfully, since the system only checks whether the password is correct. With Identity Protection enabled, Microsoft also evaluates **how** the sign in happens (location, device, network, behavior pattern), so a stolen password alone is often not enough to gain access.

### Three Core Functions

| Function | What It Means |
|---|---|
| Detect | Continuously monitors sign in activity and user behavior for anomalies (impossible travel, anonymous IP, unfamiliar device, etc.) |
| Investigate | Gives analysts details such as who signed in, from where, on what device, at what risk level, and why |
| Automate remediation | Can automatically require Multifactor Authentication (MFA), force a password reset, or block sign in without waiting for an analyst |

### SC-200 Exam Tips

> Remember the three functions in order: **Detect, Investigate, Automate.** Exam questions often describe a scenario and ask which function or capability is being used.
> Identity Protection evaluates the **manner** of authentication, not just the credentials themselves.

## How Identity Protection Works

```text
User attempts sign in
        │
        ▼
Identity Protection analyzes the login
        │
        ▼
Checks for suspicious behavior
        │
        ▼
Assigns a risk level (Low / Medium / High)
        │
        ▼
Conditional Access Policy decides
        │
        ├── Allow
        ├── Require MFA
        ├── Force Password Reset
        └── Block Sign-in
```

This end to end flow is one of the most exam relevant diagrams in the whole topic: **sign in → analysis → risk level → Conditional Access decision.**

### SC-200 Exam Tips

> Identity Protection itself does not block anything. It calculates risk; **Conditional Access** is what actually enforces the decision (allow, require MFA, force reset, or block).

## Risk Detection Types

Identity Protection recognizes many attack techniques. Each detection contributes to the overall risk score.

| Detection | What It Means | Typical Example |
|---|---|---|
| Anonymous IP Address | Sign in comes from a network that hides the true source | Tor Browser, anonymous VPN, open proxy |
| Atypical Travel (Impossible Travel) | Two sign ins from geographically distant locations in a time window too short for real travel | Login in Bangladesh, then Germany 30 minutes later |
| Malicious IP Address | Sign in originates from an IP on Microsoft's known bad IP list | IP linked to a botnet or command and control infrastructure |
| Unfamiliar Sign-in Properties | Combination of device, browser, or location differs from the user's normal pattern | Usual: Windows 11, Chrome, Dhaka. Now: Linux, Firefox, Brazil |
| Leaked Credentials | The username and password pair has been found in a public breach dump or dark web listing | Credentials matching john@contoso.com found online |
| Password Spray | One common password is tried against **many** different accounts | "Welcome123" attempted against Alice, Bob, Charlie, David |
| Microsoft Entra Threat Intelligence | Microsoft's global threat intelligence recognizes a known attack pattern reaching your tenant | A phishing campaign detected elsewhere now targets your org |
| Anomalous Token | A previously issued authentication token is used in a way that suggests theft or replay | Token issued in Bangladesh, used in Russia 5 minutes later |

**Additional detections mentioned in the source material:**

| Detection | Description |
|---|---|
| Token Issuer Anomaly | The identity provider issuing a SAML token may be compromised |
| Suspicious Browser | Same browser shows suspicious activity across multiple organizations |
| Verified Threat Actor IP | Sign in comes from an IP tied to a known threat actor |
| New Country | Sign in from a country the user has never used before |
| Activity from Anonymous IP | Detected by Microsoft Defender for Cloud Apps |
| Suspicious Inbox Forwarding | Defender for Cloud Apps detects mailbox forwarding rules attackers use to secretly copy a victim's email |

> **Password Spray vs Brute Force (frequently confused):** Brute force repeatedly tries **many passwords against one account**. Password spray tries **one (or a few) common password against many accounts** to avoid triggering per account lockout thresholds.

### SC-200 Exam Tips

> Learn to distinguish **Sign-in based detections** (Anonymous IP, Impossible Travel, Malicious IP, Unfamiliar Sign-in Properties, Anomalous Token) from **User based detections** (Leaked Credentials, Password Spray results, Threat Intelligence) because the exam ties this back to Sign-in Risk Policy vs User Risk Policy (see [section 9](#sign-in-risk-policy-vs-user-risk-policy)).
> Impossible Travel is one of the most tested detection types on the SC-200 exam.

### Conditional Access Examples

| Condition | Action |
|---|---|
| Sign in Risk = High | Block Access |
| User Risk = Medium | Require Password Change |
| Sign in Risk = Low | Require MFA |

### Sentinel Integration Workflow

```text
Identity Protection
        │
        ▼
High-risk sign-in detected
        │
        ▼
Sentinel Incident Created
        │
        ▼
SOC Analyst Investigates
        │
        ▼
Correlates with Defender XDR
        │
        ▼
Incident Closed or Escalated
```

### Real World SOC Scenario

An attacker steals a password through phishing and signs in from a Tor exit node in a new country. Identity Protection detects **Anonymous IP**, **New Country**, and **Unfamiliar Sign-in Properties**, calculates **High Sign-in Risk**, and Conditional Access blocks the attempt. Microsoft Sentinel generates an incident, the analyst confirms the compromise, forces a password reset, and verifies no further malicious activity occurred.

### SC-200 Exam Tips

> Three services work together to stop an identity attack: **Identity Protection calculates risk, Conditional Access enforces the decision, Sentinel provides incident tracking and correlation.**

## Microsoft Entra ID Fundamentals

Microsoft Entra ID is a cloud **Identity and Access Management (IAM)** service. Its job is to **authenticate** users ("Who are you?") and **authorize** access ("What are you allowed to access?"). It acts as the organization's **Identity Provider (IdP)**.

Entra ID protects **any** application that trusts it for authentication, regardless of who built the app.

| Category | Examples |
|---|---|
| Microsoft applications | Outlook, Teams, SharePoint, OneDrive, Azure Portal, Microsoft 365 |
| Third party applications | Salesforce, ServiceNow, AWS Console, Google Workspace, Dropbox, Workday |
| Custom company applications | HR systems, payroll portals, ERP systems, internal web apps |

> Entra ID protects the **identity and login process**, not the application's data. Application data stays in the application's own service (for example, Outlook mail lives in Exchange Online, Teams chats live in the Teams service).

### SC-200 Exam Tips

> Authentication answers "who are you," authorization answers "what can you access." Do not mix these up on the exam.

## Application Authentication Models

Whether Identity Protection can protect an application depends entirely on **how that application authenticates users**.

### Model 1: Application Uses Its Own Authentication

```text
User
  │
  ▼
Username + Password
  │
  ▼
Application (checks its own local database)
  │
  ▼
Login Success
```

Result: **Entra ID is NOT involved.** Identity Protection cannot detect impossible travel, anonymous IP, password spray, or leaked credentials for this application, because Entra never sees the login.

### Model 2: Application Uses Microsoft Entra ID (Recommended)

```text
User
  │
  ▼
Application
  │
  ▼  (redirects)
Microsoft Entra ID (authenticates user)
  │
  ▼  (returns token)
Application (validates token, grants access)
```

Result: **Identity Protection works fully**, because Entra ID performs the authentication.

### Comparison

| | Model 1: App Owned Auth | Model 2: Entra ID Federated |
|---|---|---|
| Who checks the password | The application itself | Microsoft Entra ID |
| Identity Protection coverage | None | Full |
| Common protocols | Proprietary / local database | OAuth 2.0, OpenID Connect (OIDC), SAML 2.0 |

### SC-200 Exam Tips

> If a scenario says an application "manages its own credentials" or "has a local user database," Identity Protection **cannot** see or protect those sign ins. This is a very common exam trap.

## Authentication Workflow for a Custom Web Application

```text
Employee opens HR portal
        │
        ▼
HR Application checks: already authenticated?
        │  (no)
        ▼
Redirect to Microsoft Entra ID
        │
        ▼
User signs in on Entra ID's login page
        │
        ▼
Entra ID verifies:
  • Username and password
  • Multifactor Authentication (if enabled)
  • Conditional Access policies
  • Identity Protection risk
  • Device compliance (if configured)
        │
        ▼
Entra ID issues a signed authentication token (JWT)
        │
        ▼
Token returned to HR Application
        │
        ▼
HR Application validates token → Access Granted
```

> The application **never receives or stores the user's password.** Microsoft applications (Outlook, Teams, SharePoint) follow this exact same pattern.

### SC-200 Exam Tips

> Know what Entra ID checks **during** authentication (password, MFA, Conditional Access, Identity Protection risk, device compliance), since exam scenarios often describe one of these checks failing and ask what happens next.

## Sign-in Risk Policy vs User Risk Policy

Identity Protection provides **two automated risk policies**. This distinction is one of the highest value topics for the exam.

| | Sign-in Risk Policy | User Risk Policy |
|---|---|---|
| Question it answers | "Is this login suspicious?" | "Is this user account compromised?" |
| Scope | A single authentication event | The overall account, based on accumulated evidence |
| Example trigger | Anonymous IP, impossible travel, unfamiliar device on one sign in | Leaked credentials found, or a previous attack confirmed |
| Typical action | Require MFA, or Block Access | Require Password Change, or Block Access |

> The account can be perfectly safe even if a single sign in looks risky (Sign-in Risk), and a user can be flagged as compromised (User Risk) even without a single unusual sign in, if their credentials were found leaked elsewhere.

### SC-200 Exam Tips

> Memorize this pairing:
> Sign-in Risk → about **one login event**.
> User Risk → about the **account as a whole**.
> If the scenario mentions a single unusual login, think Sign-in Risk Policy. If it mentions leaked credentials or a confirmed compromise, think User Risk Policy.

## Configuring a Sign-in Risk Policy

Located in the Microsoft Entra admin center under:

```text
Identity
    ▼
Protection
    ▼
Identity Protection
    ▼
Sign-in Risk Policy
```

A Sign-in Risk Policy has four components:

| Component | Purpose | Common Choice |
|---|---|---|
| 1. Assignments | Who the policy applies to | All users, excluding break-glass / emergency admin accounts |
| 2. Sign-in Risk Level | Minimum risk level that triggers the policy | Medium and above |
| 3. Controls | What action happens when triggered | Require Multifactor Authentication (MFA) |
| 4. Enforce Policy | Turns the policy on | Enabled (a disabled policy has zero effect) |

### Complete Evaluation Workflow

```text
User Attempts Sign-in
        │
        ▼
Microsoft Entra ID analyzes login
        │
        ▼
Checks: Anonymous IP, Impossible Travel,
        Malicious IP, Password Spray,
        Threat Intelligence
        │
        ▼
Risk Level Assigned
        │
        ▼
Sign-in Risk Policy: Medium or High?
        │
       Yes
        │
        ▼
Require MFA
        │
   ┌────┴────┐
   ▼         ▼
MFA Success  MFA Failure
   │         │
   ▼         ▼
 Access   Block Access
```

> **Why require MFA instead of blocking immediately?** Legitimate users (traveling, using a new device) can usually complete MFA, while attackers usually cannot. This stops attacks while minimizing disruption to genuine users.

### SC-200 Exam Tips

> Q: What is the recommended risk threshold for a Sign-in Risk Policy? **A: Medium and above.**
> Q: What is the most common control configured on a Sign-in Risk Policy? **A: Require Multifactor Authentication (MFA).**
> Q: Which accounts are commonly excluded from Identity Protection policies? **A: Break-glass / emergency administrator accounts**, so admins are never locked out.

## Monitoring, Investigating, and Remediating Risky Users

```text
User Sign-in
      ▼
Identity Protection detects risk
      ▼
Risky Sign-in / Risky User created
      ▼
SOC Investigation
      ▼
Remediation
      ▼
Risk Cleared
```

### What Is a Risky User?

A **Risky User** is an account Microsoft believes **may have been compromised**, based on evidence such as leaked credentials, password spray involvement, token theft, threat intelligence matches, administrator confirmation, or a pattern of suspicious activity over time. It is not simply "someone who had one suspicious login."

### The Three Identity Protection Reports

| Report | Focus | Key Question |
|---|---|---|
| Risky Users | The account | Is this user likely compromised? |
| Risky Sign-ins | A single authentication event | Was this particular login suspicious? |
| Risk Detections | The underlying evidence | Why did Microsoft assign this risk? |

**How they connect:**

```text
Risk Detection
      ▼
Risky Sign-in
      ▼
Risky User
```

One or more Risk Detections (for example Anonymous IP plus Impossible Travel) produce a Risky Sign-in. If Microsoft's confidence is high enough, the account itself becomes a Risky User.

> **Real-time risk level vs Aggregate risk level:** the real time risk level is calculated instantly using signals available at the moment of sign in. The aggregate risk level can be updated afterward as Microsoft processes additional, offline detections. The exam may test that these two values can differ for the same sign in.

### Investigation Checklist

Before remediating, a SOC analyst should review, in order:

1. Risk history
2. Risky sign-ins
3. Risk detections
4. Device information
5. Location
6. Applications accessed
7. MFA status

Key questions to ask: Was the user actually traveling? Is this a known corporate VPN? Was MFA completed? Was the sign in blocked? Did Defender XDR detect malware? Is the device managed? Is the IP malicious? Did mailbox forwarding rules change?

### User Risk Level and System Closed Detections

The **User Risk Level** (Low, Medium, High) reflects the likelihood that the **account** is compromised, calculated from all active detections. Microsoft can automatically close a detection when evidence shows the account is safe, for example: Impossible Travel is flagged, the user then successfully completes MFA, and the system determines the account is safe. These appear as **Closed (system)**.

### Remediation Options

| Option | When Used | Requirement |
|---|---|---|
| Self-remediation | Preferred by Microsoft; the user resets their own access | MFA and Self-Service Password Reset (SSPR) must already be registered |
| Manual password reset | Self-remediation unavailable | Admin generates a temporary password, or requires user reset (needs MFA and SSPR) |
| Dismiss User Risk | Investigation shows the account is safe | Removes risk without changing the password |
| Close Individual Risk Detection | One specific detection is confirmed incorrect | Only closes that detection, not the whole user risk |

```text
Self-Remediation Workflow

Risk Detected
      ▼
User Prompted
      ▼
Complete MFA
      ▼
Reset Password
      ▼
Risk Cleared
```

> No administrator action is required for self-remediation, but it only works if the user was already registered for MFA and SSPR **before** the risk occurred.

### Automation: Microsoft Graph API and PowerShell

| API / Tool | Purpose |
|---|---|
| `riskDetection` (Graph API) | Retrieves risk detection events |
| `riskyUsers` (Graph API) | Retrieves risky user information |
| `signIn` (Graph API) | Retrieves sign in events and risk details |
| Microsoft Graph PowerShell SDK | Retrieve risky users, sign ins, and detections; automate remediation and reporting |

These are typically used for SIEM integration, SOAR automation, custom dashboards, and automated investigations. For SC-200, understand the **purpose** of each API rather than memorizing exact syntax.

### Useful KQL for Identity Risk Investigation in Microsoft Sentinel

> The Azure AD Identity Protection data connector in Sentinel typically surfaces sign in and risk data through the tables below. Column names shown illustrate the general query pattern; always confirm exact fields against your own workspace schema.

```kql
// Find high risk sign-ins
SigninLogs
| where RiskLevelDuringSignIn == "high"
| project TimeGenerated, UserPrincipalName, IPAddress, Location, RiskEventTypes

// Find current high risk users
AADRiskyUsers
| where RiskLevel == "high"
| project TimeGenerated, UserPrincipalName, RiskLevel, RiskState

// Investigate a specific detection type
AADUserRiskEvents
| where RiskEventType == "impossibleTravel"
| project TimeGenerated, UserPrincipalName, RiskEventType, RiskLevel
```

### SC-200 Exam Tips

> Q: Which report identifies accounts Microsoft believes are compromised? **A: Risky Users.**
> Q: Which report shows suspicious authentication attempts? **A: Risky Sign-ins.**
> Q: Which report explains why a risk score was assigned? **A: Risk Detections.**
> Q: A user completed MFA successfully and the investigation confirms the activity was legitimate. What should you do? **A: Dismiss User Risk, or Confirm Sign-in Safe**, depending on whether you are closing the user level risk or a single sign in.
> Q: What are the two prerequisites for self-remediation? **A: Multifactor Authentication (MFA) and Self-Service Password Reset (SSPR)** must both be configured and registered.

## Workload Identity Protection

A **Workload Identity** is a non human identity used by an application or service (not a person) to authenticate to Microsoft Entra ID.

**Examples:** Service Principals, Managed Identities, applications, automation scripts, Azure Functions, Logic Apps, background services.

```text
Backup Application
        │
        ▼  (Client ID + Secret)
Microsoft Entra ID
        │
        ▼  (Access Token)
Azure Storage
```

If the client secret is stolen, an attacker can authenticate **as the application itself**:

```text
Attacker
        │
        ▼  (Stolen Client Secret)
Microsoft Entra ID
        │
        ▼
Azure Storage
```

### Requirements

* Microsoft Entra ID Premium P2 license
* An administrative role such as Security Administrator, Security Operator, or Security Reader

### Risk Detections for Workload Identities

Microsoft Entra Threat Intelligence, suspicious sign ins, unusual addition of credentials to an OAuth application, admin confirmed compromise, and leaked credentials.

### Remediation

Rotate client secrets or certificates, remove unauthorized credentials, review permissions, and use Conditional Access to block risky workload identities.

### SC-200 Exam Tips

> Workload identities **cannot perform MFA**, often carry privileged access, and are commonly protected by secrets or certificates rather than passwords. This makes credential rotation the primary remediation step, unlike human accounts where password reset is primary.

## Microsoft Defender for Identity (MDI)

**Microsoft Defender for Identity** (formerly Azure Advanced Threat Protection) is a cloud based identity security solution that protects **on-premises Active Directory** and hybrid identity environments. While Entra ID Identity Protection primarily protects **cloud** identities, Defender for Identity focuses on identities stored **in Active Directory**.

### Why It Is Needed

Active Directory stores user accounts, password hashes, group memberships, administrator accounts, and authentication information. If an attacker compromises Active Directory, they can potentially control the entire organization, so continuous monitoring is critical.

### Three Components

| Component | Role |
|---|---|
| MDI Sensor | Installed directly on Domain Controllers and AD FS servers; collects AD events, authentication events, Windows security events, network traffic, LDAP activity, and Kerberos / NTLM data. No dedicated monitoring server or port mirroring is needed since it runs on the monitored servers themselves. |
| Defender for Identity Cloud Service | Stores identity information, applies behavioral analytics and Microsoft Threat Intelligence, detects suspicious behavior, generates alerts |
| Microsoft Defender Portal | Where analysts view alerts, investigate incidents, analyze user activity, and respond to threats |

### Architecture

```text
Users
      │
      ▼  (Authenticate)
Domain Controller / AD FS
      │
      ▼
MDI Sensor
      │  Collects: AD entities, Windows events,
      │  authentication events, network traffic
      ▼
Microsoft Defender for Identity Cloud
      │  Behavior analytics, threat intelligence,
      │  attack detection
      ▼
Microsoft Defender Portal
      │
      ▼
SOC Investigation
```

### Integration with Microsoft Defender XDR

Defender for Identity shares identity activities, identity alerts, and identity metadata with **Microsoft Defender XDR**, which correlates these with alerts from Defender for Endpoint, Defender for Office 365, and Defender for Cloud Apps into a single unified incident.

### Defender for Identity vs Entra ID Identity Protection

| | Microsoft Entra ID Identity Protection | Microsoft Defender for Identity |
|---|---|---|
| Protects | Cloud identities | On-premises Active Directory identities |
| Monitors | Microsoft Entra ID sign ins | Domain Controllers and AD FS |
| Detects | Risky users, risky sign ins | Identity attacks inside the AD environment |
| Applies | User Risk and Sign in Risk policies | Post authentication attacker activity (enumeration, ticket requests, lateral movement) |

> Many organizations run **both**, since they complement each other across cloud and on-premises identity.

### Real SOC Scenario

An attacker steals credentials and logs into a Domain Controller, enumerates AD users, requests Kerberos tickets, attempts privilege escalation, and moves laterally. The MDI Sensor detects the unusual authentication and network activity, the cloud service analyzes and alerts, Defender XDR receives the alert, and the analyst investigates the timeline, identifies the compromised account, and remediates.

### SC-200 Exam Tips

> If a scenario mentions **Domain Controllers, Kerberos, NTLM, or on-premises Active Directory**, the answer is **Defender for Identity**, not Entra ID Identity Protection.
> If a scenario mentions **cloud sign ins, risky users, or Conditional Access risk**, the answer is **Entra ID Identity Protection**.

## Identity Risk Management Agent

The **Identity Risk Management Agent** is an AI powered assistant inside Microsoft Entra ID Identity Protection. It uses a Large Language Model (LLM) to investigate risky users, summarize findings, and recommend remediation actions automatically.

### Why It Is Needed

Without the agent, an analyst must manually open each risky user, review risky sign ins, review risk detections, determine whether the account is compromised, and choose a remediation, which does not scale for organizations with hundreds of risky users daily.

### Prerequisites

| Requirement | Detail |
|---|---|
| License | Microsoft Entra ID Premium P2 |
| Compute | Available Security Compute Units (SCUs) |
| Roles | Appropriate Microsoft Entra administrative roles |

| Role | Capability |
|---|---|
| Security Administrator | Activate, configure, review findings, and perform remediation |
| Security Reader / Global Reader | View findings and recommendations only, cannot remediate |

### Agent Triggers

| Trigger | Frequency | Best For |
|---|---|---|
| Continuous Monitoring | Approximately every 5 minutes | Production environments requiring constant coverage |
| Daily Trigger | Once per day | Environments where continuous monitoring is unnecessary |
| Manual Run | On demand | Ad hoc, targeted investigations |

### Investigation Scope

By default the agent investigates the **100 most recent risky users** from the **last 90 days**. Administrators can customize the specific users or groups, the number analyzed (1 to 100), risk levels included, and the time range (last 7, 14, 30 days, or a custom period up to 90 days).

### Agent Workflow

```text
Alice becomes Risky User
        ▼
Agent investigates automatically
        ▼
Analyzes: risky sign-ins,
risk detections, user behavior
        ▼
Risk Summary Generated
        ▼
Recommendation (e.g. Reset Password)
        ▼
SOC Analyst Reviews
        ▼
One-click Remediation
```

Instead of spending several minutes per user manually investigating, the analyst reviews the agent's summary, verifies the recommendation, and applies remediation with far less effort.

### SC-200 Exam Tips

> Know the three trigger modes (Continuous, Daily, Manual) and the default scope (**100 users, last 90 days**). The exam may ask which trigger mode fits a given scenario, for example continuous monitoring for a production tenant versus a manual run for a one time investigation.

## SC-200 Last Minute Revision

### Facts to Memorize

1. Identity Protection requires **Microsoft Entra ID Premium P2** for full functionality.
2. Recommended Sign-in Risk Policy threshold: **Medium and above.**
3. Most common Sign-in Risk Policy control: **Require MFA.**
4. Self-remediation requires: **MFA + SSPR**, both already registered.
5. Password Spray = one password against many accounts. Brute force = many passwords against one account.
6. Identity Risk Management Agent default scope: **100 users, last 90 days.**
7. Identity Risk Management Agent checks for new risky users roughly **every 5 minutes** in continuous mode.
8. Defender for Identity protects **on-premises Active Directory**; Identity Protection protects **cloud identities**.
9. Workload identities **cannot perform MFA**; remediation focuses on rotating secrets and certificates.
10. Entra ID protects the **login process**, never the application's stored data.

### Frequently Confused Concepts

| Concept A | Concept B | Key Difference |
|---|---|---|
| Sign-in Risk Policy | User Risk Policy | One event vs the whole account |
| Risky Sign-in | Risky User | A single suspicious login vs an account believed compromised |
| Password Spray | Brute Force | Many accounts, one password vs one account, many passwords |
| Entra ID Identity Protection | Defender for Identity | Cloud identities vs on-premises Active Directory |
| Self-remediation | Manual Password Reset | User resolves it themselves vs admin intervenes |
| Dismiss User Risk | Confirm Sign-in Safe | Clears account level risk vs clears a single sign in |
| Real-time risk level | Aggregate risk level | Calculated instantly vs updated after further processing |

### Quick Comparison: Identity Protection vs Defender for Identity

| | Identity Protection | Defender for Identity |
|---|---|---|
| Environment | Cloud (Entra ID) | On-premises Active Directory |
| Data source | Sign in logs, risk detections | Domain Controller / AD FS sensor traffic |
| License | Entra ID Premium P2 | Microsoft Defender for Identity license |
| Output | Risky Users, Risky Sign-ins, Risk Detections | Alerts in Microsoft Defender portal |

### Important KQL Tables for Identity Investigation

| Table | Contains |
|---|---|
| `SigninLogs` | Interactive sign in events, including risk level during sign in |
| `AADRiskyUsers` | Current risky user records and risk state |
| `AADUserRiskEvents` | Individual risk detection events per user |
| `AADServicePrincipalSignInLogs` | Sign ins by workload identities / service principals |

### Terminology Glossary

| Term | Meaning |
|---|---|
| IAM | Identity and Access Management |
| IdP | Identity Provider, the service that authenticates users (Entra ID) |
| MFA | Multifactor Authentication |
| SSPR | Self-Service Password Reset |
| SCU | Security Compute Unit, required to run the Identity Risk Management Agent |
| JWT | JSON Web Token, the signed token Entra ID issues after successful authentication |
| MDI | Microsoft Defender for Identity |
| OIDC | OpenID Connect, an authentication protocol built on OAuth 2.0 |

### One Page Cheat Sheet

```text
SIGN-IN RISK POLICY          →  one login event   →  Require MFA / Block
USER RISK POLICY             →  whole account      →  Require Password Change / Block
SELF-REMEDIATION             →  needs MFA + SSPR   →  no admin needed
IDENTITY PROTECTION          →  cloud identities    →  needs Entra ID Premium P2
DEFENDER FOR IDENTITY        →  on-prem AD          →  Sensor + Cloud + Portal
IDENTITY RISK MGMT AGENT     →  AI investigation    →  100 users / 90 days default
WORKLOAD IDENTITY            →  apps, not people    →  rotate secrets, not passwords
```

> Final tip: when a question does not clearly say "cloud" or "on-premises," look for keywords. **Domain Controller, Kerberos, NTLM, AD FS** point to Defender for Identity. **Conditional Access, risky sign in, risky user, sign in risk** point to Identity Protection.
