## What Is an Identity

In cybersecurity, an **identity** is **anything that can authenticate itself and be recognized by a system**. It is not just a human user.

| Identity Type | Examples |
|---|---|
| Users | Employees or administrators, e.g. John, Alice |
| Computers | Domain joined devices, e.g. WIN10-01$ |
| Servers | Windows or Linux servers, e.g. WEB01$, SQL01$ |
| Service Accounts | Accounts used by applications and services, e.g. SQLService |
| Applications | Cloud or on-premises applications with their own identities |
| Devices | Managed laptops, phones, tablets, printers, or IoT devices |

**Where identities are stored:**

* On-premises environments: **Active Directory**
* Cloud environments: **Microsoft Entra ID**

### SC-200 Exam Tips

> An identity is **not just a user**. It can be any user, computer, server, service account, application, or device that can authenticate and access resources. Expect the exam to test this broad definition directly.

## What Is Microsoft Defender for Identity

**Microsoft Defender for Identity** is a cloud based security solution that monitors identity signals from on-premises Active Directory, Microsoft Entra ID, and other identity providers to identify, detect, and investigate advanced threats, compromised identities, and malicious insider actions. It is classified as an **Identity Threat Detection and Response (ITDR)** solution.

### Why Identity Security Matters

In an organization of thousands of employees, every login, server management task, application authentication, service account job, VPN connection, and cloud sign in involves an identity. If an attacker steals even one privileged account, they may gain access to file servers, Domain Controllers, databases, Microsoft 365, Azure resources, and sensitive company data. This makes identity protection one of the highest priorities in modern cybersecurity.

### What Questions Does It Answer?

Who logged in? Is this normal behavior? Has this account ever done this before? Is this authentication suspicious? Is someone trying to move laterally? Has an attacker compromised Active Directory?

Instead of simply collecting logs, Defender for Identity analyzes identity behavior and detects attacks using **machine learning, behavioral analytics, and threat intelligence**.

### Where It Fits in Microsoft Security

```text
              Microsoft Defender XDR
                       │
        ┌──────────────┼──────────────┐
        ▼               ▼              ▼
 Defender for      Defender for   Defender for
   Endpoint          Office        Identity
        │               │              │
 Device Security   Email Security  Identity Security
```

Its primary monitoring targets are Active Directory, Domain Controllers, authentication, users, computers, groups, privileged accounts, and identity infrastructure.

### SC-200 Exam Tips

> Defender for Identity focuses **only on identities**, distinct from Defender for Endpoint (devices) and Defender for Office 365 (email). All three feed into **Microsoft Defender XDR**.
> Remember the classification: Defender for Identity is an **ITDR** solution.

## Architecture: Sensor vs Microsoft Defender Cloud

Defender for Identity has two core architectural components, and understanding the division of labor between them is a common exam point.

| Component | Role |
|---|---|
| MDI Sensor | Only **collects** identity telemetry. Does not decide whether activity is malicious. |
| Microsoft Defender Cloud | The **brain**. A cloud based backend service running in Microsoft Azure that receives telemetry, analyzes it, detects threats, and generates alerts. It is not installed on your Domain Controllers. |

**Microsoft Defender Cloud's responsibilities:**

1. Receive identity telemetry from MDI sensors
2. Correlate identity data from multiple sources
3. Apply behavioral analytics
4. Apply machine learning models
5. Compare activities with Microsoft Threat Intelligence
6. Detect attacks
7. Generate alerts and incidents
8. Send alerts to the Microsoft Defender XDR portal for investigation

### SC-200 Exam Tips

> The sensor **collects**; the cloud **decides**. If an exam question asks where detection logic and machine learning actually run, the answer is **Microsoft Defender Cloud**, not the sensor.

## How Defender for Identity Works: End to End Workflow

```text
User Activity
      ▼
Domain Controller (Authenticates the request)
      ▼
MDI Sensor (Collects identity telemetry)
      ▼
Microsoft Defender Cloud (Processes and analyzes telemetry)
      │
      ├── Correlation
      ├── Behavioral Analytics
      ├── Machine Learning
      ├── Threat Intelligence
      └── Threat Detection
      ▼
Security Alert
      ▼
Microsoft Defender XDR Portal
      ▼
SOC Analyst Investigation
```

### Step by Step Breakdown

| Step | What Happens |
|---|---|
| 1. User performs an activity | Logging into Windows, changing a password, accessing a shared folder, running an LDAP query, joining a computer to the domain |
| 2. Domain Controller authenticates | Verifies username, password, Kerberos or NTLM authentication, account status, group memberships; generates security events such as successful logon, failed logon, Kerberos ticket requests, LDAP queries, and group membership changes |
| 3. MDI Sensor collects telemetry | Monitors Kerberos, NTLM, LDAP, and DNS traffic, Windows Security Events, and Active Directory changes; processes information locally but **does not decide** whether it is malicious |
| 4. Sensor sends telemetry to the cloud | Sends only the information required for analysis, not every raw event |
| 5. Microsoft Defender Cloud processes the data | Correlation with other Microsoft security signals, behavioral analytics against a baseline, machine learning evaluation, and comparison against threat intelligence and MITRE ATT&CK techniques |
| 6. Threat detection | Identifies attacks such as LDAP reconnaissance, password spraying, brute force, Pass-the-Ticket, Pass-the-Hash, DCSync, DCShadow, or Golden Ticket |
| 7. Alert generation | Alert includes name, severity, affected user, affected device, timeline of events, and recommended investigation actions; displayed in the Microsoft Defender XDR portal |

### SC-200 Exam Tips

> The cloud's four analysis layers (**Correlation, Behavioral Analytics, Machine Learning, Threat Intelligence**) together produce **Threat Detection**. Memorize this order since exam scenarios may describe one layer and ask which stage of the pipeline it represents.

## Behavioral Analytics: Detecting Abnormal Identity Behavior

Defender for Identity builds a **behavioral baseline** for each identity and flags significant deviations, even when authentication succeeds normally.

**Example: John's baseline**

Normally John logs in from London, works 9 AM to 5 PM, uses Outlook and Microsoft Teams, accesses the Finance file server, and never logs into Domain Controllers.

One night at 2:00 AM, John's identity logs in from another country, connects to a Domain Controller, runs LDAP queries, and attempts to add itself to the Domain Admins group.

> Nothing here proves the identity itself is fake since it authenticated successfully. The **behavior** is what is abnormal, and behavioral baselining is what allows Defender for Identity to catch this kind of attack.

### Compact Attack Overview

```text
Phishing Email
      ▼
Credentials Stolen
      ▼
LDAP Enumeration (Reconnaissance detected)
      ▼
Password Spray (Alert generated)
      ▼
Administrator Account Compromised
      ▼
Pass-the-Ticket (Alert generated)
      ▼
DCSync Attempt (High severity alert)
      ▼
SOC Analyst Reconstructs Timeline
```

### SC-200 Exam Tips

> A successful authentication does **not** mean safe activity. Defender for Identity's value is catching **abnormal behavior from a valid identity**, which signature based tools often miss.

## Configuring Microsoft Defender for Identity Sensors

Sensors are required because Defender for Identity is a cloud service, but Active Directory usually runs on-premises. The cloud cannot directly access Windows Security Event Logs, Kerberos authentication, NTLM authentication, LDAP queries, DNS requests, or the Active Directory database. A sensor bridges this gap.

> **Without sensors:** no authentication monitoring, no identity behavior analysis, no attack detection, no identity alerts.

### Sensor Types

| Sensor Type | Installed On | Monitors |
|---|---|---|
| Domain Controller Sensor | Every Domain Controller (most common deployment) | Windows Security Events, Kerberos, NTLM, LDAP requests, DNS traffic, Active Directory objects; provides the most complete identity visibility |
| AD FS Sensor | Active Directory Federation Services servers | Federation authentication, token requests, authentication failures, suspicious authentication activities |
| AD CS Sensor | Active Directory Certificate Services servers | Certificate related activity for smart card logins, device authentication, user authentication, VPN authentication |
| Standalone Sensor | A dedicated server, not the Domain Controller | Mirrored network traffic from Domain Controllers via port mirroring |

```text
Domain Controller Sensor          Standalone Sensor

User Login                        Domain Controller
    ▼                                   ▼
Domain Controller                 Port Mirroring
    ▼                                   ▼
MDI Sensor                        Standalone Sensor
    ▼                                   ▼
Microsoft Defender Cloud          Microsoft Defender Cloud
```

### SC-200 Exam Tips

> The Domain Controller Sensor is the **preferred deployment** because it provides complete visibility into authentication activities.
> Sensors **do not perform advanced threat detection locally**; they parse and forward relevant telemetry only.
> To validate a new sensor installation, confirm the sensor service is running and that events such as **MdiDnsQuery** appear in the Microsoft Defender device timeline.
> Monitor sensor health, service status, version, and configuration on an ongoing basis.

## Attack Phases and Alert Categories

Defender for Identity groups alerts by the **stage of the attack**, which helps analysts understand where the attacker currently is in the attack chain and prioritize investigation.

```text
Reconnaissance
      ▼
Compromised Credentials
      ▼
Lateral Movement
      ▼
Domain Dominance
      ▼
Exfiltration
```

### 1. Reconnaissance Phase

The attacker gathers information about users, computers, servers, Domain Controllers, IP addresses, shared resources, and Active Directory structure, without attacking yet. Example activities: LDAP enumeration, SMB enumeration, user discovery, group enumeration, network scanning.

> Example alert: **User and IP Address Reconnaissance (SMB)**, where a user enumerates SMB sessions on the Domain Controller to discover user and IP address information.

Investigation questions: Which user performed the activity? Which computer initiated it? Which Domain Controller was queried? What information was collected? Is this normal behavior for the user?

### 2. Compromised Credential Phase

Attackers attempt to obtain and use credentials. Examples: password spraying, credential theft, Pass-the-Hash, Overpass-the-Hash, Pass-the-Ticket.

> Example alert: **Suspected Overpass-the-Hash Attack (Kerberos)**. An attacker steals an NTLM hash from a compromised computer and uses it to request a Kerberos Ticket Granting Ticket (TGT) instead of knowing the actual password.

Investigation questions: Which account was compromised? Which computer was used? Which authentication protocol was involved? What happened immediately before and after the attack?

### 3. Lateral Movement Phase

After compromising one account or device, the attacker moves to additional systems. Examples: remote authentication, remote PowerShell, PsExec, SMB connections, Remote Desktop, Pass-the-Ticket.

> Example alert: **Suspected Identity Theft (Pass-the-Ticket)**. An attacker steals a Kerberos ticket from a Domain Administrator and reuses it to access another computer without needing the password.

Investigation questions: Was the user expected to log into the destination device? Was the Kerberos ticket stolen? Which resources were accessed? Did additional suspicious activity occur after authentication?

### 4. Domain Dominance Phase

Once attackers obtain administrator privileges, they attempt to control the entire Active Directory environment. Examples: DCSync, DCShadow, Golden Ticket, Skeleton Key, creating new privileged accounts, adding users to Domain Admins.

> Example alert: **Remote Code Execution Attempt**. The activity log may show a new user account created and added to the Administrators group, using commands executed remotely on the Domain Controller, indicating an attempt to establish persistent administrative access.

### 5. Exfiltration Phase

The final stage, where the attacker extracts data from the compromised environment after achieving sufficient access.

### SC-200 Exam Tips

> Memorize the five phase order: **Reconnaissance → Compromised Credentials → Lateral Movement → Domain Dominance → Exfiltration.**
> Multiple alerts should be **correlated into a single attack timeline** rather than investigated as isolated events.

## Key Attack Techniques Glossary

These identity attack techniques appear repeatedly across Defender for Identity alerts and are heavily tested on the SC-200 exam.

| Technique | Definition |
|---|---|
| Password Spray | One common password tried against many different accounts |
| Brute-force | Many different passwords tried against a single account |
| Pass-the-Hash | Using a stolen NTLM password hash to authenticate, without ever knowing the plaintext password |
| Overpass-the-Hash | Using a stolen NTLM hash to request a Kerberos Ticket Granting Ticket (TGT), converting an NTLM credential into a Kerberos one |
| Pass-the-Ticket | Reusing a stolen Kerberos ticket to authenticate to another computer as the ticket's owner |
| DCSync | Abusing directory replication permissions so an unauthorized account impersonates a Domain Controller and retrieves password hashes from Active Directory |
| DCShadow | An attacker registers a rogue Domain Controller to push malicious changes directly into Active Directory replication |
| Golden Ticket | Forging a Kerberos TGT using the stolen krbtgt account hash, granting the attacker essentially unlimited domain access |
| Skeleton Key | Malware that patches a Domain Controller so any account can authenticate using an attacker chosen master password, alongside the legitimate one |

### SC-200 Exam Tips

> **Pass-the-Hash** authenticates with a stolen hash directly. **Overpass-the-Hash** converts that stolen hash into a Kerberos ticket. **Pass-the-Ticket** reuses an already issued Kerberos ticket. Keep these three straight, they are a favorite source of exam distractors.
> **DCSync** steals hashes by impersonating replication. **Golden Ticket** forges unlimited access using the krbtgt hash. Both are Domain Dominance techniques but work differently.

## Alert Components and Investigation Process

Every Microsoft Defender for Identity alert includes:

| Component | Description |
|---|---|
| Alert title | Official Microsoft Defender for Identity name of the alert |
| Description | Brief explanation of what happened |
| Evidence | Related data supporting the investigation |
| Excel download | Detailed report for offline analysis |
| Activity Log | Detailed information about the user, device, IP address, time, application, command performed, and activity type |

> All alerts are surfaced in the unified Microsoft Defender portal under **Incidents & alerts > Alerts**.

### Structured Investigation Process

1. Read the alert title to identify the attack type
2. Read the description to understand what occurred
3. Identify the affected user account
4. Identify the affected computer or server
5. Review the evidence provided
6. Examine the Activity Log to determine the exact actions performed
7. Determine whether other related alerts exist for the same user or device
8. Reconstruct the attack timeline
9. Assess the impact on the Active Directory environment
10. Escalate or respond according to your organization's incident response procedures

### SC-200 Exam Tips

> Memorize this ten step process as the standard SOC methodology for reviewing any Defender for Identity alert. It also generalizes well to other Defender XDR alert types on the exam.

## Full Investigation Walkthrough (Case Study)

A financial organization runs Microsoft Defender for Identity across two Domain Controllers (DC01, DC02), several workstations, and a Defender XDR deployment.

| Time | Alert | Key Details | Analyst Conclusion |
|---|---|---|---|
| Afternoon | User and IP Address Reconnaissance (SMB) | User John, Source WIN10-05, Target DC01. John enumerated SMB sessions and discovered IP addresses of multiple computers | John is a Finance employee who never performs administrative tasks, so this is suspicious |
| +30 minutes | Suspected Overpass-the-Hash Attack (Kerberos) | User John, Device WIN10-05, Target DC01. John's NTLM hash was used to request a Kerberos TGT | John's credentials are likely compromised |
| +20 minutes | Suspected Identity Theft (Pass-the-Ticket) | Source ADMIN-PC01, Destination WIN10-05 (further movement to ADMIN-PC01), User DomainAdmin. The Domain Administrator had never previously authenticated to WIN10-05 | The attacker moved laterally using a stolen Kerberos ticket |
| +1 hour | Remote Code Execution Attempt | A new user account was created, added to the Administrators group, from commands originating at the compromised workstation | The attacker is establishing persistent administrative access |

### Correlated Attack Timeline

```text
Initial Compromise
        ▼
Reconnaissance
(User and IP Address Reconnaissance)
        ▼
Credential Theft
(Overpass-the-Hash)
        ▼
Lateral Movement
(Pass-the-Ticket)
        ▼
Remote Code Execution
        ▼
Administrator Account Created
        ▼
Domain Compromise
```

> Instead of treating each alert as a separate incident, the analyst recognizes they are all part of the **same attack** and responds to the full chain rather than one symptom at a time.

### Key Learning Points

Detect suspicious identity activity early, identify compromised user accounts, track attacker movement across the environment, correlate multiple alerts into a single attack timeline, understand the complete attack path from reconnaissance to domain compromise, and respond quickly to contain and remediate.

### SC-200 Exam Tips

> This case study is a template for exam scenario questions: expect a sequence of timestamped alerts that the correct answer requires you to link into one attack, not four separate incidents.

## Integration with Other Microsoft Tools

Each Microsoft security product monitors a different area of the environment. When integrated through Microsoft Defender XDR, they provide unified incident management, automatic alert correlation, faster investigations, and complete attack visibility.

| Product | What It Detects |
|---|---|
| Microsoft Defender for Office 365 | Phishing emails |
| Microsoft Defender for Endpoint | Malware and endpoint attacks |
| Microsoft Defender for Identity | Identity based attacks |
| Microsoft Defender for Cloud Apps | Cloud application activity |
| Microsoft Entra ID Protection | Risky cloud sign ins |

### Microsoft Defender XDR as the Central Platform

```text
                Microsoft Defender XDR
                         │
   ┌───────────┬─────────┼─────────┬────────────┐
   ▼           ▼         ▼         ▼             ▼
Defender    Defender  Defender  Defender     Entra ID
for         for       for       for          Protection
Identity    Endpoint  Office365 Cloud Apps
```

Defender XDR combines these shared signals into unified incidents and supports automated response, cross product threat hunting, and threat analytics.

### What Defender for Identity Contributes

On-premises Active Directory signals, Microsoft Entra ID signals, identity alerts, and authentication events. These combine automatically with alerts from other Defender products so identity events and cloud application events appear together in the same investigation.

### Additional Integrations

| Integration | Purpose |
|---|---|
| Privileged Access Management (PAM), e.g. CyberArk, Delinea, BeyondTrust | Monitors activity involving privileged accounts managed by these platforms and detects suspicious behavior targeting high-value accounts |
| Okta | For organizations using Okta instead of, or alongside, Microsoft Entra ID; monitors sign ins, authentication activity, identity events, and suspicious login behavior |
| Microsoft Security Copilot | Analysts can ask natural language questions such as "summarize this attack," "explain why this user is risky," "show lateral movement," "list affected devices," or "recommend containment actions" |

### SC-200 Exam Tips

> Defender for Identity **relies on integration** with other Microsoft security products for complete attack visibility; it is powerful but identity focused on its own.
> Know that Defender for Identity extends beyond the Microsoft stack through **PAM platforms** and **Okta** for third-party identity providers.

## Multi Product SOC Scenario (Full Kill Chain)

A healthcare organization uses Defender for Office 365, Defender for Endpoint, Defender for Identity, Defender for Cloud Apps, Microsoft Entra ID Protection, and Defender XDR together.

```text
Step 1: Initial Access
Phishing email with malicious Word attachment
   → Detected by Defender for Office 365
        ▼
Step 2: Endpoint Compromise
Mimikatz dumps credentials, suspicious PowerShell
   → Detected by Defender for Endpoint
        ▼
Step 3: Identity Compromise
Stolen credentials authenticate to the Domain Controller
Unusual Kerberos authentication, Pass-the-Hash activity
   → Detected by Defender for Identity
        ▼
Step 4: Cloud Activity
Sign in to Microsoft 365, download files from SharePoint
Unusual file downloads, suspicious cloud session activity
   → Detected by Defender for Cloud Apps
        ▼
Step 5: Cloud Identity Risk
Same account signs in from an unfamiliar country
Risky sign-in, impossible travel, high-risk user
   → Detected by Microsoft Entra ID Protection
        ▼
Step 6: Correlation
Microsoft Defender XDR automatically merges all alerts
into a single unified incident
```

Instead of investigating five separate alerts from five different products, the analyst investigates **one unified incident**, understands the complete attack path, and responds faster.

### SC-200 Exam Tips

> This scenario is the clearest illustration of why **Microsoft Defender XDR** exists: it turns five isolated product alerts into one correlated incident spanning email, endpoint, identity, cloud app, and cloud identity risk signals.
> Know each product's contribution: Endpoint → device telemetry and malware; Office 365 → email and phishing; Identity → on-premises authentication attacks; Cloud Apps → cloud application activity; Entra ID Protection → cloud identity and sign in risk.

## SC-200 Last Minute Revision

### Facts to Memorize

1. Microsoft Defender for Identity is an **ITDR (Identity Threat Detection and Response)** solution.
2. The **MDI Sensor collects**; **Microsoft Defender Cloud analyzes and decides**.
3. The Domain Controller Sensor is the **preferred, most complete** deployment option.
4. Validate a new sensor by checking for the **MdiDnsQuery** event in the device timeline.
5. Attack phase order: **Reconnaissance → Compromised Credentials → Lateral Movement → Domain Dominance → Exfiltration.**
6. Cloud analysis pipeline: **Correlation → Behavioral Analytics → Machine Learning → Threat Intelligence → Threat Detection.**
7. Defender for Identity requires sensors because the cloud cannot directly reach on-premises Windows Security Event Logs, Kerberos, NTLM, LDAP, DNS, or the AD database.
8. All Defender for Identity alerts surface in the Microsoft Defender portal under **Incidents & alerts > Alerts**.
9. Defender for Identity also integrates with **PAM platforms** (CyberArk, Delinea, BeyondTrust), **Okta**, and **Microsoft Security Copilot**.

### Frequently Confused Concepts

| Concept A | Concept B | Key Difference |
|---|---|---|
| Pass-the-Hash | Overpass-the-Hash | Uses stolen hash directly to authenticate vs converts stolen hash into a Kerberos TGT |
| Overpass-the-Hash | Pass-the-Ticket | Steals and converts a hash vs reuses an already issued Kerberos ticket |
| DCSync | DCShadow | Impersonates a Domain Controller to pull password hashes vs registers a rogue Domain Controller to push malicious replication changes |
| Golden Ticket | Skeleton Key | Forged Kerberos TGT using the krbtgt hash vs malware allowing a master password for any account |
| MDI Sensor | Microsoft Defender Cloud | Collects telemetry only vs performs analysis, detection, and alerting |
| Microsoft Defender for Identity | Microsoft Entra ID Identity Protection | On-premises Active Directory identities vs cloud identities (see the Identity Protection revision guide for full comparison) |
| Password Spray | Brute-force | One password against many accounts vs many passwords against one account |

### Sensor Types Quick Reference

| Sensor | Best For |
|---|---|
| Domain Controller Sensor | Standard deployment, full visibility |
| AD FS Sensor | Federated authentication monitoring |
| AD CS Sensor | Certificate based authentication monitoring |
| Standalone Sensor | Environments avoiding direct DC installation, uses port mirroring |
