## 1. What Is a CASB and What Is Defender for Cloud Apps

**CASB (Cloud Access Security Broker)** is a security solution that sits between users and cloud applications to monitor, control, and protect access to cloud services. It enforces an organization's security policies at the point where users touch cloud apps.

```text
User
  │
  ▼
CASB
  │
  ▼
Cloud Application
```

**Microsoft Defender for Cloud Apps (MDCA)** is Microsoft's CASB platform. It protects the organization's cloud environment rather than only the internal network, and it continuously answers questions such as:

* Which cloud applications are employees using?
* Is sensitive data being uploaded or downloaded excessively?
* Are users behaving normally?
* Is a cloud application compliant with company policy?
* Has an attacker compromised a cloud account?

> **Exam Tip:** MDCA secures the relationship between users, cloud applications, and organizational data, not individual devices. Its former product name was **Microsoft Cloud App Security (MCAS)**; older practice questions may still use that name.

## 2. The Four Pillars of the Defender for Cloud Apps Framework

| Pillar | Core Question It Answers |
|---|---|
| 1. Discover and control Shadow IT | What unapproved cloud apps are being used? |
| 2. Protect sensitive information | Where is sensitive data and how is it moving? |
| 3. Protect against cyberthreats and anomalies | Is user or account behavior unusual? |
| 4. Assess compliance of cloud applications | Do the apps meet regulatory and organizational standards? |

Understanding each capability is more important than memorizing the names.

### 2.1 Discover and Control Shadow IT

**Shadow IT** is any technology or cloud service used without approval from the organization's IT or security team (personal Dropbox, personal OneDrive, ChatGPT, WeTransfer, free project management sites, personal email, etc.).

Employees typically adopt these tools for convenience, not malicious intent, but the organization loses control over where data is stored, who can access it, whether encryption or backups exist, and whether compliance requirements are met.

**Discovery sources MDCA analyzes:**

* Firewalls
* Proxy servers
* Secure Web Gateways
* Microsoft Defender for Endpoint
* Network traffic logs

From these logs, MDCA identifies every cloud app in use, the number of users, traffic volume, upload/download activity, and an app risk score. Administrators can then mark discovered apps as **Allowed**, **Blocked**, **Monitored**, or **Restricted**.

### 2.2 Protect Sensitive Information Anywhere in the Cloud

Storing data in the cloud does not automatically protect it. MDCA continuously monitors where sensitive information (financial reports, customer databases, HR records, intellectual property, medical information, contracts) is stored and how it moves.

**Data Classification:** MDCA integrates with Microsoft Information Protection to classify files by label (Confidential, Highly Confidential, Internal, Public) or by content (credit card numbers, passport numbers, national ID numbers, health records).

**Data Loss Prevention (DLP):** once sensitive data is identified, DLP policies can automatically:

* Block sharing
* Block downloads
* Encrypt files
* Apply sensitivity labels
* Notify administrators / alert the SOC
* Quarantine files

### 2.3 Protect Against Cyberthreats and Anomalies

Cloud attacks often involve **abuse of legitimate accounts** rather than malware, so MDCA leans heavily on behavior analysis instead of signature matching.

**Behavioral Analytics** learns what normal activity looks like (login times, typical download volume, usual work location, typical app usage) and flags significant deviations.

| Example Anomaly | What It Might Indicate |
|---|---|
| Sign in from Bangladesh, then from Germany 10 minutes later | Impossible travel, stolen credentials |
| 5 downloads/day suddenly becomes 40,000 | Insider threat or data exfiltration |
| Normal employee creates Global Administrator accounts | Account compromise |
| A user grants a third party app permission to read every mailbox | OAuth based persistence mechanism |
| Sign in from Tor or an anonymous VPN | High risk authentication |

**User and Entity Behavioral Analytics (UEBA)** builds behavior profiles for users, devices, and applications, and continuously compares live activity against that history, catching attacks even without malware involved. (Full detail in [Section 8](#8-threat-detection-ueba-and-anomaly-detection).)

### 2.4 Assess Compliance of Cloud Applications

Organizations must often satisfy regulations such as **GDPR**, **HIPAA**, **PCI DSS**, and **ISO 27001**. MDCA evaluates each discovered cloud app against security and compliance attributes, including encryption support, authentication methods, compliance certifications, industry standards, and security controls, so administrators can judge whether an app is safe for regulated data.

> **SC-200 Exam Tips (Section 2)**
> * MDCA is Microsoft's CASB; a CASB sits between users and cloud services to enforce policy and provide visibility.
> * Memorize the four pillars: discover Shadow IT, protect sensitive data (classification + DLP), detect threats (UEBA, anomaly detection, threat intelligence), assess app compliance.
> * Cloud Discovery uses firewall, proxy, and endpoint telemetry, not a live connection to the app.
> * MDCA integrates closely with **Microsoft Entra ID**, **Microsoft Defender XDR**, **Microsoft Defender for Endpoint**, **Microsoft Sentinel**, and **Microsoft Information Protection** for end to end cloud security.

## 3. How Information Flows Through the Framework

The framework operates as a continuous six step process:

```text
Step 1: Users Access Cloud Applications
  │  (corporate, personal, mobile, remote devices)
  ▼
Step 2: MDCA Collects Information
  │  (API connectors, cloud traffic, firewall/proxy logs, user sessions)
  ▼
Step 3: Policies Are Evaluated
  │  (sensitive data, session control, download, compliance, baseline policies)
  ▼
Step 4: Threat Analysis
  │  (behavioral analytics on users, devices, apps, files + threat intelligence)
  ▼
Step 5: Alerts Are Generated
  │  (impossible travel, mass downloads, risky OAuth apps, data exposure, compliance violations)
  ▼
Step 6: Response
     (block downloads, revoke sessions, disable users, remove sharing,
      revoke OAuth consent, notify SOC, trigger Microsoft Sentinel playbooks)
```

> **Exam Tip:** This flow maps directly to the SC-200 incident response mindset: detect → investigate → respond. Response actions can be manual (analyst action) or automated (Sentinel playbook triggered by an MDCA alert).

## 4. Cloud Discovery

**Cloud Discovery** is the MDCA feature that automatically discovers and analyzes the cloud applications used inside an organization. It answers: *which apps are employees using, which are unknown to IT, which are risky, and should they be allowed or blocked?*

Most organizations officially approve only a handful of apps (Microsoft 365, Azure, ServiceNow, Salesforce), yet employees regularly use additional unsanctioned tools such as personal Dropbox, Google Drive, WeTransfer, Box, ChatGPT, Trello, or Notion. That gap is **Shadow IT**, and it puts data outside the organization's encryption, access control, backup, retention, and audit logging controls.

### How Cloud Discovery Works

Cloud Discovery does **not** scan the internet or connect to apps directly. It reads the organization's own network logs.

```text
Employee PC
    │
    ▼
Corporate Firewall / Proxy / SWG / Defender for Endpoint
    │
    ▼
Cloud Application (e.g. Dropbox)
```

The firewall/proxy records source IP, destination, time, protocol, and bytes uploaded/downloaded. MDCA imports these logs and compares the discovered destinations against the **Microsoft Cloud App Catalog**, which contains **more than 16,000 cloud applications**, each scored against **more than 80 risk factors**.

### Sanctioned vs Unsanctioned Applications

| Category | Meaning | Examples |
|---|---|---|
| **Sanctioned** | Officially approved, meets security/compliance requirements | Microsoft 365, Azure, Salesforce, ServiceNow |
| **Unsanctioned** | Not approved, may expose organizational data | Unknown file sharing sites, personal cloud storage, unapproved collaboration tools |

Administrators can manually mark any discovered app as **Unsanctioned** in the Cloud Discovery portal if it poses unacceptable risk.

> **SC-200 Exam Tips**
> * Cloud Discovery = **visibility only**. It cannot block or inspect actions in real time by itself.
> * It analyzes existing network logs (firewall, proxy, SWG, Defender for Endpoint), it does not connect via API to the discovered app.
> * Know the numbers: **16,000+ apps** in the catalog, **80+ risk factors** per app.
> * Integration with **Microsoft Defender for Endpoint** enables automatic blocking of unsanctioned apps at the network level; **Microsoft Defender XDR** and **Microsoft Sentinel** provide centralized investigation.

## 5. Conditional Access App Control (CAAC)

**Conditional Access App Control (CAAC)** is an MDCA feature that provides real time monitoring and control of user sessions **after** sign in. Traditional Conditional Access only decides whether a user is allowed in; CAAC continues protecting the session once access has already been granted.

```text
User
  │
  ▼
Conditional Access
  │
  ▼
Access Granted   →   (traditional CA's job ends here)
```

Once inside the app, a user could still download confidential files, copy sensitive data, upload company information to another tenant, or share documents externally, none of which traditional Conditional Access can see. CAAC closes that gap.

### Access Controls vs Session Controls

This distinction is heavily tested on the SC-200 exam.

| | Access Controls | Session Controls |
|---|---|---|
| **When they apply** | Before access is granted | After the user has signed in |
| **Owner** | Microsoft Entra ID (Conditional Access) | Defender for Cloud Apps (CAAC) |
| **Examples** | Require MFA, require compliant device, block risky countries, require passwordless auth, require hybrid joined device | Block download/upload/print/copy/paste, scan files or Teams messages, monitor activity, end a session |

### Deploying CAAC: A Two Stage Process

CAAC is not turned on directly inside MDCA. It is deployed from **Microsoft Entra ID**.

| Stage | Owner | Decides |
|---|---|---|
| Stage 1 | Microsoft Entra ID | **When** the session should be routed through Defender for Cloud Apps |
| Stage 2 | Defender for Cloud Apps | **What** happens during that session |

### Full Sign In to Session Control Flow (Example: Alice → SharePoint Online)

```text
Step 1: Alice tries to access SharePoint Online
  │
  ▼
Step 2: SharePoint redirects Alice to Microsoft Entra ID for authentication
  │  (username/password, MFA, device compliance, user risk, sign-in risk, location)
  ▼
Step 3: Conditional Access policy is evaluated
  │  Policy example → Users: Finance dept | App: SharePoint Online | Device: Unmanaged
  │
  ├── Policy does NOT match  →  User connects directly to SharePoint
  │
  ▼ Policy DOES match
Step 4: Entra ID routes the session through Defender for Cloud Apps
  │  (Access Controls → Session → Use Conditional Access App Control)
  ▼
Step 5: Defender for Cloud Apps monitors the session
  │  (open, download, upload, print, copy, paste, share, send Teams messages)
  ▼
Step 6: Defender for Cloud Apps enforces session policies
     Example: Alice tries to download Payroll.xlsx from an unmanaged device
     → Device = Unmanaged AND File = Sensitive → Policy: Block Download → Result: Download Blocked
     (Alice can still view the file, just not download it)
```

**Identity Providers (IdPs)** authenticate the user before CAAC can act. Examples: Microsoft Entra ID, Okta, Ping Identity, Active Directory Federation Services (AD FS). CAAC integrates most directly with MDCA when **Microsoft Entra ID** is the IdP.

> **Exam Tip:** Remember the ownership split. Microsoft Entra ID decides **if** a user signs in and **when** to route the session to MDCA. Defender for Cloud Apps decides **what** the user is allowed to do once inside.

## 6. Three Protection Methods Compared

MDCA protects cloud apps using three distinct methods:

```text
                    Microsoft Defender for Cloud Apps
                                   │
        ┌──────────────────┬──────────────────┬──────────────────┐
        │                   │                   │
        ▼                   ▼                   ▼
  Cloud Discovery      App Connector      Conditional Access
                        (API Connector)     App Control (CAAC)
```

| Method | Answers | Real Time? | Requires Entra ID as IdP? |
|---|---|---|---|
| **Cloud Discovery** | "What cloud apps are my users accessing?" | No, visibility only | No |
| **App Connector (API Connector)** | "What is happening inside the cloud app?" | No, activity already occurred | No (app can use its own auth, e.g. Dropbox login, Google account) |
| **Conditional Access App Control** | "What is the user allowed to do during the session?" | Yes, blocks actions before they happen | Yes |

### Method 1: Cloud Discovery
Analyzes firewall, proxy, SWG, and Defender for Endpoint logs. Cannot block uploads; provides visibility and risk scoring only (see [Section 4](#4-cloud-discovery)).

### Method 2: App Connector (API Connector)
Connects directly to a supported app's API (Microsoft 365, Dropbox, Box, Google Workspace, Salesforce, ServiceNow) to retrieve files, sharing permissions, user activity, and malware scan results.

```text
User uploads file
        │
        ▼
Cloud app stores the file
        │
        ▼
App's API reports the activity to MDCA
        │
        ▼
MDCA generates an alert (after the fact)
```

Because the activity has already happened, App Connector cannot usually stop it in real time, but it can trigger **governance actions** afterward: remove external sharing, quarantine files, remove permissions, move files to trash, or generate alerts and notifications.

### Method 3: Conditional Access App Control
Provides true real time control by acting as a **reverse proxy** between the user and the app, but only when the app authenticates through an Identity Provider such as Microsoft Entra ID.

```text
Download File Request
        │
        ▼
Defender for Cloud Apps (reverse proxy)
        │
        ▼
Policy Check
        │
        ▼
Allow / Block
```

It can block downloads, uploads, copy, and print, and inspect Teams messages or protect downloaded files, all before the action completes.

> **SC-200 Exam Tips**
> * **Cloud Discovery** → visibility, no blocking, reads existing logs.
> * **App Connector** → deep inspection inside the app via API, after the fact governance actions, no Entra ID requirement.
> * **CAAC** → true real time blocking, requires Entra ID (or compatible IdP), acts as a reverse proxy.

## 7. Classify and Protect Sensitive Information

**Azure Information Protection (AIP)**, now part of **Microsoft Purview Information Protection**, helps organizations classify sensitive information, apply sensitivity labels, encrypt files and emails, restrict access, and keep data protected even after it leaves the organization.

### The Four Phases of Information Protection

```text
Phase 1: Discover Data
    Goal: Locate sensitive data across connected cloud apps
    Tools: App Connectors (scan data at rest via API), CAAC (monitor live sessions)
        │
        ▼
Phase 2: Classify Sensitive Information
    Goal: Identify and classify sensitive information
    Uses 100+ built in Sensitive Information Types (SITs), e.g. passport numbers,
    national ID numbers, credit card numbers
        │
        ▼
Phase 3: Protect Data
    Goal: Automatically enforce security policies and prevent data exposure
    File Policies trigger governance actions on violations
        │
        ▼
Phase 4: Monitor and Report
    Goal: Continuously monitor and respond to security incidents
    Analysts review alerts, investigate DLP incidents, dismiss false positives, export data
```

### Sensitivity Labels (Increasing Sensitivity)

| Order | Label | Meaning |
|---|---|---|
| 1 | **Personal** | Personal, non business information |
| 2 | **Public** | Safe for public sharing |
| 3 | **General** | Internal business information |
| 4 | **Confidential** | Sensitive business data that could harm the organization if exposed |
| 5 | **Highly Confidential** | Critical data such as passwords, credentials, and source code |

> **Exam Tip:** To enable automatic labeling, turn on **"Automatically scan new files for Azure Information Protection classification labels and content inspection warnings"** in Defender for Cloud Apps. **File Policies** are what actually enforce governance actions once a file is classified (generate alerts, change/remove sharing, quarantine, remove access, move to trash).

## 8. Threat Detection: UEBA and Anomaly Detection

MDCA detects suspicious user and app activity using **User and Entity Behavior Analytics (UEBA)**, **machine learning**, and **Microsoft Threat Intelligence**. Rather than relying only on known attack signatures, it flags activity that deviates from an established baseline, catching insider threats, compromised accounts, and previously unknown attack techniques.

### How Anomaly Detection Works

```text
Anomaly detection policy enabled
        │
        ▼
~7 day learning period
   (collects IP addresses, locations, devices, browsers, OS,
    apps used, sign-in patterns, typical activities)
        │
        ▼
Behavioral baseline established
        │
        ▼
Future activity is continuously compared to the baseline
        │
        ▼
Significant deviation → Risk score calculated (30+ behavioral indicators)
        │
        ▼
Alert generated if risk threshold is met
```

> **Exam Tip:** Memorize the **~7 day learning period** and the **30+ behavioral indicators** (risky IPs, login failures, admin activity, inactive accounts, unusual locations, impossible travel, unfamiliar devices/user agents, abnormal activity rates). These are classic exam facts.

### Built in Anomaly Detection Policies

| Policy | What It Detects |
|---|---|
| **Impossible Travel** | Sign ins from two geographically distant locations in a time window that makes real travel impossible; often stolen credentials |
| **Activity from Infrequent Country** | Sign in from a country/region the user or org rarely or never accessed before |
| **Malware Detection** | Files in connected cloud apps matched against Microsoft Threat Intelligence malware signatures |
| **Ransomware Activity** | Rapid encryption or modification of large numbers of files |
| **Activity from Suspicious IP Addresses** | Activity from IPs flagged malicious or high risk by Microsoft Threat Intelligence |
| **Suspicious Inbox Forwarding** | New mailbox forwarding rules, a common post compromise attacker technique |
| **Unusual Multiple File Downloads** | Download volume far above the user's normal baseline; possible data exfiltration |
| **Unusual Administrative Activities** | Abnormal admin operations (privilege changes, config changes) versus the admin's own baseline |

### Policy Sensitivity, Suppression, and Scope

These three concepts are commonly confused, so keep them clearly separate.

| Concept | Controls | Simple Definition |
|---|---|---|
| **Policy Sensitivity** | How aggressively anomalies are detected | The deviation threshold required before an alert fires |
| **Suppression** | Which known good activity should stay silent | Prevents alerts for activity already confirmed legitimate; does **not** stop or hide the activity itself, only the alert |
| **Policy Scope** | Which users/groups the policy applies to | All users (default), specific users/groups, or included/excluded users/groups |

**Policy Sensitivity levels:**

| Level | Behavior | Trade off |
|---|---|---|
| **Low** | Alerts only on major deviations | Fewer false positives, may miss subtle attacks |
| **Medium** | Balances alert volume and coverage | Recommended default for most organizations |
| **High** | Alerts on small deviations, ideal for privileged accounts | More alerts, more false positives, but higher detection coverage |

**Suppression example:** an employee who regularly flies between New York and London every week would normally trigger repeated Impossible Travel or Infrequent Country alerts. Suppression tells MDCA this travel pattern is expected, so it stops generating alerts for that user, without turning off monitoring or logging.

**Scope example:** a company wants stricter monitoring on Finance. The administrator scopes an anomaly policy to the Finance group only; HR and Sales are unaffected. Scope can also exclude accounts (service accounts, frequently traveling executives) that would otherwise generate excessive noise.

> **Exam Tip, quick recall:**
> * **Sensitivity = Detection strictness**
> * **Suppression = Ignore known normal behavior**
> * **Scope = Target users or groups**

### Real World SOC Scenario

```text
Baseline: user normally signs in from New York on a managed Windows device
        │
        ▼
Sign in from Singapore, unfamiliar browser, 15 minutes after the NY sign in
        │
        ▼
Thousands of SharePoint file downloads begin
        │
        ▼
A new mailbox forwarding rule is created
        │
        ▼
MDCA flags: Impossible Travel + Unusual Multiple File Downloads + Suspicious Inbox Forwarding
        │
        ▼
SOC analyst investigates → confirms compromise
        │
        ▼
Response: revoke active sessions, reset password, block malicious IP,
          open a full incident response investigation
```

> **Exam Tip:** This scenario is a template for SC-200 case study questions: multiple correlated anomalies, not a single alert, are what confirm account compromise. The response sequence (revoke sessions → reset credentials → block IP → investigate) is the expected answer pattern.

## 9. Frequently Confused Concepts

### Cloud Discovery vs Threat Detection

| | Cloud Discovery | Threat Detection |
|---|---|---|
| **Question answered** | "What cloud apps are my users accessing?" | "What suspicious activity is happening inside connected apps?" |
| **Scope** | All apps, discovered from network logs | Only apps actively connected/monitored |
| **Output** | App inventory, risk scores, Shadow IT list | Anomaly alerts (Impossible Travel, Suspicious Inbox Forwarding, etc.) |

### Defender for Cloud Apps vs Defender for Cloud

A very common SC-200 mix up, since the names look alike:

| | Microsoft Defender for Cloud Apps | Microsoft Defender for Cloud |
|---|---|---|
| **Category** | CASB (Cloud Access Security Broker) | Cloud Security Posture Management (CSPM) and workload protection |
| **Protects** | User to SaaS app interactions, cloud app usage, sessions | Azure, hybrid, and multi cloud infrastructure resources (VMs, storage, databases, containers) |
| **Typical questions** | Which SaaS apps are used, is data leaking, is a session risky | Is my resource configuration secure, what is my Secure Score, are workloads protected |

### Access Controls vs Session Controls (Recap)

| | Access Controls | Session Controls |
|---|---|---|
| Applies | Before sign in | After sign in |
| Owned by | Microsoft Entra ID | Defender for Cloud Apps (CAAC) |
| Example | Require MFA | Block download of a sensitive file |

## 10. SC-200 Last Minute Revision

### One Page Cheat Sheet

**Core identity:** MDCA = Microsoft's CASB, formerly named **MCAS**. Sits between users and cloud apps to give visibility and control.

**Four pillars:** Discover Shadow IT → Protect sensitive data → Detect threats/anomalies → Assess app compliance.

**Three protection methods:**

```text
Cloud Discovery        → visibility only, reads logs, no blocking
App Connector (API)    → deep inspection inside the app, after the fact governance
CAAC (reverse proxy)   → real time blocking, requires Entra ID as IdP
```

**Key numbers to memorize:**

| Number | What It Means |
|---|---|
| ~7 days | Learning period before an anomaly baseline is established |
| 30+ | Behavioral indicators used to calculate a risk score |
| 16,000+ | Cloud apps in the Microsoft Cloud App Catalog |
| 80+ | Risk factors used to evaluate each app |
| 100+ | Built in Sensitive Information Types (SITs) |
| 5 | Default sensitivity labels: Personal, Public, General, Confidential, Highly Confidential |

**Anomaly policies to recognize by name:** Impossible Travel, Activity from Infrequent Country, Malware Detection, Ransomware Activity, Activity from Suspicious IP Addresses, Suspicious Inbox Forwarding, Unusual Multiple File Downloads, Unusual Administrative Activities.

**Three easily confused controls, one line each:**

* **Sensitivity** → how strict detection is.
* **Suppression** → silence alerts for known good behavior (activity still happens and is still logged).
* **Scope** → which users/groups a policy watches.

**Deployment memory aid for CAAC:** Entra ID decides **when**, Defender for Cloud Apps decides **what**.

```text
User → Microsoft Entra ID → Conditional Access → Defender for Cloud Apps → Cloud App Session
```

**Governance actions to recognize:** block sharing, block download, encrypt file, apply sensitivity label, notify admin/SOC, quarantine file, remove permissions, move to trash, revoke OAuth consent, revoke session.

**Do not confuse:** Defender for Cloud Apps (CASB, SaaS sessions and usage) with Defender for Cloud (CSPM, infrastructure posture and workload protection).

> **Final Reminder:** Most SC-200 questions on this topic test whether you know **which component answers which question** (Cloud Discovery vs App Connector vs CAAC, Sensitivity vs Suppression vs Scope) rather than raw memorization of every feature. Focus revision time there first.
