## 1. The Standalone Experience

The **standalone experience** is the dedicated web portal for Microsoft Security Copilot (separate from the embedded experiences inside Defender or Sentinel).

**Landing page components:**

| Component | Purpose |
|---|---|
| **Navigation Panel** | Move between areas of the portal |
| **Workspaces** | Switch between isolated Copilot environments |
| **Prompts to Try** | Suggested starting prompts |
| **Prompt Bar** | Where an analyst types a prompt |

**Key features of the standalone portal:**

* **Agents** automate repetitive security tasks.
* **Promptbooks** are predefined, multi step investigation workflows.
* **Build** lets organizations create custom AI agents.
* **History** stores previous sessions. Deleted sessions have a **30 day TTL** (time to live) before permanent removal, while audit logs can be retained for **90 days**.
* **Workspaces** isolate settings, permissions, plugins, and SCU capacity from one another.
* **Owners** manage configuration, plugins, roles, workspaces, and usage monitoring.
* **Contributors** can use Security Copilot but cannot perform administrative tasks.
* **Usage Monitoring** helps administrators track SCU consumption and workspace activity.

> **SC-200 Exam Tips**
> * Know the two portal roles: **Owner** (full administrative control) versus **Contributor** (usage only, no admin tasks).
> * Memorize the retention numbers: deleted sessions, **30 day TTL**; audit logs, **90 days**.
> * The standalone portal is where **workspaces, agents, promptbooks, and Build (custom agents)** all live.

## 2. Sessions in the Standalone Experience

A **session** is a conversation in Security Copilot containing one or more prompts and responses. Everything related to a single investigation is stored in that same session.

**A session can start by:**

1. Typing a manual prompt.
2. Running a promptbook.
3. Selecting a suggested prompt.

**Four features available in every session:**

| Feature | What It Does |
|---|---|
| **Process Log** | Explains how Security Copilot generated its response and shows the safety checks performed |
| **Actions on prompts and responses** | Pin, Edit, Rerun, Delete, Export, Copy, Provide Feedback |
| **Prompt Feedback** | Rate a response as **Looks right**, **Needs improvement**, or **Inappropriate** |
| **Pin Board** | Stores important prompts and responses for quick reference; can be shared with other users and exported to **Word**, **Email**, or the clipboard |

> **SC-200 Exam Tips**
> * The **Process Log** is the transparency mechanism, it shows how a response was produced and what safety checks ran, which is what lets analysts trust AI generated output in an investigation.
> * Know the exact three feedback options: **Looks right**, **Needs improvement**, **Inappropriate**.
> * The **Pin Board** is for curating and sharing key findings, not for running new prompts.

## 3. Workspaces

A **workspace** is an isolated Security Copilot environment inside a Microsoft tenant. Each workspace has its own:

* Users and permissions
* Plugins
* Promptbooks
* Uploaded files
* Configuration
* Capacity allocation
* Data storage settings

Multiple workspaces can exist in the same tenant, but they operate completely independently from one another.

### Workspace vs Tenant

| | Tenant | Workspace |
|---|---|---|
| **Definition** | The organization's entire Microsoft environment | An isolated environment that exists **only inside Security Copilot** |
| **Contains** | Microsoft Entra ID, Microsoft 365 services, Azure resources, one or more Security Copilot workspaces | Its own users, permissions, plugins, promptbooks, files, and capacity |
| **Important note** | | A workspace is **not** Microsoft 365 and **not** Azure |

```text
Tenant
   │
   ▼
Security Copilot
   │
   ├── Workspace A  (e.g. SOC Team)
   ├── Workspace B  (e.g. Threat Hunting Team)
   ├── Workspace C  (e.g. Incident Response Team)
   └── Workspace D  (e.g. Security Research Team)
```

### Why Use Multiple Workspaces?

Organizations create multiple workspaces to:

* Separate different security teams.
* Apply different permissions per team.
* Allocate Security Compute Units (SCUs) independently.
* Control costs.
* Store data in specific geographic regions for compliance.
* Use different plugins and promptbooks per team.
* Test new plugins and promptbooks before rolling them out organization wide.

**SCUs and workspaces:** every workspace uses Security Compute Units for its AI processing capacity, and a workspace must be associated with SCU capacity before users can use Security Copilot inside it effectively.

> **SC-200 Exam Tips**
> * Creating a workspace requires the **Security Administrator** role plus Azure subscription permissions to attach capacity.
> * Workspace settings affect **only that workspace**, they do not carry over to other workspaces in the same tenant.
> * **Audit Logging** is the one major exception, it is a **tenant wide** setting applied through **Microsoft Purview** and covers all workspaces.
> * Workspace owners can create, configure, switch, manage capacity for, and delete workspaces.
> * When switching workspaces inside integrated Microsoft security portals (e.g. the Defender portal), reload the page or sign back in to avoid stale workspace context errors.

## 4. Security Copilot Plugins

A **plugin** is a software component that connects Microsoft Security Copilot to another service. Without plugins, Copilot is only a general AI assistant. With plugins enabled, Copilot can retrieve security alerts, read incidents, search devices, query Microsoft Sentinel, analyze files, execute KQL queries, access threat intelligence, and retrieve data from third party security tools.

### Plugin Categories

| Category | Connects To | Examples |
|---|---|---|
| **1. Microsoft Plugins** | Microsoft security products, many are preinstalled | Microsoft Defender XDR, Microsoft Sentinel, Azure Firewall, Azure Web Application Firewall, Microsoft Defender External Attack Surface Management |
| **2. Other Plugins** (Non Microsoft) | Third party security platforms | ServiceNow, Splunk, CrowdStrike, GreyNoise, Tanium, Netskope, Cyware |
| **3. Website Plugins** | Publicly available websites | Threat intelligence sites, documentation, security references, public knowledge bases |
| **4. Custom Plugins** | An organization's own systems | Internal security tools, proprietary applications, custom APIs, internal knowledge bases |

If a Copilot owner has restricted a plugin, it appears disabled or unavailable to other users until permissions are granted.

### Authentication

| Plugin Type | Authentication Model | Notes |
|---|---|---|
| **Microsoft Plugins** | **On-Behalf-Of (OBO)** | Copilot recognizes the signed in user and reuses that user's existing Microsoft identity and permissions, no extra sign in needed if the user already has access to the product. Some Microsoft plugins showing a **Settings** or **Set up** option (e.g. Microsoft Sentinel) still require additional configuration beyond OBO. |
| **Non Microsoft Plugins** | Defined by the vendor | Commonly **API keys**, **OAuth credentials**, or other service specific credentials; each plugin defines its own requirements |

> **SC-200 Exam Tips**
> * Memorize the four plugin categories: **Microsoft, Other, Websites, Custom**.
> * **Microsoft plugins → OBO authentication** (reuses signed in identity). **Non Microsoft plugins → API keys/OAuth/service specific credentials**.
> * **Owners** control plugin availability and can restrict a plugin to **All users** or **Owners only**.
> * Products accessed through a plugin generally require **separate licensing** for that underlying product.

## 5. Plugin vs System Capability

This pairing is one of the most heavily tested distinctions in this module.

> **Plugin = Connection.** It gives Security Copilot access to another product (e.g. Microsoft Defender XDR or Microsoft Sentinel).
>
> **System Capability = What Copilot can actually do through that connection.** A System Capability is a predefined, single purpose action (or built in prompt) exposed by an enabled plugin.

```text
Before enabling the Microsoft Defender XDR plugin
        │
        ▼
Security Copilot can answer general questions only
Security Copilot CANNOT access Defender XDR data
        │
        │   (plugin is enabled)
        ▼
Security Copilot connects to Defender XDR
        │
        ▼
New System Capabilities become available:
   Analyze a file
   Generate an incident report
   List incidents
   Show device summary
   Recommend incident response
```

> **SC-200 Exam Tips**
> * If a question describes "giving Copilot access to a product," it is testing **Plugin**.
> * If a question describes "a specific action Copilot can now perform," it is testing **System Capability**.
> * A single plugin can expose **many** System Capabilities.

## 6. Defender XDR and Sentinel Plugins

Security Copilot ships with two Defender XDR related plugins and two Sentinel related plugins.

### Microsoft Defender XDR Plugin

Enables Copilot to summarize incidents, generate incident reports, recommend guided responses, retrieve incident information, list incidents and alerts, summarize device security status, and analyze files and scripts.

**Example prompts:**

* "Summarize incident 12345"
* "Generate guided response for incident 12345"
* "Which devices are involved in incident 12345?"

A built in **Defender XDR incident investigation promptbook** is also available out of the box.

### Natural Language to KQL, Defender XDR

Converts a plain English question into Microsoft Defender XDR **Kusto Query Language (KQL)**, without the analyst writing KQL manually.

```text
Analyst asks: "Show failed logins from yesterday."
        │
        ▼
Copilot generates the equivalent KQL query
        │
        ▼
Analyst can Execute, Review, or Modify the query before running it
```

### Microsoft Sentinel Plugin

Lets analysts retrieve incidents, alerts, and workspace information from Microsoft Sentinel.

**Example prompts:**

* "Show my assigned incidents."
* "Show the latest incident."
* "Show the five highest severity incidents."

A built in **Microsoft Sentinel incident investigation promptbook** is also available.

### Natural Language to Sentinel KQL

Same concept as the Defender XDR version, but targeted at Sentinel. Example: asking "Show all failed sign-ins from the last 24 hours" produces a valid Sentinel KQL query that can be executed or edited.

> **SC-200 Exam Tips**
> * Both Defender XDR and Sentinel each have **two** plugins: the main incident/data plugin, and a **Natural Language to KQL** plugin.
> * Natural Language to KQL output is always **reviewable and editable before execution**, Copilot does not force blind execution.
> * Both products include a **built in incident investigation promptbook**.

## 7. Custom Promptbooks

A **custom promptbook** is a user created collection of prompts that run **sequentially** to automate a security investigation or repetitive task. Instead of manually typing several prompts every time, the workflow is built once and run whenever needed.

**Example:** combining "Show failed login attempts," "Identify the authentication method used," and "Summarize the findings" into a single promptbook that runs all three automatically.

**Why create custom promptbooks:**

* Automate repetitive investigation workflows.
* Standardize investigation procedures across analysts.
* Reduce manual effort and typing.
* Save time during incident response.
* Share investigation workflows with other users in the organization.
* Customize Security Copilot for organization specific needs.

### Creating a Promptbook from an Existing Session

```text
Open My Sessions
        │
        ▼
Select the session containing the prompts you want to reuse
        │
        ▼
Select one or more prompts from that session
        │
        ▼
Click Create Promptbook
        │
        ▼
Promptbook Builder opens for customization
```

### Input Parameters

One of the most important SC-200 concepts here. Instead of hardcoding values, create reusable variables using **angle brackets `< >` with no spaces inside**.

**Examples:** `<IncidentID>`, `<ThreatActor>`, `<threatactorname>`, `<number>`

Prompt example: `Show the last <number> failed login attempts.` When the promptbook runs, Security Copilot asks the user to supply a value (for example, `5`) and uses it in the investigation.

**Input parameter rules:**

1. Enclose the parameter in angle brackets `< >`.
2. Do **not** include spaces inside the brackets.
3. Use clear, descriptive names.
4. A promptbook can contain multiple input parameters.
5. Parameters are automatically detected and listed under **Inputs You'll Need**.

### Continue on Failure

Controls what happens if one prompt inside the promptbook fails.

| Setting | Behavior |
|---|---|
| **Enabled** | If a prompt fails, Security Copilot continues executing the remaining prompts in the promptbook |
| **Disabled** | The entire promptbook stops the moment any prompt fails |

Useful when some prompts are optional or may occasionally return no results, but the rest of the investigation should still proceed.

> **SC-200 Exam Tips**
> * A promptbook is configured with a **name, tags, description, plugins, prompts, and sharing settings**.
> * Sharing options are **Just me** or **Anyone in my organization**.
> * Only the **owner** of a promptbook can edit it.
> * Management options: **View, Edit, Duplicate, Delete, Run (Get Started)**.
> * Know the exact syntax rule: input parameters use `< >` with **no spaces**, e.g. `<IncidentID>` is valid, `<Incident ID>` is not.

## 8. Knowledge Base Connections

A **knowledge base connection** lets Security Copilot use an organization's own internal information when answering prompts, producing responses that are more accurate, organization specific, and context aware, grounded in real internal procedures and policy rather than general knowledge alone.

**Example knowledge sources:** security policies, compliance documents, incident response playbooks, investigation procedures, standard operating procedures (SOPs), KQL query libraries, wikis, historical investigation data, security frameworks.

### Why This Is Needed

Security Copilot only knows Microsoft's own security knowledge, public information, and whatever the Microsoft security products it is connected to expose. It does **not** know an organization's internal documents (its own policies, playbooks, past investigation reports, internal wikis) unless a knowledge base connection is configured.

### Two Connection Methods

| Method | Best For | Notes |
|---|---|---|
| **File Upload** | Small organizations, temporary documents, individual reference files, investigation playbooks, policy documents | Supported types: **PDF, DOCX, TXT, Markdown (.md)**. Files are private to the uploading user and stored in the **Security Copilot service**, not the Microsoft tenant. Not intended for malware evaluation or detonation. |
| **Azure AI Search Plugin** | Large organizations, large document repositories, frequently updated documentation, centralized knowledge bases | Connects Copilot to an existing **Azure AI Search index** so it can search indexed content on demand |

### Using File Upload

```text
Open Manage Sources
        │
        ▼
Select Files
        │
        ▼
Upload supported documents (PDF, DOCX, TXT, .md)
        │
        ▼
Enable the file using the toggle switch
        │
        ▼
Mention "uploaded files" or the specific file name in your prompt
```

Only files enabled for the current session are used by Copilot during that session.

### Using the Azure AI Search Plugin

Explicitly mention **"Azure AI Search"** in the prompt to invoke the plugin, for example: *"Summarize my organization's MFA policies in Azure AI Search"* or *"Search my Azure AI Search index for incident response steps for failed sign-in attempts."* The plugin performs both semantic and keyword search across the connected index.

**What Azure AI Search actually is:** Microsoft's enterprise search engine, essentially a private search engine for an organization's own documents (PDFs, Word documents, wikis, SharePoint content, incident playbooks, security policies, SQL data, Azure Blob Storage) rather than the public internet. It first builds a searchable **index** of all that content, similar to how a book's index lets a reader jump straight to a page instead of reading the entire book. Security Copilot cannot query Azure AI Search directly, it needs the **Azure AI Search Plugin** to bridge the two.

```text
Company Documents
  (security policies, IR playbooks, SOPs, KQL library, wikis, compliance docs)
        │
        ▼
Azure AI Search  →  creates a searchable index
        │
        ▼
Azure AI Search Plugin  (the bridge/connector)
        │
        ▼
Microsoft Security Copilot
```

**Technical requirements for the Azure AI Search index:**

* The **text field** must be searchable.
* The **title field** must be filterable.
* The **vector field** must use the `text-embedding-ada-002` embedding model.

> **SC-200 Exam Tips**
> * **File Upload** → small scale, private to the uploader, stored in the Security Copilot service (not the tenant), never for malware detonation.
> * **Azure AI Search Plugin** → large scale, centralized, requires explicit mention of **"Azure AI Search"** in the prompt to invoke.
> * Azure AI Search performs **indexing** (building the searchable structure) and **querying** (retrieving relevant results).
> * Security Copilot currently works primarily with **text content** and supports only **one Azure AI Search index at a time**.

## 9. Frequently Confused Concepts

### Plugin vs System Capability (Recap)

| | Plugin | System Capability |
|---|---|---|
| **Role** | Connection to an external product | The specific action performed through that connection |
| **Analogy** | The door into a room | What you can actually do once inside the room |
| **Example** | Microsoft Defender XDR plugin | "Summarize incident 12345" |

> **Note on terminology:** Some SC-200 materials shorten "System Capability" to simply **Capability** or **Skill** when discussing Security Copilot generally. All three terms describe the same idea: a single, specific, predefined action that becomes available once its parent plugin is enabled. Do not be thrown off if a question swaps between these labels.

### Tenant vs Workspace (Recap)

| | Tenant | Workspace |
|---|---|---|
| Scope | Entire Microsoft organization | Isolated environment inside Security Copilot only |
| Contains | Entra ID, Microsoft 365, Azure, Security Copilot workspaces | Its own users, permissions, plugins, promptbooks, files, capacity |

### File Upload vs Azure AI Search Plugin (Recap)

| | File Upload | Azure AI Search Plugin |
|---|---|---|
| Scale | Small, individual documents | Large, centralized repositories |
| Storage | Security Copilot service, private to the uploader | Existing Azure AI Search index owned by the organization |
| Invocation | Mention "uploaded files" or the file name | Explicitly mention "Azure AI Search" |

### Owner vs Contributor (Recap)

| | Owner | Contributor |
|---|---|---|
| Can use Copilot | Yes | Yes |
| Administrative tasks (plugins, roles, capacity, workspaces) | Yes | No |

## 10. SC-200 Last Minute Revision

### One Page Cheat Sheet

**Portal roles:** Owner (full admin control) vs Contributor (usage only).

**Retention numbers to memorize:**

| Item | Retention |
|---|---|
| Deleted sessions | 30 day TTL |
| Audit logs | 90 days |

**Session feedback options (exact wording):** Looks right, Needs improvement, Inappropriate.

**Session actions:** Pin, Edit, Rerun, Delete, Export, Copy, Provide Feedback.

**Containment hierarchy:**

```text
Tenant
   └── Security Copilot Workspace(s)
             └── Plugins
                     └── System Capabilities
```

**Four plugin categories:** Microsoft, Other (Non Microsoft), Websites, Custom.

**Authentication quick map:**

| Plugin Type | Auth Model |
|---|---|
| Microsoft | On-Behalf-Of (OBO), reuses the signed in user's identity |
| Non Microsoft | API keys, OAuth, or other service specific credentials |

**Plugin = Connection. System Capability = Action.** A plugin can expose many System Capabilities.

**Defender XDR and Sentinel each ship with two plugins:** the main data/incident plugin, and a Natural Language to KQL plugin. Generated KQL is always reviewable and editable before it runs.

**Promptbook input parameter syntax:** `<ParameterName>`, angle brackets, **no spaces inside**. Auto listed under **Inputs You'll Need**.

**Continue on Failure:** Enabled → remaining prompts still run after a failure. Disabled → the whole promptbook stops on the first failure.

**Knowledge base connections, quick map:**

```text
Small, individual docs        → File Upload (PDF, DOCX, TXT, .md)
Large, centralized, searchable → Azure AI Search Plugin (mention it explicitly in the prompt)
```

**Azure AI Search index requirements:** text field searchable, title field filterable, vector field uses `text-embedding-ada-002`. Supports **one index at a time**, text content primarily.

**Creating a workspace requires:** Security Administrator role **and** Azure subscription permissions to attach capacity.

**Audit Logging is the exception to "workspace settings stay local":** it is **tenant wide**, applied through **Microsoft Purview**, and covers every workspace.

> **Final Reminder:** Expect exam questions that hinge on precise terminology pairs: Plugin vs System Capability, Tenant vs Workspace, Owner vs Contributor, and File Upload vs Azure AI Search Plugin. Read each question carefully for whether it is asking about the **connection** (plugin, workspace, tenant) or the **action/content** (capability, permission, document) inside that connection.
