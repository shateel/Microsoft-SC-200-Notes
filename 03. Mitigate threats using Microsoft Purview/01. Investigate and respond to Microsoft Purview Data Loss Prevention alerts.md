## 1. DLP Alert Fundamentals

### 1.1 What Is a DLP Alert

A **DLP alert** is a notification generated when a user's action matches a condition defined in a **Data Loss Prevention (DLP) policy**.

> A DLP alert does **not** automatically mean malicious activity occurred. It only means a policy condition was met, and it always requires investigation.

A DLP alert is triggered when a user performs an action involving **sensitive information** that matches a DLP policy, for example:

* Emailing files that contain credit card numbers
* Sharing documents that contain Social Security numbers
* Uploading confidential financial records
* Copying sensitive files to an unauthorized location

### 1.2 Types of DLP Alerts

<table>
<tr><th>Type</th><th>Definition</th><th>Example</th></tr>
<tr><td><b>Single Event Alert</b></td><td>Generated when one action violates a DLP policy</td><td>A user emails one document containing customer credit card numbers to a personal account</td></tr>
<tr><td><b>Multi Event Alert (Aggregate Alert)</b></td><td>Generated when multiple related activities occur over time. Individually each action may look harmless, but together they exceed a policy threshold</td><td>A user sends several emails, each with one credit card number, none of which alone triggers a policy, but the combined volume does</td></tr>
</table>

> **Exam trap:** "Multi Event Alert" (used when describing alert behavior) and "Aggregate Alert" (used when describing policy configuration) refer to the same underlying mechanism: several related matches are combined into a single alert instead of generating a flood of individual alerts. Do not treat them as two different features.

### 1.3 Where DLP Alerts Appear

The same DLP alert surfaces in **two different Microsoft products**, each with a different purpose.

<table>
<tr><th>Product</th><th>Primary Purpose</th><th>What It Is Used For</th></tr>
<tr><td><b>Microsoft Defender XDR</b></td><td>Security investigation</td><td>Correlates DLP alerts with other security events, combines alerts into incidents, and determines whether the DLP alert is part of a larger attack</td></tr>
<tr><td><b>Microsoft Purview</b></td><td>Compliance and policy management</td><td>Shows which DLP policy and rule matched, why the alert occurred, and whether the policy needs tuning to reduce false positives</td></tr>
</table>

              │

   ▼                     ▼
Microsoft Purview     Microsoft Defender XDR
(Compliance and       (Security investigation
 policy tuning)        and incident correlation)

### 1.4 Initial Investigation Workflow

When first investigating any DLP alert, follow this general sequence:

```text
Review what triggered the alert
              │
              ▼
Identify the user involved
              │
              ▼
Determine what sensitive data was affected
              │
              ▼
Decide: legitimate or suspicious?
              │
              ▼
Check Microsoft Defender XDR for related events
              │
              ▼
False positive → tune the policy in Purview
Malicious → continue investigation and response
```

### 1.5 What Is Microsoft Purview

**Microsoft Purview** is Microsoft's data security, compliance, governance, and risk management platform. It helps organizations:

* Discover, classify, and label sensitive data
* Prevent sensitive data from being leaked
* Monitor how users interact with sensitive data
* Detect insider threats
* Investigate compliance and legal cases
* Meet regulatory requirements such as GDPR, HIPAA, and PCI DSS

Purview protects data regardless of where it lives, including Exchange Online email, Teams chats, SharePoint documents, OneDrive files, Office files, PDFs, and Azure data.

### SC-200 Exam Tips

> * A DLP alert fires when an action matches a DLP policy condition. It is a signal to investigate, not proof of wrongdoing.
> * Know the two alert types: **Single Event** (one action) and **Multi Event / Aggregate** (multiple related actions over time).
> * Memorize the split: **Defender XDR = security investigation and correlation**, **Purview = compliance, policy analysis, and policy tuning**.
> * False positives lead to **policy tuning** in Purview. Confirmed malicious activity leads to **incident response**, typically in Defender XDR.

## 2. The DLP Alert Lifecycle

The DLP alert lifecycle has **six stages**. This sequence is a very likely exam topic, memorize the order.

```text
Trigger
   │
   ▼
Notify
   │
   ▼
Triage
   │
   ▼
Investigate
   │
   ▼
Remediate
   │
   ▼
Tune
```

### 2.1 Trigger

A DLP alert begins when a user action matches a condition in a DLP policy. Common triggers include:

* Sharing sensitive data outside the organization
* Downloading confidential files to removable media (USB)
* Uploading protected files to an unsanctioned cloud application

Depending on policy configuration, Purview can **block** the action, **warn** the user, and/or **generate a DLP alert**.

### 2.2 Notify

After an alert is generated, notifications help administrators begin the investigation. The alert appears in:

* **Microsoft Defender Portal**, used to correlate DLP alerts with other security signals and group related alerts into incidents
* **Microsoft Purview Alerts Dashboard**, used to view alert details, review alert history, and perform basic alert management

Additional capabilities at this stage include email notifications to users, administrators, or security teams; **Activity Explorer** for reviewing user activity; and API based export of activity data for reporting or long term storage.

### 2.3 Triage

Triage determines whether an alert needs further investigation. The analyst decides whether the alert is a **false positive**, a **valid policy violation**, or a **high priority incident**.

If valid, the analyst assigns an owner, sets the priority, and begins investigation. Useful triage tools:

* Microsoft Defender groups related alerts into a single incident
* **Tags**, **Comments**, and **Filters** help organize incidents
* Filter incidents by **Service/Detection Source → Microsoft Data Loss Prevention**
* If **Insider Risk Management** is integrated, the user's insider risk severity displays alongside the DLP alert
* **Microsoft Security Copilot** can summarize alert context and recommend next steps

### 2.4 Investigate

Once assigned, the analyst gathers evidence to determine whether malicious activity occurred. Pick the right tool for the goal:

<table>
<tr><th>Tool</th><th>When to Use It</th></tr>
<tr><td><b>Microsoft Defender</b></td><td>Determine whether the DLP alert is part of a broader attack by correlating endpoint, identity, email, and cloud signals</td></tr>
<tr><td><b>Purview Alerts Dashboard</b></td><td>Review which policy and rule triggered, examine the matched file or message, decide whether the policy needs adjustment</td></tr>
<tr><td><b>Activity Explorer</b></td><td>Review and compare user activities over time without opening individual alerts</td></tr>
<tr><td><b>Content Explorer</b></td><td>Inspect the actual content (file or email) that triggered the DLP policy</td></tr>
</table>

If **Insider Risk Management** is enabled, analysts can also review a **User Activity Summary** covering up to **120 days** of user behavior, including risky activity such as data exfiltration attempts or attempts to bypass policy warnings.

### 2.5 Remediate

After confirming the alert, the analyst chooses a response, such as:

* Mark the alert as informational
* Contact the user to explain the risky action
* Block file sharing or revoke sharing permissions
* Remove the file from cloud storage
* Apply a sensitivity label
* Reset passwords or disable user accounts
* Isolate affected devices

From the **Microsoft Defender portal**, administrators can also remove or quarantine files, revoke sharing permissions, disable accounts, reset passwords, download or delete emails, and use **Advanced Hunting** to search for related events.

### 2.6 Tune (Policy Improvement)

The final stage improves the DLP policy based on investigation results. Administrators may adjust the sensitivity threshold, the policy scope (users, groups, locations), notification settings, or whether certain low risk activities should generate alerts at all. The goals are to reduce false positives, improve detection accuracy, and ensure policies generate meaningful alerts.

### SC-200 Exam Tips

> * Memorize the six stages in order: **Trigger, Notify, Triage, Investigate, Remediate, Tune.**
> * **Trigger** = policy match. **Notify** = alert appears in Defender and Purview. **Triage** = decide validity and priority.
> * **Investigate** uses different tools for different goals: Defender (correlation), Purview (policy analysis), Activity Explorer (user behavior over time), Content Explorer (actual file/message content).
> * **User Activity Summary** requires **Insider Risk Management** and covers **120 days**.
> * **Tune** is the feedback loop that reduces false positives and alert fatigue, it is easy to forget this final stage exists as part of the lifecycle.

## 3. Configuring DLP Policies to Generate Alerts

### 3.1 What You Configure

When creating or editing a DLP policy, you decide which activities to monitor, which action the policy takes (block, warn, allow), whether an alert should be generated, who receives notifications, and when an alert is created (every match, or only after a threshold).

### 3.2 Configuration Workflow

```text
Open Microsoft Purview
              │
              ▼
Solutions → Data Loss Prevention → Policies
              │
              ▼
Create a new policy or edit an existing one
              │
              ▼
Select locations (Exchange, SharePoint, OneDrive, Teams, Devices, etc.)
              │
              ▼
Create or edit a DLP rule
              │
              ▼
Configure Incident Reports and Alert Settings
              │
              ▼
Deploy: live, simulation mode, or disabled
              │
              ▼
Save the policy
```

### 3.3 Single Event vs Aggregate Alerts

<table>
<tr><th>Setting</th><th>Single Event Alerts</th><th>Aggregate Alerts</th></tr>
<tr><td>When generated</td><td>On every policy match</td><td>Only after a threshold (matches, data volume, or time) is reached</td></tr>
<tr><td>Purpose</td><td>Catch every individual violation</td><td>Reduce alert fatigue by grouping repeated matches</td></tr>
<tr><td>Licensing</td><td>Available on lower Microsoft 365 licenses</td><td>Requires E5/G5 or an eligible add on</td></tr>
</table>

**User and rule based alert aggregation** combines repeated matches from the same user under the same rule into a single alert, simplifying SOC investigations.

> **Timing note:** New or modified DLP policies can take **up to 3 hours** before alerts start appearing.

### 3.4 Real World Scenario Takeaway

A company protecting customer financial records in SharePoint configured a policy at **High severity**, with **aggregate** alerting and a threshold of **10 matches within 60 minutes**. During an attempted exfiltration involving repeated uploads to personal cloud storage, Purview generated **one aggregate alert** instead of ten separate ones. The analyst investigated the single alert in Defender XDR, correlated it with endpoint activity, and confirmed an insider threat. Takeaway: aggregation surfaces meaningful, high signal alerts instead of noisy duplicates.

### SC-200 Exam Tips

> * Alert settings are configured **inside** the DLP policy or rule, not as a separate object.
> * **Single Event** = every match. **Aggregate** = threshold based, requires E5/G5.
> * Allow **up to 3 hours** for a new or edited policy to start producing alerts.
> * A policy can be deployed **live**, in **simulation mode** (test without enforcing), or left **disabled**.

## 4. Investigating DLP Alerts in Microsoft Purview

### 4.1 Where to Investigate

DLP alerts are investigated in the **Microsoft Purview Portal**, under **Data Loss Prevention → Alerts**. The Alerts dashboard lets analysts view all DLP alerts, filter them, investigate policy violations, and triage incidents. Alert retention depends on the organization's **Purview Audit retention policy**.

### 4.2 Supported Workloads

DLP alerts can originate from Exchange Online, SharePoint Online, OneDrive, Microsoft Teams (chat and channel messages), Endpoint Devices (Endpoint DLP), Microsoft Fabric/Power BI, on premises repositories, and connected cloud instances.

### 4.3 Investigation Sequence

```text
Filter Alerts
      │
      ▼
Review Alert Details tab (what happened)
      │
      ▼
Review User Activity Summary (up to 120 days, needs Insider Risk Mgmt)
      │
      ▼
Examine Events tab (why the alert triggered)
      │
      ▼
Take remediation action
      │
      ▼
Mark the alert Resolved
```

<table>
<tr><th>Tab</th><th>Answers</th></tr>
<tr><td><b>Details</b></td><td>What happened</td></tr>
<tr><td><b>Events</b></td><td>Why the alert was triggered</td></tr>
<tr><td><b>User Activity Summary</b></td><td>Related user behavior over 120 days (requires Insider Risk Management)</td></tr>
</table>

Remediation actions available directly from Purview include unsharing files, deleting files, applying sensitivity labels, downloading matched content (with permissions), and sending notification emails. **Microsoft Security Copilot** can automatically summarize DLP alerts and recommend next steps.

### 4.4 Real World Scenario Takeaway

An employee uploaded HR data to OneDrive and tried to share it externally; the policy blocked the action and raised an alert. The analyst opened the alert in Purview, reviewed Details (policy, user, data involved), checked the User Activity Summary for prior exfiltration patterns, examined Events for the exact file and action, then unshared the file, notified the user, documented findings, and marked the alert **Resolved**.

### SC-200 Exam Tips

> * Path to memorize: **Purview → Data Loss Prevention → Alerts**.
> * **Details = what happened. Events = why it happened.**
> * Conclude a Purview investigation by setting status to **Resolved**.
> * Security Copilot in Purview summarizes alerts and suggests next steps, it does not make the final decision.

## 5. Investigating DLP Alerts in Microsoft Defender XDR

### 5.1 Why Investigate Here

A single DLP alert rarely tells the whole story. Defender XDR correlates multiple related alerts into one **incident**, giving analysts the complete attack picture across endpoints, Exchange Online, SharePoint, OneDrive, Teams, cloud apps, and identities, instead of "user downloaded a sensitive file" in isolation.

### 5.2 Advanced Hunting with KQL

Defender XDR supports **Advanced Hunting** using **Kusto Query Language (KQL)**. DLP related activity across Microsoft 365 workloads (Exchange, SharePoint, OneDrive, Devices) is investigated using the **CloudAppEvents** table. Analysts can hunt for externally shared files, file activity, site activity, and user DLP violations over the last 30 days, and can save queries for ongoing monitoring.

> **Useful starting query pattern (memorize the table and filter, not the exact syntax):**
> ```kql
> CloudAppEvents
> | where ActionType has "DlpRuleMatch"
> ```
> This returns raw DLP policy match events recorded in the CloudAppEvents table, which analysts then filter further by application, user, or time.

### 5.3 Microsoft Sentinel Integration

Sentinel extends Defender XDR by adding cross platform investigation, correlation with third party data sources, **SOAR** (Security Orchestration, Automation, and Response), and automated playbooks.

```text
Connect Microsoft Defender XDR to Sentinel
              │
              ▼
Enable the CloudAppEvents connector
              │
              ▼
Use KQL to correlate DLP alerts with other security events
```

### 5.4 Incident Investigation Sequence

Navigate to **Microsoft Defender Portal → Incidents & alerts → Incidents**, filter **Service/Detection source** by **Microsoft Data Loss Prevention**, then follow:

```text
Open the DLP incident
      │
      ▼
Review the Alert Story (timeline of events)
      │
      ▼
Examine Related Events (downloads, sharing, overrides, uploads)
      │
      ▼
Check Sensitive Info Types (what data was detected)
      │
      ▼
Review the Source tab (inspect the affected file)
      │
      ▼
Manage Incident: set Severity, Status, and Tags
```

<table>
<tr><th>Tab / Feature</th><th>Purpose</th></tr>
<tr><td>Alert Story</td><td>Timeline of events that caused the DLP policy match</td></tr>
<tr><td>Related Events</td><td>Additional user activity tied to the alert, helps confirm a broader incident</td></tr>
<tr><td>Sensitive Info Types</td><td>Exact sensitive data detected: credit card numbers, passport numbers, custom types</td></tr>
<tr><td>Source tab</td><td>Inspect the affected file. Viewing file content for Endpoint DLP requires Evidence Collection for file activities to be enabled</td></tr>
</table>

Response actions available directly from the incident include downloading suspicious emails (Exchange), unsharing/deleting/downloading/labeling SharePoint and OneDrive files, applying retention labels, sending notification emails, resetting passwords or disabling accounts through the **User card**, and isolating or managing devices through the **Device card**. **Security Copilot** can generate an AI powered incident summary covering severity, matched policy, file details, user identity, and recommended next steps.

### 5.5 Real World Scenario Takeaway

An employee uploaded a spreadsheet with credit card numbers to personal OneDrive, downloaded confidential SharePoint files, and emailed attachments externally. Defender XDR automatically correlated these into **one incident**. The analyst reviewed the Alert Story, Related Events, and Sensitive Info Types, confirmed unauthorized activity via the Source tab, then unshared the file, disabled the account, and isolated the device. The incident was classified **True Positive (Malicious User Activity)**, marked **Resolved**, and an Advanced Hunting query was run to check for similar violations elsewhere in the organization.

### SC-200 Exam Tips

> * Defender XDR groups related DLP alerts into an **Incident**, Purview manages **individual alerts**.
> * Path to memorize: **Defender Portal → Incidents & alerts → Incidents**, filter by **Microsoft Data Loss Prevention**.
> * **CloudAppEvents** is the Advanced Hunting table for DLP and cloud app activity across Microsoft 365.
> * Sentinel setup order: **connect Defender XDR → enable CloudAppEvents connector → correlate with KQL.**
> * Only Defender XDR supports **True Positive / False Positive** classification with a required reason, Purview does not have this field.

## 6. Security Copilot and the DLP Triage Agent

### 6.1 Why the DLP Triage Agent Is Needed

Organizations generate large numbers of DLP alerts daily from Exchange Online, SharePoint Online, OneDrive, Teams, and endpoint devices. Most are harmless or low risk, only a small percentage represent real data exfiltration. The **Microsoft Purview DLP Triage Agent** is an AI powered capability, built on **Microsoft Security Copilot**, that automatically analyzes, prioritizes, and summarizes DLP alerts so analysts can focus on the alerts that matter.

### 6.2 How It Works

The agent evaluates every supported DLP alert by analyzing sensitive information detected, DLP policy actions, user activity, potential exfiltration behavior, policy severity, and file context. It then ranks alerts by **overall risk** instead of chronological order, based on:

* **Content Risk**
* **Exfiltration Risk**
* **Policy Risk**

Alerts are grouped into three categories:

* **Needs Attention**
* **Less Urgent**
* **Not Categorized**

The agent can run in **Automatic** (scheduled) mode or **Manual** (single alert) mode. Only **Active** DLP policies are triaged, **Simulation Mode** policies are excluded.

### 6.3 Customization

Administrators can give the agent **natural language instructions** to influence prioritization, for example: focus on alerts containing tax or finance information with more than five credit card numbers or Social Security Numbers. The agent converts these instructions into logical evaluation rules applied automatically on every run.

### 6.4 Real World Scenario Takeaway

A financial institution generated over 300 DLP alerts in a day across Exchange, Teams, SharePoint, and OneDrive. The Triage Agent placed only five in **Needs Attention** because they involved multiple credit card numbers shared externally through Teams. Security Copilot explained the prioritization, summarized user activity, correlated related actions across OneDrive and Exchange, and flagged a possible exfiltration pattern. The analyst confirmed the risk, escalated, notified the information protection team, and began containment, while low risk alerts stayed in the **Less Urgent** queue.

### 6.5 Limitations

* No support for **Custom SIT only** or **Custom Trainable Classifier only** alerts
* Maximum analyzed file size is **2 MB**
* Only the **10 most relevant files** are analyzed when an alert has more than 10 files
* **Administrative Unit scoped** and **Simulation Mode** policies are not supported

### SC-200 Exam Tips

> * The DLP Triage Agent runs **inside Microsoft Purview**, powered by **Microsoft Security Copilot**.
> * Ranking is based on three risk types: **Content, Exfiltration, Policy**.
> * Three output categories: **Needs Attention, Less Urgent, Not Categorized**.
> * Two run modes: **Automatic** (scheduled) and **Manual** (single alert).
> * Know the hard limits: **2 MB** max file size, **10 files** max analyzed per alert, **Simulation Mode** policies excluded.
> * Security Copilot assists and explains, it never replaces analyst decision making.

## 7. Responding to DLP Alerts

DLP response happens in **two different platforms**, and the exam expects you to know which actions live where.

### 7.1 Responding in Microsoft Purview

Purview manages the **lifecycle of individual DLP alerts** from the **DLP Alerts** dashboard rather than correlating events into a larger incident. Typical response actions:

<table>
<tr><th>Action</th><th>Details</th></tr>
<tr><td>Update Alert Status</td><td><b>Investigating</b> (under review) or <b>Resolved</b> (investigation complete)</td></tr>
<tr><td>Assign the Alert</td><td>Assign to another analyst or team, improves accountability and prevents duplicate work</td></tr>
<tr><td>Add Investigation Comments</td><td>Record what was investigated, findings, evidence, business justification, final decision, and remediation performed. Creates an audit trail</td></tr>
<tr><td>Share Alert Details</td><td>Generates a read only link so auditors, managers, or compliance staff can review without modifying the alert</td></tr>
<tr><td>View User Activity Summary</td><td>Requires Insider Risk Management integration, shows behavioral context around the alert</td></tr>
</table>

### 7.2 Responding in Microsoft Defender XDR

Defender XDR groups related alerts into a single **Incident** that may span Defender for Endpoint, Defender for Office 365, Defender for Identity, Defender for Cloud Apps, and Purview DLP. This gives a much broader view of a potential attack, for example a DLP alert correlated with suspicious sign in activity, malware on the endpoint, impossible travel, privilege escalation, and cloud app access, investigated as **one** incident instead of several unrelated events.

Response actions include updating incident status, assigning the incident, adding notes, **classifying** the incident, and performing remediation such as disabling accounts, removing file access, and applying sensitivity or retention labels.

### 7.3 Purview vs Defender XDR: Response Actions Compared

<table>
<tr><th>Capability</th><th>Microsoft Purview</th><th>Microsoft Defender XDR</th></tr>
<tr><td>Unit of work</td><td>Individual DLP alert</td><td>Correlated Incident (multiple alerts)</td></tr>
<tr><td>Status values</td><td>Investigating, Resolved</td><td>In Progress, Resolved, etc.</td></tr>
<tr><td>Classification field</td><td>None, documented via comments and status</td><td>True Positive / False Positive (reason required)</td></tr>
<tr><td>Assignment</td><td>Yes</td><td>Yes</td></tr>
<tr><td>Notes / comments</td><td>Yes, forms an audit trail</td><td>Yes</td></tr>
<tr><td>Sharing</td><td>Read only link</td><td>Not applicable</td></tr>
<tr><td>Remediation actions</td><td>Unshare, delete, label, notify</td><td>Disable account, remove file access, isolate device, apply labels</td></tr>
</table>

> **Key clarification for the exam:** A sensitivity label classifies and protects content (encryption, watermarking, access restriction), while a retention label manages the content lifecycle (how long it is kept and what happens when it expires). Both can appear as remediation actions, know the difference between them.

### SC-200 Exam Tips

> * Purview responds to **alerts**, Defender XDR responds to **incidents**. This is the single most important distinction in this whole topic.
> * Only Defender XDR requires a **True Positive / False Positive** classification with a reason, Purview relies on comments and status instead.
> * If legitimate activity keeps triggering alerts, **tune the policy** (adjust conditions, add exceptions, narrow scope) instead of repeatedly resolving the same alert.
> * Setting status to **Resolved** closes the current investigation but does **not** suppress future alerts for the same activity.
> * Retention: Defender XDR keeps resolved incidents for up to **six months**, Purview retention depends on the organization's audit log settings.

## 8. SC-200 Last Minute Revision (Cheat Sheet)

### 8.1 The One Page Summary

* A **DLP alert** = a policy match, not proof of malicious intent.
* **Purview** = compliance and policy management, works on individual **alerts**.
* **Defender XDR** = security investigation, works on correlated **incidents**.
* Lifecycle order: **Trigger → Notify → Triage → Investigate → Remediate → Tune.**
* **Single Event** alert = one match. **Aggregate/Multi Event** alert = threshold based, needs E5/G5.
* **CloudAppEvents** is the Advanced Hunting table for DLP and cloud app activity.
* The **DLP Triage Agent** (Security Copilot, inside Purview) ranks alerts by Content, Exfiltration, and Policy risk into Needs Attention, Less Urgent, and Not Categorized.
* Only **Defender XDR** has True Positive/False Positive classification, Purview does not.
