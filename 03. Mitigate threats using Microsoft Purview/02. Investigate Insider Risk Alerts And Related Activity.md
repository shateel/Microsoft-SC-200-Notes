## 1. How Insider Risk Alerts Are Generated

### Key Idea

An Insider Risk alert in Microsoft Purview is never random. It is the output of a defined, five stage process. Knowing this sequence lets an analyst work out what triggered an alert, what evidence was evaluated, and whether the underlying activity actually met policy criteria.

### The Five Stage Process

```text
Settings Configured
      │
      ▼
Policy Created
      │
      ▼
Triggering Event Occurs
      │
      ▼
User Activity Evaluated and Scored
      │
      ▼
Alert Generated
```

| Stage | What Happens |
|---|---|
| Settings Configured | Organization level settings define privacy preferences, monitored and excluded indicators, and included or ignored domains. |
| Policy Created | Insider Risk policies define who is monitored, what activities are detected, and which events trigger monitoring. |
| Triggering Event Occurs | An event (e.g. resignation, access to a risky website, possible exfiltration) activates monitoring for a user. A trigger alone does not create an alert. |
| User Activity Evaluated and Scored | Activities are scored using activity type, configured thresholds, and the user's history. |
| Alert Generated | An alert fires only once the user's calculated risk score exceeds the policy defined threshold. |

> **Exam tip:** A single risky action rarely generates an alert by itself. It is the combination of policy configuration, a triggering event, and an accumulated risk score crossing a threshold that produces the alert. Expect scenario questions that test whether you understand this chain rather than just the individual pieces.

### SC 200 Exam Tips

* Insider Risk alerts follow the sequence: Settings, Policy, Trigger, Score, Alert.
* A triggering event only starts monitoring; it does not by itself create an alert.
* Understanding this pipeline supports consistent triage and helps you avoid wasting time on low risk activity.

## 2. Managing Alert Volume

### Why Alert Volume Matters

The objective is a healthy ratio of signal to noise.

* **Too few alerts:** investigators can miss genuine insider threats.
* **Too many alerts:** analysts experience alert fatigue, investigation workload rises, and the SOC becomes less effective.

### If You Are Receiving Too Few Alerts

Too few alerts usually points to overly restrictive policies or thresholds set too high. Options to increase volume:

| Action | Where |
|---|---|
| Enable more risk indicators | Policy Indicators settings |
| Include more users | Users and Groups section of the policy |
| Lower trigger thresholds | Policy configuration (e.g. resignation, sensitive content access) |
| Lower indicator thresholds | Policy configuration; allows lower severity or less frequent activity to alert |
| Move the Alert Volume slider toward More alerts | Settings → Intelligent detections |

> **Exam tip:** The **Alert Volume** slider under **Settings → Intelligent detections** is the fastest way to raise or lower overall detection sensitivity, including medium and low severity alerts, across the whole environment.

### If You Are Receiving Too Many Alerts

| Action | Purpose |
|---|---|
| Enable Analytics (Settings → Analytics) | Surface tuning recommendations |
| Use Real-Time Insights | Adjust thresholds and indicators based on live data |
| Narrow the policy scope | Reduce the population or activity types monitored |
| Enable Inline Alert Customization | Fine tune alert generation logic directly |
| Bulk dismiss low priority alerts | Clear noise quickly |
| Use Global Exclusions | Prevent trusted, expected activity from generating alerts |
| Use Detection Groups | Apply different policies to different groups of users |
| Use Indicator Variants | Add more granular detection logic |

> **Exam tip: Data Leaks** and **Risky Browser Usage** policy templates support custom thresholds. These can be lowered to raise alert volume for those specific scenarios.

### SC 200 Exam Tips

* Alert volume tuning is continuous work, not a one time setup, and should combine Analytics, Real-Time Insights, and manual policy adjustments.
* Know the difference between tools that **increase** volume (more indicators, more users, lower thresholds, the Alert Volume slider) and tools that **decrease** volume (Global Exclusions, Detection Groups, narrower scope, bulk dismissal).

## 3. Investigating and Triaging Alerts: The Alerts Dashboard

### Investigation Workflow

```text
Insider Risk policy detects suspicious activity
      │
      ▼
Alert is created
      │
      ▼
Alert appears on the Alerts dashboard
      │
      ▼
Analyst reviews the alert and examines additional context
      │
      ▼
Analyst decides: legitimate or not
      │
      ▼
Action taken (dismiss, confirm, create case, assign, keep monitoring)
```

### Alerts Dashboard Fields

| Field | Meaning |
|---|---|
| ID | Unique identifier for the alert |
| Copilot icon | Shows whether Copilot can summarize this alert |
| Users | The person tied to the risky activity |
| Policy | The policy that generated the alert |
| Status | New, confirmed, dismissed, or resolved |
| Spotlight | Flags high priority alerts meeting specific risk criteria |
| Alert severity | Automatically calculated: Low, Medium, or High |
| Time detected | When the alert was generated |
| Assigned to | Current owner, if any |
| Case | Any case this alert is linked to |

> **Exam tip: Spotlight** uses Microsoft's rule based logic (activity type, risk scoring, organizational patterns, and risk indicators) to surface the highest priority alerts automatically, which is especially valuable in environments producing a large daily alert volume.

### Analyst Actions

* Dismiss the alert (expected or non risky activity).
* Confirm the alert and optionally create a case for deeper investigation.
* Assign the alert to another analyst.
* Continue monitoring the user without further action yet.

> **Exam tip:** New risky activity for a user who already has an open alert is added to that **existing** alert rather than generating a duplicate.

### Numbers Worth Memorizing

| Fact | Value |
|---|---|
| Alerts dismissible in a single bulk operation | Up to 400 low priority alerts |
| Retention of Needs review alerts not linked to a case | 120 days |
| Retention of active, unresolved cases | Indefinite |
| Maximum concurrent active Insider Risk cases per organization | 100 |

> **Exam tip:** Security Copilot can summarize an alert (policy name, triggering event, the activity that generated the alert, key user attributes, top risk factors) and answer additional investigation questions, but analysts must still validate any AI generated output before acting on it.

### SC 200 Exam Tips

* The Alerts dashboard is the analyst's central workspace: filters, saved views, custom columns, and keyword search all help manage volume.
* Alert severity is calculated automatically from user history, activity frequency, and detected risk indicators.
* Memorize the retention numbers above; they are easy, discrete exam facts.

## 4. AI Powered Triage: Security Copilot and the Insider Risk Triage Agent

### What the Triage Agent Does

The Insider Risk Triage Agent is an AI capability inside Purview Insider Risk Management. It analyzes alerts automatically, evaluates multiple risk indicators together, prioritizes the alerts that carry the greatest insider risk, and reduces manual investigation effort so analysts can focus on the most critical incidents first.

### Alert Categories

| Category | Meaning |
|---|---|
| Needs Attention | Highest insider risk; strong likelihood of a policy violation; investigate immediately |
| Less Urgent | Lower severity and lower likelihood of a violation; still worth reviewing later |
| Not Categorized | The agent could not evaluate the alert, typically due to unsupported policy types; requires manual review |

> **Exam tip:** Alert priority is **dynamic**. As new activity or evidence appears, the agent can reprioritize an alert the next time it runs.

### Prioritization Factors

| Factor | Examples |
|---|---|
| Risk Indicators | Unusual downloads, external sharing, access from unmanaged devices |
| Policy Type | Data theft, security violation, risky AI usage |
| User Context | Adaptive Protection risk score, recent HR signals, organizational role changes |

> **Good to know:** Adaptive Protection is a related Purview capability that automatically tightens Data Loss Prevention controls for users whose calculated insider risk level is elevated. It is one of the contextual signals the Triage Agent factors into prioritization, and it also appears as a response action analysts can apply after confirming risky activity.

### How the Triage Agent Works

```text
User Activity
      │
      ▼
Microsoft Purview Insider Risk Policies
      │
      ▼
Alerts Generated
      │
      ▼
AI Triage Agent
      │
      ├── Analyzes risk signals
      ├── Correlates activities
      ├── Evaluates user context
      ├── Assigns priority
      ▼
Categorized Alerts
      │
      ▼
SOC Analyst
      │
      ▼
Security Copilot Investigation
      │
      ▼
Response and Remediation
```

### Requirements to Use the Triage Agent

* Required Purview roles: **Insider Risk Administrator**, **Insider Risk Analyst**, **Security Copilot Contributor**.
* Requires Microsoft Purview Insider Risk Management, Security Compute Units (SCUs), and the Purview plugin enabled in Security Copilot.
* The agent runs under the security context of the user who last saved the configuration; that authorization must be renewed every 90 days.
* Supports both scheduled automatic execution and manual execution.
* Only **active** Insider Risk policies are triaged; **Simulation mode policies are excluded**.

### Analyst Process

1. Open **Insider Risk Management → Alerts**.
2. Open **Alert Triage Agent**.
3. Review **Needs Attention** alerts first.
4. Open **Agent Summary**.
5. Generate an AI summary using **Summarize**.
6. Review the evidence.
7. Escalate or assign ownership.
8. Apply Adaptive Protection if warranted.

### Memory Trick: P → T → C → I → R

| Letter | Meaning |
|---|---|
| P | Purview detects insider risk and generates alerts |
| T | Triage Agent prioritizes and categorizes alerts using AI |
| C | Copilot explains the alert, summarizes findings, and correlates evidence |
| I | Investigator (SOC analyst) validates the evidence |
| R | Respond by escalating, assigning ownership, or applying protection controls |

> **Exam tip:** Remembering **P → T → C → I → R** answers most scenario based questions about who or what does each part of the Insider Risk investigation flow.

### SC 200 Exam Tips

* Know the three category names exactly: Needs Attention, Less Urgent, Not Categorized.
* Know the three required roles for the Triage Agent and the 90 day reauthorization requirement.
* Simulation mode policies never get triaged by the agent.
* Security Copilot's job is to explain, summarize, correlate, and recommend; the SOC analyst always makes the final call.

## 5. The All Risk Factors Tab

### Purpose

An alert usually reflects **one** suspicious activity. The **All Risk Factors** tab shows the user's **broader** risk context, including signals that did not directly trigger the alert but are still relevant, such as prior uploads, external sharing, access from unmanaged devices, sensitive file access, or unusual browsing.

It helps answer: why does this alert matter, what else has this user done, is this isolated or part of a pattern, and should the investigation continue?

### Investigation Workflow

```text
User Activity
      │
      ▼
Insider Risk Policy
      │
      ▼
Alert Generated
      │
      ▼
Open Alert
      │
      ▼
All Risk Factors Tab
      │
      ├── View additional risk signals
      ├── Analyze user behavior
      ├── Review sensitive content
      ├── Identify behavior patterns
      ▼
SOC Analyst Decision
      │
      ▼
Investigate, Dismiss, or Escalate
```

### Key Panels on This Tab

| Panel | What It Shows |
|---|---|
| Top Exfiltration Activities | The user's primary data movement methods |
| Cumulative Exfiltration | Repeated activity that increases risk over time |
| Sequences of Activities | Related actions correlated into a recognizable pattern |
| Priority Content | Interaction with sensitive or business critical files |
| Unallowed Domains | Transfers to prohibited destinations |
| Unusual Behavior / High Impact User Status | Additional context on elevated user risk |
| Content Detected | File name, file type, file location, and applied sensitivity label for specific items involved |

> **Exam tip:** From **Content Detected**, analysts can jump straight into **Activity Explorer** for a detailed timeline, related activities, and file history. This is the natural bridge between the two tabs.

### SC 200 Exam Tips

* Always distinguish between the single **alert trigger** and the **additional risk factors** shown on this tab; exam scenarios frequently test this distinction.
* Risk factor summaries do **not always match** the activity that originally triggered the alert.
* Activity sequences may include **excluded events** if they help explain broader risky behavior.
* Review the Alert Summary and the All Risk Factors tab **together** before deciding.

## 6. The Activity Explorer Tab

### Purpose

Activity Explorer validates the complete sequence of user actions rather than relying only on the alert summary. Each row is a single scored activity event, shown in chronological order, which may include: the activity that directly caused the alert, other scored activity by the same user, and activity that adds investigation context.

### Relationship to Other Tabs

| Tab | Answers |
|---|---|
| Alert Summary | Why was the alert generated? |
| All Risk Factors | What additional risk indicators raise this user's overall risk? |
| Activity Explorer | What actually happened, in order, with full metadata? |

### SC 200 Exam Tips

* Review activity details: date and time, activity type, file name, file location, sensitivity label, risk score, and related risk factors.
* Selecting an activity opens **Activity Details**, showing event metadata, the assigned risk score, and contributing risk indicators.
* Use **Activity Scope** to switch between all scored activity for the user and activity tied only to the current alert.
* Filter by **Risk Factor** or **Review Status** to cut investigation noise; customize columns, sort by date or risk score, and save views.
* Excluded events get a risk score of **0**, are marked **Excluded**, and can still appear in sequences if useful for context.
* Activity counts may differ from raw logs because of cumulative exfiltration detection, policy changes, and excluded items included in sequences.
* Use **Export** to collect evidence; use **Save this view** to reuse filters and layouts on future investigations.

## 7. The User Activity Tab

### Purpose

Where Activity Explorer focuses on individual events, the **User Activity** tab is a high level visual timeline built to reveal long term behavioral patterns: is risky behavior continuing, increasing, or decreasing; are multiple alerts related; and what is this user's overall risk profile (not just one alert)?

### Reading the Timeline

* Each activity is a **colored bubble** on a scatter chart.
* X axis: when the activity happened.
* Y axis: the assigned risk score (higher position means higher risk).
* **Risk sequences:** related events are joined by connecting lines, showing they belong to a single behavioral sequence, for example reading a confidential document, downloading it, compressing it, and uploading the archive to cloud storage.

> **Exam tip:** Selecting a bubble shows the event date, risk category, risk score, and associated files or emails. Selecting a **sequence** (the connecting lines) shows the sequence name, date range, combined risk score, total events, and associated content.

### Risk Categories

Access, Collection, Deletion, Exfiltration, Infiltration, Obfuscation, Security, Defense Evasion, Privilege Escalation, Communication Risk, User Compromise Risk, AI Usage, and Custom Indicators.

### Filters and Options

Filter by Risk Category, Activity Type, Date Range, Sort By, and Review Status. Timeline windows available: **1 month, 3 months, 6 months**.

### Relationship to Other Tabs (Full Picture)

| Tab | Focus |
|---|---|
| Alert Summary | Why the alert was generated |
| All Risk Factors | Extra indicators that raise overall risk |
| Activity Explorer | Detailed metadata for each individual activity |
| User Activity | Long term behavior, recurring patterns, and links across multiple alerts |

Typical analyst sequence: review the alert, examine additional risk factors, investigate detailed events in Activity Explorer, then use User Activity to judge whether the behavior is isolated or part of an ongoing pattern.

### SC 200 Exam Tips

* Know the axis meanings cold: X axis is time, Y axis is risk score.
* Connecting lines between bubbles indicate a **risk sequence**, not just proximity in time.
* Memorize the twelve risk categories at a high level; exam questions may ask you to classify an activity into one.
* User Activity can surface **cumulative exfiltration trends** and sequences containing excluded file types when they matter to the overall pattern.

## 8. Insider Risk Alerts in Microsoft Defender XDR

### Why Integrate

Purview Insider Risk Management specializes in detecting risky user behavior. Microsoft Defender XDR specializes in correlating security signals across Microsoft security products. Integrating them means Insider Risk alerts appear inside Defender XDR, can be grouped into larger incidents, and can be investigated alongside endpoint, identity, email, cloud, and DLP data from a single portal, improving visibility and cutting investigation time.

### Prerequisite

Enable **Share user risk details with other security solutions** under **Purview → Settings → Insider Risk Management → Data sharing**. Without this, nothing synchronizes to Defender XDR.

### Viewing Insider Risk Incidents in Defender XDR

```text
Microsoft Defender portal
      │
      ▼
Investigation & response
      │
      ▼
Incidents & alerts
      │
      ▼
Incidents
      │
      ▼
Filter Service source
      │
      ▼
Select Microsoft Purview Insider Risk Management
      │
      ▼
Only Insider Risk incidents are displayed
```

### Required Roles

| Portal | Roles |
|---|---|
| Microsoft Defender XDR | Security Operator or Security Reader |
| Microsoft Purview | Insider Risk Management, Insider Risk Management Analyst, or Insider Risk Management Investigator |

### Status and Classification Synchronization

Synchronization between Defender XDR and Purview typically completes within **30 minutes**.

| Defender XDR Status | Purview Status |
|---|---|
| New / In Progress | Needs review |
| Resolved | Dismissed or Confirmed |

| Defender XDR Classification | Purview Status |
|---|---|
| True Positive | Confirmed |
| Information / Expected Activity | Dismissed |
| False Positive | Dismissed |

### What Does Not Appear in Defender XDR

Microsoft Defender XDR does **not** include every Insider Risk event. Missing items include: custom detections, risky AI usage events, events from apps that are not Microsoft apps, email exfiltration events, events that occurred before the alert was generated, and policy excluded events.

### Advanced Hunting Tables to Memorize

| Table | Contains |
|---|---|
| AlertInfo | Core alert metadata |
| AlertEvidence | Entities and evidence tied to an alert |
| DataSecurityBehaviors | Behavioral signals related to data security |
| DataSecurityEvents | Underlying data security events |

### Real World Scenario

A departing employee downloads confidential engineering documents from SharePoint and uploads them to a personal cloud storage account. Purview generates an Insider Risk alert for potential exfiltration. Because sharing is enabled, the alert is shared to Defender XDR, where it is grouped into a single incident together with a Defender for Endpoint alert (USB device connected), a Defender for Identity alert (unusual sign in location), and a Purview DLP alert (sensitive documents copied). The analyst reviews one correlated incident instead of three separate systems, confirms the Insider Risk alert as **True Positive** (which synchronizes back to Purview as **Confirmed**), then uses **Advanced Hunting** to search for additional uploaded ZIP files before escalating to incident response.

### SC 200 Exam Tips

* Insider Risk alerts can show up as individual alerts, part of a unified incident, or linked to other Microsoft security signals.
* Memorize both mapping tables (status and classification); these are classic exam facts.
* Know the exact navigation path: Investigation & response → Incidents & alerts → Incidents → filter by Service source.
* Know the four Advanced Hunting tables by name.
* Know what is deliberately excluded from Defender XDR so you are not caught assuming full parity between the two portals.

## 9. Managing and Resolving Insider Risk Cases

### What Is a Case

An Insider Risk **case** is an investigation container that focuses on **one user** and can pull together **multiple related alerts**, evidence, notes, and investigation activity into a single place. Unlike an alert, which flags one suspicious activity, a case consolidates everything relevant and stays open until investigators finish and resolve it.

### When to Create One

Not every alert needs a case.

| Alert Outcome | When |
|---|---|
| Dismiss | It is a false positive, or no further investigation is required |
| Confirm | A policy violation occurred, or further investigation is needed; creating a case is then optional |

Creating a case is recommended when the risk is serious, multiple related incidents exist, multiple teams need to collaborate, or long term tracking is required.

### Case Investigation Tabs

| Tab | Purpose |
|---|---|
| Case Overview | Overall summary and the user's risk score |
| Alerts | Alerts included in the case |
| User Activity | High level risk timeline |
| Activity Explorer | Detailed event metadata |
| Forensic Evidence | Screenshots captured during the activity |
| Content Explorer | Affected files and emails |
| Case Notes | Investigation log and findings |
| Contributors | Collaborators on the case |

> **Exam tip:** Sending an email notice does **not** close a case. A case is only closed by formally resolving it.

### Escalation and Automation

* Escalate to **Microsoft Purview eDiscovery (Premium)** for legal or HR investigations.
* Use **Power Automate** to trigger workflows such as ServiceNow ticket creation or manager notification.
* If enabled, **Microsoft Teams** integration automatically creates a collaboration team for new cases.

### Resolving a Case

Every case is resolved as either **Benign** or **Confirmed Policy Violation**, with a documented reason, after which its status changes to **Closed**.

### Real World Scenario

A finance employee downloads confidential payroll spreadsheets, copies them to a USB drive, and uploads them to a personal cloud storage service, generating several alerts. The analyst confirms the alerts (rather than dismissing them) and creates a case, grouping all related alerts for that user. Within the case the analyst reviews Case Overview for the overall risk score, Alerts for each policy match, User Activity for the sequence of risky actions, Activity Explorer for detailed metadata, Forensic Evidence for screenshots, and Content Explorer for the payroll files themselves, documenting findings in Case Notes throughout. Because the matter may require legal review, the analyst escalates to eDiscovery (Premium) and auto creates a ServiceNow ticket via Power Automate. After HR confirms intentional exfiltration, the analyst resolves the case as **Confirmed Policy Violation**, records the justification, and closes it.

### SC 200 Exam Tips

* A case is centered on **one user** but can hold **multiple alerts**.
* Confirming an alert can pull in all of that user's currently active alerts.
* Know all eight case tabs and what each one is for; expect "which tab would you use" style questions.
* Know the two and only two case resolution outcomes: Benign and Confirmed Policy Violation.

## 10. SC 200 Last Minute Revision

### One Page Cheat Sheet

**Alert generation:** Settings → Policy → Trigger → Score → Alert. A trigger alone never creates an alert; the score must cross the policy threshold.

**Raise alert volume:** more indicators, more users and groups, lower trigger thresholds, lower indicator thresholds, Alert Volume slider (Settings → Intelligent detections) toward More alerts.

**Lower alert volume:** Analytics, Real-Time Insights, narrower scope, Inline Alert Customization, bulk dismissal, Global Exclusions, Detection Groups, Indicator Variants.

**Alert actions:** dismiss, confirm (optionally create a case), assign, continue monitoring. Bulk dismiss up to 400 low priority alerts at once.

**Triage Agent categories:** Needs Attention (highest, review first), Less Urgent, Not Categorized (agent could not evaluate, e.g. unsupported policy type or Simulation mode).

**Triage Agent roles:** Insider Risk Administrator, Insider Risk Analyst, Security Copilot Contributor. Authorization renews every 90 days.

**Memory trick:** P (Purview detects) → T (Triage Agent prioritizes) → C (Copilot explains) → I (Investigator validates) → R (Respond).

**Investigation tabs, one line each:**

| Tab | One Line Summary |
|---|---|
| Alert Summary | Why this alert exists |
| All Risk Factors | The user's broader risk picture beyond the trigger |
| Activity Explorer | Chronological, detailed event log |
| User Activity | Long term pattern and trend timeline (bubbles = events, lines = sequences) |

**Defender XDR sync:** completes within 30 minutes. New/In Progress → Needs review; Resolved → Dismissed or Confirmed. True Positive → Confirmed; Information/Expected Activity or False Positive → Dismissed.

**Defender XDR does NOT show:** custom detections, risky AI usage events, non Microsoft app events, email exfiltration events, pre alert events, policy excluded events.

**Advanced Hunting tables:** AlertInfo, AlertEvidence, DataSecurityBehaviors, DataSecurityEvents.

**Enable sync first:** Purview → Settings → Insider Risk Management → Data sharing → Share user risk details with other security solutions.

**Cases:** one user, many alerts. Resolve as Benign or Confirmed Policy Violation only. Email notice never closes a case. Up to 100 active cases per organization; needs review alerts expire after 120 days unless linked to a case; active cases are retained indefinitely.

**Case tabs:** Case Overview, Alerts, User Activity, Activity Explorer, Forensic Evidence, Content Explorer, Case Notes, Contributors.

### Frequently Confused Concepts

| Concept A | Concept B | The Distinction |
|---|---|---|
| Alert | Case | An alert flags one suspicious activity; a case is a container for one user that can hold many alerts |
| Activity Explorer | User Activity tab | Explorer shows individual event metadata; User Activity shows long term trend and pattern across events |
| All Risk Factors | Alert Summary | Summary explains the trigger only; All Risk Factors shows the wider risk context |
| Dismiss | Confirm | Dismiss closes out a false positive; Confirm indicates a violation and optionally opens a case |
| Trigger threshold | Indicator threshold | Trigger threshold decides when monitoring starts; indicator threshold decides how much activity is needed before an alert fires |
| Alert (Insider Risk) | Incident (Defender XDR) | An alert is the single Purview detection; an incident is the Defender XDR grouping that can combine it with signals from other products |

### Quick KQL Reminder for Advanced Hunting

No KQL syntax was present in the source material for this module, but the exam expects you to be comfortable querying the four Insider Risk related Advanced Hunting tables. A typical pattern for pulling recent Insider Risk alert evidence looks like this:

```kql
AlertInfo
| where ServiceSource == "Microsoft Purview Insider Risk Management"
| join kind=inner AlertEvidence on AlertId
| project Timestamp, Title, Severity, EntityType, FileName, AccountName
| order by Timestamp desc
```

> **Exam tip:** You do not need to memorize this exact query, but you should recognize `AlertInfo` and `AlertEvidence` as the tables to `join` on `AlertId` when correlating an alert to its supporting evidence.

### Final Word

Think of the whole workflow as one continuous pipeline: **Purview generates → Triage Agent prioritizes → Copilot explains → Analyst investigates across four tabs → Defender XDR correlates → Case captures and resolves.** Most SC 200 scenario questions are really just asking you to identify where in this pipeline a given action belongs.
