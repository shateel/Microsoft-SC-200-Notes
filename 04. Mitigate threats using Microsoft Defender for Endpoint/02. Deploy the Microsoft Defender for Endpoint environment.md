## Overview and Deployment Foundations

Microsoft Defender for Endpoint is a **cloud service**. Before any device can send telemetry, the organization must first configure the Defender tenant. This one time setup determines:

* Where security data is stored
* How long data is retained
* Whether preview features are enabled
* How endpoint sensors communicate with the cloud

> **Exam framing:** these settings are configured **once**, during initial deployment, and they become the foundation for everything else you do with onboarded devices. If a question describes "the very first thing" an admin must do, the answer is almost always tenant configuration, not device onboarding.

## Required Permissions

| Role | Can Configure Defender Settings? | Recommended Use |
|---|---|---|
| **Security Administrator** | Yes | Standard role for configuring Defender for Endpoint |
| **Global Administrator** | Yes (unrestricted) | Emergency use only |
| **Reader** | No (read only) | Monitoring without changes |

Microsoft recommends the **principle of least privilege**: administrators should receive only the permissions necessary to do their job. Global Administrator is technically capable of performing every configuration task, but Microsoft recommends reserving it for emergencies because it carries unrestricted privileges across the tenant.

### SC 200 Exam Tips

* Only **Security Administrator** should routinely configure Defender for Endpoint settings.
* **Global Administrator** works, but is reserved for emergencies due to unrestricted access.
* Least privilege is a recurring exam theme across permissions, RBAC roles, and Device Groups.

## Initial Configuration Settings

### 1. Data Storage Location

The organization chooses the geographic region where Microsoft stores Defender for Endpoint data.

| Region | Notes |
|---|---|
| United States (US) | |
| European Union (EU) | |
| United Kingdom (UK) | |

> **Critical exam point:** the storage location is chosen once, during initial setup, and it **cannot be changed later**. Microsoft does not migrate the organization's data to a different region afterward. Choose carefully, this affects data residency and compliance obligations.

### 2. Data Retention

Telemetry is stored for a default period of **6 months**. During this window, SOC analysts can investigate historical activity using:

* Device Timeline
* Advanced Hunting
* Incident Investigation

Organizations with higher license tiers may unlock extended retention options.

### 3. Preview Features

Preview features give early access to capabilities still under development.

* Enabled by default
* Can be disabled or changed later (unlike the storage region)
* Commonly enabled in test or pilot environments before wider production rollout

### SC 200 Exam Tips

* Configure the environment in **Microsoft Defender portal → Settings → Endpoints**.
* Storage region: US, EU, or UK; chosen once; permanent.
* Default retention: **6 months**.
* Preview features: **on by default**, changeable later.

## Network Configuration (WinHTTP)

Once the tenant is configured, endpoint devices must reach the Defender for Endpoint cloud securely. The embedded sensor uses **Microsoft Windows HTTP Services (WinHTTP)**, not the browser networking stack, to talk to the cloud.

| Fact | Detail |
|---|---|
| Sensor account | Runs under the **LocalSystem** account |
| Protocol used | **WinHTTP** |
| Protocol NOT used | WinINet (this is what browsers use) |
| Proxy relationship | WinHTTP settings are **independent** of browser proxy settings |

> **Common exam trap:** configuring a browser proxy does **not** automatically configure connectivity for Defender for Endpoint, because WinHTTP maintains its own, separate proxy configuration. Supported proxy discovery methods include **Transparent Proxy** and **WPAD (Web Proxy Auto Discovery Protocol)**.

### SC 200 Exam Tips

* Sensor communicates using **WinHTTP**, under **LocalSystem**.
* Browser proxy configuration is irrelevant to sensor connectivity.
* Know the two supported proxy discovery methods: Transparent Proxy and WPAD.
* Always verify network connectivity **before** onboarding devices.

## Deployment Workflow

The overall sequence, from tenant configuration through ongoing operations, is:

```text
Configure the Defender for Endpoint environment
        │
        ▼
Choose the data storage region
        │
        ▼

        │
        ▼
Verify network connectivity (WinHTTP / proxy)
        │
        ▼

        │
        ▼

        │
        ▼

```

### SC 200 Exam Tips

* Memorize this order. Exam scenarios often present steps out of order and ask which one comes first or is missing.
* Environment configuration and network verification always happen **before** onboarding.

## Operating System Compatibility

Microsoft Defender for Endpoint supports:

* Windows
* macOS
* Linux
* Android
* iOS

### SC 200 Exam Tips

* Defender for Endpoint is cross platform; it is not limited to Windows.
* Onboarding methods differ by platform (for example, Windows uses onboarding scripts, Group Policy, Intune, or Configuration Manager, while mobile platforms typically onboard through Intune app protection or MDM enrollment). Know that a method appropriate for Windows is not automatically valid for macOS, Linux, Android, or iOS.

## Role Based Access Control (RBAC) Fundamentals

### What Is RBAC?

**Role Based Access Control (RBAC)** is a security model that assigns permissions based on a user's **role**, rather than granting permissions to each person individually.

| Example Role | Typical Capability |
|---|---|
| Tier 1 SOC Analyst | View alerts and investigate incidents |
| Tier 2 SOC Analyst | Investigate incidents and isolate devices |
| Security Administrator | Full Defender management |

### Why Use RBAC?

RBAC helps organizations:

* Limit user permissions
* Protect sensitive security settings
* Separate administrative responsibilities
* Reduce accidental or malicious changes
* Support large SOC teams with different responsibilities

As with tenant permissions, Microsoft recommends the **least privilege principle** here too: grant users only the minimum access required, and reserve Global Administrator for emergencies.

### What Does RBAC Control?

RBAC governs two distinct things. Keeping these separate is one of the most exam relevant distinctions in this module.

| Controls | Mechanism | Examples |
|---|---|---|
| **What a user can do** | Custom Roles / Permissions | View alerts, manage alerts, run antivirus scans, isolate devices, collect investigation packages, run Live Response, configure policies, manage indicators, manage onboarding, manage settings |
| **Which devices a user can see** | Device Groups (Machine Groups) | Windows Team → only Windows devices; Finance Devices → only finance computers; Production Servers → only production servers; Europe Region → only European devices |

> **Memorize this pairing:** RBAC roles define **actions**. Device Groups define **scope (which devices)**. A user needs both a role with the right permissions and access to the relevant Device Group to fully investigate a device.

### SC 200 Exam Tips

* RBAC = Role Based Access Control.
* RBAC controls two things: allowed actions, and which devices are visible.
* Roles are assigned to **Microsoft Entra user groups**, never directly to individual users.
* Sequence to remember: Create Role → Assign Permissions → Create Device Group → Assign Role to Entra Group → Add Users.
* Before RBAC is explicitly configured, default access looks like this:

| Built in Role | Access Level |
|---|---|
| Security Administrator | Full access |
| Global Administrator | Full access |
| Reader | Read only access |

* **Unified RBAC (URBAC)** is the newer, consolidated permission model that applies automatically to **new** Defender for Endpoint customers starting **February 16, 2025**. It unifies role management across the Defender portal instead of using the legacy, endpoint only RBAC model. Expect exam questions to test whether you know URBAC is the current direction Microsoft is moving toward.

## Microsoft Entra ID and Its Relationship to Defender for Endpoint

**Microsoft Entra ID** (formerly **Azure Active Directory / Azure AD**) is Microsoft's Identity and Access Management (IAM) service, delivered from the cloud. It authenticates users and controls access to applications, devices, and cloud resources. Entra ID manages:

* Users
* Groups
* Devices
* Applications
* Authentication and authorization
* Single Sign On (SSO)
* Multi Factor Authentication (MFA)
* Conditional Access

### Why This Matters for SC 200

Defender for Endpoint does not assign roles to individual named users. Instead, it assigns Defender roles to **Entra groups**, and any user placed into that group inherits the associated Defender permissions automatically.

Worked example: a company has three analysts, Alice, Bob, and John. An administrator creates an Entra group called "SOC Analysts" and adds all three to it. The administrator then creates a Defender RBAC role called "Tier 1 Analyst" and assigns that role to the "SOC Analysts" Entra group.

```text
SOC Analysts (Microsoft Entra Group)
        │
        ▼
Tier 1 Defender Role (RBAC assignment)
        │
        ▼
Microsoft Defender Portal access
```

All members of the Entra group automatically receive the Defender permissions tied to that role. Add a person to the group, and they gain access; remove them, and access is revoked, without touching Defender configuration directly.

### SC 200 Exam Tips

* Entra ID is the identity backbone that RBAC role assignments depend on.
* Defender roles attach to **Entra groups**, not to individuals.
* Changing group membership in Entra ID is the standard way to grant or revoke Defender access at scale.

## Creating and Managing RBAC Roles

After RBAC is enabled, administrators create **custom roles** that define what actions a user can perform in the Defender portal, instead of giving every analyst identical, broad permissions.

| Example Role | Responsibilities |
|---|---|
| Tier 1 SOC Analyst | View alerts, investigate incidents |
| Tier 2 SOC Analyst | View alerts, isolate devices, start automated investigations |
| Security Administrator | Configure Defender settings, manage onboarding, create RBAC roles |

### Permission Categories

| Category | What It Covers |
|---|---|
| View Data | Read only visibility into alerts and device data |
| Active Remediation Actions | Approve or dismiss remediation, manage automation, submit remediation requests |
| Threat and Vulnerability Management | Vulnerability and exposure related capabilities |
| Alerts Investigation | Manage alerts, start automated investigations, run scans, collect investigation packages |
| Manage Security Settings | Onboard/offboard devices, configure alert suppression |
| Manage Endpoint Security Settings (Intune) | Integrates with Microsoft Intune for endpoint security and compliance management |
| Live Response Capabilities | See the Live Response comparison below |

### Live Response Permission Levels

| Level | Capability |
|---|---|
| Live Response Basic | Start sessions, run read only commands |
| Live Response Advanced | Download/upload files, remotely execute scripts |

### SC 200 Exam Tips

* Create roles in **Microsoft Defender Portal → Settings → Endpoints → Permissions → Roles**.
* RBAC must be **enabled** before you can create custom roles.
* Only **Security Administrator** creates and manages RBAC roles.
* Creating a role alone does **not** grant device access, you must also create and assign a Device Group.
* Full sequence to remember: Create Role → Assign Permissions → Assign Entra Group → Create Device Group → Assign Role to Device Group.
* Know the difference between Live Response Basic (read only) and Live Response Advanced (can execute and transfer files).

## Device Groups

A **Device Group** (sometimes called a **Machine Group**) is a logical collection of devices sharing common characteristics, such as device name, domain, operating system, or tags. Device Groups are used primarily alongside RBAC to control **which devices** a user can see and act on, and they also let organizations apply different automated remediation behavior to different sets of machines.

### Why Use Device Groups?

* Limit access to alerts and device data for specific Entra user groups
* Control which analysts can investigate which devices
* Apply different Automated Investigation and Remediation (AIR) settings per group
* Assign different remediation levels during automated investigations
* Filter investigation results by device group

### Automated Remediation Levels (AIR)

Each Device Group carries its own **Automated Investigation and Remediation (AIR)** configuration, letting the organization tune how aggressively Defender responds automatically.

| Device Group Example | AIR Behavior |
|---|---|
| Finance Devices | Full automation |
| Production Servers | Semi automated, requires analyst approval |
| Domain Controllers | No automatic remediation |

> **Why this matters:** high value or fragile systems (domain controllers, production servers) are typically set to require human approval or no automation at all, reducing the risk that an automated action disrupts a critical system.

### SC 200 Exam Tips

* Device Groups can be built from device name, domain, operating system, or tags.
* A device that matches multiple groups is assigned only to the **highest ranked** Device Group; ranking resolves conflicts.
* Preview matching devices **before** saving a Device Group to confirm the rule is correct.
* Only **Entra user groups already assigned to an RBAC role** can be granted access to a Device Group.
* Creating a Device Group alone does **not** grant access, an Entra group with an RBAC role must still be assigned to it.
* Core relationship to memorize:

| Concept | Controls |
|---|---|
| RBAC | User permissions (what actions) |
| Device Groups | Device visibility (which machines) |

* For SC 200, Device Groups are a key mechanism for enforcing the **principle of least privilege** at the device level.

## Advanced Features

Found in **Settings → Endpoints → Advanced features**, these toggles extend detection, automated response, endpoint protection, and integration with the wider Microsoft security ecosystem.

| Feature | What It Does |
|---|---|
| Automated Investigation | Enables Automated Investigation and Remediation (AIR); other AIR dependent features build on this |
| Live Response | Requires Automated Investigation to be enabled first |
| Live Response for Servers | Extends Live Response to Windows Servers |
| Unsigned Script Execution | Allows unsigned PowerShell scripts during Live Response; restrict to trusted responders |
| Always Remediate PUA | Automatically removes Potentially Unwanted Applications tenant wide |
| Restrict Correlation to Scoped Device Groups | Limits incident correlation to an analyst's assigned Device Groups |
| EDR in Block Mode | Protects devices even when Defender Antivirus runs in Passive Mode |
| Auto resolve Remediated Alerts | Automatically closes alerts after successful remediation or when no threat is found |
| Allow or Block File | Uses indicators to explicitly allow or block specific files |
| Custom Network Indicators | Create allow/block rules for IP addresses, domains, and URLs |
| Tamper Protection | Prevents malware or users from disabling Defender Antivirus or changing critical security settings |
| Show User Details | Displays Entra ID user information during investigations |
| Microsoft Defender for Identity Integration | Enriches endpoint investigations with identity signals |
| Office 365 Threat Intelligence Connection | Combines Defender for Office 365 and Defender XDR investigations |
| Microsoft Defender for Cloud Apps Integration | Forwards endpoint signals to Defender for Cloud Apps |
| Web Content Filtering | Blocks unwanted website categories; requires Network Protection in Block Mode |
| Share Endpoint Alerts with Microsoft Purview | Supports Insider Risk Management and compliance investigations |
| Microsoft Intune Connection | Enables risk based Conditional Access using Defender device risk |
| Device Discovery | Identifies unmanaged devices on the corporate network |
| Preview Features | Test upcoming Defender capabilities before general availability |

This diagram shows the dependency chain the exam likes to test:

```text
Automated Investigation (must be enabled first)
        │
        ▼
Live Response
        │
        ▼
Live Response for Servers
```

### SC 200 Exam Tips

* Advanced Features live in **Settings → Endpoints → Advanced features**.
* Remember the dependency: Automated Investigation → Live Response → Live Response for Servers.
* Web Content Filtering depends on **Network Protection in Block Mode**.
* EDR in Block Mode is a safety net that still works even if antivirus is in Passive Mode.
* Tamper Protection defends the Defender configuration itself, not just endpoints in general.

### Frequently Confused Concepts

| Concept A | Concept B | Key Difference |
|---|---|---|
| RBAC | Device Groups | RBAC = permitted actions. Device Groups = visible devices. Both are needed for full, scoped access. |
| Security Administrator | Global Administrator | Security Administrator is the day to day recommended role. Global Administrator is technically capable but reserved for emergencies. |
| WinHTTP | WinINet | WinHTTP is used by the Defender sensor and has its own proxy configuration. WinINet is used by browsers and is unrelated to sensor connectivity. |
| Live Response Basic | Live Response Advanced | Basic is read only. Advanced allows file transfer and script execution. |
| Preview Features (tenant setting) | Preview Features (Advanced feature toggle) | Both refer to early access capabilities, but they appear as separate configuration points, one during initial setup and one under Advanced features. |
| Data storage region | Data retention period | Storage region is permanent once set. Retention period can extend with higher licensing. |
