## 1. Overview and Big Picture

Microsoft Defender for Endpoint (MDE) is the endpoint protection and EDR workload inside Microsoft Defender XDR. For the SC-200 exam you must be comfortable moving through three connected activities on a single device:

* Spotting a risky device in the **Device Inventory**.
* Opening the **Device Page** to investigate alerts, timeline, and vulnerabilities.
* Using **Response Actions** to contain and remediate the threat.

> Exam focus: SC-200 tests whether you know **where** to look, **what each screen shows**, and **which response action fits a given scenario**. It rarely asks for exact click paths, but it frequently gives a scenario and asks you to choose the correct action or interpret a status field.

### How Device Investigation Fits Into the Wider Ecosystem

```text
Microsoft Defender for Endpoint
   (device telemetry, alerts, response actions)
              │
              ▼
Microsoft Defender XDR
   (correlates alerts across identity, email, apps, and endpoint into incidents)
              │
              ▼
Microsoft Sentinel
   (SIEM and SOAR; ingests Defender XDR incidents through the Microsoft Defender XDR connector)
```

This relationship matters for the exam because incidents raised in Microsoft Defender for Endpoint automatically surface inside Microsoft Defender XDR, and can then flow into Microsoft Sentinel for correlation with other data sources, automation, and long term retention.

## 3. Device Inventory

The **Device Inventory** page is a centralized list of every device that has reported to Microsoft Defender for Endpoint. It is usually the **starting point** for endpoint investigations because it gives quick visibility into device security status and operational health.

### Fields Shown for Each Device

* Device name
* Domain
* Risk level
* Exposure level
* Operating system platform
* Health state
* Last seen timestamp

### Risk Level vs Exposure Level vs Health State

| Field | What It Measures | Analyst Use |
|---|---|---|
| Risk Level | Current security risk based on active alerts and detected threats | Tells you if the device may already be compromised |
| Exposure Level | How vulnerable a device is due to missing recommendations or weak configuration | Tells you if the device is an easy future target |
| Health State | Whether the device is communicating properly with Microsoft Defender for Endpoint | Tells you if telemetry can be trusted; not a threat indicator by itself |

> Exam tip: A device can be **Low Risk but High Exposure** (poorly secured, not yet attacked) or **High Risk but Low Exposure** (currently under attack despite generally good security). Do not assume the two values move together.

> Exam tip: If a device stops reporting telemetry, check its **Health State** first before concluding there are no threats. A silent device is not necessarily a safe device.

Antivirus status is another useful triage indicator. A status of Disabled, Not Reporting, or Not Updated raises the likelihood of a successful attack and should be investigated promptly.

Device Inventory is integrated with **Incidents**, **Alerts**, and the **Device Page**, letting analysts pivot directly into a detailed investigation from a single high risk entry.

### SC-200 Exam Tips

* Know the difference between Risk Level, Exposure Level, and Health State cold; scenario questions test this directly.
* Remember Device Inventory is the typical **entry point** for endpoint investigations.
* Antivirus status (Disabled, Not Reporting, Not Updated) is a red flag worth investigating.

## 4. Investigating a Device (The Device Page and Response Actions)

### Entry Points Into a Device Investigation

The same Device Page opens no matter which entry point you use.

```text
Devices List
Alerts Queue
Security Operations Dashboard
Individual Alert
File Details Page
IP Address Details Page
Domain Details Page
              │
              ▼
         Device Page
              │
              ▼
Device Details, Response Actions, Overview, Alerts, Timeline,
Security Recommendations, Software Inventory,
Discovered Vulnerabilities, Missing KBs
```

### Device Page Sections

| Section | Purpose |
|---|---|
| Device Details | Device name, domain, operating system, health status, and investigation package availability |
| Response Actions | Immediate remote actions against the device (see table below) |
| Overview | Active alerts, logged on user, and the device security assessment |
| Alerts | All alerts tied to the device, with severity, status, classification, and investigation state |
| Timeline | Chronological view of endpoint activity; supports search, filter by date, export, grouping, custom columns, and event flagging |
| Security Recommendations | Generated by Microsoft Defender Vulnerability Management |
| Software Inventory | Installed software and its associated risk |
| Discovered Vulnerabilities | Known weaknesses (CVEs) on the endpoint |
| Missing KBs | Missing Windows security updates that increase exposure |

> Exam tip: The **Timeline** tab is one of the most heavily tested tools. Know that flagging events builds a clean attack timeline, and that the **Event Details** pane lets you pivot straight into an **Advanced Hunting** query.

### Response Actions

| Response Action | What It Does | Typical Use Case |
|---|---|---|
| Manage Tags | Assigns labels such as Finance, HR, Critical Server, Domain Controller | Filtering, reporting, and scoping RBAC |
| Isolate Device | Disconnects the device from the network while keeping Defender communication alive | Stop malware spread and attacker communication, commonly used in ransomware incidents |
| Restrict App Execution | Allows only Microsoft signed processes and Defender components to run | Stop attacker tools and unauthorized applications while keeping the device reachable |
| Run Antivirus Scan | Triggers a remote Microsoft Defender Antivirus scan | Confirm or clean known malware |
| Collect Investigation Package | Gathers forensic artifacts: event logs, registry information, running processes, network configuration, system information | Formal incident response and forensic analysis |
| Initiate Live Response | Opens a remote interactive session to execute commands, collect files, and analyze processes | Deep manual investigation without physical access; requires appropriate RBAC permission |
| Initiate Automated Investigation | Starts Automated Investigation and Remediation (AIR) | Let Defender automatically investigate and remediate at scale |
| Ask Defender Experts | Escalates the device or alert to Microsoft's Defender Experts team | Complex or ambiguous incidents that need outside expertise |
| Action Center | Central hub that records pending and completed remediation actions | Review, approve, or undo response actions across devices |

> Exam tip: **Isolate Device** keeps Defender connectivity alive so you can still manage the endpoint remotely; it is not a full power off or full disconnect.

> Exam tip: **Restrict App Execution** vs **Isolate Device**: Restrict App Execution still allows network connectivity but blocks unapproved processes, while Isolate Device cuts general network access entirely except for the Defender channel.

### Real World SOC Scenario Walkthrough

A finance employee opens a phishing email with a malicious attachment. Microsoft Defender for Endpoint raises an alert for suspicious PowerShell execution.

```text
Phishing Email Received
              │
              ▼
Malicious Attachment Opened
              │
              ▼
Microsoft Word Launches PowerShell
              │
              ▼
PowerShell Attempts Malware Download
              │
              ▼
Suspicious Network Activity Detected
              │
              ▼
Alert Generated in Microsoft Defender for Endpoint
```

**Investigation steps taken by the analyst:**

* Opened the device from the Alerts Queue.
* Overview tab showed several high severity alerts and the logged on user.
* Alerts tab confirmed PowerShell execution followed by suspicious network activity.
* Timeline revealed Word launched PowerShell, which attempted to download malware.
* Flagged key events to build a clean attack timeline.
* Event Details pane enabled an Advanced Hunting query to check for similar activity on other devices.
* Security Recommendations showed PowerShell logging was not fully configured.
* Software Inventory identified an outdated, vulnerable PDF reader.
* Discovered Vulnerabilities confirmed several critical CVEs.
* Missing KBs showed the device lacked recent Windows security updates.

**Containment actions:**

```text
Isolate Device
              │
              ▼
Run Antivirus Scan
              │
              ▼
Collect Investigation Package
              │
              ▼
Initiate Live Response (deeper analysis)
              │
              ▼
Initiate Automated Investigation (AIR)
              │
              ▼
Threat Contained, Attack Timeline Documented
```

> Takeaway: This scenario is a template for SC-200 case style questions. It links Timeline evidence, Security Recommendations, Software Inventory, and Discovered Vulnerabilities to a concrete set of Response Actions. Practice reproducing this chain from memory.

### SC-200 Exam Tips

* Memorize all seven entry points into a device investigation.
* Know every Response Action and match it to the correct scenario; this is a favorite exam pattern.
* Remember that Security Recommendations come from **Microsoft Defender Vulnerability Management**, not from Defender for Endpoint directly.
* Live Response and Automated Investigation both require adequate RBAC permissions; do not assume every analyst role can use them.
* The Timeline plus Event Details plus Advanced Hunting pivot is the core workflow tested for deep endpoint investigation.

## 5. Behavioral Blocking

### What Is Behavioral Blocking?

Traditional antivirus mainly relies on known signatures. Modern attacks often evade that approach using:

* Fileless malware
* Polymorphic malware
* Living off the Land (LotL) techniques
* Human operated ransomware
* In memory attacks

Behavioral Blocking analyzes **how a process behaves** instead of what the file looks like. If behavior matches a known malicious technique, Microsoft Defender blocks the threat even if the specific file has never been seen before. Protection applies both **before** and **after** malware execution.

### Why It Matters

Behavioral Blocking helps by:

* Detecting previously unknown malware.
* Detecting fileless and in memory attacks.
* Stopping attacks already in progress.
* Preventing lateral spread.
* Automatically generating alerts for SOC analysts.

### Components

| Component | Role |
|---|---|
| Microsoft Defender Antivirus | Signature based and behavior based malware detection and blocking |
| Endpoint Detection and Response (EDR) | Collects security signals, raises alerts, and groups related alerts into incidents |
| Machine Learning (ML) and Artificial Intelligence (AI) | Identify malicious behavior patterns at scale |
| Cloud Protection | Rapid cloud based analysis and intelligence sharing |
| Microsoft Defender for Endpoint | Coordinates detection, prevention, and response across the above |

### Key Capabilities to Remember

* **Next-generation protection** analyzes process behavior to detect running threats. (Official Microsoft feature name, hyphen retained.)
* **Client Behavioral Blocking** automatically inspects, classifies, blocks, and remediates malicious artifacts directly on the endpoint.
* **Feedback-loop blocking** (also called rapid protection) shares intelligence through Microsoft's cloud so other devices worldwide get protected quickly after one detection. (Official Microsoft feature name, hyphen retained.)
* **EDR in block mode** blocks and remediates malicious artifacts even after a breach has started, and integrates with Microsoft Defender Vulnerability Management.
* Detection engines operate both before execution and after execution, providing layered protection.

> Exam tip: Behavior based detections are named according to the **MITRE ATT&CK Enterprise Matrix**. Know the tactic order, since exam scenarios often ask you to map an observed behavior to a tactic.

### MITRE ATT&CK Enterprise Matrix Tactics (Order to Memorize)

```text
Initial Access
Execution
Persistence
Privilege Escalation
Defense Evasion
Credential Access
Discovery
Lateral Movement
Collection
Command and Control
Exfiltration
Impact
```

### Alert to Incident Workflow

```text
Malicious Behavior Detected
              │
              ▼
Alert Generated
              │
              ▼
Related Alerts Grouped Together
              │
              ▼
Incident Created in Microsoft Defender Portal
              │
              ▼
Completed Remediation Actions Logged in Action Center
```

### SC-200 Exam Tips

* Behavioral Blocking detects threats by behavior, not only by signature.
* It defends against fileless malware, polymorphic malware, in memory attacks, Living off the Land techniques, and human operated ransomware.
* Know the five listed components: Defender Antivirus, EDR, ML, AI, Cloud Protection, working together under Microsoft Defender for Endpoint.
* Distinguish **Next-generation protection** (behavior analysis of running processes) from **Client Behavioral Blocking** (local inspection, classification, and remediation) from **Feedback-loop blocking** (rapid cloud wide intelligence sharing) from **EDR in block mode** (post breach block and remediate).
* Memorize the twelve MITRE ATT&CK Enterprise Matrix tactics in order; this list reappears throughout SC-200.

## 6. Device Discovery

### What Is Device Discovery?

**Device Discovery** is a Microsoft Defender for Endpoint capability that automatically finds **unmanaged devices** connected to the corporate network. Instead of deploying separate scanning appliances, Defender uses **already onboarded endpoints as discovery sensors**. This improves visibility into unknown assets, reduces attack surface, and helps organizations onboard unmanaged devices.

```text
Onboarded Endpoints Act as Discovery Sensors
              │
              ▼
Observe Traffic and, in Standard mode, Probe the Network
              │
              ▼
Unmanaged Devices Identified
              │
              ▼
Devices Appear in Device Inventory
              │
              ▼
Microsoft Defender Vulnerability Management Assesses the Devices
              │
              ▼
Onboarding Recommended for Supported Devices
```

### Device Discovery Modes

| Aspect | Basic Discovery | Standard Discovery (Recommended) |
|---|---|---|
| Method | Passive only | Passive plus active |
| Additional network traffic | None | Minimal, described by Microsoft as negligible |
| Underlying component | SenseNDR.exe | Common discovery protocols plus passive monitoring |
| Device visibility | Limited | Higher, with richer device information |
| Microsoft recommendation | Not preferred | Recommended |

> Exam tip: Basic Discovery is purely passive and uses **SenseNDR.exe**. Standard Discovery adds active probing using common discovery protocols and is the mode Microsoft recommends for the most complete inventory.

### Devices Device Discovery Can Identify

* Enterprise endpoints
* Network devices
* IoT devices

### Onboarding Status Values

| Status | Meaning |
|---|---|
| Onboarded | Device is fully managed by Microsoft Defender for Endpoint |
| Can Be Onboarded | Device is supported but not yet onboarded |
| Unsupported | Device platform is not supported by Microsoft Defender for Endpoint |
| Insufficient Info | Not enough data has been collected yet; often resolved by enabling Standard Discovery |

### Relationship With Microsoft Defender Vulnerability Management

Once Device Discovery finds a device, Microsoft Defender Vulnerability Management can:

* Recommend onboarding of supported devices.
* Assess vulnerabilities.
* Identify missing security controls.
* Help prioritize remediation.

### SC-200 Exam Tips

* Device Discovery uses already onboarded endpoints as sensors; no extra hardware is required.
* Know the two modes cold: Basic (passive, SenseNDR.exe, no extra traffic, limited visibility) vs Standard (passive plus active, minimal extra traffic, recommended, richer data).
* Memorize the four onboarding status values and what each one means, especially the difference between **Can Be Onboarded** and **Unsupported**.
* Understand the pipeline: Device Discovery finds a device, it lands in Device Inventory, then Vulnerability Management assesses and recommends onboarding.

## 7. Advanced Hunting Quick Reference (Supporting Content)

The source material references pivoting from Event Details into **Advanced Hunting**, but does not include KQL syntax. Since Advanced Hunting is a core SC-200 exam skill and directly extends this topic, the reference below is added to support revision.

Advanced Hunting uses **KQL (Kusto Query Language)** to proactively search raw telemetry across Microsoft Defender XDR, including device data collected by Microsoft Defender for Endpoint.

### Common Device Related Tables

| Table | Contains |
|---|---|
| DeviceInfo | Device metadata: OS, health, risk information |
| DeviceProcessEvents | Process creation events |
| DeviceNetworkEvents | Network connections initiated by devices |
| DeviceFileEvents | File creation, modification, and deletion events |
| DeviceRegistryEvents | Registry key and value changes |
| DeviceLogonEvents | Logon activity on devices |
| DeviceEvents | Miscellaneous endpoint events, including many security control events |

### Example: Hunting for Word Launching PowerShell

This mirrors the Real World SOC Scenario above and is a realistic style of query for the exam.

```kql
DeviceProcessEvents
| where InitiatingProcessFileName =~ "winword.exe"
| where FileName =~ "powershell.exe"
| project Timestamp, DeviceName, AccountName, FileName, ProcessCommandLine
| order by Timestamp desc
```

> Exam tip: You are unlikely to need to write complex KQL from scratch on SC-200, but you should be able to read a query and identify what it hunts for, and know which table holds which type of telemetry.

## 8. SC-200 Last Minute Revision

### One Page Cheat Sheet

**Device Inventory fields:** Device name, Domain, Risk level, Exposure level, OS platform, Health state, Last seen.

**Three device health concepts, never confuse them:**

| Field | Answers the Question |
|---|---|
| Risk Level | Is this device likely compromised right now? |
| Exposure Level | Is this device an easy target due to weak configuration? |
| Health State | Is this device even talking to Defender properly? |

**Seven entry points into a device investigation:** Devices list, Alerts queue, Security operations dashboard, Individual alert, File details page, IP address details page, Domain details page.

**Nine Response Actions:** Manage Tags, Isolate Device, Restrict App Execution, Run Antivirus Scan, Collect Investigation Package, Initiate Live Response, Initiate Automated Investigation, Ask Defender Experts, Action Center.

**Behavioral Blocking defends against:** fileless malware, polymorphic malware, in memory attacks, Living off the Land techniques, human operated ransomware.

**Four Behavioral Blocking capabilities:** Next-generation protection, Client Behavioral Blocking, Feedback-loop blocking (rapid protection), EDR in block mode.

**Twelve MITRE ATT&CK Enterprise Matrix tactics, in order:** Initial Access, Execution, Persistence, Privilege Escalation, Defense Evasion, Credential Access, Discovery, Lateral Movement, Collection, Command and Control, Exfiltration, Impact.

**Two Device Discovery modes:** Basic (passive, SenseNDR.exe, no extra traffic, limited visibility), Standard (passive plus active, minimal extra traffic, recommended, richer visibility).

**Four onboarding status values:** Onboarded, Can Be Onboarded, Unsupported, Insufficient Info.

### Frequently Confused Concepts

| Concept A | Concept B | Key Difference |
|---|---|---|
| Risk Level | Exposure Level | Risk Level reflects active threat evidence from alerts; Exposure Level reflects vulnerability from missing recommendations or weak configuration |
| Health State | Risk Level | Health State shows communication status with Defender; Risk Level shows compromise likelihood |
| Isolate Device | Restrict App Execution | Isolate Device cuts general network access except the Defender channel; Restrict App Execution keeps network access but blocks unapproved processes |
| Collect Investigation Package | Initiate Live Response | Investigation Package is a one time forensic snapshot; Live Response is an interactive remote session |
| Basic Discovery | Standard Discovery | Basic is passive only with no extra traffic; Standard adds active probing for deeper visibility with minimal extra traffic |
| Alert | Incident | An alert is a single detection; an incident groups related alerts into one investigable case |
| Automated Investigation (AIR) | Behavioral Blocking | AIR automatically investigates and remediates after detection; Behavioral Blocking is real time detection and prevention during execution |
| Can Be Onboarded | Unsupported | Can Be Onboarded means the platform is supported but not yet enrolled; Unsupported means the platform cannot be onboarded at all |
