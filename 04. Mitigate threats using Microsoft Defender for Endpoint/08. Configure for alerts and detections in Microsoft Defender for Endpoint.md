## Overview

This module covers three tightly related capabilities of Microsoft Defender for Endpoint that shape how alerts are investigated, how the SOC is notified, and how custom detections are enforced:

1. **Advanced Features for Alerts and Detections** — Live Response, Live Response Unsigned Script Execution, and Custom Network Indicators.
2. **Alert Notifications** — automatic email alerts to designated SOC recipients.
3. **Indicators (IoCs)** — custom detection and response rules for files, IP addresses, URLs, domains, and certificates.

> **Exam framing:** expect scenario based questions that describe a SOC need (remote investigation, custom scripts, blocking a malicious domain, notifying a team, importing bulk threat intel) and ask which specific feature satisfies it. Knowing the exact feature name and its configuration path is essential.

## Advanced Features for Alerts and Detections

**Location:** `Microsoft Defender Portal → Settings → Endpoints → General → Advanced Features`

### 1. Live Response

**Live Response** lets authorized analysts remotely connect to an endpoint through a secure command line session, without physically touching the device. It requires:

* Appropriate **RBAC (Role Based Access Control)** permissions.
* Authorization to investigate the target device.

With Live Response, analysts can investigate suspicious devices remotely, collect forensic evidence, run investigation commands, retrieve files, and perform incident response actions, all of which reduces investigation time.

### 2. Live Response Unsigned Script Execution

By default, Live Response only allows trusted or signed scripts. Enabling this feature allows analysts to run **unsigned PowerShell scripts** during a Live Response session, which is useful for custom forensic scripts, tools specific to the organization, or evidence collection not supported by built in commands.

> Because unsigned scripts carry more risk, this should only be enabled for trusted security administrators and SOC analysts.

### 3. Custom Network Indicators

This toggle allows administrators to create indicators for **IP addresses, domains, and URLs** that determine whether a network connection is allowed or blocked, based on the organization's own security policy rather than Microsoft's built in threat intelligence alone.

Typical uses: blocking a known malicious Command and Control (C2) server, blocking phishing domains, or allowing a trusted internal domain even if an external reputation service flags it.

> **Critical relationship:** this Advanced Feature toggle is a **prerequisite**. It must be enabled before an analyst can actually create IP, URL, or Domain Indicators under the separate "Manage indicators" area covered later in this guide.

### Quick Comparison

| Feature | Purpose | Typical Trigger Scenario |
|---|---|---|
| **Live Response** | Remote command line investigation session | Analyst needs remote access to investigate an endpoint |
| **Live Response Unsigned Script Execution** | Run custom, unsigned PowerShell scripts in a session | Analyst must execute a custom PowerShell investigation script |
| **Custom Network Indicators** | Enable org defined allow/block rules for network traffic | Organization wants to block a malicious domain or IP across all managed devices |

### SC 200 Exam Tips

* All three settings live under `Settings → Endpoints → General → Advanced Features`.
* Live Response needs proper **RBAC** permissions and explicit authorization for the target device.
* Unsigned script execution is off by default because of the added risk; enable only for trusted personnel.
* Custom Network Indicators is the enabling toggle; the actual indicator objects are created separately in Manage Indicators.
* Microsoft Threat Intelligence = Microsoft managed indicators. Custom Network Indicators = indicators created and managed by your own organization.

## Configure Alert Notifications

Alert notifications let Microsoft Defender for Endpoint automatically email designated recipients whenever a new alert is generated.

### Required Permissions

* **Manage security settings**, or
* If using Basic Permissions Management: **Security Administrator** or **Global Administrator**

### Steps to Configure

1. Open the **Microsoft Defender Portal**.
2. Navigate to **Settings → Endpoints → Email Notifications**.
3. Select **+ Add Item**.
4. Configure: Rule Name, Organization Name, Tenant specific Portal Link, Device Information, Device Groups, Alert Severity.
5. Select **Next**.
6. Add one or more recipient email addresses.
7. Select **Send Test Email** to confirm recipients actually receive it.
8. Save the notification rule.

```text
New Alert Generated
       │
       ▼
Matches a Notification Rule?
(Device Group + Alert Severity)
       │
       ▼
Email Sent to Configured Recipients
       │
       ▼
Recipient Opens Portal Link to Investigate
```

### What the Notification Contains

* Basic alert information
* A link to the Microsoft Defender portal
* Optional device information
* Organization name
* Tenant specific portal link

### How RBAC Affects Notifications

* Notifications follow **device group permissions**.
* Users only receive alerts for the device groups they manage.
* Only Global Administrators can manage notification rules that cover **all** device groups.

### SC 200 Exam Tips

* Configuration path: `Settings → Endpoints → Email Notifications`.
* Required permission: **Manage security settings**, or **Security Administrator** / **Global Administrator** under Basic Permissions Management.
* Notifications are filtered by **device group** and **alert severity**.
* Always use **Send Test Email** before relying on a new rule in production.
* Scenario cue: "notify analysts automatically for High severity alerts" → configure Email Notifications with severity filter. "Different SOC teams manage different departments" → pair **Device Groups** with **RBAC**.

## Manage Indicators (IoCs)

**Indicators of Compromise (IoCs)** are custom detection rules that tell Microsoft Defender for Endpoint how to respond when a specific file, IP address, URL, domain, or certificate is seen. They let a SOC act on threats it has discovered internally, even before Microsoft's global threat intelligence has caught up.

**Location:** `Microsoft Defender Portal → Settings → Endpoints → Indicators`

### Supported Indicator Types

#### File Indicators

Created from the file hash (for example SHA256) of a potentially malicious executable. Primarily support Portable Executable (PE) files such as `.exe` and `.dll`.

**Supported actions:** Allow, Audit, Warn, Block Execution, Block and Remediate.

**Requires:** Microsoft Defender Antivirus enabled, and cloud based protection enabled.

#### IP Address, URL, and Domain Indicators

Control network communication: allow a trusted domain, block a malicious website, block a C2 server, block a phishing URL, or block a malicious external IP. These work together with **Microsoft Defender SmartScreen** and **Network Protection** to inspect traffic.

**Supported actions:** Allow, Audit, Warn, Block.

**Requires:** Network Protection enabled, and the Custom Network Indicators advanced feature enabled. Only **external** IP addresses are supported; **CIDR ranges are not supported**.

#### Certificate Indicators

Trust or block software based on its signing certificate. Only **leaf certificates** are supported, and Microsoft signed certificates cannot be blocked.

**Supported actions:** Allow, Block.

**Supported formats:** `.CER`, `.PEM`.

**Requires:** Microsoft Defender Antivirus, cloud protection, and updated malware definitions.

### Comparison Table

| Indicator Type | Supported Actions | Key Requirements | Notable Limits |
|---|---|---|---|
| **File** | Allow, Audit, Warn, Block Execution, Block and Remediate | Defender Antivirus + cloud based protection | Mainly PE files (`.exe`, `.dll`) |
| **IP / URL / Domain** | Allow, Audit, Warn, Block | Network Protection + Custom Network Indicators enabled | External IPs only; no CIDR ranges |
| **Certificate** | Allow, Block | Defender Antivirus + cloud protection + updated definitions | Leaf certificates only; cannot block Microsoft signed certs |

### Machine Group Scope

Indicators can be applied to **all devices** or scoped to **selected machine (device) groups only**, allowing targeted enforcement (for example, production servers only).

### Which Defender Components Honor Indicators

* Cloud Detection Engine
* Microsoft Defender Antivirus (Endpoint Prevention Engine)
* Automated Investigation and Remediation (AIR)

### Real World SOC Scenario (Summary)

Threat intelligence reveals a ransomware campaign using a malicious domain, a malicious IP, and a malicious executable. The analyst creates a **File Indicator** (SHA256 hash, "Block and Remediate"), a **URL/Domain Indicator**, and an **IP Indicator**, scopes them to the production device group, and imports additional IoCs in bulk from a **CSV file**. When an employee later downloads the same ransomware, Defender blocks execution, blocks the C2 communication, raises an alert, and AIR automatically removes the malicious file, containing the attack before encryption occurs.

```text
Threat Intelligence Received
       │
       ▼
Create Indicators
(File / URL / Domain / IP)
       │
       ▼
Scope to Device Group
       │
       ▼
Employee Encounters the Threat
       │
       ▼
Defender Enforces Indicator
(Block Execution / Block Connection)
       │
       ▼
Alert Generated → AIR Remediates
```

### SC 200 Exam Tips

* Five supported indicator categories: **Files, IP Addresses, URLs, Domains, Certificates**.
* Memorize the action list per type — File indicators have the most options (5), IP/URL/Domain and Certificate indicators have fewer.
* File and Certificate indicators both depend on Microsoft Defender Antivirus and cloud protection; Network indicators depend on Network Protection and Custom Network Indicators instead.
* CIDR ranges are **not** supported for IP indicators, only individual external IPs.
* Bulk deployment of indicators is done via **CSV import**.
* Indicators are enforced by three components: the Cloud Detection Engine, Microsoft Defender Antivirus, and AIR.
* Scenario cue: "prevent a known malicious executable from running anywhere" → File Indicator, Block and Remediate. "Stop devices from talking to a phishing site" → URL/Domain Indicator. "Block a malicious C2 IP" → IP Indicator. "Deploy hundreds of indicators quickly" → CSV import. "Allow one trusted signed app while blocking others" → Certificate Indicator.

## Related Concepts and Common Exam Confusions

The following clarifications are not verbatim from the source material but directly support SC 200 preparation, since these relationships are easy to mix up under exam pressure.

### Custom Network Indicators (the toggle) vs Network Indicators (the objects)

There are two different things sharing a similar name:

| Term | What It Actually Is | Where Configured |
|---|---|---|
| **Custom Network Indicators** (Advanced Feature) | An On/Off toggle that permits the organization to use network based indicators at all | `Settings → Endpoints → General → Advanced Features` |
| **IP / URL / Domain Indicators** (Manage Indicators) | The actual allow or block rule objects created for specific IPs, URLs, or domains | `Settings → Endpoints → Indicators` |

> You must enable the **toggle** before the **indicator objects** will actually take effect. Exam questions may test this dependency directly.

### Live Response vs AIR vs Indicators

| Capability | Trigger | Nature |
|---|---|---|
| **Live Response** | Manually started by an analyst | Interactive, real time, one device at a time |
| **AIR** | An alert on a managed endpoint | Automatic investigation and remediation per the device group's automation level |
| **Indicators (IoCs)** | A file, IP, URL, domain, or certificate matching a rule | Preventive or detective, applies broadly based on scope, enforced continuously without analyst involvement |

### SC 200 Exam Tips

* If the scenario is "an analyst is actively working a live session on one device," think **Live Response**.
* If the scenario is "Defender automatically investigated and fixed an alert," think **AIR**.
* If the scenario is "we want to proactively stop a known bad file, IP, domain, or certificate everywhere," think **Indicators**.
* Remember the enabling relationship: Custom Network Indicators toggle must be on before IP/URL/Domain indicator objects can function.

## SC 200 Last Minute Revision

A one page style cheat sheet for the day before the exam.

### Core Facts to Memorize

1. Advanced Features for alerts/detections live at `Settings → Endpoints → General → Advanced Features`.
2. **Live Response** = secure remote command line session; requires RBAC permissions and device authorization.
3. **Live Response Unsigned Script Execution** = allows unsigned PowerShell scripts; enable only for trusted personnel.
4. **Custom Network Indicators** (toggle) must be enabled before network based indicator objects will work.
5. Alert Notifications are configured at `Settings → Endpoints → Email Notifications` and require Manage security settings, Security Administrator, or Global Administrator permission.
6. Notification rules filter by **device group** and **alert severity**; always test with **Send Test Email**.
7. RBAC limits notification visibility to the device groups a user manages; only Global Admins see all groups.
8. Indicators (IoCs) live at `Settings → Endpoints → Indicators` and support five types: File, IP, URL, Domain, Certificate.
9. File indicator actions: Allow, Audit, Warn, Block Execution, Block and Remediate.
10. IP/URL/Domain indicator actions: Allow, Audit, Warn, Block.
11. Certificate indicator actions: Allow, Block only.
12. CIDR ranges are **not supported** for IP indicators; only external individual IPs.
13. Only **leaf certificates** are supported for certificate indicators; Microsoft signed certs cannot be blocked.
14. Bulk indicator deployment uses **CSV import**.
15. Indicators are enforced by the Cloud Detection Engine, Microsoft Defender Antivirus, and AIR.

### Frequently Confused Concepts

| Easily Confused | Key Distinction |
|---|---|
| Custom Network Indicators (toggle) vs IP/URL/Domain Indicators (objects) | Toggle enables the capability; objects are the actual allow/block rules |
| Live Response vs Live Response Unsigned Script Execution | Base feature = signed/trusted scripts only; the extra toggle unlocks unsigned PowerShell scripts |
| File Indicators vs Certificate Indicators | Files use a hash (SHA256) of an executable; certificates trust or block based on the signing certificate itself |
| Microsoft Threat Intelligence vs Custom Network Indicators | Microsoft managed indicators vs indicators your own organization creates and manages |
| Alert Notifications vs Indicators | Notifications inform people by email; indicators actively allow, block, audit, or warn on matching activity |

### Quick Navigation Path Reference

| Setting | Path |
|---|---|
| Live Response, Unsigned Scripts, Custom Network Indicators | Settings → Endpoints → General → Advanced Features |
| Alert (Email) Notifications | Settings → Endpoints → Email Notifications |
| Indicators (IoCs) | Settings → Endpoints → Indicators |

### Indicator Actions Quick Table

| Type | Allow | Audit | Warn | Block Execution | Block | Block and Remediate |
|---|---|---|---|---|---|---|
| File | Yes | Yes | Yes | Yes | — | Yes |
| IP / URL / Domain | Yes | Yes | Yes | — | Yes | — |
| Certificate | Yes | — | — | — | Yes | — |

### Final Reminders

* Live Response is manual and interactive; AIR is automatic; Indicators are rule based and continuous.
* The Custom Network Indicators toggle must be on before network indicator objects will actually enforce anything.
* Always confirm email delivery with **Send Test Email** before relying on a notification rule.
* CSV import is the answer whenever a scenario mentions deploying **many** indicators quickly.
* Remember which prerequisite goes with which indicator type: Antivirus and cloud protection for File and Certificate; Network Protection and the Custom Network Indicators toggle for IP/URL/Domain.
