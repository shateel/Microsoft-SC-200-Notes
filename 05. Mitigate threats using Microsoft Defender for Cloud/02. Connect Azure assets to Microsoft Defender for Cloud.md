## 1. Asset Inventory

### 1.1 What It Is

**Asset Inventory** is a centralized resource management page inside **Microsoft Defender for Cloud**. It gives SOC analysts and administrators a single place to view every connected cloud resource, its security posture, and its outstanding recommendations.

Asset Inventory:

* Displays all connected resources.
* Shows each resource's security posture.
* Lists security recommendations per resource.
* Helps identify vulnerable resources quickly.
* Lets administrators search and filter resources.
* Provides management actions directly from the inventory view.

> **Exam Tip:** A resource automatically appears with attention in Asset Inventory whenever it has an outstanding security recommendation. You do not need to manually add resources for them to be tracked.

### 1.2 Why Use It

Asset Inventory answers common SOC questions without checking every resource one by one, such as:

* Which Azure subscriptions have outstanding recommendations?
* Which production servers are missing the Log Analytics Agent?
* Which tagged resources have unresolved security recommendations?
* Which resource group contains vulnerable resources?

### 1.3 How It Works

Asset Inventory is powered by **Azure Resource Graph (ARG)**.

Azure Resource Graph:

* Collects information from Azure resources at scale.
* Enables searches across many subscriptions at once.
* Uses **Kusto Query Language (KQL)** for fast querying.
* Combines resource properties with Defender for Cloud security data.

```text
Azure Resources (across subscriptions)
        │
        ▼
Azure Resource Graph (ARG)
        │
        ▼
Merged with Defender for Cloud security data
        │
        ▼
Asset Inventory (searchable, filterable view)
```

### 1.4 Filtering, Export, and Management Actions

**Summary metrics** shown at the top of Asset Inventory:

| Metric | Meaning |
|---|---|
| Total Resources | All resources connected to Defender for Cloud |
| Unhealthy Resources | Resources with active security recommendations |
| Unmonitored Resources | Resources with monitoring or agent health issues |

**Defender for Cloud protection filter:**

| State | Meaning |
|---|---|
| Off | No Defender plan enabled on the resource |
| On | A Defender plan is enabled |
| Partial | Only some Defender plans are enabled |

**Filtering options:** resource name, tags, subscriptions, resource groups, security findings, and protection status. The **Security Findings** filter accepts **Finding IDs**, **Security Check names**, and **CVE IDs**, which makes it the fastest way to locate every resource affected by a specific vulnerability.

**Export options:**

* Export results to **CSV**.
* Export the underlying query to **Azure Resource Graph Explorer** for deeper KQL based analysis.

**Management actions available from Asset Inventory:** assigning tags, onboarding servers outside Azure, and triggering an **Azure Logic App** against filtered resources.

> **Good to Know:** Asset Inventory sits on top of Defender for Cloud's Recommendations engine. Each unresolved recommendation also contributes to the subscription's **Secure Score**, so improving Asset Inventory's unhealthy count generally improves Secure Score as well. Secure Score is not detailed in the source material but is a closely related, frequently tested SC-200 concept.

### 1.5 SC-200 Exam Tips

* Know the primary purpose of Asset Inventory: a centralized inventory of cloud resources connected to Microsoft Defender for Cloud, used to locate resources with findings and recommendations.
* Memorize the three summary metrics: **Total**, **Unhealthy**, **Unmonitored**.
* Remember what powers Asset Inventory: **Azure Resource Graph (ARG)**, queried with **KQL**.
* Know the two export destinations: **CSV** and **Azure Resource Graph Explorer**.
* Understand the three protection states: **Off**, **On**, **Partial**.

**Common scenario style questions:**

| Scenario | Correct Answer |
|---|---|
| Find every resource affected by a specific CVE | Use the **Security Findings** filter in Asset Inventory |
| Identify resources not protected by any Defender plan | Filter for **Defender for Cloud = Off** |
| Search across multiple Azure subscriptions at once | Use **Asset Inventory**, powered by **Azure Resource Graph (ARG)** |
| Automate an action on a filtered set of resources | Trigger an **Azure Logic App** from Asset Inventory |

## 2. Auto Provisioning

### 2.1 What It Is

**Auto Provisioning** is an automatic onboarding feature in **Microsoft Defender for Cloud**. It automatically installs, configures, and maintains the required security agents and extensions on supported Azure and non Azure compute resources, so administrators do not need to deploy agents manually on every machine.

### 2.2 Agents Used

**Azure Monitor Agent (AMA)** is Microsoft's modern monitoring agent. It:

* Collects security related configurations.
* Collects event logs.
* Sends data to a Log Analytics Workspace.
* Supports Defender for Cloud analysis.

> **Exam Tip:** Microsoft recommends **AMA** for all new deployments. The legacy **Log Analytics Agent (also called MMA/OMS agent)** was retired in **August 2024** and should never be the answer for a new deployment scenario.

| Agent | Status | Notes |
|---|---|---|
| Azure Monitor Agent (AMA) | Current, recommended | Uses Data Collection Rules (DCRs) to control what is collected |
| Log Analytics Agent (MMA/OMS) | Retired August 2024 | Collected all logs by default, no granular control |

### 2.3 Why Use It

Without Auto Provisioning:

* Every VM requires manual agent installation.
* Every new server must be configured by hand.
* Administrators may forget to install required agents.

With Auto Provisioning:

* Existing machines are configured automatically.
* New machines receive required agents automatically.
* Security coverage stays consistent across the estate.
* Administrative effort is reduced.

### 2.4 How It Works

Auto Provisioning relies on **Azure Policy**. When an extension is enabled, Defender for Cloud assigns a **DeployIfNotExists** Azure Policy that checks and remediates missing components automatically.

```text
New Azure VM is created
        │
        ▼
Azure Policy evaluates the VM
        │
        ▼
Defender for Cloud checks for required agent/extension
        │
        ▼
Missing component? → Azure installs it automatically
        │
        ▼
VM sends security telemetry to Defender for Cloud
```

This workflow applies to both **existing** and **newly created** resources, which is what keeps coverage consistent over time.

### 2.5 Direct Onboarding vs Azure Arc

Machines outside Azure (on premises, AWS, or GCP) can be connected in two different ways, and the exam expects you to tell them apart:

| Method | What It Does | Time to Appear |
|---|---|---|
| **Direct Onboarding** | Connects a server straight to Defender for Cloud through Microsoft Defender for Endpoint, without needing Azure Arc | Up to 24 hours |
| **Azure Arc** | Registers the machine as an Azure resource, unlocking full Azure Policy based management including Auto Provisioning and DCR association | Varies, generally required for full feature parity |

> **Exam Tip:** Direct Onboarding is the quicker, lighter path for basic protection. Some advanced management capabilities, including certain Auto Provisioning and policy driven scenarios, still require **Azure Arc**.

> **Good to Know:** Do not confuse per server onboarding (Direct Onboarding or Azure Arc) with **multicloud connectors**. Multicloud connectors are configured at the subscription/account level in Environment Settings and onboard an entire AWS or GCP account, covering more than just compute resources (for example storage, identity, and containers). Server level onboarding is only one piece of that broader multicloud connection.

### 2.6 SC-200 Exam Tips

* Auto Provisioning automatically deploys security agents and extensions to supported resources.
* **AMA** is the recommended replacement for the retired Log Analytics Agent.
* Auto Provisioning uses the **DeployIfNotExists** Azure Policy effect to install missing extensions.
* Configuration path: **Environment Settings → Settings & Monitoring**.
* **Microsoft Defender for Endpoint** integration is automatically enabled with Defender for Servers but can also be enabled manually.
* **Direct Onboarding** allows servers outside Azure to connect to Defender for Cloud without Azure Arc, though some advanced capabilities still require Azure Arc.
* In a shared Log Analytics workspace, configure **Security Events** collection in **either** Defender for Cloud **or** Microsoft Sentinel, never both, to avoid duplicate ingestion.
* Know the difference between **Minimal** and **Common** Windows Security Event sets (see table below).
* MDE sensor deployment can take **up to 1 hour**.
* Direct onboarding can take **up to 24 hours** for servers outside Azure to appear.

| Event Set | Volume | Purpose |
|---|---|---|
| Minimal | Lower volume | Focused specifically on detection |
| Common | Higher volume | Broader audit trail for investigation |

**Supported resources for Auto Provisioning:** Azure VMs, VM Scale Sets, IaaS Containers, and servers outside Azure.

## 3. Manual Agent Provisioning

### 3.1 What It Is

**Manual Agent Provisioning** is the manual installation and configuration of **Azure Monitor Agent (AMA)** using **Data Collection Rules (DCRs)**.

Unlike the legacy Log Analytics Agent, AMA does not collect every type of log by default. A **DCR** must explicitly define what to collect. This gives far more control, reduces unnecessary data collection, lowers storage costs, and improves overall monitoring performance.

### 3.2 Data Collection Rules (DCR)

A **DCR** defines:

* Which machines receive monitoring.
* Which logs are collected.
* Which performance counters are collected.
* Where the collected data is sent.

Without a DCR, AMA does not know what information to collect.

**Why DCRs exist:** organizations rarely want every server collecting every log. DCRs let administrators build different monitoring policies for different workloads, for example:

| Workload | Typical Data Collected |
|---|---|
| Domain Controllers | Security Event Logs |
| IIS Servers | IIS Logs |
| Linux Servers | Syslog |
| SQL Servers | Performance Counters |

> **Exam Tip:** The **DCR region must match the Log Analytics Workspace region**. Supported platform types when creating a DCR are **Windows**, **Linux**, or **All**.

### 3.3 Log Analytics Workspace

The **Log Analytics Workspace** is the central repository that stores telemetry collected by AMA. Both **Microsoft Defender for Cloud** and **Microsoft Sentinel** query this workspace using **KQL**. Without a workspace, collected telemetry cannot be stored or analyzed.

### 3.4 Deployment Methods

| Method | Best For |
|---|---|
| Azure Portal | Small environments, interactive deployments, initial testing |
| ARM Templates | Repeatable deployments, Infrastructure as Code (IaC), large enterprises |
| PowerShell | Automation, administrative scripting, bulk deployments |
| Azure CLI | Linux administrators, DevOps pipelines, cross platform automation |

> **Exam Tip:** If AMA is not already installed on a supported VM, associating a DCR with that VM can trigger automatic installation of the agent.

### 3.5 Telemetry Pipeline (End to End)

```text
Data Collection Rule (DCR) is created
        │
        ▼
DCR is associated with target machines
        │
        ▼
Azure Monitor Agent (AMA) installs if missing
        │
        ▼
AMA collects the configured data sources
        │
        ▼
Telemetry is sent to the Log Analytics Workspace
        │
        ▼
Microsoft Defender for Cloud analyzes the data
        │
        ▼
Microsoft Sentinel investigates and correlates alerts
```

> **Exam Tip:** After creating a DCR, telemetry data can take **up to 5 minutes** to appear. Verify successful deployment using the **Heartbeat** table in Log Analytics.

### 3.6 SC-200 Exam Tips

* AMA is the recommended monitoring agent for all new deployments.
* Log Analytics Agent is a legacy agent and should never be selected in a new environment scenario.
* AMA relies entirely on **DCRs** to determine what data is collected.
* A DCR defines **what to collect**, **from which resources**, and **where to send the data**.
* Common data sources: Windows Events, Syslog, Performance Counters, Text Logs, and IIS Logs.
* Verify deployment success using the **Heartbeat** table.
* Avoid duplicate DCRs collecting the same data from the same VM. This causes duplicate ingestion and extra cost, a common exam distractor.
* Defender for Cloud and Sentinel both consume AMA telemetry for detection, investigation, and hunting.

## 4. How These Concepts Connect

The three topics in this guide form a single pipeline: resources are onboarded (automatically or manually), telemetry flows into a shared workspace, and Defender for Cloud plus Sentinel both consume that telemetry.

```text
Azure / non Azure Resource
        │
        ▼
Onboarding: Auto Provisioning (Azure Policy)  OR  Manual Provisioning (DCR)
        │
        ▼
Azure Monitor Agent (AMA) installed and configured
        │
        ▼
Log Analytics Workspace (central telemetry store)
        │
        ├──▶ Microsoft Defender for Cloud → Recommendations → Asset Inventory → Secure Score
        │
        └──▶ Microsoft Sentinel → Analytics Rules → Incidents → Investigation → Response
```

**Defender for Cloud vs Microsoft Sentinel**, a distinction the exam tests directly:

| Aspect | Microsoft Defender for Cloud | Microsoft Sentinel |
|---|---|---|
| Primary role | Cloud Security Posture Management (CSPM) and workload protection | Cloud native SIEM and SOAR |
| Main output | Recommendations, Secure Score, alerts | Incidents, investigation, automated response |
| Data source | Resource configuration plus AMA telemetry | Connectors including Defender for Cloud, AMA, and third party sources |
| Typical question focus | "Where do I check posture/compliance for a resource?" | "Where do I investigate and respond to a threat?" |

## 5. SC-200 Last Minute Revision

### One Page Cheat Sheet

**Asset Inventory**
Centralized resource view, powered by **Azure Resource Graph (ARG)**, queried with **KQL**. Metrics: Total, Unhealthy, Unmonitored. Export to CSV or ARG Explorer. Filter statuses: Off / On / Partial.

**Auto Provisioning**
Automatic agent deployment via **Azure Policy**, effect = **DeployIfNotExists**. Recommended agent = **AMA**. Legacy Log Analytics Agent retired **August 2024**. Path: Environment Settings → Settings & Monitoring.

**Manual Agent Provisioning**
Manual AMA deployment controlled by a **Data Collection Rule (DCR)**. DCR defines what, from where, and where to send. DCR region must match workspace region. Verify with the **Heartbeat** table.

### Frequently Confused Concepts

| Term | Is Actually | Not To Be Confused With |
|---|---|---|
| Azure Resource Graph (ARG) | The query engine behind Asset Inventory, uses KQL | Log Analytics Workspace (stores telemetry, also queried with KQL, but different data) |
| Azure Policy | The engine that enforces DeployIfNotExists for Auto Provisioning | Data Collection Rule (defines what AMA collects, not policy enforcement) |
| Direct Onboarding | Per server connection to Defender for Cloud via MDE, no Arc required | Azure Arc (registers the machine as a full Azure resource) |
| AMA | Current, DCR based monitoring agent | Log Analytics Agent (legacy, retired August 2024, no DCR support) |
| Log Analytics Workspace | Storage and query destination for telemetry | Data Collection Rule (defines collection rules, not storage) |

### Quick KQL and Syntax Reminders

* Both **Asset Inventory** (via Azure Resource Graph) and the **Log Analytics Workspace** (via Defender for Cloud and Sentinel) are queried using **Kusto Query Language (KQL)**, but they query different data: ARG queries resource metadata, while workspace queries target ingested telemetry tables such as **Heartbeat**.
* Policy effect to memorize: **DeployIfNotExists**.

### Key Numbers to Memorize

| Fact | Value |
|---|---|
| Log Analytics Agent retirement | August 2024 |
| MDE sensor deployment time | Up to 1 hour |
| Direct onboarding appearance time (non Azure) | Up to 24 hours |
| Telemetry appearance after DCR creation | Up to 5 minutes |

### Final Architecture Diagram to Memorize

```text
Resource
   │
   ▼
Onboarding (Auto or Manual)
   │
   ▼
AMA + DCR
   │
   ▼
Log Analytics Workspace
   │
   ▼
Defender for Cloud  +  Microsoft Sentinel
```

> **Last Minute Reminder:** If a question asks "how do I see posture across many subscriptions," think **Asset Inventory / ARG**. If it asks "how do I automatically deploy an agent," think **Auto Provisioning / Azure Policy / DeployIfNotExists**. If it asks "how do I control exactly what is collected," think **DCR**. If it asks "where is the data stored and investigated," think **Log Analytics Workspace** feeding **Defender for Cloud** and **Microsoft Sentinel**.
