## 1. Azure Arc Fundamentals

### 1.1 What Is Azure Arc

**Azure Arc** is a Microsoft service that extends Azure management and security capabilities to resources running outside Azure.

Azure Arc does **not** move workloads into Azure. Instead it **projects** resources located outside Azure into **Azure Resource Manager (ARM)**, so they can be managed as if they were native Azure resources.

Azure Arc provides a **single management plane** for:

* Servers hosted on premises
* VMware virtual machines
* AWS resources
* Google Cloud resources
* Kubernetes clusters
* SQL Servers
* Azure data services

This lets administrators apply Azure security, governance, compliance, monitoring, and automation consistently across every environment.

### 1.2 Unified Management

Azure Arc creates a single management platform for **hybrid** and **multicloud** environments. Organizations often end up with multiple, disconnected management tools; Azure Arc reduces that complexity by letting administrators manage everything from Azure.

**Benefits:**

* Single pane of glass
* Centralized management
* Consistent administration
* Simplified operations

### 1.3 Defender for Cloud Integration

Azure Arc enables **Microsoft Defender for Cloud** to protect machines outside Azure. Once onboarded, Defender for Cloud can provide:

* Secure Score
* Security recommendations
* Threat detection
* Vulnerability assessment
* Regulatory compliance
* Workload protection

> **Exam Tip:** From the SOC analyst's perspective, Azure and non Azure servers become almost identical from a monitoring standpoint once Azure Arc has onboarded them.

### 1.4 Azure Resource Manager (ARM) Relationship

**Azure Resource Manager (ARM)** is Azure's centralized management layer. Azure Arc projects external resources into ARM so they appear as Azure resources, giving administrators one management interface regardless of where a resource is physically located.

SOC analysts investigate Arc connected resources using Azure's familiar interface, without switching between AWS, VMware, or on premises native tools.

### 1.5 SC-200 Exam Tips

* Azure Arc extends Azure management to **hybrid and multicloud** resources.
* Azure Arc **does not migrate** resources into Azure; it **projects** them into **Azure Resource Manager (ARM)**.
* Azure Arc enables Microsoft Defender for Cloud to protect non Azure servers.
* Azure Arc supports: Windows Servers, Linux Servers, physical servers, virtual machines, Kubernetes clusters, SQL Servers, and Azure data services.
* Azure Arc enables the use of: Azure Policy, Azure Monitor, Microsoft Defender for Cloud, Azure Automation, and Azure Update Manager.
* Azure Arc provides **one management plane** across Azure, AWS, GCP, VMware, and on premises environments.
* Azure Policy can be applied to Arc connected resources for governance and compliance.

> **Frequently Tested Distinction:** **Azure Arc** handles management and onboarding. **Microsoft Defender for Cloud** handles security posture and workload protection. Azure Arc is commonly a **prerequisite** before advanced Defender for Cloud features can protect resources outside Azure.

## 2. Connecting Non Azure Machines

### 2.1 What It Is

Modern organizations operate in **hybrid** and **multicloud** environments, with servers hosted both inside and outside Microsoft Azure. Because Microsoft Defender for Cloud protects Azure resources, machines outside Azure must first be connected to Azure before they can receive the same monitoring, recommendations, and protection.

The recommended way to connect Windows and Linux machines outside Azure is by using **Azure Arc enabled servers**. Once connected, these machines become Azure resources and can be managed, monitored, and protected using Microsoft Defender for Cloud, Microsoft Sentinel, Azure Policy, Azure Monitor, and other Azure services.

Machines that can be onboarded this way include:

* Windows servers on premises
* Linux servers on premises
* VMware virtual machines
* Hyper-V virtual machines
* AWS EC2 instances
* Google Cloud virtual machines

After onboarding, Azure treats each of these as a native Azure resource, allowing centralized management and security.

### 2.2 Why It Is Important

Without Azure Arc:

* Microsoft Defender for Cloud cannot fully protect machines outside Azure.
* Azure Policy cannot enforce security settings on them.
* Azure Monitor cannot centrally collect their monitoring data.
* Security posture becomes fragmented across different environments.

With machines connected through Azure Arc:

* Security monitoring becomes centralized.
* Hybrid environments receive the same protection as native Azure VMs.
* SOC analysts investigate all servers from one portal.
* Compliance and governance become consistent.

### 2.3 How It Fits Into Microsoft Security

```text
Windows Server, Linux Server, VMware VM, AWS EC2, GCP VM
        │
        ▼
Azure Connected Machine Agent
        │
        ▼
Azure Arc
        │
        ▼
Azure Resource Manager (ARM)
        │
        ▼
Microsoft Defender for Cloud
        │
        ├── Secure Score
        ├── Security Recommendations
        ├── Vulnerability Assessment
        ├── Threat Detection
        └── Compliance
                │
                ▼
        Microsoft Sentinel
```

Azure Arc acts as the connection layer between hybrid resources and Azure security services.

### 2.4 Azure Arc Enabled Servers

**Azure Arc enabled servers** allow Windows and Linux machines hosted outside Azure to be managed as Azure resources. Once onboarded:

* The machine receives its own **Azure Resource ID**.
* It belongs to an **Azure Resource Group**.
* Azure tags can be applied.
* Azure Policy can enforce configurations.
* Microsoft Defender for Cloud can monitor the machine.
* Azure services can be deployed to it.

From Azure's perspective, the machine behaves similarly to a native Azure virtual machine.

### 2.5 Azure Connected Machine Agent vs Azure Monitor Agent

> **Important Exam Point:** The **Azure Connected Machine Agent** is **not** the **Azure Monitor Agent (AMA)**. These are two different agents with two different jobs, and the exam commonly tests this distinction directly.

| Agent | Purpose |
|---|---|
| Azure Connected Machine Agent | Registers the machine with Azure Arc, makes it appear as an Azure resource, and enables Azure management features |
| Azure Monitor Agent (AMA) | Collects logs and performance counters, sends telemetry to the Log Analytics Workspace, and supports Microsoft Defender for Cloud and Microsoft Sentinel |

In short: **the Connected Machine Agent provides connectivity, while AMA provides monitoring.** The Connected Machine Agent does **not** replace AMA. Both are typically present on a fully protected Arc connected machine.

### 2.6 Deployment Methods

* **Azure Arc Setup** (interactive onboarding) is available only for **Windows Server 2022 and later**, and is suitable for onboarding a few machines at a time.
* **At scale deployment** is intended for enterprise environments and can be performed using:
  1. Configuration Manager
  2. Group Policy
  3. PowerShell
  4. Azure Automation
  5. Service Principal

> **Good to Know:** **VM Insights** provides performance monitoring for Arc connected machines, complementing the security telemetry collected by AMA.

### 2.7 SC-200 Exam Tips

* Azure Arc enabled servers are the **recommended** method for connecting machines outside Azure.
* Azure Arc supports both **Windows** and **Linux** servers.
* Connecting a machine with Azure Arc makes it an Azure resource with its own Resource ID.
* The **Azure Connected Machine Agent** connects the machine to Azure Arc; it does **not** collect monitoring telemetry.
* **Azure Arc Setup** (interactive) requires **Windows Server 2022 or later**.
* At scale onboarding methods: Configuration Manager, Group Policy, PowerShell, Azure Automation, Service Principal.
* Azure Arc enables: Azure Policy, Microsoft Defender for Cloud, Microsoft Sentinel, Azure Monitor, Azure Update Manager, and Azure Automation.
* AMA sends logs to a **Log Analytics Workspace**; Defender for Cloud and Sentinel both consume that telemetry for recommendations, alerts, correlation, and hunting.
* Expect a scenario question asking you to distinguish the roles of the **Azure Connected Machine Agent** and **Azure Monitor Agent (AMA)**. Connectivity versus telemetry is the key difference to remember.

## 3. Connecting AWS Accounts

### 3.1 Why Connect AWS

Many organizations run a **multicloud environment**, with workloads in both Microsoft Azure and Amazon Web Services (AWS). Microsoft Defender for Cloud can onboard entire AWS accounts so security teams manage and monitor Azure and AWS resources from a single dashboard, a **single pane of glass** for security operations.

### 3.2 Benefits

* Monitor Azure and AWS resources from one portal.
* Receive security recommendations for AWS resources.
* Improve Secure Score with AWS resources included.
* Detect cloud misconfigurations.
* Protect EC2 servers using **Defender for Servers**.
* Monitor Amazon EKS clusters with **Defender for Containers**.
* Protect AWS databases with **Defender for SQL**.
* Simplify SOC investigations across multiple cloud providers.

### 3.3 Native AWS Connector Workflow

Microsoft provides a **native AWS connector** that integrates AWS services with Defender for Cloud. The high level onboarding process is:

1. Sign in to the Azure Portal.
2. Open **Microsoft Defender for Cloud**.
3. Navigate to **Environment settings**.
4. Select **Add Environment → Amazon Web Services**.
5. Enter AWS account details.
6. Choose which Defender plans to enable.
7. Configure access permissions.
8. Deploy using **AWS CloudFormation** or **Terraform**.
9. Review and create the connector.
10. Defender for Cloud begins scanning AWS resources.

```text
Configure Native Connector (Environment Settings)
        │
        ▼
Choose Defender Plans to Enable
        │
        ▼
Deploy Permissions (CloudFormation or Terraform)
        │
        ▼
Connector Created
        │
        ▼
Defender for Cloud Scans AWS Resources
```

### 3.4 After Onboarding

Once the connector is created:

* Defender for Cloud starts scanning AWS resources.
* Security recommendations begin appearing.
* Secure Score includes AWS resources.
* Compliance assessments become available.
* Vulnerability findings are displayed.
* Alerts are generated for suspicious activity.
* **AWS Security Hub** findings are correlated with Defender for Cloud.

### 3.5 SC-200 Exam Tips

* The native AWS connector is configured through **Environment settings → Add Environment → Amazon Web Services**.
* Permissions are deployed using **AWS CloudFormation** or **Terraform** templates.
* Memorize the Defender plan mapping for AWS workloads:

| AWS Resource | Protected By |
|---|---|
| EC2 instances | Defender for Servers |
| Amazon EKS clusters | Defender for Containers |
| AWS hosted databases | Defender for SQL |

* **AWS Security Hub** findings correlate into Defender for Cloud, giving one investigation surface across clouds.
* Onboarding an AWS account improves Secure Score by including AWS resources in its calculation.

> **Good to Know:** When the **Defender for Servers** plan is enabled through the native AWS connector, Defender for Cloud can automatically deploy the **Azure Arc Connected Machine Agent** and **Azure Monitor Agent** onto EC2 instances behind the scenes. This is the same Arc based onboarding pattern covered in Section 2, just triggered automatically at the account level instead of manually per machine.

## 4. Connecting GCP Accounts

### 4.1 Why Connect GCP

Microsoft Defender for Cloud supports **multicloud security**, allowing organizations to monitor both **Microsoft Azure** and **Google Cloud Platform (GCP)** from a single security platform. After connecting GCP projects, or an entire GCP organization, Defender for Cloud provides centralized visibility, security recommendations, compliance monitoring, Secure Score calculations, and workload protection across both cloud environments.

### 4.2 Benefits

* Multicloud visibility.
* Centralized security recommendations.
* Secure Score calculations that include GCP resources.
* Compliance assessments.
* Continuous cloud posture monitoring.
* Unified SOC investigations.
* Integration with **Google Security Command Center** findings.

### 4.3 SC-200 Exam Tips

* GCP onboarding can target a **single project** or an **entire GCP organization**; know that both scopes are supported.
* Benefits mirror the AWS connector: Secure Score, recommendations, and compliance assessments all extend to GCP resources.
* **Google Security Command Center** findings correlate into Defender for Cloud, the GCP equivalent of AWS Security Hub correlation.
* As with AWS, protecting individual GCP virtual machines under **Defender for Servers** relies on the same underlying Arc based Connected Machine Agent and AMA pattern described in Section 2.

## 5. How These Connection Methods Compare

| Method | Scope | Typical Use Case | Result |
|---|---|---|---|
| Azure Arc enabled servers | A single machine | Onboard one on premises, VMware, Hyper-V, EC2, or GCP virtual machine | Machine becomes an Azure resource with its own Resource ID |
| Native AWS connector | An entire AWS account | Onboard a broad AWS environment at once (EC2, EKS, databases, and more) | Multiple AWS resource types monitored through Defender plans |
| Native GCP connector | A GCP project or organization | Onboard a broad GCP environment at once | Multiple GCP resource types monitored through Defender plans |

> **Exam Tip:** Do not confuse **machine level** onboarding (Azure Arc enabled servers, one machine at a time) with **account or project level** onboarding (native AWS or GCP connectors, an entire cloud environment at once). Behind the scenes, individual compute instances protected under Defender for Servers, whether reached through Arc directly or through a native cloud connector, still rely on the same Connected Machine Agent plus AMA pattern.

## 6. SC-200 Last Minute Revision

### One Page Cheat Sheet

**Azure Arc**
Projects resources outside Azure into **Azure Resource Manager (ARM)**. Does not migrate workloads. Enables Defender for Cloud, Azure Policy, Azure Monitor, Azure Automation, and Azure Update Manager for hybrid and multicloud resources.

**Azure Arc Enabled Servers**
Recommended way to connect individual Windows or Linux machines outside Azure. Interactive setup needs **Windows Server 2022 or later**; at scale methods include Configuration Manager, Group Policy, PowerShell, Azure Automation, and Service Principal.

**Azure Connected Machine Agent vs AMA**
Connected Machine Agent = connectivity and identity in Azure Arc. AMA = telemetry collection sent to the Log Analytics Workspace. They are separate agents; neither replaces the other.

**AWS Connector**
Native connector configured in Environment settings, permissions deployed with CloudFormation or Terraform. EC2 → Defender for Servers, EKS → Defender for Containers, AWS databases → Defender for SQL. AWS Security Hub findings correlate into Defender for Cloud.

**GCP Connector**
Onboards a project or an entire organization. Google Security Command Center findings correlate into Defender for Cloud.

### Frequently Confused Concepts

| Term | Is | Not To Be Confused With |
|---|---|---|
| Azure Connected Machine Agent | Registers a machine with Azure Arc, providing connectivity and an Azure identity | Azure Monitor Agent (AMA), which collects and sends telemetry, not connectivity |
| Azure Arc | The connection and management layer that projects outside resources into ARM | Microsoft Defender for Cloud, the security posture and protection service that consumes Arc onboarded resources |
| Azure Arc enabled servers | Onboards one machine outside Azure at a time | Native AWS or GCP connector, which onboards an entire cloud account or project at once |
| Native AWS/GCP connector | Account or project level onboarding for broad multicloud visibility | Azure Arc enabled servers, which works per machine |

### Key Facts to Memorize

| Fact | Value |
|---|---|
| Minimum OS for interactive Azure Arc Setup | Windows Server 2022 or later |
| At scale Arc deployment methods | Configuration Manager, Group Policy, PowerShell, Azure Automation, Service Principal |
| AWS permission deployment tools | AWS CloudFormation, Terraform |
| GCP onboarding scopes | Single project or entire GCP organization |
| AWS external findings source | AWS Security Hub |
| GCP external findings source | Google Security Command Center |

### Defender Plan to Resource Mapping

| Resource Type | Defender Plan |
|---|---|
| Azure or Arc connected VM | Defender for Servers |
| EC2 instance | Defender for Servers |
| Amazon EKS cluster | Defender for Containers |
| AWS hosted database | Defender for SQL |

> **Last Minute Reminder:** If a question asks "how do I onboard one on premises or third party VM," think **Azure Arc enabled servers**. If it asks "how do I onboard an entire AWS or GCP environment at once," think **native connector**. If it asks "what connects the machine versus what monitors the machine," think **Connected Machine Agent (connectivity) versus AMA (telemetry)**.
