## Where This Guide Fits in SC-200

Microsoft Defender for Cloud is the Cloud Security Posture Management (CSPM) and Cloud Workload Protection (CWP) service that generates security alerts for Azure, on premises, and hybrid resources. On the SC-200 exam, this content sits inside the domain generally described as **"Mitigate threats using Microsoft Defender for Cloud."**

> Quick orientation for the wider exam: **Microsoft Sentinel** is the cloud native SIEM and SOAR platform that ingests alerts from many sources (including Defender for Cloud) using KQL backed analytics rules. **Microsoft Defender XDR** is the extended detection and response suite covering endpoints, identities, email, and cloud apps. This particular module focuses only on Defender for Cloud, so Sentinel and Defender XDR topics are covered in their own dedicated study modules and are only referenced here where directly relevant.

### Key Definitions to Anchor the Whole Module

| Term | Meaning |
|---|---|
| Security Alert | A single suspicious activity or detection raised by Defender for Cloud |
| Security Incident | A group of correlated, related alerts combined into one investigation |
| Remediation | The action taken to eliminate a threat and stop it from recurring |
| Automation | Predefined actions (through Azure Logic Apps) triggered automatically in response to an alert or recommendation |
| Suppression | Automatically marking matching future alerts as dismissed |

## How Microsoft Defender for Cloud Detects Threats

Defender for Cloud does not rely on simple signature matching alone. It continuously collects and correlates data from several sources to identify malicious behavior:

1. Azure resource logs
2. Network logs
3. Connected security solutions
4. Threat intelligence
5. Security telemetry from Microsoft services

### The Three Core Detection Methods

```text
Data Collection
(Resource logs, network logs, connected solutions, telemetry, threat intel)
        │
        ▼
Correlation Engine
        │
        ├──▶ Integrated Threat Intelligence
        │        Matches activity against known malicious IPs, domains,
        │        attacker infrastructure, and known techniques
        │
        ├──▶ Behavioral Analytics
        │        Compares activity against known malicious behavior
        │        patterns using machine learning and historical attacks
        │
        └──▶ Anomaly Detection
                 Builds a normal baseline, then flags significant
                 deviation from that baseline
        │
        ▼
Security Alert
```

**Integrated Threat Intelligence** draws on one of the world's largest threat intelligence sources, fed by Azure, Microsoft 365, Microsoft Dynamics 365, Outlook.com, MSN, the Microsoft Digital Crimes Unit (DCU), the Microsoft Security Response Center (MSRC), third party providers, and other cloud providers. It identifies known malicious IP addresses, malicious domains, attacker infrastructure, emerging campaigns, and known attacker techniques.

**Behavioral Analytics** uses machine learning, large datasets, and historical attack behavior instead of simple signatures. It can detect compromised virtual machines, suspicious administrator activity, unusual network behavior, and abnormal resource activity.

**Anomaly Detection** establishes what is normal for an environment through machine learning, then alerts when activity meaningfully differs from that baseline, for example logins from unusual locations, unexpected administrative actions, rare resource access, or abnormal network communication.

> Exam tip: If a question asks which method relies on a learned baseline of normal activity, the answer is **Anomaly Detection**. If it asks which method compares activity to known malicious patterns using machine learning, the answer is **Behavioral Analytics**. If it references known malicious IPs, domains, or attacker infrastructure, the answer is **Integrated Threat Intelligence**.

### Continuous Improvement Mechanisms

| Mechanism | What It Does |
|---|---|
| Threat Intelligence Monitoring | Continuously tracks internal and external feeds, emerging attack techniques, new malware campaigns, and security advisories |
| Signal Sharing | Collects and shares security signals across Microsoft cloud services, on premises products, and endpoint devices to sharpen detection accuracy |
| Microsoft Security Specialists | Security experts research malware, web attacks, incident response, and digital forensics; their findings feed back into detection logic |
| Detection Tuning | Continuously refines algorithms using real customer telemetry along with true positive and false positive results, improving accuracy and reducing noise |

### Alert Severity Levels

| Severity | Meaning | Analyst Action |
|---|---|---|
| High | High confidence that a resource is compromised | Investigate immediately |
| Medium | Suspicious activity detected | Investigation is likely needed |
| Low | Possibly benign activity, or an attack that was already blocked | Review at lower priority |
| Informational | Contextual data | Most useful when correlated with other alerts |

Every alert also carries a description, severity, affected resource, and a mapped **MITRE ATT&CK** tactic, which helps analysts understand where the activity sits in the overall attack lifecycle.

### SC-200 Exam Tips

1. Know the difference: an **Alert** is a single detection; an **Incident** is multiple related alerts grouped together.
2. Defender for Cloud reduces false positives by combining threat intelligence, behavioral analytics, machine learning, and anomaly detection together, not any single method alone.
3. Related, grouped alerts are combined into incidents through **Cloud Smart Alert Correlation**.
4. Memorize the four severities in order: High, Medium, Low, Informational, and what each implies about confidence versus urgency.
5. Every alert maps to the **MITRE ATT&CK Enterprise Matrix**; expect questions that ask what this mapping is used for (understanding attacker tactics and the attack lifecycle).
6. Expect scenario questions asking you to match a detection description (baseline deviation, known malicious pattern, known bad IP or domain) to the correct detection method.

## Remediate Alerts and Automate Responses

After Defender for Cloud detects a threat, the analyst workflow is to **investigate, remediate, and automate the response**.

* **Alert remediation** is analyzing an alert, understanding what happened, and taking action to eliminate the threat and prevent recurrence.
* **Response automation** lets Defender for Cloud automatically trigger predefined actions using **Azure Logic Apps**, reducing manual effort and speeding up response.

### Investigating a Security Alert

Alerts are found on the **Security alerts** page. Selecting one opens summary and technical detail together, including:

1. Alert title
2. Severity
3. Status
4. Activity time
5. Alert description
6. Affected resource
7. Azure tags (organizational context, for example Production versus Development)
8. Related entities
9. Alert details

### The Take Action Tab: Four Response Options

```text
Security Alert
      │
      ▼
  Take Action Tab
      │
      ├──▶ Mitigate the Threat
      │        Manual remediation guidance for this specific alert
      │
      ├──▶ Prevent Future Attacks
      │        Security recommendations that reduce the attack surface
      │
      ├──▶ Trigger Automated Response
      │        Runs an Azure Logic App automatically
      │
      └──▶ Suppress Similar Alerts
               Creates a suppression rule for recurring, low value alerts
```

### Workflow Automation and Azure Logic Apps

**Workflow Automation** is the Defender for Cloud feature that automatically performs predefined actions whenever a matching alert or recommendation is generated. It relies on **Azure Logic Apps** to actually carry out the automated steps.

```text
Trigger Event
      │
      ▼
"When a Defender for Cloud Alert is created"
        or
"When a Defender for Cloud Recommendation is created or triggered"
      │
      ▼
Workflow Automation Rule (matches the trigger condition)
      │
      ▼
Azure Logic App (executes the automated workflow)
      │
      ▼
Automated Action
(send email, notify Microsoft Teams, create an ITSM ticket, etc.)
```

Logic Apps can also be run manually, directly from an alert or a recommendation, without waiting for the automated trigger.

> Exam tip: If a recommendation used as a trigger is later deprecated or replaced, the workflow automation built on it can stop firing. Update the trigger whenever this happens.

### SC-200 Exam Tips

1. Learn the **four Take Action options** by name and purpose: Mitigate the Threat, Prevent Future Attacks, Trigger Automated Response, Suppress Similar Alerts.
2. **Don't confuse these pairs**, they are a classic exam trap:

| Concept A | Concept B |
|---|---|
| **Workflow Automation** defines *when* automation runs | **Azure Logic Apps** defines *what* automated actions are performed |
| **Mitigate the Threat** gives immediate manual response guidance | **Prevent Future Attacks** gives longer term recommendations to reduce the attack surface |

3. Workflow Automation needs two things to function: a trigger condition, and an associated Azure Logic App.
4. The two supported triggers are alert creation and recommendation creation or trigger.
5. Common automated actions: send an email, notify Microsoft Teams, create an IT service management (ITSM) ticket.
6. Azure tags on an alert give organizational context such as environment or ownership, useful for prioritization during triage.

## Suppress Alerts from Defender for Cloud

**Alert suppression** automatically dismisses alerts that match predefined conditions, instead of an analyst manually dismissing the same repetitive alert every time. It is used for known false positives, high frequency low value alerts, and approved administrative or testing activity.

> Important distinction: suppression does **not** stop Defender for Cloud from detecting the underlying event. The alert is still generated. Its state simply changes automatically to **Dismissed** whenever it matches an enabled suppression rule.

```text
Security Alert Is Generated
      │
      ▼
Does it match an enabled suppression rule?
      │
      ├──▶ Yes: state automatically changes to Dismissed
      │         (alert still exists, filterable under dismissed alerts)
      │
      └──▶ No: alert remains active for normal triage
```

### Creating and Configuring a Suppression Rule

Rules can be created either from a specific alert, or from the dedicated **Suppression Rules** page. A rule can target all resources, or specific entities such as IP addresses, users, processes, resources, or locations.

| Configuration Field | Purpose |
|---|---|
| Subscription | Scopes which subscription the rule applies to |
| Alert type | Which alert the rule matches |
| Entity filters | Narrows the rule to specific IPs, users, processes, resources, or locations |
| Rule name | Identifier for the rule |
| State | Enabled or disabled |
| Reason | Documented justification for suppressing |
| Expiration | When the rule stops applying |
| Simulate option | Preview which existing alerts the rule would match before activating it |

**Rule naming requirements:**

1. Must start with a letter or a number.
2. Must be between 2 and 50 characters long.
3. May use only the hyphen character (`-`) or the underscore character (`_`) as symbols.

**Suppression rules can remain active for up to six months.**

### SC-200 Exam Tips

1. Suppression rules **automatically dismiss future alerts** that match the specified criteria; they do not delete or block detection.
2. Typical use cases: false positives, frequent low value alerts, approved administrative or testing activity.
3. Rules can be created from a specific alert, or from the Suppression Rules page directly.
4. Remember the maximum lifetime: **up to six months**.
5. Remember the naming rule: starts with a letter or number, 2 to 50 characters, only hyphen or underscore as symbols.
6. Suppressed alerts move to a **Dismissed** state and can still be found by filtering for dismissed alerts, they are never deleted outright.

## Generate Threat Intelligence Reports

### Security Incident, Revisited

A **Security Incident** is a collection of related security alerts that Defender for Cloud correlates into a single attack investigation, instead of showing dozens of separate alerts. An incident provides a single view of the attack, its related alerts, affected Azure resources, investigation details, and recommended response actions, which greatly reduces investigation time for SOC analysts.

The Security Incident page shows title, severity, status, activity time, description, affected resource, and Azure resource tags. Its **Alerts tab** lists every alert that belongs to the incident, and its **Take Action tab** supports the same four actions covered earlier: threat mitigation, security recommendations, Azure Logic App automation, and alert suppression.

### What Is a Threat Intelligence Report?

A **Threat Intelligence Report** is generated by Defender for Cloud to give deeper context beyond the alert itself. Depending on the attack, it may include:

1. Attacker identity or known associations, when available
2. Attacker objectives
3. Current and historical attack campaigns
4. Tactics, techniques, and procedures (TTPs)
5. Indicators of Compromise (IoCs) such as URLs and file hashes
6. Victimology: industries and geographic regions commonly targeted
7. Mitigation guidance
8. Remediation recommendations

### Three Report Types

| Report Type | Focus | Best Used For |
|---|---|---|
| Activity Group Report | Attacker profile, objectives, tactics, techniques | Understanding *who* is likely behind the activity and *how* they typically operate |
| Campaign Report | A specific attack campaign, its details, and patterns | Understanding a particular ongoing or historical campaign |
| Threat Summary Report | Combines the Activity Group Report and the Campaign Report | Getting the full picture in one place |

### Accessing a Threat Intelligence Report

```text
Open Microsoft Defender for Cloud
      │
      ▼
Navigate to Security Alerts
      │
      ▼
Select a Security Alert
      │
      ▼
Open the Alert Details Page
      │
      ▼
Select the Threat Intelligence Report Link
      │
      ▼
Report Opens as a PDF in the Browser
```

### SC-200 Exam Tips

1. Reinforce: a **Security Incident** is correlated alerts, never a single alert.
2. Know the three report types by name and purpose, especially that the **Threat Summary Report** is the combined view.
3. Remember that a report is opened from the **alert details page** and renders as a **PDF**.
4. Be able to list what an IoC typically includes: file hashes, URLs, and other attack artifacts.
5. TTP stands for **Tactics, Techniques, and Procedures**, a common term across Microsoft security products, not unique to Defender for Cloud.

## Respond to Alerts from Azure Resources

This section compares alert handling across three specific Azure resource protections. These are a classic source of "don't confuse" exam questions.

### Microsoft Defender for Key Vault

Protects **Azure Key Vault**, which stores secrets, cryptographic keys, and certificates. It detects suspicious attempts to access these protected objects.

Key Vault alerts include:

1. Object ID
2. User Principal Name (UPN)
3. IP address of the suspicious user or application

> Always verify whether detected activity is **expected** before taking remediation action, this applies across all three resource types below, not just Key Vault.

For unknown or unexpected Key Vault access:

1. Enable the Key Vault firewall.
2. Configure trusted virtual networks.
3. Remove suspicious Azure RBAC permissions.

> **Azure RBAC is the recommended authorization model for Key Vault. Vault Access Policies are deprecated.** This is a frequently tested fact.

During a Key Vault investigation: review accessed secrets, review timestamps, review diagnostic logs, and rotate any compromised secrets and certificates.

### Microsoft Defender for DNS

Detects malicious DNS activity originating from Azure resources. Response steps:

1. Verify whether the activity is expected.
2. If malicious: isolate the resource, perform malware scanning, remove unknown software, restore from a trusted state if required, and resolve the related Defender for Cloud recommendations.

### Microsoft Defender for Resource Manager

Protects Azure management operations performed through **Azure Resource Manager (ARM)**, meaning the control plane rather than the data plane. Remediation includes:

1. Reset compromised credentials.
2. Review Azure Activity Logs.
3. Remove unauthorized Runbooks.
4. Review IAM permissions.
5. Remove unknown Azure resources.
6. Reimage compromised virtual machines if necessary.

### Comparison Table: Don't Confuse These Three

| Plan | Protects | Key Alert Details | Typical Remediation |
|---|---|---|---|
| Defender for Key Vault | Secrets, keys, and certificates | Object ID, UPN, source IP address | Enable firewall, configure trusted virtual networks, remove suspicious Azure RBAC permissions, rotate secrets and certificates |
| Defender for DNS | DNS activity from Azure resources | Suspicious DNS queries or responses | Isolate resource, scan for malware, remove unknown software, restore from a trusted state, resolve recommendations |
| Defender for Resource Manager | Azure management and control plane operations (ARM) | Suspicious management operations | Reset credentials, review Activity Logs, remove unauthorized Runbooks, review IAM permissions, remove unknown resources, reimage VMs if necessary |

### SC-200 Exam Tips

1. The exam commonly presents a scenario (suspicious Key Vault access, odd DNS query, unexpected ARM operation) and asks you to pick the correct remediation sequence, use the comparison table above to recognize the pattern quickly.
2. Memorize that **Vault Access Policies are deprecated in favor of Azure RBAC** for Key Vault authorization.
3. "Isolate the resource" is specific to a **confirmed malicious** DNS related compromise, not a first step for every alert, always verify first.
4. Resource Manager alerts concern **control plane** activity (management operations), which is different from data plane activity inside a resource.
5. Across all three resource types, the very first analyst action is the same: **confirm whether the activity is expected** before remediating.

### Master Workflow: Detection to Response

```text
Data Collection
```

### Alert Severity Quick Table

| Severity | Confidence / Meaning |
|---|---|
| High | High confidence, investigate now |
| Medium | Suspicious, investigation likely needed |
| Low | Possibly benign, or already blocked |
| Informational | Context only, valuable when correlated |

### The Four Take Action Options

| Option | Purpose |
|---|---|
| Mitigate the Threat | Immediate manual remediation guidance |
| Prevent Future Attacks | Recommendations to reduce attack surface |
| Trigger Automated Response | Runs an Azure Logic App |
| Suppress Similar Alerts | Creates a suppression rule |

### Suppression Facts to Memorize

1. Maximum active duration: **up to six months**.
2. Naming rule: starts with a letter or number, 2 to 50 characters, only hyphen (`-`) or underscore (`_`) symbols allowed.
3. Suppressed alerts are **not deleted**, they change state to **Dismissed**.
4. Suppression does not stop detection, it only changes what the analyst sees by default.
5. Create rules from a specific alert or from the Suppression Rules page.

### Threat Intelligence Report Types

| Report | Covers |
|---|---|
| Activity Group Report | Attacker profile, objectives, tactics, techniques |
| Campaign Report | A specific campaign's details and patterns |
| Threat Summary Report | Combination of both of the above |

### Frequently Confused Pairs

| Easy to Mix Up | The Distinction |
|---|---|
| Workflow Automation vs Azure Logic Apps | Workflow Automation defines **when**; Logic Apps define **what** happens |
| Mitigate the Threat vs Prevent Future Attacks | Mitigate is **immediate**; Prevent is **longer term posture** |
| Alert vs Incident | Alert is **one** detection; Incident is **correlated, multiple** alerts |
| Suppress vs Delete | Suppression changes state to **Dismissed**; nothing is deleted |
| Defender for Key Vault vs DNS vs Resource Manager | Secrets and keys, versus DNS activity, versus ARM control plane operations |
| Azure RBAC vs Vault Access Policies | RBAC is **recommended**; Access Policies are **deprecated** |

1. Always confirm whether an activity is **expected** before remediating, across every resource type.

3. Azure tags provide organizational context (for example, Production versus Development) that helps with prioritization.
4. This module sits inside the "Mitigate threats using Microsoft Defender for Cloud" portion of SC-200; Sentinel and Defender XDR are tested separately in their own domains.
5. When a scenario question mixes remediation steps from Key Vault, DNS, and Resource Manager, match the clue in the question (secrets, DNS query, or management operation) to the correct plan before choosing an answer.
