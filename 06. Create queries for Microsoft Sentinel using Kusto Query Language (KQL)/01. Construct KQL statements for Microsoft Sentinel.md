## Why KQL Matters for SC-200

KQL (Kusto Query Language) is the query language behind:

* The **Logs** blade in **Microsoft Sentinel**
* **Analytics rules** that generate alerts and incidents
* **Hunting queries** used for proactive threat hunting
* **Workbooks** and **notebooks** used for reporting and investigation
* **Advanced Hunting** in **Microsoft Defender XDR**, since Sentinel and Defender XDR both query data through the same Kusto engine

> **Exam Tip:** Even though this guide is scoped to constructing KQL statements, expect KQL syntax to reappear across the entire SC-200 exam, including analytics rule creation, hunting, and Defender XDR advanced hunting questions.

## KQL Statement Structure

* Every KQL query is made of one or more **query statements**.
* Every query must contain at least one **tabular expression statement**, meaning it processes data shaped like rows and columns.
* Data moves from one operator to the next using the **pipe operator (`|`)**.

**General shape of a query:**

```kql
TableName
| Operator1
| Operator2
| Operator3
```

Each operator receives, transforms, and passes on the output of the operator before it. This chaining behavior is the single most important concept in KQL: **read every query top to bottom, one operator at a time, and track how the table changes at each step.**

### Core Vocabulary, Shown Against a Real Table

`SecurityEvent` contains Windows Security Log data. Below is a tiny sample of that table so each term has something concrete to point at.

| EventID | Account | Computer | TimeGenerated |
|---|---|---|---|
| 4624 | John | `PC-01` | 09:10 |
| 4625 | Bob | `PC-02` | 09:15 |
| 4688 | Alice | `PC-03` | 09:20 |

| Term | Meaning | Where to see it above |
|---|---|---|
| **Table** | A collection of similar events | The whole thing is the table `SecurityEvent` |
| **Row** | One single event or record | Each line, for example `4625, Bob, PC-02, 09:15`, is one row |
| **Column** | A field that describes each event | `EventID`, `Account`, `Computer`, `TimeGenerated` are the columns |
| **Pipe (`\|`)** | Passes the output of one operator into the next operator | Not shown in the table itself; it connects operators in the query |

> **Exam Tip:** Columns are simply fields. If a question asks you to identify what a column represents, think "what property of the event does this describe."

### KQL Exam Tips

* A query must always start by naming a **table**.
* The **pipe operator** is the backbone of every KQL query; operators are always chained left to right, top to bottom.
* KQL is **case insensitive for identifiers** (table names, column names, variable names, function names), so `Account`, `account`, and `ACCOUNT` all refer to the same column.
* KQL is **case sensitive for string comparisons** unless you explicitly use a case insensitive operator such as `=~`.

## Reading a Full Query Like a SOC Analyst

Worked example used throughout the source material:

```kql
SecurityEvent
| where EventID == 4625
| summarize count() by Account
| limit 10
```

Read in plain English:

1. **Open** the `SecurityEvent` table.
2. **Filter** to keep only `EventID == 4625` (failed logon events).
3. **Group** the remaining rows by `Account`.
4. **Count** how many failed logons each account has.
5. **Display** up to the first 10 results.

Watch the table change at every single step below.

### Step 1: Open SecurityEvent (every row is available)

| EventID | Account | Computer | TimeGenerated |
|---|---|---|---|
| 4624 | John | `PC-01` | 09:10 |
| 4625 | Bob | `PC-02` | 09:15 |
| 4688 | Alice | `PC-03` | 09:20 |
| 4625 | John | `PC-01` | 09:22 |
| 4625 | Bob | `PC-02` | 09:25 |
| 4720 | Admin | `DC-01` | 09:30 |
| 4624 | David | `PC-04` | 09:32 |
| 4625 | Alice | `PC-03` | 09:35 |
| 4625 | Bob | `PC-02` | 09:40 |
| 4625 | John | `PC-01` | 09:45 |

Nothing has happened yet, the query has simply opened the table.

### Step 2: `| where EventID == 4625` (keep only failed logons)

| EventID | Account | Computer | TimeGenerated |
|---|---|---|---|
| 4625 | Bob | `PC-02` | 09:15 |
| 4625 | John | `PC-01` | 09:22 |
| 4625 | Bob | `PC-02` | 09:25 |
| 4625 | Alice | `PC-03` | 09:35 |
| 4625 | Bob | `PC-02` | 09:40 |
| 4625 | John | `PC-01` | 09:45 |

`4624` (successful logon), `4688` (process creation), and `4720` (user account created) rows are gone. Only failed logon events remain.

### Step 3: `| summarize count() by Account` (group and count)

`summarize` builds a **brand new table**. Only the grouping column (`Account`) and the calculated value (`count_`) survive, `EventID`, `Computer`, and `TimeGenerated` disappear from the output.

| Account | count_ |
|---|---|
| Bob | 3 |
| John | 2 |
| Alice | 1 |

### Step 4: `| limit 10` (cap the output)

There are only 3 rows, so `limit 10` changes nothing here.

| Account | count_ |
|---|---|
| Bob | 3 |
| John | 2 |
| Alice | 1 |

```text
SecurityEvent               (open the table, every row available)
  │
  ▼
| where EventID == 4625     (keep only failed logon rows)
  │
  ▼
| summarize count() by Account   (group rows, calculate a count per account)
  │
  ▼
| limit 10                  (cap the output to 10 rows)
  │
  ▼
Final Result Table
```

### Common Windows Event IDs Referenced in the Source Material

| Event ID | Meaning |
|---|---|
| 4624 | Successful logon |
| 4625 | Failed logon |
| 4688 | Process creation |
| 4720 | User account created |

> **Exam Tip:** SC-200 frequently tests recognition of `4624` versus `4625`. Memorize: **4624 = success, 4625 = failure.**

## The Log Analytics Workspace

A **Log Analytics Workspace** (an Azure Monitor Logs workspace) is the **central storage location** for logs. Think of it as one large database that stores logs from many different Microsoft services and devices, for example:

* Windows Servers and Windows PCs
* Linux Servers
* Firewalls
* Microsoft Entra ID
* Microsoft Defender for Endpoint
* Microsoft Defender for Cloud
* Azure resources
* Microsoft 365

Microsoft Sentinel does not store the data itself; it **reads data from the workspace** and lets analysts query it with KQL.

```text
Log sources
(Windows Servers, Windows PCs, Linux Servers, Firewalls,
Microsoft Entra ID, Defender for Endpoint, Defender for Cloud,
Azure resources, Microsoft 365)
  │
  ▼
Log Analytics Workspace (central storage)
  │
  ▼
Tables: SecurityEvent, SigninLogs, Syslog,
Device* tables, SecurityAlert, CommonSecurityLog
  │
  ▼
Microsoft Sentinel (reads the workspace)
  │
  ▼
SOC Analyst runs KQL queries
```

### Data Hierarchy Inside a Workspace

```text
Log Analytics Workspace
  │
  ▼
Tables (for example SecurityEvent)
  │
  ▼
Columns (for example EventID, Account, Computer, TimeGenerated)
  │
  ▼
Rows (individual events)
```

Applied to a concrete example:

| Level | Example |
|---|---|
| Workspace | Container holding all log tables |
| Table | `SecurityEvent` |
| Columns | `EventID`, `Account`, `Computer`, `TimeGenerated` |
| Row | `4624, John, PC-01, 09:10` (one event) |

### Typical Table to Source Mapping

| Log Source | Typical Table(s) |
|---|---|
| Windows Servers / PCs | `SecurityEvent` |
| Linux Servers | `Syslog` |
| Microsoft Entra ID | `SigninLogs` |
| Defender for Endpoint | `DeviceEvents`, `DeviceProcessEvents`, `DeviceNetworkEvents`, `DeviceFileEvents` |
| Firewalls and other CEF sources | `CommonSecurityLog` |
| Analytics rule detections | `SecurityAlert` |

> **Exam Tip:** If a scenario question describes "central storage for logs across an organization's Microsoft services," the answer is a **Log Analytics Workspace**.

### Workspace Exam Tips

* A workspace is a **container**; tables, columns, and rows live inside it.
* Microsoft Sentinel is layered **on top of** a Log Analytics Workspace; it does not replace it.
* Knowing which log source populates which table (see table above) is a common scenario question pattern.

## The search Operator

The `search` operator scans across **multiple tables and multiple columns** at once. It is useful when you know **what** you are looking for (a keyword or value) but you do **not know where it is stored**.

**General syntax:**

```kql
search "text"
```

```kql
search in (Table1, Table2) "text"
```

**Example, searching only selected tables:**

```kql
search in (SecurityEvent, SecurityAlert, A*) "err"
```

This searches `SecurityEvent`, `SecurityAlert`, and every table whose name begins with `A`, for the keyword `err`. Because `search` does not target one table or column, there is no single "before and after" table to show, it checks the keyword against many tables such as `SecurityEvent`, `DeviceProcessEvents`, `SecurityAlert`, and `DeviceFileEvents` at once, and returns whichever rows in any of them contain a match.

> **Important trade off:** Because `search` scans many tables and columns, it is **slower and less efficient** than using `where` on a known table and column.

### search Exam Tips

* Use `search` when you are **unsure** which table or column holds the data.
* Use `where` instead of `search` whenever you already know the target table and column, for better performance.
* `search "keyword"` scans **all** available tables.
* `search in (Table1, Table2) "keyword"` restricts the scan to specific tables.
* Wildcards, such as `A*`, can match table names by pattern.
* If a search returns no results, check the **time range** in the query window before assuming the query itself is wrong.

## The where Operator

The `where` operator filters a table and returns only the rows that satisfy a condition (a predicate). It is the most commonly used operator in KQL.

**General syntax:**

```kql
TableName
| where Condition
```

### Filtering by Time

```kql
SecurityEvent
| where TimeGenerated > ago(1d)
```

| Function | Meaning |
|---|---|
| `ago(1h)` | Last 1 hour |
| `ago(1d)` | Last 1 day |
| `ago(7d)` | Last 7 days |

> **Exam Tip:** `ago()` always calculates time **relative to the current moment**. Filtering by `TimeGenerated` is one of the most common uses of `where` in real investigations.

### Combining Conditions with `and`

```kql
SecurityEvent
| where TimeGenerated > ago(1h)
  and EventID == 4624
```

**Before, the full table:**

| EventID | Account | Computer | AccountType | TimeGenerated |
|---|---|---|---|---|
| 4624 | John | `PC-01` | User | 20 minutes ago |
| 4625 | Bob | `PC-02` | User | 10 minutes ago |
| 4624 | Alice | `PC-03` | User | Yesterday |
| 4624 | David | `PC-04` | Admin | 30 minutes ago |

KQL checks every row against both conditions (within the last hour, **and** `EventID == 4624`): John passes both checks, Bob fails on `EventID`, Alice fails on time (`Yesterday` is outside the window), David passes both checks.

**After:**

| EventID | Account | Computer | AccountType | TimeGenerated |
|---|---|---|---|---|
| 4624 | John | `PC-01` | User | 20 minutes ago |
| 4624 | David | `PC-04` | Admin | 30 minutes ago |

### Case Insensitive Comparison (`=~`)

```kql
SecurityEvent
| where AccountType =~ "user"
```

`=~` compares text **without** regard to uppercase or lowercase letters. A plain `==` comparison is case sensitive.

**Before:**

| Account | AccountType |
|---|---|
| John | User |
| Bob | USER |
| Alice | user |
| David | Admin |

**After:**

| Account | AccountType |
|---|---|
| John | User |
| Bob | USER |
| Alice | user |

David is removed because `"Admin"` does not match `"user"`, even with case insensitive matching.

### The in Operator

Checks whether a column's value matches any value in a list or another table. `in` always comes **after** the column name.

```kql
TableName
| where ColumnName in (Value1, Value2, Value3)
```

```kql
SecurityEvent
| where EventID in (4624, 4625)
```

**Before:**

| EventID | Account |
|---|---|
| 4624 | John |
| 4625 | Bob |
| 4688 | Alice |
| 4720 | Admin |

**After:**

| EventID | Account |
|---|---|
| 4624 | John |
| 4625 | Bob |

`4688` and `4720` are removed because neither value is in the list `(4624, 4625)`.

`in` can also compare against a table built with `let` and `datatable()` instead of a literal list, this pattern is covered in the next section.

### Comparison and Filter Operators Reference

| Operator | Meaning | Case Sensitive |
|---|---|---|
| `==` | Equals | Yes |
| `!=` | Not equal to | Yes |
| `=~` | Equals | No |
| `in (...)` | Matches any value in a list or table | Yes |
| `contains` | Text contains the given substring | No |
| `and` | All conditions must be true | n/a |

### where Exam Tips

* `where` filters **rows**; it never adds or removes columns.
* Always filter by `TimeGenerated` early in a query to reduce the dataset and improve performance.
* Remember: `==` is case sensitive, `=~` is case insensitive.
* `in` always follows the column name: `ColumnName in (...)`.
* `in` accepts either a literal list of values or a table/variable produced by `let`.

## The let Statement

The `let` statement works like declaring a variable in a programming language such as PowerShell or Python.

**Basic syntax:**

```kql
let VariableName = Expression;
```

**Example:**

```kql
let timeOffset = 7d;
SecurityEvent
| where TimeGenerated > ago(timeOffset * 2)
  and TimeGenerated < ago(timeOffset)
```

### Why Use let

Without `let`, changing a value that appears many times in a query means editing every occurrence manually. With `let`, the value is defined **once** and reused everywhere it is needed, which is far easier to maintain and less error prone.

```kql
let targetAccount = "administrator";
SecurityEvent
| where Account == targetAccount
| summarize count() by Computer
| where count_ > 10
| project Computer, count_
```

Changing the investigation target later only requires editing the single `let` line, from `"administrator"` to `"SQLService"`, instead of hunting through the whole query.

### Creating a Temporary Table with datatable()

`datatable()` builds a small table **inside the query itself**, existing only while the query runs.

```kql
let suspiciousAccounts = datatable(account:string)
[
    @"administrator",
    @"NT AUTHORITY\SYSTEM"
];
SecurityEvent
| where Account in (suspiciousAccounts)
```

**The temporary table `suspiciousAccounts` created by `let`:**

| account |
|---|
| administrator |
| `NT AUTHORITY\SYSTEM` |

**The `SecurityEvent` table before filtering:**

| Account |
|---|
| John |
| administrator |
| Alice |
| `NT AUTHORITY\SYSTEM` |
| Bob |

For each row in `SecurityEvent`, KQL checks whether `Account` appears in `suspiciousAccounts`: John, no match, removed. administrator, match, kept. Alice, no match, removed. `NT AUTHORITY\SYSTEM`, match, kept. Bob, no match, removed.

**After `| where Account in (suspiciousAccounts)`:**

| Account |
|---|
| administrator |
| `NT AUTHORITY\SYSTEM` |

### Storing a Query Result as a Reusable Table

`let` can also store the **result of an entire query**, not just a single value:

```kql
let LowActivityAccounts =
    SecurityEvent
    | summarize cnt = count() by Account
    | where cnt < 1000;
LowActivityAccounts
| where Account contains "SQL"
```

Read in plain English: create a temporary table called `LowActivityAccounts` containing accounts that generated fewer than 1000 events, then search only that temporary table for accounts whose name contains `"SQL"`.

**Step 1, the original `SecurityEvent` table (imagine millions of rows, a small sample shown):**

| EventID | Account | Computer |
|---|---|---|
| 4624 | John | `PC-01` |
| 4625 | John | `PC-01` |
| 4624 | Alice | `PC-02` |
| 4625 | Alice | `PC-02` |
| 4624 | `SQLServer` | `DB-01` |
| 4625 | `SQLServer` | `DB-01` |
| 4624 | `SQLServer` | `DB-01` |
| 4624 | `BackupSvc` | `SRV-01` |
| 4625 | `BackupSvc` | `SRV-01` |

**Step 2, after `| summarize cnt = count() by Account`:**

| Account | cnt |
|---|---|
| John | 1500 |
| Alice | 400 |
| `SQLServer` | 800 |
| `BackupSvc` | 250 |

The table has been completely transformed, millions of events become one row per account.

**Step 3, after `| where cnt < 1000` (this becomes `LowActivityAccounts`):**

| Account | cnt |
|---|---|
| Alice | 400 |
| `SQLServer` | 800 |
| `BackupSvc` | 250 |

**Step 4, after `LowActivityAccounts \| where Account contains "SQL"`:**

| Account | cnt |
|---|---|
| `SQLServer` | 800 |

> **Exam Tip:** There are two distinct uses of `let`: storing a **scalar value** (a number, string, or time span) and storing a **tabular result** (an entire mini table, as in `LowActivityAccounts` above). Both use the same `let Name = ...;` syntax, but the right side of the expression determines which one it is.

### Real World SOC Scenario (Investigation Workflow)

A company monitors high value, frequently targeted accounts such as `administrator` and `NT AUTHORITY\SYSTEM`. Sentinel raises an alert for unusual authentication activity on a domain controller. The analyst reuses the `suspiciousAccounts` watchlist shown earlier to query `SecurityEvent`:

**Result of the watchlist query:**

| Time | EventID | Account | Computer | Description |
|---|---|---|---|---|
| 09:15 | 4625 | administrator | `DC01` | Failed Logon |
| 09:16 | 4625 | administrator | `DC01` | Failed Logon |
| 09:17 | 4624 | administrator | `DC01` | Successful Logon |
| 09:20 | 4688 | `NT AUTHORITY\SYSTEM` | `DC01` | Process Creation |

From this table the analyst observes multiple failed logons (`4625`) against `administrator`, followed immediately by a successful logon (`4624`), and a process creation event (`4688`) under `NT AUTHORITY\SYSTEM`, a pattern worth escalating.

```text
Sentinel raises an alert
(unusual authentication activity)
  │
  ▼
Analyst builds a watchlist with
let + datatable() of privileged accounts
  │
  ▼
KQL filters SecurityEvent for those accounts
  │
  ▼
Analyst reviews source IP, logon type, time of day,
and processes started after the logon
  │
  ▼
Activity correlated with Sentinel and Defender incidents
  │
  ▼
If confirmed malicious: disable the account, reset
credentials, isolate the host, block the attacker IP,
and open incident response
```

> **Exam Tip:** This pattern, filter for privileged or high risk accounts using a `let` based watchlist, then pivot into logon type, source IP, and post logon process activity, mirrors the real SC-200 incident investigation workflow tested throughout the exam.

### let Exam Tips

* `let` improves query maintainability by centralizing values that are reused multiple times.
* `datatable(columnName:type) [ values ]` builds an inline, temporary table.
* `let` can store either a single value (scalar) or an entire query result (tabular).
* A `let` defined table only exists for the duration of that query; it is not saved permanently.

## The extend Operator

`extend` adds a **new calculated column** to the table without removing or modifying existing columns.

**General syntax:**

```kql
TableName
| extend NewColumn = Expression
```

### Example 1: Adding a Constant Column

```kql
SecurityEvent
| extend Severity = "Medium"
```

**Before:**

| EventID | Account | Computer | TimeGenerated |
|---|---|---|---|
| 4624 | John | `PC-01` | 09:10 |
| 4625 | Bob | `PC-02` | 09:15 |
| 4688 | Alice | `PC-03` | 09:20 |

**After:**

| EventID | Account | Computer | TimeGenerated | Severity |
|---|---|---|---|---|
| 4624 | John | `PC-01` | 09:10 | Medium |
| 4625 | Bob | `PC-02` | 09:15 | Medium |
| 4688 | Alice | `PC-03` | 09:20 | Medium |

Every row gets the same new column and value, since the expression is a fixed string rather than a calculation.

### Example 2: Deriving a Folder Path (Microsoft's Example)

```kql
SecurityEvent
| where ProcessName != "" and Process != ""
| extend StartDir =
    substring(ProcessName, 0, string_size(ProcessName) - string_size(Process))
```

| Function | Meaning | Example | Result |
|---|---|---|---|
| `substring(text, start, length)` | Extracts part of a string | `substring("Windows",0,3)` | `Win` |
| `string_size(text)` | Returns the number of characters in a string | `string_size("cmd.exe")` | `7` |

**Before (after the `where` filter has already run):**

| ProcessName | Process |
|---|---|
| `C:\Windows\System32\cmd.exe` | `cmd.exe` |
| `C:\Windows\System32\notepad.exe` | `notepad.exe` |
| `C:\Program Files\Google\Chrome\chrome.exe` | `chrome.exe` |

**How the calculation works for row 1:** `ProcessName` is 28 characters long and `Process` is 7 characters long. `28 − 7 = 21`, so `substring(ProcessName, 0, 21)` takes the first 21 characters, `C:\Windows\System32\`, and that becomes the value of `StartDir`.

**After `| extend StartDir = ...`:**

| ProcessName | Process | StartDir |
|---|---|---|
| `C:\Windows\System32\cmd.exe` | `cmd.exe` | `C:\Windows\System32\` |
| `C:\Windows\System32\notepad.exe` | `notepad.exe` | `C:\Windows\System32\` |
| `C:\Program Files\Google\Chrome\chrome.exe` | `chrome.exe` | `C:\Program Files\Google\Chrome\` |

### extend Exam Tips

* `extend` **adds** a column; it never removes rows or existing columns.
* Common companion functions: `substring()` to slice text, `string_size()` to measure text length.
* `extend` is frequently combined with `order by` and `project` to shape investigation output.

## The order by Operator

`order by` sorts the rows of a table, similar to sorting a spreadsheet. It changes **row order only**; it never changes the data itself.

**Basic syntax:**

```kql
Table
| order by ColumnName asc   // smallest to largest, A to Z
```

```kql
Table
| order by ColumnName desc  // largest to smallest, Z to A
```

### Example: Sorting Failed Logins

```kql
Table
| order by FailedLogins desc
```

**Before:**

| Account | FailedLogins |
|---|---|
| Alice | 12 |
| John | 3 |
| Bob | 20 |
| David | 8 |

**After:**

| Account | FailedLogins |
|---|---|
| Bob | 20 |
| Alice | 12 |
| David | 8 |
| John | 3 |

Nothing changed except the order of the rows.

### Multiple Column (Secondary) Sort

```kql
SecurityEvent
| where ProcessName != "" and Process != ""
| extend StartDir =
    substring(ProcessName,0, string_size(ProcessName)-string_size(Process))
| order by StartDir desc, Process asc
```

**Before (after the `extend` step, five rows this time):**

| ProcessName | Process | StartDir |
|---|---|---|
| `C:\Windows\System32\cmd.exe` | `cmd.exe` | `C:\Windows\System32\` |
| `C:\Program Files\Google\Chrome\chrome.exe` | `chrome.exe` | `C:\Program Files\Google\Chrome\` |
| `C:\Users\John\Downloads\malware.exe` | `malware.exe` | `C:\Users\John\Downloads\` |
| `C:\Windows\System32\notepad.exe` | `notepad.exe` | `C:\Windows\System32\` |
| `C:\Program Files\Adobe\acrobat.exe` | `acrobat.exe` | `C:\Program Files\Adobe\` |

KQL first sorts by `StartDir` in descending order. When two rows share the same `StartDir` (the two `System32` rows), it then sorts those tied rows by `Process` in ascending order, `cmd.exe` before `notepad.exe`. This is called a **secondary sort**.

**After `| order by StartDir desc, Process asc`:**

| StartDir | Process |
|---|---|
| `C:\Windows\System32\` | `cmd.exe` |
| `C:\Windows\System32\` | `notepad.exe` |
| `C:\Users\John\Downloads\` | `malware.exe` |
| `C:\Program Files\Google\Chrome\` | `chrome.exe` |
| `C:\Program Files\Adobe\` | `acrobat.exe` |

> **Exam Tip:** In `order by ColumnA desc, ColumnB asc`, the **first** column listed always takes priority; later columns only break ties.

### order by Exam Tips

* `order by` never removes rows or columns; it only changes their sequence.
* `asc` = ascending (smallest to largest, or A to Z). `desc` = descending (largest to smallest, or Z to A).
* Multiple sort columns create tie breaking rules, evaluated left to right.

## The project Operator Family

The `project` family controls **which columns appear and in what order**. None of these operators filter rows.

| Operator | Purpose |
|---|---|
| `project` | Selects and reorders specific columns |
| `project-away` | Removes the specified columns; keeps everything else |
| `project-keep` | Keeps only the specified columns |
| `project-rename` | Renames columns |
| `project-reorder` | Changes the display order of columns |

### 1. project

```kql
SecurityEvent
| project Computer, Account
```

**Before:**

| EventID | Account | Computer | TimeGenerated |
|---|---|---|---|
| 4624 | John | `PC-01` | 09:10 |
| 4625 | Alice | `PC-02` | 09:15 |
| 4624 | Bob | `PC-03` | 09:20 |

**After:**

| Computer | Account |
|---|---|
| `PC-01` | John |
| `PC-02` | Alice |
| `PC-03` | Bob |

The rows stay the same; only the displayed columns and their order change. This is exactly how the closing step of the combined example works too, taking the `ProcessName / Process / StartDir` table from the `extend` and `order by` sections and reducing it to just `Process, StartDir` with `| project Process, StartDir`.

### 2. project-away

```kql
SecurityEvent
| project-away ProcessName
```

`project-away` removes the columns you specify and keeps everything else, the opposite of `project`.

**Before:**

| EventID | Account | Computer | ProcessName |
|---|---|---|---|
| 4624 | John | `PC-01` | `cmd.exe` |
| 4625 | Alice | `PC-02` | `chrome.exe` |

**After:**

| EventID | Account | Computer |
|---|---|---|
| 4624 | John | `PC-01` |
| 4625 | Alice | `PC-02` |

### 3. project-keep

```kql
Table
| project-keep Account, Computer
```

**Before:**

| Account | Computer | EventID | TimeGenerated |
|---|---|---|---|
| John | `PC-01` | 4624 | 09:10 |

**After:**

| Account | Computer |
|---|---|
| John | `PC-01` |

### 4. project-rename

```kql
Table
| project-rename User = Account
```

**Before:**

| Account | Computer |
|---|---|
| John | `PC-01` |

**After:**

| User | Computer |
|---|---|
| John | `PC-01` |

### 5. project-reorder

```kql
Table
| project-reorder EventID, Account, Computer
```

**Before:**

| Account | Computer | EventID |
|---|---|---|
| John | `PC-01` | 4624 |

**After:**

| EventID | Account | Computer |
|---|---|---|
| 4624 | John | `PC-01` |

### project Family Exam Tips

* `project` selects and can reorder the columns to keep.
* `project-away` removes only the columns you name; everything else stays.
* `project-keep` keeps only the columns you name; everything else is dropped.
* `project-rename` changes column names, and does not change values or row count.
* `project-reorder` changes column position only.
* **None of the `project` operators filter rows.** Filtering rows is the job of `where`.
* Returning fewer columns with `project` can reduce result size and improve query performance.

## Putting It All Together

The source material builds one continuous example across the `extend`, `order by`, and `project` modules. Reading it as a single pipeline, and watching the table change at every stage, is one of the best ways to revise how operators chain together:

```kql
SecurityEvent
| where ProcessName != "" and Process != ""
| extend StartDir =
    substring(ProcessName, 0, string_size(ProcessName) - string_size(Process))
| order by StartDir desc, Process asc
| project Process, StartDir
```

**Stage 1, after `where` (only rows with both columns populated):**

| ProcessName | Process |
|---|---|
| `C:\Windows\System32\cmd.exe` | `cmd.exe` |
| `C:\Windows\System32\notepad.exe` | `notepad.exe` |
| `C:\Program Files\Google\Chrome\chrome.exe` | `chrome.exe` |

**Stage 2, after `extend StartDir = ...` (a new calculated column appears):**

| ProcessName | Process | StartDir |
|---|---|---|
| `C:\Windows\System32\cmd.exe` | `cmd.exe` | `C:\Windows\System32\` |
| `C:\Windows\System32\notepad.exe` | `notepad.exe` | `C:\Windows\System32\` |
| `C:\Program Files\Google\Chrome\chrome.exe` | `chrome.exe` | `C:\Program Files\Google\Chrome\` |

**Stage 3, after `order by StartDir desc, Process asc` (row order changes, columns do not):**

| ProcessName | Process | StartDir |
|---|---|---|
| `C:\Windows\System32\cmd.exe` | `cmd.exe` | `C:\Windows\System32\` |
| `C:\Windows\System32\notepad.exe` | `notepad.exe` | `C:\Windows\System32\` |
| `C:\Program Files\Google\Chrome\chrome.exe` | `chrome.exe` | `C:\Program Files\Google\Chrome\` |

**Stage 4, after `project Process, StartDir` (only the two chosen columns remain):**

| Process | StartDir |
|---|---|
| `cmd.exe` | `C:\Windows\System32\` |
| `notepad.exe` | `C:\Windows\System32\` |
| `chrome.exe` | `C:\Program Files\Google\Chrome\` |

```text
SecurityEvent
  │
  ▼
| where ProcessName != "" and Process != ""
  │
  ▼
| extend StartDir = substring(ProcessName, 0,
   string_size(ProcessName) - string_size(Process))
  │
  ▼
| order by StartDir desc, Process asc
  │
  ▼
| project Process, StartDir
  │
  ▼
Final, sorted, trimmed result table
```

> **Exam Tip:** SC-200 scenario questions often chain three or four operators together and ask what the **final output table** looks like. Work through each operator one line at a time, tracking the table exactly as shown above, rather than trying to predict the end result in one step.

## SC-200 Last Minute Revision

A one page cheat sheet for the day before the exam.

### Key Definitions

| Term | Definition |
|---|---|
| KQL | Kusto Query Language, used to query Microsoft Sentinel and Microsoft Defender XDR data |
| Tabular expression statement | A query statement that processes data as rows and columns; every KQL query needs at least one |
| Table | A collection of similar events, for example `SecurityEvent` |
| Row | One event |
| Column | A field describing an event |
| Log Analytics Workspace | Central Azure Monitor storage location for logs from many Microsoft services |

### Operator Quick Reference

| Operator | Category | What It Does to the Table |
|---|---|---|
| `search` | Filter | Scans multiple tables and columns for a value; simple but slower |
| `where` | Filter | Removes rows that do not match a condition on a known table and column |
| `let` | Setup | Declares a reusable variable or a reusable temporary table; does not change rows or columns by itself |
| `extend` | Shape | Adds a new calculated column, keeps all existing rows and columns |
| `order by` | Shape | Sorts rows ascending or descending; rows and columns stay the same |
| `project` | Shape | Selects and reorders columns; rows stay the same |
| `project-away` | Shape | Removes named columns; rows stay the same |
| `project-keep` | Shape | Keeps only named columns; rows stay the same |
| `project-rename` | Shape | Renames columns; rows and values stay the same |
| `project-reorder` | Shape | Reorders columns; rows and values stay the same |
| `summarize` | Aggregate | Replaces the table with one row per group plus a calculated value, for example `count()` |
| `limit` | Shape | Caps the number of returned rows |

### Frequently Confused Concepts

| Concept A | Concept B | Key Difference |
|---|---|---|
| `where` | `search` | `where` targets a known table and column and is faster; `search` scans broadly and is slower |
| `==` | `=~` | `==` is case sensitive; `=~` is case insensitive |
| `project` | `project-keep` | Nearly identical in effect; `project` also supports reordering and building expressions |
| `project` | `project-away` | Opposites: `project` states what to keep, `project-away` states what to remove |
| `extend` | `project` | `extend` adds a column while keeping the rest; `project` selects/limits which columns show |
| `let` (scalar) | `let` (tabular) | A scalar `let` stores one value (like a number or time span); a tabular `let` stores an entire query result as a mini table |
| `asc` | `desc` | `asc` = smallest to largest / A to Z; `desc` = largest to smallest / Z to A |
| `and` | `in` | `and` joins multiple separate conditions; `in` checks one column against a list or table of values |

> **Final Exam Tip:** When faced with any multi operator KQL question, always trace the table through each pipe (`|`) one operator at a time, and picture the actual rows and columns, exactly like the before and after tables throughout this guide. Identify first whether each operator **filters rows** (`where`, `search`), **adds a column** (`extend`), **changes column visibility or names** (`project` family), **changes row order** (`order by`), or **transforms the table shape entirely** (`summarize`). This single habit resolves the majority of KQL scenario questions on the SC-200 exam.
