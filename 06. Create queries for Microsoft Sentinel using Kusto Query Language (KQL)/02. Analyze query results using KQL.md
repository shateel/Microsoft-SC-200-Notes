## Why This Matters for SC-200

Raw log tables can contain thousands or millions of rows. `summarize` is how an analyst turns that noise into an answer, questions like "how many failed logins per user," "which computer generated the most events," or "how many unique IP addresses connected" are all answered with `summarize`. The `render` operator then turns a summarized table into a chart, which is exactly what powers **Microsoft Sentinel Workbooks**, **hunting query visualizations**, and dashboard style reporting.

> **Exam Tip:** Expect SC-200 questions that give you a small sample table and a `summarize` or `render` query, and ask what the output looks like. Practicing the "before and after" habit throughout this guide is the best preparation for that question style.

## The summarize Operator

`summarize` groups similar rows together and calculates something about each group. It is the single most important operator for turning large numbers of events into meaningful statistics.

**General syntax:**

```kql
Table
| summarize AggregateFunction() by Column
```

```kql
Table
| summarize Calculation by GroupingColumn
```

Think of `summarize` as performing two steps:

```text
Rows sharing the same value in the by column
  │
  ▼
Step 1: Group similar rows together
  │
  ▼
Step 2: Perform a calculation for each group
  │
  ▼
One output row per group
```

### Worked Example

```kql
SecurityEvent
| summarize count() by Account
```

**Before:**

| EventID | Account |
|---|---|
| 4624 | John |
| 4625 | Bob |
| 4624 | John |
| 4624 | Alice |
| 4625 | Bob |
| 4624 | Bob |
| 4624 | John |

**After:**

| Account | count_ |
|---|---|
| John | 3 |
| Bob | 3 |
| Alice | 1 |

Seven individual rows become three summarized rows. Notice that `EventID` disappears entirely, `summarize` builds a **brand new table** containing only the grouping column(s) and the calculated value(s).

### summarize Exam Tips

* `summarize` replaces the original table with a completely new one, only the `by` columns and the calculated values survive.
* Always think in two steps: group first, then calculate.
* The output has exactly one row per unique group.

## Understanding the by Clause

The word `by` tells KQL how to group the rows.

* **Without `by`**, KQL treats the **entire table as one single group**.
* **With `by`**, KQL creates **multiple groups**, one for every unique value in the specified column.

### Example: Summarize Without by

```kql
SecurityEvent
| summarize count()
```

**Before:**

| EventID |
|---|
| 4624 |
| 4625 |
| 4624 |
| 4624 |
| 4625 |

**After (no by clause, the whole table is one group):**

| count_ |
|---|
| 5 |

### Example: Summarize With by

Same starting table, this time grouped by `EventID`.

```kql
SecurityEvent
| summarize count() by EventID
```

**Before:**

| EventID |
|---|
| 4624 |
| 4625 |
| 4624 |
| 4624 |
| 4625 |

**After (grouped by EventID, two groups form):**

| EventID | count_ |
|---|---|
| 4624 | 3 |
| 4625 | 2 |

> **Exam Tip:** One of the most common SC-200 trick questions is "what happens if you remove the `by` clause." Remember: **no `by` means the whole table collapses into a single group and a single result row.**

### by Clause Exam Tips

* `by` is what turns one big calculation into many small, grouped calculations.
* The number of output rows always equals the number of unique values in the `by` column (or unique combinations, if multiple columns are used).

## Summarize Without an Aggregate Function

You can use `summarize by Column` with **no aggregate function at all**. This groups the rows but does not calculate anything, the result is effectively a list of **distinct values**.

```kql
SecurityEvent
| summarize by Activity
```

**Before:**

| Activity |
|---|
| Logon |
| Logoff |
| Logon |
| File Access |
| Logoff |
| Logon |

**After:**

| Activity |
|---|
| Logon |
| Logoff |
| File Access |

Every repeated `Activity` value collapses into a single row. This behaves like a distinct or unique values list.

> **Exam Tip:** `summarize by Column` (no aggregate function) is functionally similar to asking "what are all the distinct values in this column."

## Grouping by Multiple Columns

`summarize` can group by **more than one column at once**. Each **unique combination** of the grouping columns becomes its own group.

```kql
SecurityEvent
| where EventID == 4688
| summarize count() by Process, Computer
```

**Before:**

| EventID | Process | Computer |
|---|---|---|
| 4688 | `cmd.exe` | `PC-01` |
| 4688 | `cmd.exe` | `PC-01` |
| 4688 | `cmd.exe` | `PC-02` |
| 4688 | `chrome.exe` | `PC-01` |
| 4688 | `chrome.exe` | `PC-01` |
| 4688 | `chrome.exe` | `PC-02` |
| 4688 | `powershell.exe` | `PC-01` |

`| where EventID == 4688` does not remove any rows here, every row already matches. The real transformation happens at `summarize`, which groups by **both** `Process` and `Computer` together, not by either column alone.

**After:**

| Process | Computer | count_ |
|---|---|---|
| `cmd.exe` | `PC-01` | 2 |
| `cmd.exe` | `PC-02` | 1 |
| `chrome.exe` | `PC-01` | 2 |
| `chrome.exe` | `PC-02` | 1 |
| `powershell.exe` | `PC-01` | 1 |

Five distinct `Process` and `Computer` combinations produce five groups, even though there are only three unique process names and two unique computers.

### Multiple Column Grouping Exam Tips

* Grouping by two columns is **not** the same as grouping by each column separately, groups form from the **combination**.
* This pattern is common in real investigations: "which process ran on which computer, and how often."

## Naming the Result Column

By default, `count()` automatically creates a column named **`count_`**. You can override this by naming the calculation yourself.

```kql
SecurityEvent
| summarize count() by Account
```

**Default naming:**

| Account | count_ |
|---|---|
| John | 10 |
| Alice | 5 |

```kql
SecurityEvent
| summarize cnt = count() by Account
```

**Custom naming, same underlying calculation:**

| Account | cnt |
|---|---|
| John | 10 |
| Alice | 5 |

Only the column header changes, from the automatic `count_` to the analyst chosen `cnt`. This pattern, `NewName = Function()`, works for every aggregate function, not just `count()`.

> **Exam Tip:** Naming your aggregate columns (`applicationCount = dcount(...)`, `cnt = count()`) makes downstream `where`, `order by`, and `project` steps far easier to read, and is common in Microsoft's own sample detection queries.

## Common Aggregate Functions Reference

`summarize` becomes powerful because of the aggregate functions available to it.

| Function | What It Calculates |
|---|---|
| `count()` | Number of rows in the group |
| `dcount()` | Number of distinct (unique) values in a column |
| `avg()` | Average (mean) of a numeric column |
| `max()` | Largest value in a numeric column |
| `min()` | Smallest value in a numeric column |
| `sum()` | Total of a numeric column |
| `percentile()` | The value below which a given percentage of data falls |
| `stdev()` | Standard deviation, how spread out the values are from the average |
| `variance()` | Variance, the square of the standard deviation |

### Illustrative Example: avg, min, max, and sum Together

```kql
Table
| summarize AvgResponse = avg(ResponseTime),
            MinResponse = min(ResponseTime),
            MaxResponse = max(ResponseTime),
            TotalResponse = sum(ResponseTime)
```

**Before:**

| Account | ResponseTime |
|---|---|
| John | 120 |
| Alice | 340 |
| Bob | 90 |
| David | 500 |
| Eve | 210 |

**After:**

| AvgResponse | MinResponse | MaxResponse | TotalResponse |
|---|---|---|---|
| 252 | 90 | 500 | 1260 |

All five rows collapse into a single result row (no `by` clause), and each aggregate function calculates its own statistic across the whole `ResponseTime` column.

### Aggregate Function Exam Tips

* `count()` counts rows; `dcount()` counts **unique** values, they are not interchangeable.
* `avg()`, `min()`, `max()`, and `sum()` only work on numeric columns.
* Multiple aggregate calculations can be combined in a single `summarize` statement, separated by commas.

## dcount(): Counting Unique Values

`dcount()` counts **distinct (unique)** values in a column, duplicate values only count once.

```kql
SecurityEvent
| summarize dcount(IPAddress)
```

**Before:**

| IPAddress |
|---|
| 10.0.0.1 |
| 10.0.0.2 |
| 10.0.0.1 |
| 10.0.0.3 |
| 10.0.0.2 |

**After:**

| dcount_ |
|---|
| 3 |

Even though there are **5 rows**, there are only **3 unique IP addresses**, `10.0.0.1`, `10.0.0.2`, and `10.0.0.3` each count once no matter how many times they repeat.

> **Exam Tip:** `count()` would have returned `5` here (every row counted). `dcount()` returns `3` (only unique values counted). This distinction is a favorite SC-200 exam trap.

## Full Detection Query Walkthrough: Password Spray Pattern

This is a real style Microsoft Sentinel detection query. It demonstrates `let`, `where`, `dcount()`, and a second `where`, all chained together to detect a specific attack pattern.

**What is this query trying to detect?** An attacker who knows a user's password but does not know which Microsoft application the account can access might try signing into Outlook, Teams, SharePoint, OneDrive, Azure Portal, and Power BI, all using the same username. A normal user typically mistypes a password in **one** application. An attacker generates failed logins across **multiple** applications from the same IP address.

```kql
let timeframe = 30d;
let threshold = 1;
SigninLogs
| where TimeGenerated >= ago(timeframe)
| where ResultDescription has "Invalid password"
| summarize applicationCount = dcount(AppDisplayName) by UserPrincipalName, IPAddress
| where applicationCount >= threshold
```

**In plain English:** look at the last 30 days of sign in logs, keep only invalid password failures, count how many different applications each user and IP address combination tried, then keep only the combinations that met or exceeded the threshold.

### Step 1 and 2: The let Statements

```kql
let timeframe = 30d;
let threshold = 1;
```

These two lines create reusable variables, `timeframe = 30 days` and `threshold = 1`. Nothing in the table has been touched yet.

### Step 3: The Starting Table

```text
SigninLogs
```

| TimeGenerated | UserPrincipalName | IPAddress | AppDisplayName | ResultDescription |
|---|---|---|---|---|
| 2 days ago | `john@contoso.com` | `10.1.1.10` | Outlook | Invalid password |
| 2 days ago | `john@contoso.com` | `10.1.1.10` | Teams | Invalid password |
| 2 days ago | `john@contoso.com` | `10.1.1.10` | SharePoint | Invalid password |
| 5 days ago | `alice@contoso.com` | `10.1.1.20` | Outlook | Success |
| 40 days ago | `bob@contoso.com` | `10.1.1.30` | Outlook | Invalid password |

### Step 4: `| where TimeGenerated >= ago(timeframe)`

`timeframe` resolves to `30d`, so this becomes `where TimeGenerated >= ago(30d)`, keep only events from the last 30 days.

**After:**

| TimeGenerated | UserPrincipalName | IPAddress | AppDisplayName | ResultDescription |
|---|---|---|---|---|
| 2 days ago | `john@contoso.com` | `10.1.1.10` | Outlook | Invalid password |
| 2 days ago | `john@contoso.com` | `10.1.1.10` | Teams | Invalid password |
| 2 days ago | `john@contoso.com` | `10.1.1.10` | SharePoint | Invalid password |
| 5 days ago | `alice@contoso.com` | `10.1.1.20` | Outlook | Success |

Bob's event is removed because it is 40 days old, older than the 30 day window.

### Step 5: `| where ResultDescription has "Invalid password"`

The `has` operator checks whether a string **contains a whole term**. This keeps only rows whose `ResultDescription` mentions `"Invalid password"`.

**After:**

| UserPrincipalName | IPAddress | AppDisplayName | ResultDescription |
|---|---|---|---|
| `john@contoso.com` | `10.1.1.10` | Outlook | Invalid password |
| `john@contoso.com` | `10.1.1.10` | Teams | Invalid password |
| `john@contoso.com` | `10.1.1.10` | SharePoint | Invalid password |

Alice's row is removed because her login was a `Success`, not an invalid password failure.

### Step 6: `| summarize applicationCount = dcount(AppDisplayName) by UserPrincipalName, IPAddress`

Looking at John's remaining events, three different `AppDisplayName` values appear: Outlook, Teams, SharePoint, so `dcount(AppDisplayName)` returns `3`.

**After:**

| UserPrincipalName | IPAddress | applicationCount |
|---|---|---|
| `john@contoso.com` | `10.1.1.10` | 3 |

The new column is named `applicationCount` because the query explicitly wrote `applicationCount = dcount(AppDisplayName)`.

### Step 7: `| where applicationCount >= threshold`

`threshold` resolves to `1`, so this becomes `where applicationCount >= 1`.

**Final Result:**

| UserPrincipalName | IPAddress | applicationCount |
|---|---|---|
| `john@contoso.com` | `10.1.1.10` | 3 |

> **Note:** This example uses `ago()` on relative times such as "2 days ago" to simplify the walkthrough. In a real workspace, `TimeGenerated` holds actual timestamps, for example `2026-07-23 10:15:32`, and `ago(30d)` is calculated against the current date automatically.

### The Detection Logic as a Workflow

```text
Attacker knows a password but not which app the
account can access
  │
  ▼
Attacker tries signing in to multiple Microsoft apps
using the same username and password
  │
  ▼
Each failed attempt logs an "Invalid password" event
in SigninLogs
  │
  ▼
KQL counts distinct AppDisplayName values per
UserPrincipalName and IPAddress (dcount)
  │
  ▼
If the distinct app count meets or exceeds the
threshold, the user and IP are flagged
  │
  ▼
SOC analyst investigates the flagged account for a
password spray or credential testing attack
```

### dcount Detection Query Exam Tips

* This pattern, `let` variables, time filtering, a text filter with `has`, `dcount()` grouped by two columns, then a final `where` on the calculated value, is a common shape for real Sentinel analytics rules.
* `has` matches whole terms and is generally faster than `contains`, which matches any substring.
* Grouping by **both** `UserPrincipalName` and `IPAddress` together ties the suspicious pattern to a specific user **and** a specific source location.

## arg_max() and arg_min(): Finding the Latest or Oldest Event

`arg_max()` returns the **entire row** that has the largest value in a specified column. SOC analysts most commonly use it with `TimeGenerated` or `Timestamp` to retrieve the **most recent event** per group.

**Syntax:**

```kql
Table
| summarize arg_max(ColumnName, *) by GroupColumn
```

* `ColumnName`, find the maximum value of this column.
* `*`, return all columns from that winning row, not just the maximum value itself.
* `GroupColumn`, find one winning row for each unique value.

### Example 1: Latest Event per User

```kql
SecurityEvent
| summarize arg_max(TimeGenerated, *) by Account
```

**Before:**

| TimeGenerated | Account | EventID | Computer |
|---|---|---|---|
| 10:00 | John | 4624 | `PC-01` |
| 10:15 | Alice | 4624 | `PC-02` |
| 10:30 | John | 4625 | `PC-01` |
| 10:45 | Bob | 4624 | `PC-03` |
| 11:00 | Alice | 4634 | `PC-02` |
| 11:20 | John | 4624 | `PC-01` |

For each account, KQL finds the row with the latest `TimeGenerated`: John's latest is `11:20`, Alice's latest is `11:00`, Bob's latest is `10:45`. It returns the **whole row**, not just the timestamp.

**After:**

| Account | TimeGenerated | EventID | Computer |
|---|---|---|---|
| John | 11:20 | 4624 | `PC-01` |
| Alice | 11:00 | 4634 | `PC-02` |
| Bob | 10:45 | 4624 | `PC-03` |

### Example 2: Combine with where First

```kql
SecurityEvent
| where Computer == "SQL10.na.contosohotels.com"
| summarize arg_max(TimeGenerated, *) by Computer
```

**Before (already filtered to one computer):**

| TimeGenerated | Computer | EventID | Account |
|---|---|---|---|
| 09:00 | `SQL10.na.contosohotels.com` | 4624 | John |
| 10:15 | `SQL10.na.contosohotels.com` | 4625 | Bob |
| 11:30 | `SQL10.na.contosohotels.com` | 4634 | Alice |

**After:**

| TimeGenerated | Computer | EventID | Account |
|---|---|---|---|
| 11:30 | `SQL10.na.contosohotels.com` | 4634 | Alice |

### arg_min(): The Opposite of arg_max()

`arg_min()` works exactly like `arg_max()`, except it returns the row with the **smallest** value, usually the **oldest** event.

```kql
SecurityEvent
| summarize arg_min(TimeGenerated, *) by Account
```

**Before:**

| TimeGenerated | Account | EventID | Computer |
|---|---|---|---|
| 09:00 | John | 4624 | `PC-01` |
| 09:30 | John | 4625 | `PC-01` |
| 10:15 | Alice | 4624 | `PC-02` |
| 11:20 | John | 4634 | `PC-01` |
| 11:40 | Alice | 4625 | `PC-02` |

**After:**

| Account | TimeGenerated | EventID | Computer |
|---|---|---|---|
| John | 09:00 | 4624 | `PC-01` |
| Alice | 10:15 | 4624 | `PC-02` |

### arg_max / arg_min Exam Tips

* `arg_max()` finds the row with the **largest** value in a column, typically the most recent event.
* `arg_min()` finds the row with the **smallest** value in a column, typically the oldest event.
* Both return the **entire row** when `*` is used, not just the column being compared.

## Why Operator Order Changes the Result

The exact same starting table can produce **two different results** depending on whether `where` runs **before** or **after** `summarize arg_max()`. This is one of the most important lessons in this guide.

**Starting table for both statements:**

| TimeGenerated | Account | EventID |
|---|---|---|
| 09:00 | John | 4624 |
| 10:00 | John | 4625 |
| 09:15 | Alice | 4624 |
| 11:00 | Alice | 4624 |
| 09:30 | Bob | 4625 |
| 10:30 | Bob | 4624 |

### Statement 1: summarize First, Then where

```kql
SecurityEvent
| summarize arg_max(TimeGenerated, *) by Account
| where EventID == 4624
```

**Step 1, `summarize` finds each account's latest event:**

| Account | TimeGenerated | EventID |
|---|---|---|
| John | 10:00 | 4625 |
| Alice | 11:00 | 4624 |
| Bob | 10:30 | 4624 |

**Step 2, `where EventID == 4624` filters that result:**

| Account | TimeGenerated | EventID |
|---|---|---|
| Alice | 11:00 | 4624 |
| Bob | 10:30 | 4624 |

John disappears, because his **latest** event happened to be a `4625`, not a `4624`.

### Statement 2: where First, Then summarize

```kql
SecurityEvent
| where EventID == 4624
| summarize arg_max(TimeGenerated, *) by Account
```

**Step 1, `where EventID == 4624` keeps only login events:**

| TimeGenerated | Account | EventID |
|---|---|---|
| 09:00 | John | 4624 |
| 09:15 | Alice | 4624 |
| 11:00 | Alice | 4624 |
| 10:30 | Bob | 4624 |

**Step 2, `summarize` finds each remaining account's latest `4624` event:**

| Account | TimeGenerated | EventID |
|---|---|---|
| John | 09:00 | 4624 |
| Alice | 11:00 | 4624 |
| Bob | 10:30 | 4624 |

This time John **does** appear, because among only his `4624` events, `09:00` is his latest.

```text
Statement 1: summarize, then where          Statement 2: where, then summarize
  │                                            │
  ▼                                            ▼
Find each account's overall latest event    Keep only EventID 4624 rows first
  │                                            │
  ▼                                            ▼
Then keep only rows where EventID == 4624   Then find each account's latest
  │                                          remaining (4624 only) event
  ▼                                            │
Result: John is dropped                        ▼
(his latest event was a 4625)               Result: John is kept
                                             (his latest 4624 event survives)
```

> **Exam Tip:** This is a classic SC-200 concept: **KQL operators run in the exact order they are written**, and reordering `where` and `summarize` can change which rows survive. Always trace the pipeline top to bottom rather than assuming the result is the same either way.

## make_list() and make_set(): Collecting Values into Arrays

Both functions collect all the values of a column into a **JSON array** (a list of values inside square brackets, for example `["John","Alice","Bob"]`), used together with `summarize`.

| Function | Keeps Duplicates? |
|---|---|
| `make_list()` | Yes, every occurrence is preserved |
| `make_set()` | No, only unique values remain |

### make_list() Example

```kql
SecurityEvent
| where EventID == 4624
| summarize make_list(Account) by Computer
```

**Before:**

| Computer | EventID | Account |
|---|---|---|
| `PC-01` | 4624 | John |
| `PC-01` | 4624 | Bob |
| `PC-01` | 4624 | John |
| `PC-02` | 4624 | Alice |
| `PC-02` | 4624 | Bob |
| `PC-02` | 4625 | Alice |

`| where EventID == 4624` removes the last row (`PC-02, 4625, Alice`) first.

**After:**

| Computer | list_Account |
|---|---|
| `PC-01` | `["John","Bob","John"]` |
| `PC-02` | `["Alice","Bob"]` |

John appears **twice** in the `PC-01` list, `make_list()` does not remove duplicates.

### make_set() Example

```kql
SecurityEvent
| where EventID == 4624
| summarize make_set(Account) by Computer
```

**Before:**

| Computer | EventID | Account |
|---|---|---|
| `PC-01` | 4624 | John |
| `PC-01` | 4624 | Bob |
| `PC-01` | 4624 | John |
| `PC-02` | 4624 | Alice |
| `PC-02` | 4624 | Bob |
| `PC-02` | 4624 | Alice |

**After:**

| Computer | set_Account |
|---|---|
| `PC-01` | `["John","Bob"]` |
| `PC-02` | `["Alice","Bob"]` |

John appears **only once** for `PC-01`, and Alice appears **only once** for `PC-02`, duplicates were removed.

### make_list / make_set Exam Tips

* Both functions require `summarize` and a `by` grouping column.
* `make_list()` preserves every occurrence, including duplicates.
* `make_set()` removes duplicates, keeping only unique values.
* Useful for investigation reports, for example "list every account that logged into this computer" in a single readable row instead of many separate rows.

## The render Operator and Visualizations

`render` tells KQL to display the query results as a chart instead of a plain table. It is always placed **at the end of a query**, since it formats the final result rather than transforming data further.

**General syntax:**

```kql
Table
| summarize ...
| render ChartType
```

SOC analysts often investigate thousands of log records, a chart can immediately reveal patterns, such as which user has the highest number of events, that would be easy to miss while scanning rows.

### Bar Chart

```kql
SecurityEvent
| summarize count() by Account
| render barchart
```

**Before render (after summarize):**

| Account | count_ |
|---|---|
| John | 3 |
| Bob | 3 |
| Alice | 1 |

**After render, a horizontal bar chart:**

```text
John   ████████████ 3
Bob    ████████████ 3
Alice  ████         1
```

### Time Chart

A **timechart** is a line chart designed for time series data, one of the most commonly used charts in Microsoft Sentinel. Raw logs may contain thousands of individual timestamps, plotting every single one would create a cluttered, unreadable chart. Instead, `bin()` rounds timestamps down into fixed size groups before `summarize` counts events per group.

**Syntax:**

```kql
bin(Column, Interval)
```

```kql
bin(TimeGenerated, 1d)
```

```kql
SecurityEvent
| summarize count() by bin(TimeGenerated, 1d)
| render timechart
```

**Step 1, `bin(TimeGenerated, 1d)` rounds every timestamp down to the start of its day:**

| Original Timestamp | Rounded to 1 Day |
|---|---|
| 2026-07-20 09:10 | 2026-07-20 |
| 2026-07-20 10:45 | 2026-07-20 |
| 2026-07-20 16:30 | 2026-07-20 |
| 2026-07-21 08:20 | 2026-07-21 |
| 2026-07-21 11:15 | 2026-07-21 |
| 2026-07-22 13:40 | 2026-07-22 |

**Step 2, `summarize count() by bin(TimeGenerated, 1d)` groups the rounded dates:**

| TimeGenerated | count_ |
|---|---|
| 2026-07-20 | 3 |
| 2026-07-21 | 2 |
| 2026-07-22 | 1 |

**Step 3, `render timechart` displays a line chart:**

```text
Events
3 │●
  │ \
2 │  ●
  │   \
1 │    ●
  └──────────────
   Jul20 Jul21 Jul22
```

```text
Raw timestamps (thousands of individual values)
  │
  ▼
bin(TimeGenerated, 1d) rounds each one down to its day
  │
  ▼
summarize count() by bin(...) groups identical days
  │
  ▼
render timechart draws a line chart of events per day
```

> **Exam Tip:** `bin()` is almost always paired with `summarize` before a `timechart`. Without binning, a time series query on raw timestamps produces far too many distinct groups to chart cleanly.

### Chart Type Quick Reference

| Chart Type | `render` Keyword | Best For |
|---|---|---|
| Bar chart | `barchart` | Comparing totals across categories, horizontal bars |
| Time chart | `timechart` | Trends over time, typically paired with `bin()` |
| Column chart | `columnchart` | Comparing totals across categories, vertical bars |
| Pie chart | `piechart` | Showing proportions of a whole, as percentages |
| Area chart | `areachart` | Trends over time with emphasis on volume or growth |
| Scatter chart | `scatterchart` | Relationship between two numeric values |

### render Exam Tips

* `render` must come **last** in the query, after any `summarize` or `bin()` steps.
* `bin()` is the standard way to prepare raw timestamps for a `timechart`.
* Choosing the right chart type is itself an exam relevant skill: proportions favor `piechart`, trends over time favor `timechart` or `areachart`, category comparisons favor `barchart` or `columnchart`, and relationships between two numbers favor `scatterchart`.

## SC-200 Last Minute Revision

A one page cheat sheet for the day before the exam.

### Key Definitions

| Term | Definition |
|---|---|
| `summarize` | Groups similar rows together and calculates a value for each group |
| `by` clause | Defines which column(s) form the groups; omitting it treats the whole table as one group |
| `count_` | The default column name KQL creates for `count()`, unless renamed |
| `bin()` | Rounds a value (commonly a timestamp) down into fixed size groups |
| `render` | Displays query results as a chart instead of a table; always the final operator |

### Aggregate Function Quick Reference

| Function | Counts or Calculates | Duplicates |
|---|---|---|
| `count()` | Number of rows | Counted every time |
| `dcount()` | Number of unique values | Counted once |
| `avg()` | Average of a numeric column | n/a |
| `sum()` | Total of a numeric column | n/a |
| `min()` / `max()` | Smallest / largest value | n/a |
| `arg_min()` / `arg_max()` | Entire row with the smallest / largest value in a column | n/a |
| `make_list()` | All values as a JSON array | Kept |
| `make_set()` | All values as a JSON array | Removed |

### Frequently Confused Concepts

| Concept A | Concept B | Key Difference |
|---|---|---|
| `count()` | `dcount()` | `count()` counts every row; `dcount()` counts only unique values |
| `make_list()` | `make_set()` | `make_list()` keeps duplicates; `make_set()` removes them |
| `arg_max()` | `arg_min()` | `arg_max()` returns the row with the largest value (often latest); `arg_min()` returns the row with the smallest value (often oldest) |
| `summarize` then `where` | `where` then `summarize` | Can produce **different results**, always trace operator order top to bottom |
| `summarize by Column` | `summarize count() by Column` | The first lists distinct values with no calculation; the second also counts how many rows are in each |
| `has` | `contains` | `has` matches a whole term and is faster; `contains` matches any substring |

### Important KQL Syntax to Memorize

```kql
Table
| summarize count() by Column
```

```kql
Table
| summarize cnt = count() by Column
```

```kql
Table
| summarize arg_max(TimeGenerated, *) by GroupColumn
```

```kql
Table
| summarize count() by bin(TimeGenerated, 1d)
| render timechart
```

### The Complete Mental Model

```text
Raw log rows (potentially millions)
  │
  ▼
summarize groups rows and calculates per group
(count, dcount, avg, arg_max, make_list, and so on)
  │
  ▼
Optional bin() rounds timestamps into clean intervals
  │
  ▼
Optional render turns the grouped result into a chart
  │
  ▼
The SOC analyst spots patterns, trends, and outliers
that individual rows would never reveal
```

> **Final Exam Tip:** Whenever a question shows a `summarize` query, first identify the `by` column (or columns) to know how many groups will form, then identify the aggregate function to know what is being calculated for each group. If `where` appears both before and after `summarize`, trace the pipeline in the exact order written, since reordering changes the result, as shown in the arg_max comparison above.
