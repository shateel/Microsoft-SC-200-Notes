## Why This Matters for SC-200

Real investigations rarely live in a single table. An account compromise might show up in `SecurityEvent`, `SigninLogs`, and `SecurityAlert` at the same time. Microsoft Sentinel gives analysts two different tools for working across tables:

* `union`, **stack** rows from multiple tables into one combined result.
* `join`, **match** rows from two tables based on a shared column, side by side.

> **Exam Tip:** The single most tested concept in this guide is the difference between `union` (stacking) and `join` (matching). Keep that distinction in mind through every example below.

---

## The union Operator

`union` combines two or more tables into a single result by returning **all rows** from each table, think of it as **stacking one table underneath another**. If Table A has 100 rows and Table B has 50 rows, `union` returns 150 rows (assuming no filtering).

**General syntax:**

```kql
Table1
| union Table2
```

### Worked Example

```kql
SecurityEvent
| union SigninLogs
```

**Before, two separate tables:**

`SecurityEvent`

| EventID | Account |
|---|---|
| 4624 | John |
| 4625 | Bob |
| 4624 | Alice |

`SigninLogs`

| User | Result |
|---|---|
| David | Success |
| Emma | Failure |

**After, all rows stacked into one combined table:**

| EventID | Account | User | Result |
|---|---|---|---|
| 4624 | John | | |
| 4625 | Bob | | |
| 4624 | Alice | | |
| | | David | Success |
| | | Emma | Failure |

Rows are appended underneath each other, not merged side by side. Since `SecurityEvent` has no `User` or `Result` columns, and `SigninLogs` has no `EventID` or `Account` columns, KQL builds one combined schema and fills every column that a given row does not have with **null (blank)**.

### union Exam Tips

* `union` **stacks** rows, it never compares or matches values between tables.
* The output row count is the sum of the input row counts (before any further filtering).
* Columns that do not exist in a given source table become **null** for that table's rows.
* `union` works even when the two tables have completely different columns.

## Running summarize After union

Operators placed after `union` run on the **combined** dataset, not on the original tables separately.

```kql
SecurityEvent
| union SigninLogs
| summarize count()
| project count_
```

**Step 1, read `SecurityEvent`:**

| EventID | Account |
|---|---|
| 4624 | John |
| 4625 | Bob |
| 4624 | Alice |

**Step 2, `union SigninLogs` appends every row from `SigninLogs`:**

| EventID | Account | User | Result |
|---|---|---|---|
| 4624 | John | | |
| 4625 | Bob | | |
| 4624 | Alice | | |
| | | David | Success |
| | | Emma | Failure |

There are now 5 rows in the combined table.

**Step 3, `summarize count()` counts every row:**

| count_ |
|---|
| 5 |

`summarize` builds a brand new table, the original `EventID`, `Account`, `User`, and `Result` columns are gone, only the calculated `count_` remains.

**Step 4, `project count_`:**

| count_ |
|---|
| 5 |

There was already only one column, so `project count_` changes nothing here, it simply confirms which column to keep.

```text
SecurityEvent (3 rows)
  │
  ▼
| union SigninLogs      (append 2 more rows, 5 total)
  │
  ▼
| summarize count()     (collapse to 1 row, count_ = 5)
  │
  ▼
| project count_        (already 1 column, nothing changes)
  │
  ▼
Final Result: count_ = 5
```

## Union a Table with the Summary of Another Table

`union` can combine a full table with the **summarized result** of another table, by writing a subquery inside parentheses.

```kql
SecurityEvent
| union (
    SigninLogs
    | summarize count()
    | project count_
)
```

**Step 1, read `SecurityEvent`:**

| EventID | Account |
|---|---|
| 4624 | John |
| 4625 | Bob |
| 4624 | Alice |

**Step 2, run the subquery in parentheses on `SigninLogs`:**

`SigninLogs`

| User | Result |
|---|---|
| David | Success |
| Emma | Failure |

After `summarize count()`, then `project count_`:

| count_ |
|---|
| 2 |

**Step 3, append the subquery's single summarized row to `SecurityEvent`:**

| EventID | Account | count_ |
|---|---|---|
| 4624 | John | |
| 4625 | Bob | |
| 4624 | Alice | |
| | | 2 |

`SecurityEvent` contributes all of its individual rows, while `SigninLogs` contributes only **one summarized row**. Since the two results have different columns, KQL again creates one combined schema and fills missing values with null.

### Subquery union Exam Tips

* A parenthesized subquery after `union` can contain its own full pipeline, `where`, `summarize`, `project`, and so on, before being appended.
* This pattern is useful for appending a single summary statistic (like a total count) alongside detailed rows from another table.

## Using Wildcards with union

The `*` character is a **wildcard**. `Security*` means "select every table whose name starts with `Security`."

**Example workspace tables:**

| Table Name | Matches `Security*`? |
|---|---|
| `SecurityEvent` | Yes |
| `SecurityAlert` | Yes |
| `SigninLogs` | No |
| `DeviceEvents` | No |

### Worked Example (Microsoft's Example)

```kql
union Security*
| summarize count() by Type
```

**Before, two matching tables:**

`SecurityEvent`

| EventID | Account | Type |
|---|---|---|
| 4624 | John | Event |
| 4625 | Bob | Event |

`SecurityAlert`

| AlertName | Severity | Type |
|---|---|---|
| Malware | High | Alert |
| Phishing | Medium | Alert |

**Step 1, `Security*` finds every matching table:** `SecurityEvent` and `SecurityAlert` (`SigninLogs` and `DeviceEvents` are excluded, their names do not start with `Security`).

**Step 2, `union` appends all rows:**

| EventID | Account | AlertName | Severity | Type |
|---|---|---|---|---|
| 4624 | John | | | Event |
| 4625 | Bob | | | Event |
| | | Malware | High | Alert |
| | | Phishing | Medium | Alert |

**Step 3, `summarize count() by Type` groups by the existing `Type` column:**

| Type | count_ |
|---|---|
| Event | 2 |
| Alert | 2 |

> **Important:** `Type` was **not created** by `union`, it already existed as a real column in both source tables. `union` only works this cleanly when the tables share a meaningful common column.

### Wildcard union Exam Tips

* `Security*` matches every table whose name **starts with** `Security`, not tables that merely contain the word.
* Wildcard `union` is useful for querying an entire family of related tables (for example all `Security*` tables, or all `Device*` tables) in one statement.
* Grouping after a wildcard `union` only works if the matched tables share a common column to group by.

## Labeling Rows by Source Table with withsource

Many tables do **not** share a common column like `Type` that identifies where each row came from. Without help, a wildcard `union` can make it impossible to tell which table a row originated from.

### The Problem

```kql
union DeviceEvents, SigninLogs
```

**Before:**

`DeviceEvents`

| DeviceName |
|---|
| `PC-01` |
| `PC-02` |

`SigninLogs`

| User |
|---|
| John |
| Alice |

**After, ambiguous result:**

| DeviceName | User |
|---|---|
| `PC-01` | |
| `PC-02` | |
| | John |
| | Alice |

Looking at this result alone, there is no column that says which table each row came from.

### The Solution: withsource

```kql
union withsource=SourceTable DeviceEvents, SigninLogs
```

**After, with the origin labeled:**

| SourceTable | DeviceName | User |
|---|---|---|
| `DeviceEvents` | `PC-01` | |
| `DeviceEvents` | `PC-02` | |
| `SigninLogs` | | John |
| `SigninLogs` | | Alice |

`withsource=SourceTable` creates a **new column**, here named `SourceTable`, and labels every row with the name of the table it came from, **before** the tables are combined.

### Combined Example: Wildcard union with withsource

```kql
union withsource=SourceTable Security*
| summarize count() by SourceTable
```

**Before:**

`SecurityEvent`

| EventID | Account | Type |
|---|---|---|
| 4624 | John | Event |
| 4625 | Bob | Event |

`SecurityAlert`

| AlertName | Severity | Type |
|---|---|---|
| Malware | High | Alert |
| Phishing | Medium | Alert |

**Step 1, `Security*` finds `SecurityEvent` and `SecurityAlert`.**

**Step 2, `withsource=SourceTable` labels every row before combining:**

| SourceTable | EventID | Account | AlertName | Severity | Type |
|---|---|---|---|---|---|
| `SecurityEvent` | 4624 | John | | | Event |
| `SecurityEvent` | 4625 | Bob | | | Event |
| `SecurityAlert` | | | Malware | High | Alert |
| `SecurityAlert` | | | Phishing | Medium | Alert |

**Step 3, `summarize count() by SourceTable` groups by the new label:**

| SourceTable | count_ |
|---|---|
| `SecurityEvent` | 2 |
| `SecurityAlert` | 2 |

### withsource Exam Tips

* `withsource=ColumnName` is the fix for ambiguous `union` results when tables do not already share an identifying column.
* The labeling happens **before** the union combines the rows, so the new column is available immediately for grouping or filtering.
* This is especially useful with wildcard `union` across many tables at once.

## The join Operator

Unlike `union`, which **stacks** rows, `join` **matches** rows between two tables based on a shared column value.

```text
Left Table row
  │
  ▼
Compare the key column value
  │
  ▼
Right Table row with a matching key
  │
  ▼
Merged row (columns from both tables combined)
```

**Simple concept example:**

`SecurityEvent` contains: John, Alice, Bob
`SigninLogs` contains: John, David

| Account | In Both Tables? |
|---|---|
| John | Yes, matched |
| Alice | No |
| Bob | No |
| David | No |

Only `John` appears in both tables, so a basic (inner) join returns only `John`.

### Join Syntax

```kql
LeftTable
| join [JoinParameters] (
    RightTable
) on JoinColumn
```

```kql
LeftTable
| join kind=inner (
    RightTable
) on User
```

| Part | Meaning |
|---|---|
| `LeftTable` | The first table, referred to as the **left table** |
| `RightTable` | The table inside the parentheses, referred to as the **right table** |
| `kind` | Specifies how rows should be matched, see the reference table below |
| `on JoinColumn` | Specifies which column to compare, for example `on User` compares `Left.User` with `Right.User` |

> **Exam Tip:** The table written **before** the pipe into `join` is always the left table. The table written **inside the parentheses** is always the right table. This ordering matters for `leftouter`, `rightouter`, `leftanti`, `rightanti`, `leftsemi`, and `rightsemi`.

### join Exam Tips

* `join` compares a specified column between two tables and keeps only the rows KQL is told to keep, based on `kind`.
* `on Column` compares `Left.Column` with `Right.Column`.
* If no `kind` is specified, KQL defaults to `innerunique`.

---

## Join Kinds Reference

| Kind | What It Returns |
|---|---|
| `inner` | Only rows where the key matches in **both** tables |
| `leftouter` | All rows from the left table; matched right columns filled in where possible, otherwise null |
| `rightouter` | All rows from the right table; matched left columns filled in where possible, otherwise null |
| `fullouter` | All rows from **both** tables; unmatched columns become null |
| `leftsemi` | Only left rows that **have** a match, right columns are not included |
| `rightsemi` | Only right rows that **have** a match, left columns are not included |
| `leftanti` | Left rows that **do not** have a match in the right table |
| `rightanti` | Right rows that **do not** have a match in the left table |
| `innerunique` | The **default** when no `kind` is specified; behaves like `inner`, but first reduces the left table to one row per distinct key before matching |

> **Exam Tip:** Memorize the pattern: `left...` keeps left rows, `right...` keeps right rows, `...anti` keeps the **unmatched**, `...semi` keeps the **matched but only from one side**, `full...` keeps everything, `inner` keeps only what is common to both.

---

## Worked Example: Inner Join

```kql
SigninLogs
| join kind=inner (
    UserInfo
) on User
```

**Left table, `SigninLogs`:**

| User | Result |
|---|---|
| John | Success |
| Bob | Failure |
| Alice | Success |

**Right table, `UserInfo`:**

| User | Department |
|---|---|
| John | HR |
| Alice | IT |
| David | Finance |

**Comparing the `User` column:**

| User | In SigninLogs? | In UserInfo? | Result |
|---|---|---|---|
| John | Yes | Yes | Matched |
| Bob | Yes | No | Dropped |
| Alice | Yes | Yes | Matched |
| David | No | Yes | Dropped (inner join ignores unmatched right rows) |

**After, only matching rows survive, merged side by side:**

| User | Result | Department |
|---|---|---|
| John | Success | HR |
| Alice | Success | IT |

Bob is dropped because he has no matching row in `UserInfo`. David is dropped because he has no matching row in `SigninLogs`. This is exactly what `inner` means, keep only what exists on **both** sides.

## Full Example: Joining Logon and Logoff Counts

This is the Microsoft Learn style example, and one of the richest patterns in this guide, it combines `where`, `summarize`, `project`, and `join` into one investigation query.

```kql
SecurityEvent
| where EventID == "4624"
| summarize LogOnCount = count() by EventID, Account
| project LogOnCount, Account
| join kind=inner (
    SecurityEvent
    | where EventID == "4634"
    | summarize LogOffCount = count() by EventID, Account
    | project LogOffCount, Account
) on Account
```

**What it does:** counts successful logons (`4624`) and logoffs (`4634`) per account, then joins the two counts together using the `Account` column.

**Starting table, `SecurityEvent`:**

| EventID | Account |
|---|---|
| 4624 | John |
| 4624 | John |
| 4624 | Alice |
| 4624 | Bob |
| 4634 | John |
| 4634 | John |
| 4634 | Alice |
| 4634 | David |

### Building the Left Table

**Step 1, `where EventID == "4624"`:**

| EventID | Account |
|---|---|
| 4624 | John |
| 4624 | John |
| 4624 | Alice |
| 4624 | Bob |

**Step 2, `summarize LogOnCount = count() by EventID, Account`:**

| EventID | Account | LogOnCount |
|---|---|---|
| 4624 | John | 2 |
| 4624 | Alice | 1 |
| 4624 | Bob | 1 |

**Step 3, `project LogOnCount, Account`, this becomes the left table:**

| Account | LogOnCount |
|---|---|
| John | 2 |
| Alice | 1 |
| Bob | 1 |

### Building the Right Table (the Subquery)

**Step 1, `where EventID == "4634"`:**

| EventID | Account |
|---|---|
| 4634 | John |
| 4634 | John |
| 4634 | Alice |
| 4634 | David |

**Step 2, `summarize LogOffCount = count() by EventID, Account`:**

| EventID | Account | LogOffCount |
|---|---|---|
| 4634 | John | 2 |
| 4634 | Alice | 1 |
| 4634 | David | 1 |

**Step 3, `project LogOffCount, Account`, this becomes the right table:**

| Account | LogOffCount |
|---|---|
| John | 2 |
| Alice | 1 |
| David | 1 |

### Joining on Account

| Account | In Left (LogOn)? | In Right (LogOff)? | Result |
|---|---|---|---|
| John | Yes | Yes | Matched |
| Alice | Yes | Yes | Matched |
| Bob | Yes | No | Dropped |
| David | No | Yes | Dropped |

**Final Result:**

| Account | LogOnCount | LogOffCount |
|---|---|---|
| John | 2 | 2 |
| Alice | 1 | 1 |

Bob logged on but the query found no matching logoff event for him, and David logged off with no matching logon event, since `kind=inner` was used, both are dropped from the final result.

```text
SecurityEvent
  │
  ├─────────────────────────────┐
  ▼                              ▼
where EventID == "4624"      where EventID == "4634"
  │                              │
  ▼                              ▼
summarize LogOnCount by      summarize LogOffCount by
EventID, Account             EventID, Account
  │                              │
  ▼                              ▼
project LogOnCount, Account  project LogOffCount, Account
  │                              │
  └───────────────┬──────────────┘
                   ▼
        join kind=inner on Account
                   │
                   ▼
   Account | LogOnCount | LogOffCount
   (only accounts present in both branches)
```

> **Exam Tip:** This pattern, filter, summarize, and project the **same source table twice** with different conditions, then `join` the two results together, is a very common way to compare two categories of events (logon vs logoff, success vs failure, before vs after a change) for the same set of entities.

### Full Example Exam Tips

* A subquery inside a `join`'s parentheses can be a **complete multi step pipeline**, not just a raw table name.
* Renaming aggregate columns (`LogOnCount`, `LogOffCount`) before the join makes the final result immediately readable, avoiding two confusingly named `count_` columns.
* With `kind=inner`, any account missing from either branch is dropped entirely from the final result.

## union vs join

| | `union` | `join` |
|---|---|---|
| What it does | **Stacks** rows underneath each other | **Matches** rows side by side using a key column |
| Requires a shared column? | No, mismatched columns become null | Yes, an `on` column is required |
| Typical output row count | Sum of both tables' row counts | Depends on the `kind` and how many keys match |
| Common use case | Searching across several related tables at once | Enriching one dataset with details from another (for example adding department info to a sign in log) |

```text
union: stacking                         join: matching
  Table A rows                            Left Table row
    │                                       │
    ▼                                       ▼
  Table B rows appended                   Compare key column
  underneath                                │
    │                                       ▼
    ▼                                     Matching Right Table row
  Combined table, all rows                  │
  from both, unmatched                      ▼
  columns are null                        Merged row, columns
                                           from both tables
```

> **Exam Tip:** If a scenario says "search across multiple log tables for the same keyword" or "combine records from several tables," think `union`. If it says "enrich," "cross reference," "match," or "combine details from two related tables," think `join`.

## SC-200 Last Minute Revision

A one page cheat sheet for the day before the exam.

### Key Definitions

| Term | Definition |
|---|---|
| `union` | Combines two or more tables by stacking (appending) all their rows into one result |
| `join` | Combines two tables by matching rows on a shared key column |
| `withsource=Column` | Labels each row, before a `union`, with the name of the table it came from |
| Wildcard `*` | Matches every table whose name starts with the given prefix, for example `Security*` |
| Left table | The table written before the pipe into `join` |
| Right table | The table written inside the `join`'s parentheses |
| `on Column` | Specifies which column `join` uses to compare `Left.Column` with `Right.Column` |

### union vs join Quick Reference

| | union | join |
|---|---|---|
| Action | Stack rows | Match rows |
| Needs a shared key column | No | Yes (`on Column`) |
| Missing values become | null | Depends on `kind` |

### Join Kinds Quick Reference

| Kind | Keeps |
|---|---|
| `inner` | Matches only |
| `leftouter` | All left rows |
| `rightouter` | All right rows |
| `fullouter` | All rows from both |
| `leftsemi` | Matched left rows only (no right columns) |
| `rightsemi` | Matched right rows only (no left columns) |
| `leftanti` | Unmatched left rows only |
| `rightanti` | Unmatched right rows only |
| `innerunique` | Default; like inner, deduplicated on the left key first |

### Frequently Confused Concepts

| Concept A | Concept B | Key Difference |
|---|---|---|
| `union` | `join` | `union` stacks rows underneath each other; `join` matches rows side by side on a key |
| `inner` | `leftouter` | `inner` keeps only matches; `leftouter` keeps every left row regardless of a match |
| `leftsemi` | `leftouter` | `leftsemi` keeps matched left rows **without** adding right columns; `leftouter` keeps all left rows **with** right columns added where matched |
| `leftanti` | `rightanti` | `leftanti` returns left rows with **no** match on the right; `rightanti` returns right rows with **no** match on the left |
| `union Table1, Table2` | `union withsource=Col Table1, Table2` | The first gives no way to tell which row came from which table; the second adds a labeled column showing the origin |

### Important KQL Syntax to Memorize

```kql
Table1
| union Table2
```

```kql
union withsource=SourceTable Prefix*
| summarize count() by SourceTable
```

```kql
LeftTable
| join kind=inner (
    RightTable
) on JoinColumn
```

```kql
SecurityEvent
| where EventID == "4624"
| summarize LogOnCount = count() by Account
| project LogOnCount, Account
| join kind=inner (
    SecurityEvent
    | where EventID == "4634"
    | summarize LogOffCount = count() by Account
    | project LogOffCount, Account
) on Account
```

### The Complete Mental Model

```text
Multiple related tables across the workspace
  │
  ▼
Need every matching keyword or event type?
Use union to stack the rows together
  │
  ▼
Need to enrich or cross reference one dataset
with details from another? Use join to match
rows on a shared key column
  │
  ▼
Combined or matched result feeds summarize,
where, project, and render for investigation
```

> **Final Exam Tip:** When a scenario question describes searching, combining, or reporting across multiple tables, first decide: does the question want **every row from every table stacked together** (`union`), or does it want **rows from two tables lined up and merged based on a shared value** (`join`)? That single decision resolves most multiple table questions on the SC-200 exam.
