## Why This Matters for SC-200

Not every useful piece of information sits neatly in its own column. Sometimes it is buried inside one long text string, packed into a JSON object, or sitting in a file outside Sentinel entirely, like a threat intelligence feed. This guide covers the KQL tools that turn that messy or external data into something you can filter, group, and investigate, exactly like a native column.

> **Exam Tip:** SC-200 tests whether you recognize which tool fits which situation: `extract()` for one value from free text, `parse` for several values from a consistent pattern, dot notation for JSON, `externaldata` for outside files, and functions for reusable queries.

---

## Structured vs Unstructured Data

**Structured data**, every value already has its own column.

`SecurityEvent`

| Account | IPAddress | Port | Action |
|---|---|---|---|
| John | 192.168.1.10 | 443 | Allow |
| Alice | 10.10.10.5 | 80 | Block |

Easy to search directly:

```kql
SecurityEvent
| where Account == "John"
```

**Unstructured data**, everything is packed inside one string.

`SecurityLogs`

| LogMessage |
|---|
| `User=John IP=192.168.1.10 Port=443 Action=Allow` |
| `User=Alice IP=10.10.10.5 Port=80 Action=Block` |

You cannot write `where Account == "John"` here, there is **no Account column**, only one long `LogMessage` string. The value must first be **extracted**.

| Tool | Best For |
|---|---|
| `extract()` | Pulling out **one** specific value using a regular expression (regex) |
| `parse` | Pulling out **several** values at once from a consistent, known text pattern |

### Structured vs Unstructured Exam Tips

* If you need **one** value from messy text, reach for `extract()`.
* If you need **several** values from a text pattern that repeats the same way every time, reach for `parse`.

## The extract() Function

`extract()` searches a string using a **regular expression (regex)** and returns the matching part.

**Syntax:**

```kql
extract(regex, captureGroup, text)
```

```kql
extract(regex, captureGroup, text, typeof(long))
```

| Argument | Meaning |
|---|---|
| `regex` | The pattern to search for, for example `IP=([0-9.]+)` means "find `IP=` followed by numbers and dots" |
| `captureGroup` | Which part of the regex match to return |
| `text` | The column or string to search inside |
| `typeLiteral` (optional) | Converts the extracted value to another type, for example `typeof(long)` or `typeof(datetime)` |

**captureGroup values:**

| Value | Returns |
|---|---|
| `0` | The entire match |
| `1` | The **first** `()` capture group |
| `2` | The **second** `()` capture group |
| `3` | The **third** `()` capture group |

### Worked Example: Extract a Username

```kql
SecurityLogs
| extend Username = extract(@"User=(\w+)", 1, LogMessage)
```

`regex`: `User=(\w+)`, meaning "the text `User=` followed by one or more word characters, captured as group 1."

**Before:**

| LogMessage |
|---|
| `User=John IP=192.168.1.10 Port=443 Action=Allow` |
| `User=Alice IP=10.10.10.5 Port=80 Action=Block` |
| `User=Bob IP=172.16.5.20 Port=22 Action=Allow` |

**After:**

| LogMessage | Username |
|---|---|
| `User=John IP=192.168.1.10 Port=443 Action=Allow` | John |
| `User=Alice IP=10.10.10.5 Port=80 Action=Block` | Alice |
| `User=Bob IP=172.16.5.20 Port=22 Action=Allow` | Bob |

Nothing was removed, `extend` only **added** a column, exactly like every other `extend` example in this guide.

### extract() Exam Tips

* `extract()` is almost always paired with `extend`, since it produces a single value that becomes a new column.
* `captureGroup 0` returns the whole match; `1`, `2`, `3` return only the text inside the corresponding parentheses in the regex.
* If the regex does not match a given row at all, the extracted value becomes null for that row.

## Full Walkthrough: Extracting a Username with Regex

This is the Microsoft Learn style example, extracting a clean username out of several messy `Account` formats at once.

```kql
SecurityEvent
| where EventID == 4672 and AccountType == "User"
| extend Account_Name = extract(@"^(.*\\)?([^@]*)(@.*)?$", 2, tolower(Account))
| summarize LoginCount = count() by Account_Name
| where Account_Name != ""
| where LoginCount < 10
```

**Purpose:** extract only the username portion from the `Account` field, convert it to lowercase, count logins per user, remove any blank extractions, and keep only users with fewer than 10 logins, useful for spotting rarely used privileged accounts.

**Before:**

| EventID | Account | AccountType |
|---|---|---|
| 4672 | `CONTOSO\John` | User |
| 4672 | `CONTOSO\Alice` | User |
| 4672 | `John@contoso.com` | User |
| 4672 | `Bob@contoso.com` | User |

### Breaking Down the Regex

`^(.*\\)?([^@]*)(@.*)?$`

| Part | Pattern | Matches |
|---|---|---|
| Anchors | `^` and `$` | Start and end of the entire string |
| Part 1 | `(.*\\)?` | An **optional** domain prefix, for example `CONTOSO\` |
| Part 2, capture group 2 | `([^@]*)` | The username itself, any characters that are **not** `@`, for example `John` |
| Part 3 | `(@.*)?` | An **optional** domain suffix, for example `@contoso.com` |

Capture group `2` is what `extract()` returns, since that is the piece surrounded by the optional domain prefix and optional email suffix, the username itself.

### Stage 1: after `extend Account_Name = extract(...)`

| Account | Account_Name |
|---|---|
| `CONTOSO\John` | john |
| `CONTOSO\Alice` | alice |
| `John@contoso.com` | john |
| `Bob@contoso.com` | bob |

Every format, domain style or email style, resolves to the same clean, lowercase username.

### Stage 2: after `summarize LoginCount = count() by Account_Name`

| Account_Name | LoginCount |
|---|---|
| john | 2 |
| alice | 1 |
| bob | 1 |

### Stage 3: after `where Account_Name != ""`

| Account_Name | LoginCount |
|---|---|
| john | 2 |
| alice | 1 |
| bob | 1 |

No rows were removed in this sample, but this step exists to drop any row where the regex failed to extract a username at all, which would otherwise appear as a blank group.

### Stage 4 (Final Result): after `where LoginCount < 10`

| Account_Name | LoginCount |
|---|---|
| john | 2 |
| alice | 1 |
| bob | 1 |

All three accounts stay, since each logged fewer than 10 times, this final filter is what narrows a busy environment down to accounts using privileged logon rights unusually rarely, worth a closer look.

```text
SecurityEvent
  │
  ▼
| where EventID == 4672 and AccountType == "User"
  │
  ▼
| extend Account_Name = extract(regex, 2, tolower(Account))
  │
  ▼
| summarize LoginCount = count() by Account_Name
  │
  ▼
| where Account_Name != ""
  │
  ▼
| where LoginCount < 10
  │
  ▼
Final Result: rarely used privileged accounts
```

### Full Walkthrough Exam Tips

* `tolower()` is commonly combined with `extract()` so that `John` and `john` are treated as the same account.
* A single, well built regex can normalize several different text formats (domain style and email style accounts) into one clean value.
* Chaining `where Account_Name != ""` after an extraction is a standard defensive step, always expect that some rows will fail to match.

## The parse Operator

`parse` reads a string and splits it into **several** new columns at once, based on a known, repeating text pattern.

**Syntax:**

```kql
Table
| parse Column with
    "Prefix1" NewColumn1
    "Prefix2" NewColumn2
    "Prefix3" NewColumn3
```

### Worked Example

```kql
SecurityLogs
| parse LogMessage with
    "User=" Username
    " IP=" IPAddress
    " Port=" Port
```

**Before:**

| LogMessage |
|---|
| `User=John IP=192.168.1.10 Port=443` |
| `User=Alice IP=10.10.10.5 Port=80` |

**How it reads row 1:** find `User=`, capture everything up to the next marker into `Username` (`John`), find ` IP=`, capture into `IPAddress` (`192.168.1.10`), find ` Port=`, capture into `Port` (`443`).

**After:**

| LogMessage | Username | IPAddress | Port |
|---|---|---|---|
| `User=John IP=192.168.1.10 Port=443` | John | 192.168.1.10 | 443 |
| `User=Alice IP=10.10.10.5 Port=80` | Alice | 10.10.10.5 | 80 |

### parse Exam Tips

* `parse` extracts **multiple** columns in a single step, `extract()` normally returns only one.
* `parse` relies on the text markers (`"User="`, `" IP="`, `" Port="`) appearing in the same order every time, it is best suited to consistent, predictable log formats.

## Working with JSON and Dynamic Fields

Sometimes a single column stores **multiple values inside one string**, already organized into keys and values, this is called **structured string data**, commonly **JSON** (JavaScript Object Notation).

```json
{
    "operatingSystem":"Windows 11",
    "browser":"Chrome",
    "deviceId":"ABC123"
}
```

A **Dynamic** field is a column that stores this kind of structured data, a JSON object, a JSON array, or key and value pairs, instead of one plain value.

### Dot Notation

To pull a single value out of a Dynamic field, use `.` followed by the key name.

| Expression | Result |
|---|---|
| `DeviceDetail.browser` | `Chrome` |
| `DeviceDetail.operatingSystem` | `Windows 11` |

### Worked Example

```kql
SigninLogs
| extend OS = DeviceDetail.operatingSystem
```

**Before:**

| Identity | DeviceDetail |
|---|---|
| John | `{"browser":"Chrome","operatingSystem":"Windows 11"}` |
| Alice | `{"browser":"Edge","operatingSystem":"Windows 10"}` |
| Bob | `{"browser":"Firefox","operatingSystem":"Ubuntu"}` |

For each row, KQL looks inside the `DeviceDetail` JSON object for the key `operatingSystem` and returns its value.

**After:**

| Identity | DeviceDetail | OS |
|---|---|---|
| John | `{"browser":"Chrome","operatingSystem":"Windows 11"}` | Windows 11 |
| Alice | `{"browser":"Edge","operatingSystem":"Windows 10"}` | Windows 10 |
| Bob | `{"browser":"Firefox","operatingSystem":"Ubuntu"}` | Ubuntu |

### JSON / Dynamic Field Exam Tips

* Dot notation (`Column.key`) is the standard way to read a value out of a Dynamic JSON column, no regex needed.
* Dynamic fields are common in `SigninLogs` (`DeviceDetail`, `LocationDetails`) and many Defender XDR tables.
* If a key does not exist in a given row's JSON, the result for that row is null.

## The externaldata Operator

Normally KQL only queries data already inside your Log Analytics Workspace. `externaldata` reads data from an **outside storage location**, such as a CSV file in Azure Blob Storage, while you define the table's schema directly in the query.

### Why Use It

Imagine a Threat Intelligence team sends a `malicious_ips.csv` file every morning, and your firewall logs already live in Sentinel as `CommonSecurityLog`. Instead of importing the CSV into Sentinel first, `externaldata` reads it directly, on demand, inside the query.

```text
CSV file in Azure Blob Storage
  │
  ▼
externaldata reads the file using the
column schema you define
  │
  ▼
Temporary KQL table (exists only for
the duration of this query)
  │
  ▼
join, where, or search against your
existing Sentinel tables
```

Nothing is permanently imported, the table exists only while the query runs.

### Syntax

```kql
externaldata (ColumnName: ColumnType [, ...])
[
    StorageConnectionString
]
[with (PropertyName = PropertyValue [, ...])]
```

```kql
externaldata(IPAddress:string)
[
    @"https://storage.blob.core.windows.net/ioc/malicious_ips.csv"
]
```

| Part | Meaning |
|---|---|
| `externaldata` | Read data from an external file |
| `IPAddress:string` | Defines the schema: one column named `IPAddress`, of type `string`. KQL does **not** inspect the file first, you must declare the columns yourself |
| `[ @"https://..." ]` | The storage connection string, where the file is located, typically Azure Blob Storage or Azure Data Lake Storage |

### Worked Example: Read an External CSV

```kql
externaldata(IPAddress:string)
[
    @"https://storage.blob.core.windows.net/ioc/malicious_ips.csv"
]
```

**Before, the file `malicious_ips.csv` sitting in Blob Storage:**

| IPAddress |
|---|
| 192.168.1.10 |
| 10.10.10.5 |
| 172.16.20.15 |

**After, the same data now available as a temporary KQL table:**

| IPAddress |
|---|
| 192.168.1.10 |
| 10.10.10.5 |
| 172.16.20.15 |

The content looks identical, but it is now a real KQL table you can filter, join, or search against, and it disappears once the query finishes.

### externaldata Exam Tips

* You must declare the column names and types yourself, `externaldata` does not read the file's header to guess them.
* The resulting table is **temporary**, it exists only for that single query execution.
* Typical sources: Azure Blob Storage or Azure Data Lake Storage.

## Full Walkthrough: Matching Logs Against a Threat Intelligence File

```kql
let IOC =
    externaldata(IPAddress:string)
    [
        @"https://storage.blob.core.windows.net/ioc/malicious_ips.csv"
    ];
CommonSecurityLog
| where SourceIP in (IOC)
```

**Step 1, `let IOC = externaldata(...)` reads the external file:**

| IPAddress |
|---|
| 192.168.1.10 |
| 172.16.20.15 |

**Step 2, the existing `CommonSecurityLog` table:**

| SourceIP | DestinationIP |
|---|---|
| 192.168.1.10 | 8.8.8.8 |
| 20.20.20.20 | 8.8.4.4 |
| 172.16.20.15 | 1.1.1.1 |

**Step 3, `where SourceIP in (IOC)` keeps only rows whose `SourceIP` appears in the external list:**

| SourceIP | Found in IOC List? |
|---|---|
| 192.168.1.10 | Yes |
| 20.20.20.20 | No |
| 172.16.20.15 | Yes |

**Final Result:**

| SourceIP | DestinationIP |
|---|---|
| 192.168.1.10 | 8.8.8.8 |
| 172.16.20.15 | 1.1.1.1 |

The connection from `20.20.20.20` is dropped, it never appeared in the threat intelligence file, while the two known malicious source IPs remain for investigation.

> **Exam Tip:** `let VariableName = externaldata(...) [...]` followed by `where Column in (VariableName)` is the standard pattern for matching Sentinel logs against an outside indicator list, exactly like the `let` plus `datatable()` watchlist pattern covered in the companion KQL construction guide, except the list comes from a real file instead of being typed inline.

## The with() Clause and SAS Tokens

### The with() Clause

Sometimes KQL needs extra information to correctly read a file.

```kql
externaldata(Column1:string, Column2:int)
[
    StorageConnectionString
]
with (
    format="csv"
)
```

`format="csv"` tells KQL explicitly that the file is CSV formatted. If `with()` is omitted, KQL tries to determine the format automatically, often from the file extension.

### What Is a SAS Token

Some storage files are private. A **Shared Access Signature (SAS) token** is a temporary key that grants access to a specific storage resource, think of it like a temporary visitor pass.

| Without a SAS Token | With a Valid SAS Token |
|---|---|
| Access denied | File can be read |

### Worked Example with a SAS Token

```kql
Users
| where UserID in (
    externaldata(UserID:string)
    [
        @"https://storageaccount.blob.core.windows.net/storagecontainer/users.txt"
        h@"?...SAS..."
    ]
)
```

This reads a text file of user IDs from Azure Blob Storage, using the SAS token for temporary authorization, then returns only the rows in `Users` whose `UserID` appears in that external file.

**Before, the `Users` table:**

| UserID |
|---|
| john |
| alice |
| bob |
| david |
| emma |

**The external file `users.txt`:**

| UserID |
|---|
| alice |
| emma |

**Comparing every user against the external file:**

| UserID | In users.txt? |
|---|---|
| john | No |
| alice | Yes |
| bob | No |
| david | No |
| emma | Yes |

**Final Result:**

| UserID |
|---|
| alice |
| emma |

### with() and SAS Token Exam Tips

* `with(format="csv")` (or `json`, `txt`, and similar) is only needed when KQL cannot infer the format from the file extension, or when you want to be explicit.
* A SAS token grants **temporary, scoped** access to a specific storage file, it is not a permanent credential.
* Without a valid SAS token on a private file, the `externaldata` call fails with an access error.

## Saving Queries as Functions (Parsers)

As queries grow longer, you may find yourself typing the same query repeatedly. KQL lets you **save a query as a function**, giving it a short, reusable name. Microsoft Learn calls these saved functions **parsers**, because they often return data that is already filtered or shaped, making future queries simpler.

### Without a Function

Every time you investigate privileged logins, you type:

```kql
SecurityEvent
| where EventID == 4672
| where AccountType == "User"
```

### Saved as a Function

Save the exact same query under a name, for example `PrivLogins`. From then on, you simply write:

```kql
PrivLogins
```

KQL automatically runs the saved query behind that name and returns the same result, no retyping required.

```text
Write a KQL query once
  │
  ▼
Save it as a Function and give it a
short name, for example PrivLogins
  │
  ▼
Call the function by name in any
future query
  │
  ▼
KQL runs the saved query automatically
```

### How Functions Are Created (Microsoft Learn Steps)

| Step | Action |
|---|---|
| 1 | Open the **Logs** window in Microsoft Sentinel |
| 2 | Write the query |
| 3 | Click **Save** |
| 4 | Choose **Save as Function** |
| 5 | Give it a name, for example `PrivLogins` |

The function is then stored in the workspace and can be reused like any table name.

### Function / Parser Exam Tips

* A function is simply a **saved query with a name**, calling the function produces the exact same result as running the original query.
* Microsoft's own **parsers** (including ASIM parsers, covered next) are built exactly this way, as saved functions.
* Saving common investigation queries as functions reduces repetition and keeps hunting queries consistent across a team.

## ASIM: Advanced Security Information Model

**ASIM** stands for **Advanced Security Information Model**, a Microsoft Sentinel framework that **normalizes logs from different vendors into a common schema**. Microsoft ships ready made ASIM parsers, which are themselves implemented as saved functions.

### Why It Is Needed

Suppose an organization has three different firewall vendors, and each one names the source IP field differently:

| Vendor | Field Name for Source IP |
|---|---|
| Cisco | `SourceIP` |
| Fortinet | `SrcIP` |
| Palo Alto | `Source_Address` |

Without ASIM, an analyst would need to write and remember three separate queries, one per vendor, using three different column names.

**After ASIM normalizes all three:**

| Vendor | Normalized Field Name |
|---|---|
| Cisco | `SourceIP` |
| Fortinet | `SourceIP` |
| Palo Alto | `SourceIP` |

Now **one single query** works across every vendor.

```text
Cisco Logs (field: SourceIP)
Fortinet Logs (field: SrcIP)
Palo Alto Logs (field: Source_Address)
  │
  ▼
ASIM Parser normalizes every vendor's
field names into one common set
  │
  ▼
Common Schema (SourceIP)
  │
  ▼
One KQL query now works across every
vendor, instead of three separate queries
```

### Memory Trick

| Term | Single Line Definition |
|---|---|
| Function | Save a query once, reuse it many times |
| Parser | A function that prepares or extracts data for you |
| ASIM | One common field naming language for logs from many different security vendors |

### ASIM Exam Tips

* ASIM solves the problem of the **same kind of data** (like a source IP) having **different column names** across vendors.
* ASIM parsers are themselves ordinary KQL functions, just published and maintained by Microsoft.
* A hunting query written against an ASIM normalized schema keeps working even if a new vendor product is added later, as long as that vendor also has an ASIM parser.

## SC-200 Last Minute Revision

A one page cheat sheet for the day before the exam.

### Key Definitions

| Term | Definition |
|---|---|
| `extract()` | Returns **one** value from a string using a regular expression |
| `parse` | Splits a string into **several** new columns using a known text pattern |
| Dynamic field | A column that stores structured data such as JSON, accessed with dot notation |
| `externaldata` | Reads an outside file (for example from Azure Blob Storage) into a temporary KQL table |
| `with()` | Supplies extra details about an external file, such as its format |
| SAS token | A temporary key granting scoped access to a private storage file |
| Function | A saved, reusable, named query |
| Parser | A function that returns data already filtered, extracted, or shaped |
| ASIM | A Microsoft Sentinel framework normalizing multiple vendors' logs into one common schema |

### extract() vs parse Quick Reference

| | `extract()` | `parse` |
|---|---|---|
| Values returned | One | Several at once |
| Uses | Regular expression | A known, repeating text pattern |
| Best for | Pulling a single field out of free text | Splitting a consistent log format into multiple fields |

### Frequently Confused Concepts

| Concept A | Concept B | Key Difference |
|---|---|---|
| `extract()` | `parse` | `extract()` returns one value with a regex; `parse` returns several values from a known pattern |
| Dot notation (`Column.key`) | `extract()` | Dot notation reads a key directly out of JSON; `extract()` is for plain text that is not already structured as JSON |
| `externaldata` | Importing data into Sentinel | `externaldata` reads the file live for one query only; nothing is stored permanently |
| Function | Parser | Every parser is a function; not every function is described as a parser, the term is used for functions that extract or shape data |
| ASIM parser | An ordinary saved function | Both are functions; ASIM parsers specifically normalize multiple vendors into one common schema and are maintained by Microsoft |

### Important KQL Syntax to Memorize

```kql
Table
| extend NewColumn = extract(@"regex", captureGroup, SourceColumn)
```

```kql
Table
| parse Column with
    "Prefix1" NewColumn1
    " Prefix2" NewColumn2
```

```kql
Table
| extend Value = DynamicColumn.keyName
```

```kql
let IOC =
    externaldata(IPAddress:string)
    [
        @"https://storageaccount.blob.core.windows.net/container/file.csv"
    ];
Table
| where SourceIP in (IOC)
```

### The Complete Mental Model

```text
Raw, messy, or external data
  │
  ▼
One value hidden in text? Use extract()
Several values in a pattern? Use parse
JSON already structured? Use dot notation
File outside Sentinel? Use externaldata
  │
  ▼
Repeating the same query often? Save it
as a Function (a Parser)
  │
  ▼
Same kind of data, different vendor field
names? Use ASIM to normalize it
  │
  ▼
Clean, structured, reusable data ready
for where, summarize, join, and render
```

> **Final Exam Tip:** When a question describes messy or outside data, first ask what shape the source is in: free text needing one value (`extract()`), free text needing several values (`parse`), already structured JSON (dot notation), or a file that lives outside Sentinel entirely (`externaldata`). Then ask whether the query will be reused often enough to justify saving it as a function, and whether the data spans multiple vendors that ASIM could normalize.
