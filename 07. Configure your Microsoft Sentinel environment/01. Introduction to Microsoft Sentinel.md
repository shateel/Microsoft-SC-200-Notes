## 1. SIEM and Microsoft Sentinel Fundamentals

### 1.1 What Is a SIEM

A **Security Information and Event Management (SIEM)** system collects, stores, analyzes, and correlates security logs from many devices and applications in order to detect threats.

A SIEM performs three primary functions:

* Collects and stores security logs.
* Analyzes and correlates events to identify suspicious activity.
* Generates alerts and incidents for security teams to investigate.

### 1.2 What Is Microsoft Sentinel

Microsoft Sentinel is a **cloud native SIEM** that runs entirely inside Microsoft Azure. It is also described as a SIEM plus SOAR platform, since it both detects threats and can automate the response to them.

Unlike a traditional SIEM, Microsoft Sentinel:

* Requires **no on premises SIEM server**.
* Requires **no hardware appliances**.
* Is deployed entirely through the **Azure portal**.
* Has its underlying infrastructure managed by **Microsoft**.

### 1.3 Traditional SIEM vs Microsoft Sentinel

| Aspect | Traditional SIEM | Microsoft Sentinel |
|---|---|---|
| Hosting | On premises servers | Fully cloud native, runs in Azure |
| Hardware | Physical appliances required | None required |
| Deployment | Manual install and configuration | Deployed through the Azure portal |
| Infrastructure management | Managed by your own team | Managed by Microsoft |
| Scaling | Limited by physical capacity | Elastic cloud scaling |

> **Exam tip.** If a question describes a SIEM that needs **no on premises hardware** and is deployed from a **portal**, the expected answer is Microsoft Sentinel.

### SC-200 Exam Tips

* Know the **three core SIEM functions**: collect, analyze and correlate, alert.
* Microsoft Sentinel is both a **SIEM** and a **SOAR** platform.
* Memorize the phrase **cloud native**, it is the key differentiator tested against legacy SIEM tools.

```text

   │

   │
```

* Exam scenarios often describe a stage of this lifecycle in plain language and ask which Sentinel feature it maps to.

## 3. Data Collection and Data Connectors

Everything in Microsoft Sentinel begins with **data ingestion**. Security data must be collected before any detection or investigation can happen.

**Workflow to enable a data source:**

```text
Content Hub Solution
      │
      ▼
Install Data Connector
      │
      ▼
Configure or Enable Connector
      │
      ▼
Logs flow into Log Analytics Workspace
```

Microsoft Sentinel uses **Data Connectors** to import logs from Microsoft services and third party products into a **Log Analytics Workspace**.

Many connectors are installed through the **Content Hub**, which bundles Microsoft and partner solutions containing connectors, analytics rules, workbooks, hunting queries, and playbooks together. Some connectors only need to be enabled with a single action, while others, such as **Syslog** and **Common Event Format (CEF)**, require additional configuration.

### Common Data Sources

| Category | Examples |
|---|---|
| Microsoft security services | Microsoft Defender XDR, Microsoft Defender for Endpoint |
| Identity | Microsoft Entra ID |
| Azure platform | Azure Activity Logs |
| On premises servers | Windows Event Logs, Linux Syslog |
| Standardized log formats | Common Event Format (CEF) |
| Threat intelligence | Threat Intelligence (TAXII) |
| Multi cloud | Amazon Web Services (AWS), Google Cloud Platform (GCP) |
| Network and security appliances | Firewalls, IDS/IPS solutions |
| Other | Third party security products |

> **Exam tip.** Know that **Syslog and CEF connectors require extra configuration** (an agent or forwarder), while many native Microsoft connectors can be enabled with one click.

### SC-200 Exam Tips

* **Content Hub = one stop shop** for connectors, rules, workbooks, hunting queries, and playbooks for a given product.
* Microsoft Defender XDR appears in the connector list because it can forward its own correlated alerts into Sentinel for centralized SOC visibility.
* Data ingestion is always the **first stage** of the Sentinel lifecycle. No detection or hunting can occur without it.

## 4. Log Analytics Workspace

When Microsoft Sentinel collects logs, **it does not store them inside Sentinel itself**. Instead, all logs are stored in an **Azure Log Analytics Workspace**, and Sentinel reads and analyzes data from that workspace.

**Data flow architecture:**

```text
Windows Server   Linux Server   Microsoft Entra ID
Microsoft Defender   Firewall   AWS   GCP
      │
      ▼
  Data Connectors
      │
      ▼
┌───────────────────────────┐
│  Log Analytics Workspace  │
│     (stores all logs)     │
└───────────────────────────┘
      │
      ▼
   Microsoft Sentinel
      │
      ├── KQL Queries
      ├── Workbooks
      ├── Analytics Rules
      ├── Threat Hunting
      ├── Incidents
      └── Playbooks
```

### What Is Stored in the Workspace

Everything collected from every connected data source, for example:

* Windows Event Logs
* Linux Syslog
* Firewall logs
* Microsoft Defender alerts
* Azure Activity Logs
* Microsoft Entra ID sign in logs
* Microsoft 365 audit logs
* AWS CloudTrail logs
* GCP logs

All of these logs sit together in **one workspace**, which is what allows KQL queries to correlate across completely different log sources.

### Why Log Storage Matters

The Log Analytics Workspace is the **central repository** for all security data. It provides long term storage, indexing, and search.

Benefits include:

* Centralized log storage
* Fast searching
* Historical investigations
* Data retention
* Advanced analytics
* Threat hunting

> **Exam tip.** The **quality of an investigation depends directly on the completeness of the collected logs.** If a scenario says an analyst cannot find evidence of an event, check whether the relevant data connector was ever enabled.

### SC-200 Exam Tips

* Sentinel is an **analysis layer on top of** the Log Analytics Workspace, it is not itself the storage layer.
* All ingested data types share one workspace, enabling cross source correlation.
* Retention and long term storage are properties of the **workspace**, not of Sentinel.

## 5. Kusto Query Language (KQL)

Microsoft Sentinel uses **Kusto Query Language (KQL)** to search and analyze security data stored in the Log Analytics Workspace.

SOC analysts use KQL to:

* Search logs
* Investigate incidents
* Perform threat hunting
* Build dashboards
* Create analytics rules
* Generate reports

> KQL is one of the **most heavily tested skills** on the SC-200 exam. Expect questions asking you to read or complete a KQL query, not just define what it is.

### SC-200 Exam Tips

* KQL underlies almost every Sentinel feature: **workbooks, analytics rules, hunting queries, and investigation** are all built on KQL queries against the workspace.
* Even where no KQL syntax is provided in a source document, expect the exam to test **reading and interpreting** basic KQL query results.

***

## 6. Workbooks

Workbooks provide **interactive dashboards** for visualizing security data. A workbook displays information using charts, graphs, maps, and metrics, all generated from underlying KQL queries.

SOC analysts use workbooks to:

* Monitor security posture
* Track attack trends
* Review authentication activity
* Visualize endpoint activity
* Measure security metrics
* Build executive dashboards

Microsoft provides many built in workbooks, and organizations can customize existing ones or build entirely new dashboards for their environment.

### SC-200 Exam Tips

* Workbooks are the **Visualize** stage of the SOC lifecycle.
* Remember the underlying data source for every workbook is a **KQL query**, workbooks do not generate their own data.

## 7. Analytics Rules

Analytics Rules analyze collected data and generate alerts when suspicious activity is detected. This is the **Detect** stage of the SOC lifecycle.

| Rule Type | Created By | Behavior | Customization |
|---|---|---|---|
| **Built in Rules** | Microsoft | Cover common, known attack techniques | Easy to deploy, limited tuning |
| **Scheduled Rules** | Analyst or organization | Run a KQL query on a defined schedule | Fully customizable |
| **Machine Learning Rules** | Microsoft (ML driven) | Use behavioral analytics to detect anomalies | Requires minimal manual tuning |
| **Fusion Rules** | Microsoft's correlation engine | Combine multiple low confidence alerts into one high confidence incident | Not manually written, ML based |

**Fusion** is worth extra attention: it uses Microsoft's machine learning and correlation engine to link separate, individually low confidence alerts into a single high confidence incident, helping surface sophisticated multi stage attacks that would otherwise look like unrelated events.

### SC-200 Exam Tips

* If a scenario describes **several unrelated low severity alerts turning into one incident automatically**, the answer is **Fusion**.
* **Scheduled rules** are the type you write yourself using KQL, this is the customizable option.
* Analytics rules are the mechanism that **create alerts**, which then become incidents.

## 8. Threat Hunting

Threat Hunting is a **proactive** activity where analysts search for threats that have **not yet triggered an alert**. Instead of waiting for an analytics rule to fire, analysts actively search historical data using KQL.

Microsoft Sentinel provides:

* Built in hunting queries
* Custom hunting queries
* Hunting bookmarks
* Integration with Azure Notebooks

Threat hunting is especially valuable for catching **advanced attackers who evade automated detection**.

### SC-200 Exam Tips

* The key distinction to memorize: **Analytics rules are reactive (wait for a trigger); Threat hunting is proactive (analyst initiated search).**
* **Bookmarks** let an analyst save interesting query results during a hunt for later reference or to build an incident.

## 9. Incidents and Investigation

When one or more alerts are generated, Microsoft Sentinel creates an **Incident**. An incident groups related alerts into a single investigation, which reduces alert fatigue and gives the analyst a complete picture of an attack.

SOC analysts can, on an incident:

* Assign it to an analyst
* Change its status
* Set its severity
* Add comments
* Record evidence
* Close it
* Escalate the investigation

Microsoft Sentinel also provides an **Investigation Graph**, which visually maps relationships between users, devices, IP addresses, files, processes, and alerts, making the full attack path easier to understand.

**Incident investigation flow:**

```text
Alert
   │
   ▼
Alert Correlation
   │
   ▼
Incident Created
   │
   ▼
Analyst Assignment & Triage
   │
   ▼
Investigation Graph
   │
   ▼
Evidence & Comments Recorded
   │
   ▼
Resolution (Closed or Escalated)
```

### SC-200 Exam Tips

* **Incident ≠ Alert.** An alert is a single detection; an incident is a **grouping** of one or more related alerts.
* The **Investigation Graph** is the visual entity relationship map, know this name specifically, it is commonly tested.

## 10. Automation and Playbooks (SOAR)

Microsoft Sentinel can respond to incidents automatically, which makes the SOC more productive. This capability set is called **security orchestration, automation, and response (SOAR)**.

Automation is implemented through three building blocks:

* **Automation Rules** decide when and how automation should run.
* **Playbooks** are the automated workflows themselves.
* **Azure Logic Apps** are the underlying engine that playbooks run on.

**How automation is triggered:**

```text
Incident or Event Occurs
        │
        ▼
   Automation Rule
        │
        ▼
      Playbook
        │
        ▼
   Azure Logic App
        │
        ▼
   Action Executed
```

Playbooks can automatically:

* Notify analysts
* Send emails
* Create ServiceNow tickets
* Enrich alerts with threat intelligence
* Disable compromised accounts
* Block malicious IP addresses
* Trigger Microsoft Defender response actions

Automation reduces repetitive manual work, shortens response times, and improves overall SOC efficiency.

### SC-200 Exam Tips

* Memorize the chain: **Automation Rule → Playbook → Azure Logic App → Action.**
* Playbooks are built on **Azure Logic Apps**, this is a very commonly tested fact.
* SOAR = **Security Orchestration, Automation, and Response**, spell out the acronym confidently.

## 11. When to Use Microsoft Sentinel (Supplementary)

The uploaded source ends immediately after this heading with no further detail. The following points are accurate, generally known context added to make the note usable, not content copied from the source:

* Organizations typically adopt Microsoft Sentinel when they want a **single cloud native SOC platform** instead of maintaining on premises SIEM hardware.
* It fits well for environments that are **already using Azure**, Microsoft 365, or Microsoft Defender products, since native connectors make ingestion simple.
* It also supports **hybrid and multi cloud** environments through AWS and GCP connectors, so it is not limited to Azure only estates.
* Because pricing is consumption based on ingested data volume, cost planning (data retention policies, connector selection) is a real world and exam relevant consideration.

## 12. SC-200 Last Minute Revision

### One Page Cheat Sheet

**Core definition.** Microsoft Sentinel is a cloud native SIEM plus SOAR platform running entirely in Azure, with no on premises hardware.

**The lifecycle to memorize cold:**

```text
Collect → Store → Visualize → Detect → Hunt → Investigate → Respond
```

**Component mapping:**

```text
Data Connectors → Log Analytics Workspace → Workbooks →
Analytics Rules → Threat Hunting → Incidents → Playbooks
```

### Quick Terminology Table

| Term | One Line Definition |
|---|---|
| SIEM | Collects, analyzes, and alerts on security logs |
| SOAR | Automates and orchestrates the response to incidents |
| Data Connector | Pipes logs from a source into the workspace |
| Log Analytics Workspace | Central Azure store for all ingested logs |
| KQL | Query language used to search and analyze logs |
| Workbook | Dashboard built from KQL query results |
| Analytics Rule | Logic that turns log data into an alert |
| Alert | A single detection of suspicious activity |
| Incident | A group of one or more related alerts |
| Investigation Graph | Visual map of entities related to an incident |
| Automation Rule | Decides when and how a playbook runs |
| Playbook | Automated response workflow, built on Logic Apps |
| Fusion | ML correlation engine linking low confidence alerts into one high confidence incident |

### Frequently Confused Concepts

| Often Confused | Clarification |
|---|---|
| Alert vs Incident | Alert = single detection. Incident = grouped set of related alerts. |
| Analytics Rule vs Playbook | Analytics rule **detects** (creates an alert). Playbook **responds** (takes action). |
| Automation Rule vs Playbook | Automation rule is the **trigger and condition logic**. Playbook is the **actual workflow** that runs. |
| Threat Hunting vs Analytics Rules | Hunting is proactive and analyst driven. Analytics rules are automatic and reactive. |
| Sentinel vs Log Analytics Workspace | Sentinel is the SIEM/SOAR application layer. The workspace is the underlying data store. |
| Scheduled Rule vs Fusion Rule | Scheduled = analyst writes the KQL manually. Fusion = Microsoft's ML engine correlates automatically. |

### Analytics Rule Types, Quick Recall

| Type | Trigger Word to Remember |
|---|---|
| Built in | "Microsoft made it, deploy as is" |
| Scheduled | "I wrote the KQL myself, runs on a timer" |
| Machine Learning | "Detects anomalies, minimal tuning" |
| Fusion | "Combines many low confidence alerts into one incident" |

### Automation Chain, Quick Recall

```text
Automation Rule → Playbook → Azure Logic App → Action
```

### Final Reminders Before the Exam

* Sentinel **never stores logs itself**, the Log Analytics Workspace does.
* **KQL is everywhere**: workbooks, hunting, analytics rules, and investigation all depend on it.
* **SOAR = Automation Rules + Playbooks + Logic Apps.**
* **Content Hub** is the packaged bundle of connector, rules, workbooks, hunting queries, and playbooks for a given product or vendor.
* Always be ready to map a scenario description back to the exact lifecycle stage: Collect, Store, Visualize, Detect, Hunt, Investigate, or Respond.
