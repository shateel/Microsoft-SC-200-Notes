## 1. Sharing a Log Analytics Workspace

Microsoft Sentinel is not a standalone database. It is deployed **on top of** a **Log Analytics Workspace**, and that same workspace can be shared with other Azure security services, most commonly **Microsoft Defender for Cloud**.

```text
Defender for Cloud          Microsoft Sentinel
            \                    /
             \                  /
              ▼                ▼
          Log Analytics Workspace
```

Both services write to and read from a single centralized data source instead of maintaining separate logs.

### Why Share a Workspace

* One central location for security logs
* Easier investigations, since analysts do not switch between workspaces
* No need to search multiple workspaces for related evidence
* Better correlation between Defender alerts and Sentinel incidents

> **Example:** Defender for Cloud flags a vulnerable virtual machine. Because the workspace is shared, Sentinel can immediately correlate that finding with sign in logs, network events, and other telemetry already stored in the same workspace.

### Defender for Cloud Consideration

You **cannot** point Microsoft Sentinel at the **default** Defender for Cloud Log Analytics Workspace. Instead:

1. Create your own Log Analytics Workspace.
2. Enable Microsoft Sentinel on it.
3. Configure Microsoft Defender for Cloud to use that same workspace.

This produces one shared, centrally managed workspace instead of relying on the default Defender workspace.

### SC-200 Exam Tips

* **Enabling Sentinel is a separate step.** Creating a Log Analytics Workspace does **not** automatically deploy Sentinel; you must add Sentinel to the workspace afterward.
* Four required inputs when creating the workspace: **Subscription**, **Resource Group**, **Workspace Name**, **Region**.
* The **Region** cannot be changed after the workspace is created, and it determines where the data physically resides.
* **Contributor** permission is required to deploy and enable Sentinel on a workspace.
* Main Sentinel navigation areas to recognize: **General**, **Threat Management**, **Content Management**, **Configuration**.
* Microsoft recommends sharing one workspace between Sentinel and Defender for Cloud when both are in use.
* The **default Defender for Cloud workspace cannot be used**; create a dedicated workspace and point Defender for Cloud to it.

## 2. Managing Multiple Sentinel Workspaces

### 2.1 Why Organizations End Up With Multiple Workspaces

* A multinational company with separate workspaces for the US, Europe, and Asia
* A bank with separate Production and Development workspaces
* A Managed Security Service Provider (MSSP) monitoring Sentinel for dozens of customers

```text
Global Company
        │
        ├── Europe Workspace
        ├── Asia Workspace
        ├── US Workspace
        ├── Research Workspace
        └── Production Workspace
```

Without a centralized way to manage these, every workspace must be configured individually, which does not scale.

### 2.2 The Cross Tenant Challenge

An **Azure Tenant** is a company's own isolated Microsoft cloud environment. Contoso normally cannot access Fabrikam's tenant, and each tenant has its own users, subscriptions, and Sentinel deployment.

> **Scenario:** An MSSP SOC monitors 150 customers, one tenant and one workspace per customer. Without a centralized tool, that means 150 separate logins, 150 dashboards, 150 sets of permissions, and constant context switching. Not practical.

Microsoft addresses this with two distinct solutions:

| Tool | Solves | Scope |
|---|---|---|
| **Microsoft Sentinel Workspace Manager** | Centrally managing and publishing Sentinel **content** | Multiple workspaces, typically within reach of one or more tenants |
| **Azure Lighthouse** | Securely managing Azure **resources** across tenants without separate sign ins | Multiple **tenants** |

### 2.3 Microsoft Sentinel Workspace Manager

Workspace Manager centrally manages multiple Sentinel workspaces from one **Central Workspace**, which distributes content to **Member Workspaces**. Think of it as a headquarters managing several branch offices.

```text
                Central Workspace
               /        │        \
              ▼         ▼         ▼
        Workspace A  Workspace B  Workspace C
```

It publishes:

* Analytics rules
* Hunting queries
* Automation rules
* Watchlists
* Workbooks
* Other Sentinel content

Supported architecture patterns: **Simple/Direct-Link**, **Co-Management**, and **N-Tier**.

> **Example:** Your SOC builds a new ransomware detection rule.
>
> Without Workspace Manager, you recreate the rule separately in every workspace:
>
> ```text
> Workspace A → Create Rule
> Workspace B → Create Rule
> Workspace C → Create Rule
> Workspace D → Create Rule
> ```
>
> With Workspace Manager, you create it once and publish it everywhere:
>
> ```text
>         Create Rule
>              │
>              ▼
>       Central Workspace
>              │
>              ▼
>           Publish
>              │
>       ┌──────┼──────┬──────┐
>       ▼      ▼      ▼      ▼
>      A       B      C      D
> ```

### 2.4 Azure Lighthouse

Workspace Manager only manages **Sentinel content**. It does not solve access **across different Azure tenants**. That is the job of **Azure Lighthouse**, which lets administrators securely manage Azure resources, including Sentinel workspaces, in other tenants without a separate sign in for each one.

```text
           MSSP Tenant
                │
                ▼
        Azure Lighthouse
                │
        ┌───────┼───────┐
        ▼       ▼       ▼
   Customer A  Customer B  Customer C
```

The administrator signs in **once** and securely manages authorized resources across all customer tenants.

### 2.5 Workspace Manager vs Azure Lighthouse

| | Microsoft Sentinel Workspace Manager | Azure Lighthouse |
|---|---|---|
| Manages | Sentinel **content** (rules, workbooks, queries) | Azure **resources** across tenants |
| Best for | Keeping configuration consistent across workspaces | MSSPs accessing customer subscriptions securely |
| Easy way to remember | **Content Management** | **Cross Tenant Resource Management** |

### SC-200 Exam Tips

* Organizations run multiple Sentinel workspaces for regional, departmental, environment (Prod/Dev), or multi customer reasons.
* **Workspace Manager** = centrally manage and **publish content** to Member Workspaces from a Central Workspace.
* **Azure Lighthouse** = **delegated, cross tenant access** to Azure resources, commonly used by MSSPs.
* If a question is about publishing analytics rules or workbooks to many workspaces, think **Workspace Manager**. If it is about accessing a customer's tenant without separate credentials, think **Azure Lighthouse**.
* Know the supported Workspace Manager architectures: **Simple/Direct-Link**, **Co-Management**, **N-Tier**.

## 3. Microsoft Sentinel Permissions and Roles

### 3.1 Azure RBAC Fundamentals

**Azure Role Based Access Control (Azure RBAC)** is Azure's authorization system. Instead of giving every analyst administrator rights, RBAC assigns permissions through roles, following the **Principle of Least Privilege**.

```text
       User
        │
        ▼
       Role
        │
        ▼
     Resource
```

> **Example:** Alice is assigned **Microsoft Sentinel Reader** on the SOC Workspace. Result: Alice can investigate data but cannot modify detection rules. Bob is assigned **Microsoft Sentinel Contributor** on the same workspace, so he can create analytics rules, modify workbooks, and configure Sentinel.

Giving everyone full administrator rights risks accidental deletion of analytics rules, unwanted changes to data connectors, disabled automation rules, or deleted incidents. RBAC prevents this.

### 3.2 The Four Built In Sentinel Roles

| Role | Can Do | Cannot Do | Typical User |
|---|---|---|---|
| **Reader** | View incidents, workbooks, analytics rules, dashboards, logs, and alerts | Edit rules, assign or close incidents, create workbooks, change settings | Tier 1 SOC analyst (night shift monitoring) |
| **Responder** | Everything a Reader can do, plus assign incidents, change incident status, close incidents, investigate alerts | Create analytics rules, modify workbooks, configure data connectors | Tier 2 SOC analyst handling active incidents |
| **Contributor** | Everything a Responder can do, plus create and edit analytics rules, create and modify workbooks, configure Sentinel resources | (Full operational control within Sentinel) | Security engineer building detections |
| **Automation Contributor** | Lets Sentinel's **service identity** attach Playbooks to Automation Rules | Not intended for human sign in at all | Sentinel's own automation service account |

> **Exam framing:** Reader = view only. Responder = Reader plus incident management. Contributor = Responder plus configuration. Automation Contributor is not a "bigger" role, it is a **different purpose** role used by the platform itself.

### 3.3 Why the Automation Contributor Role Exists

Sentinel automation runs under a **service account**, not a personal user account, which is more secure because automation does not depend on any one person's credentials.

```text
    Incident Created
            │
            ▼
     Automation Rule
            │
            ▼
         Playbook
            │
   ┌────────┼────────┐
   ▼        ▼         ▼
Disable   Notify     Create
 User      SOC       Ticket
```

The **Microsoft Sentinel Automation Contributor** role grants the service account permission to run that Playbook.

### 3.4 Custom Roles

When the built in roles are too restrictive or too permissive, create a **custom Azure RBAC role**. For example, an analyst who should view and manage incidents and view analytics rules, but never create them, does not match any built in role exactly. A custom role solves this precisely.

### 3.5 Related Roles You Must Recognize

* **Logic App Contributor** is required to create or edit **Playbooks**, because Playbooks are Azure Logic Apps, not native Sentinel objects.
* **Directory Reader** (a Microsoft Entra role) is required for **guest users** who need to assign incidents.
* Standard Azure roles (**Owner**, **Contributor**, **Reader**) and **Log Analytics** roles can also grant permissions that extend beyond the Sentinel specific roles.

> **Exam tip:** In scenario questions, always check **all** roles assigned to a user, not just the Sentinel specific one. A broader Azure role can override the limits you would expect from a Sentinel role alone.

### SC-200 Exam Tips

* Sentinel uses **Azure RBAC**, assignable at Management Group, Subscription, Resource Group, or Workspace level.
* Memorize: **Reader** (view) → **Responder** (view + manage incidents) → **Contributor** (manage incidents + configure Sentinel).
* **Automation Contributor** exists for Sentinel's own service identity to run Playbooks, not for people.
* **Logic App Contributor** is needed to build or edit Playbooks; **Directory Reader** is needed for guests assigning incidents.
* Azure level roles and Log Analytics roles can grant capability beyond what the Sentinel role name implies, since Sentinel stores its data in a Log Analytics Workspace.
* Use **custom RBAC roles** when no built in role matches the required permission set exactly.

## 4. Microsoft Sentinel Settings

### 4.1 Two Places Settings Live

Sentinel settings are split across two locations because Sentinel is built **on top of** Log Analytics: Sentinel supplies the security features, and Log Analytics supplies the storage platform.

```text
       Microsoft Sentinel
                │
   ┌────────────┼────────────┐
   ▼            ▼            ▼
Analytics   Automation   Workspace
Settings     Settings     Settings
                │
                ▼
     Log Analytics Workspace
                │
   ┌────────────┼────────────┬────────────┐
   ▼            ▼             ▼            ▼
 Log        Data          Pricing       Usage
Storage    Retention                  Monitoring
```

| Managed in | Examples |
|---|---|
| **Sentinel Settings** | Analytics settings, Automation settings, Workspace settings (how Sentinel behaves as a SIEM/SOAR) |
| **Log Analytics Workspace Settings** | Log retention, pricing tier, data usage, storage configuration |

> **Rule of thumb:** Creating an analytics rule is a **Sentinel** task. Configuring how long logs are kept is a **Log Analytics** task.

### 4.2 Log Retention

Log retention defines how long logs remain available in the workspace. Most workspaces support **30 up to 730 days (2 years)**, depending on the pricing tier.

**To change retention:**

1. Open the Log Analytics Workspace.
2. Go to **Usage and Estimated Costs**.
3. Select **Data Retention**.
4. Set the number of retention days.
5. Save.

Sentinel automatically uses the updated retention, since it reads from the same workspace.

### 4.3 Usage and Estimated Costs

| Concept | What It Shows |
|---|---|
| **Usage** | Volume of data ingested, which data sources are the largest contributors, daily and monthly totals |
| **Estimated Costs** | Projected storage cost based on ingestion volume, retention period, and pricing tier |

> **Example:** Windows Logs ingest 25 GB/day, Firewall Logs 40 GB/day, and Defender data 18 GB/day. If firewall log volume suddenly increases tenfold, both usage and estimated cost rise accordingly, letting administrators balance coverage against budget.

### SC-200 Exam Tips

* Sentinel settings and Log Analytics Workspace settings live in **different blades**; know which task belongs where.
* Retention range for most workspaces: **30 to 730 days**, tier dependent.
* Path to change retention: **Log Analytics Workspace → Usage and Estimated Costs → Data Retention**.
* Longer retention improves threat hunting, investigations, and compliance, but increases cost.
* Scenario mapping: **Analytics configuration → Sentinel settings**. **Storage, retention, pricing → Log Analytics Workspace settings**.

## 5. Configuring Logs: Data States, Table Plans, and Data Tiers

When planning log configuration, three related concepts are tested: the two **data states**, the three **table plans**, and the storage **data tiers**.

### 5.1 Data States

| State | Nickname | Availability | Used For |
|---|---|---|---|
| **Analytics Retention** | "Hot" | Immediately available | KQL queries, analytics rules, hunting, workbooks, dashboards, near real time investigations |
| **Long Term Retention** | "Cold" / archive | Not immediately available; needs a search job or restore | Compliance, audits, and future investigations at lower cost |

```text
       Analytics Retention
    (fast, active, higher cost)
                │
                ▼
      Long Term Retention
     (slower, archive, lower cost)
```

### 5.2 Log Analytics Table Plans

Every log lands in a **table**, and every table follows one of three plans.

| Plan | Cost | Query Capability | Interactive Retention | Long Term Retention | Typical Data |
|---|---|---|---|---|---|
| **Analytics** (default) | Highest | Full KQL, multiple table queries, best performance | 30 days up to 2 years | Up to 12 years | Windows Security Events, Defender logs, firewall logs, Microsoft Entra ID sign in logs |
| **Basic** | Lower | Optimized **single table** queries only; not full Sentinel feature set | 30 days | Can be extended separately | DHCP logs, DNS logs, occasionally reviewed network logs |
| **Auxiliary** | Lowest | Single table queries only; limited analytics; not for real time detection | Not specified as interactive | Long term by design | Verbose/application debug logs, detailed audit records, large compliance datasets |

> **Exam tip:** Only the **Analytics Plan** supports full analytics rules, multiple table (cross table) KQL queries, and hunting. Basic and Auxiliary trade query power for lower cost, and are best for data you rarely need to search interactively.

### 5.3 Data Tiers

| Tier | Nickname | Description | Retention |
|---|---|---|---|
| **Analytics Tier** | "Hot storage" | Primary working area for SOC analysts: alerting, analytics rules, threat hunting, workbooks, near real time detection | 30 days to 2 years active; total up to 12 years |
| **Data Lake Tier** | "Cold storage" | Microsoft's low cost layer; not for real time analytics; supports KQL jobs and notebooks; good for historical investigations | Long term, cost optimized |
| **XDR Default Tier** | Defender's own tier | Where Microsoft Defender XDR automatically stores supported threat hunting data, separate from Sentinel's own tiers; can later be ingested into the Analytics Tier | 30 days of analytics retention by default |

> **Example:** A bank must keep transaction logs for seven years for regulatory reasons. Most of that data sits in the **Data Lake Tier** rather than the (more expensive) Analytics Tier.

### 5.4 Table Types

| Type | Description | Examples |
|---|---|---|
| **Sentinel Tables** | Built in tables created by Azure services and Sentinel; fully manageable in the workspace | `AzureDiagnostics`, `SigninLogs`, `SecurityAlert` |
| **Custom Tables** | Created manually or via imports; fully manageable | Application logs, custom connectors, search result tables |
| **XDR Tables** | Owned by Microsoft Defender XDR; viewable but management is limited since Defender XDR controls them | `IdentityInfo` |

### 5.5 Supplementary Note: KQL and Table Plans

The source material did not include specific KQL queries, but the following distinction is commonly tested:

* Tables on the **Analytics Plan** support the full range of KQL, including operators that combine or correlate **multiple tables** (for example `union` or `join`), which is what analytics rules and hunting queries rely on.
* Tables on the **Basic** or **Auxiliary** plans are restricted to **optimized single table queries**, so cross table correlation and scheduled analytics rules are not available directly against that data without first considering plan or tier changes.

> This is why storing high value, frequently correlated data (sign in logs, security alerts, Defender logs) on the **Analytics Plan** matters for exam scenario questions about detection coverage.

### SC-200 Exam Tips

* **Analytics Retention** (hot) vs **Long Term Retention** (archive, needs a search job or restore) is a core distinction.
* Three table plans: **Analytics** (full features), **Basic** (lower cost, single table queries), **Auxiliary** (lowest cost, most limited).
* Three data tiers: **Analytics Tier**, **Data Lake Tier**, **XDR Default Tier**.
* **Total Retention = Analytics Retention + Long Term Retention**, up to 12 years overall for Analytics Plan data.
* Not every table can move between tiers or plans; expect scenario questions asking which plan or tier best balances **performance, retention, and cost**.
* Three table types: **Sentinel Tables** (built in), **Custom Tables** (fully manageable), **XDR Tables** (limited management, owned by Defender XDR).

## 6. SC-200 Last Minute Revision

### 6.1 One Page Cheat Sheet

```text
Log Analytics Workspace
        │
        ▼
Enable Microsoft Sentinel (manual step, needs Contributor)
        │
        ├── Share with Defender for Cloud (never the default DfC workspace)
        │
        ├── Multiple workspaces? →  Workspace Manager (content)  /  Azure Lighthouse (cross tenant access)
        │
        ├── Access control →  Azure RBAC
        │        Reader → Responder → Contributor → Automation Contributor (service identity only)
        │
        ├── Settings split →  Sentinel Settings (Analytics/Automation/Workspace)
        │                      Log Analytics Settings (Retention/Pricing/Usage)
        │
        └── Log configuration
                 ├── Data States: Analytics Retention (hot) → Long Term Retention (cold)
                 ├── Table Plans: Analytics / Basic / Auxiliary
                 └── Data Tiers: Analytics Tier / Data Lake Tier / XDR Default Tier
```

### 6.2 Key Definitions

| Term | One Line Definition |
|---|---|
| **Log Analytics Workspace** | The underlying data store Sentinel and other Azure services write logs into |
| **Microsoft Sentinel Workspace Manager** | Centrally publishes Sentinel content (rules, workbooks, queries) from a Central Workspace to Member Workspaces |
| **Azure Lighthouse** | Delegated, cross tenant management of Azure resources without separate sign ins |
| **Azure RBAC** | Role based permission model following least privilege |
| **Analytics Retention** | Hot, immediately queryable log storage |
| **Long Term Retention** | Cold, archived log storage accessed via search jobs or restore |
| **Analytics Plan** | Table plan with full KQL and analytics rule support (default, highest cost) |
| **Basic Plan** | Table plan with lower cost, single table optimized queries |
| **Auxiliary Plan** | Table plan with lowest cost, most limited query capability |
| **Analytics Tier** | Hot storage tier for real time detection and hunting |
| **Data Lake Tier** | Cold, low cost storage tier for historical investigation |
| **XDR Default Tier** | Default storage for Defender XDR threat hunting data, separate from Sentinel tiers |

### 6.3 Frequently Confused Concepts

| Easy to Confuse | The Distinction |
|---|---|
| Workspace Manager vs Azure Lighthouse | Workspace Manager moves **content** between workspaces; Lighthouse grants **access** across tenants |
| Responder vs Contributor | Responder manages **incidents**; Contributor also manages **configuration** (rules, workbooks) |
| Sentinel Settings vs Log Analytics Settings | Sentinel Settings control **security behavior**; Log Analytics Settings control **storage, retention, cost** |
| Table Plans vs Data Tiers | **Plans** (Analytics/Basic/Auxiliary) set cost and query power **per table**; **Tiers** (Analytics/Data Lake/XDR Default) describe the broader **storage layer** the data lives in |
| Analytics Retention vs Long Term Retention | Analytics Retention is interactive and immediate; Long Term Retention is archival and requires extra steps to query |

### 6.4 Role Permission Quick Table

| Action | Reader | Responder | Contributor | Automation Contributor |
|---|---|---|---|---|
| View incidents and workbooks | Yes | Yes | Yes | No (service role) |
| Assign or close incidents | No | Yes | Yes | No |
| Create or edit analytics rules | No | No | Yes | No |
| Attach Playbooks to Automation Rules | No | No | No | Yes |

### 6.5 Numbers Worth Memorizing

| Setting | Value |
|---|---|
| Standard workspace log retention range | 30 to 730 days (2 years) |
| Analytics Plan interactive retention | 30 days up to 2 years |
| Analytics Plan total retention ceiling | Up to 12 years |
| Basic Plan interactive retention | 30 days |
| XDR Default Tier analytics retention | 30 days |
| Example MSSP scale problem | 150 customers without Lighthouse = 150 logins, dashboards, and permission sets |

### 6.6 Final Reminders

> Sentinel needs a workspace **and** an explicit enable step. A workspace alone is not Sentinel.

> The **default** Defender for Cloud workspace is off limits for this integration, always create a dedicated one.

> **Automation Contributor** is for Sentinel itself, not for a human analyst's day to day account.

> When a scenario question mixes roles, check **every** assigned role (Sentinel role, Azure role, Log Analytics role, Entra role) before answering, since the most restrictive assumption is often wrong.
