## Where You Run KQL Queries

There are three main places to execute KQL in the Microsoft security ecosystem, and the exam expects you to know which one fits which scenario.

### Advanced Hunting

Advanced Hunting is Microsoft's interactive investigation interface for searching data collected by Microsoft Defender products, including:

* Microsoft Defender for Endpoint
* Microsoft Defender for Identity
* Microsoft Defender for Office 365
* Microsoft Defender for Cloud Apps
* Microsoft Sentinel (in supported scenarios)

It includes a KQL editor, schema browser, saved queries, query history, results grid, charts, and export options. It is typically used **during active investigations**.

### Data Lake Exploration

Used to query security data stored in the **Microsoft Sentinel Data Lake**. This matters when:

* Logs have aged out of the Analytics Tier.
* A historical investigation requires older data.
* A compliance or forensic case needs archived logs.

Archived data here is optimized for lower storage cost rather than real time performance, which is the opposite tradeoff of the Analytics Tier.

### The Logs Page (Log Analytics)

The **Logs** page in the Azure portal is the primary workspace for writing and running KQL against a **Log Analytics Workspace**. From here you can write and run queries, save and reopen them, create Analytics Rules, export results, and browse available tables and columns. Results appear immediately below the query.

### Quick Comparison Table

| Location | Data Source | Best For |
|---|---|---|
| Advanced Hunting | Microsoft Defender products | Interactive, active investigations |
| Data Lake Exploration | Microsoft Sentinel Data Lake | Aged out or archived / historical data |
| Logs (Azure portal) | Log Analytics Workspace | Building Analytics Rules, general querying |

> **SC 200 Exam Tips**
> * If a question mentions data that has "aged out" of the Analytics Tier or needs long term / forensic retrieval, the answer is **Data Lake Exploration**.
> * If a question is about active, interactive threat hunting across Defender products, the answer is **Advanced Hunting**.
> * If a question is about creating an Analytics Rule or general workspace querying, the answer is the **Logs** page.


## Core Microsoft Sentinel Tables (SIEM Objects)

Microsoft Sentinel stores security data in **tables** inside a **Log Analytics Workspace**. Every KQL query begins by selecting a table, so knowing which table holds which type of data is a foundational SC 200 skill.

### SecurityAlert

Stores alerts generated by **Analytics Rules**, or sent directly by certain data connectors (not every alert has to come from a rule). Typical examples: Password Spray, Impossible Travel, Malware Detected, Suspicious PowerShell, Brute Force Attack.

**Typical fields:** Alert Name, Severity, Time Generated, Alert Description, Provider, Related Entities.

**What are Analytics Rules?** They continuously analyze incoming log data using KQL, and generate an alert when conditions match. They do not always create incidents directly, alerts are generated first and may then be grouped into incidents depending on the rule configuration.

### SecurityIncident

A **Security Incident** groups one or more related alerts into a single investigation case. Incidents give the broader view of an attack; alerts identify individual suspicious activities.

**Typical fields:** Incident Name, Status, Severity, Owner, Related Alerts, Assigned Analyst.

```text
Multiple Alerts
     │
     ▼
Grouped Together
     │
     ▼
One Incident
```

### ThreatIntelligenceIndicator

Stores Indicators of Compromise (IOCs): malicious IP addresses, domains, file hashes, URLs, and email addresses. Indicators can be created manually by analysts, imported from Threat Intelligence platforms, or ingested through Data Connectors.

### Watchlist

A custom list built **by your own organization** (for example VIP users, critical servers, or approved IP addresses). Unlike threat intelligence, which stores known malicious indicators, a watchlist stores information important to your specific environment.

> **SC 200 Exam Tips**
> * Every KQL query starts by selecting a **table**.
> * **Alert = one individual detection. Incident = a collection of related alerts.**
> * `SecurityAlert` and `SecurityIncident` are Microsoft Sentinel objects, not raw log sources.
> * Expect scenario questions asking which table to query for alerts, incidents, threat intelligence, or watchlist data.


## Common Log Analytics Tables

These are the general purpose tables fed by Data Connectors from Azure, identity, on premises systems, third party devices, and Microsoft 365.

| Table | Stores | Answers the Question |
|---|---|---|
| **AzureActivity** | Azure management operations (create, delete, modify resources) | "Who changed something in Azure?" |
| **AzureDiagnostics** | Resource logs from Azure services (Firewall, Key Vault, App Gateway, Storage, SQL, Web Apps) | "What is this Azure resource doing?" |
| **AuditLogs** | Microsoft Entra ID administrative changes (user/group management, role changes) | "What administrative changes were made?" |
| **CommonSecurityLog** | CEF formatted logs from third party security devices (Palo Alto, Fortinet, Check Point, Cisco ASA) | "What did my firewall / IDS / IPS see?" |
| **McasShadowITReporting** | Microsoft Defender for Cloud Apps, Shadow IT detection | "What unapproved apps are being used?" |
| **OfficeActivity** | Microsoft 365 audit logs (Exchange Online, SharePoint Online, Teams, OneDrive, Purview) | "What happened inside Microsoft 365?" |
| **SecurityEvent** | Windows Security Event Logs | "What happened on this Windows machine?" |
| **SigninLogs** | Microsoft Entra ID sign in / authentication events | "Who logged into the cloud, and how?" |
| **Syslog** | Linux system logs | "What happened on this Linux machine?" |
| **Event** | Sysmon events (deep endpoint telemetry on Windows) | "What detailed process/file/network activity occurred?" |
| **WindowsFirewall** | Windows Defender Firewall allow/block events | "Did the local firewall allow or block this?" |

### Key Definitions

**CEF (Common Event Format):** a standardized log format used by many third party security products so that Microsoft Sentinel can process logs from different vendors consistently. Devices such as firewalls, IDS, IPS, web proxies, secure web gateways, and VPN appliances commonly forward logs in CEF into `CommonSecurityLog`.

**Shadow IT:** applications or cloud services employees use without IT department approval (personal Dropbox, Google Drive, WeTransfer, personal OneDrive, unapproved SaaS). This raises risk of data leakage, compliance violations, and unauthorized sharing, and is surfaced through `McasShadowITReporting`.

### Frequently Confused Table Pairs

| Comparison | Table A | Table B | Memory Trick |
|---|---|---|---|
| Windows login vs cloud login | **SecurityEvent** — Windows OS authentication | **SigninLogs** — Microsoft Entra ID (cloud) authentication | Windows Login → SecurityEvent, Cloud Login → SigninLogs |
| Admin changes vs authentication | **AuditLogs** — administrative changes | **SigninLogs** — authentication events | Audit = Changes, Signin = Login |
| Management vs resource operation | **AzureActivity** — who changed a resource | **AzureDiagnostics** — how a resource is behaving | Activity = admin did something, Diagnostics = the Azure service did something |

### How These Tables Work Together (Example Attack Chain)

```text
User logs into Microsoft 365
         │
         ▼
     SigninLogs
         │
         ▼
Attacker modifies Entra ID group
         │
         ▼
      AuditLogs
         │
         ▼
   Downloads malware
         │
         ▼
    OfficeActivity
         │
         ▼
  Runs malware on Windows
         │
         ▼
 SecurityEvent / Event (Sysmon)
         │
         ▼
Firewall blocks outbound traffic
         │
         ▼
WindowsFirewall / CommonSecurityLog
         │
         ▼
Azure administrator deletes VM
         │
         ▼
     AzureActivity
```

> **SC 200 Exam Tips**
> * Memorize the eleven tables above, they are the most common ones referenced in scenario based questions.
> * `SecurityEvent` is Windows, `Syslog` is Linux, `CommonSecurityLog` is third party network/security appliances.
> * `OfficeActivity` covers Microsoft 365 (Exchange, SharePoint, Teams, OneDrive), not Entra ID sign ins.
> * Choosing the correct table is one of the most tested skills in Microsoft Sentinel, since every KQL query starts with the appropriate data source.


## Microsoft Defender XDR Tables

When Microsoft Defender XDR is connected to Microsoft Sentinel, its telemetry (from Defender for Endpoint, Defender for Office 365, Defender for Identity, and Defender for Cloud Apps) lands in specialized tables. These give much richer detail than general tables like `SecurityEvent`, for example not just that PowerShell started, but who started it, the parent process, the full command line, network connections created, files modified, and registry keys changed.

### Device Tables (Endpoint)

| Table | Stores |
|---|---|
| **DeviceProcessEvents** | Process creation (process name, parent process, command line, user, timestamp). One of the most used tables for threat hunting. |
| **DeviceFileEvents** | File creation, deletion, modification, rename. |
| **DeviceNetworkEvents** | Outbound/inbound connections, DNS requests, TCP/UDP sessions. |
| **DeviceRegistryEvents** | Registry key creation, modification, deletion, often tied to malware persistence. |
| **DeviceLogonEvents** | Authentication occurring directly on the endpoint device (local logon, RDP, unlock). |
| **DeviceEvents** | General purpose endpoint security events: antivirus, Exploit Protection, Attack Surface Reduction (ASR), other endpoint protection controls. |
| **DeviceInfo** | Endpoint metadata: computer name, OS, OS version, device ID, health status. |
| **DeviceNetworkInfo** | Network configuration: IP address, MAC address, adapter, connected network, domain membership. |
| **DeviceImageLoadEvents** | DLL loading events, useful for detecting DLL injection / hijacking. |
| **DeviceFileCertificateInfo** | Digital certificate details for signed executables (signed, unsigned, trusted publisher, invalid certificate). |

### Email Tables

| Table | Stores |
|---|---|
| **EmailEvents** | Email delivery status: delivered, blocked, quarantined, spam, phishing verdict. |
| **EmailPostDeliveryEvents** | Actions taken **after** delivery, such as Zero-hour Auto Purge (ZAP), user reported phishing, and post delivery remediation. |
| **EmailUrlInfo** | URLs and hyperlinks found inside emails, including Safe Links data. |
| **EmailAttachmentInfo** | Attachment metadata: filename, file type, SHA256 hash, size. |

### Identity Tables

| Table | Stores |
|---|---|
| **IdentityLogonEvents** | Authentication events for Active Directory and Microsoft online services. |
| **IdentityDirectoryEvents** | Active Directory changes from on premises domain controllers: user creation, group membership changes, account modifications. |
| **IdentityQueryEvents** | Queries against Active Directory objects (user lookups, group enumeration, device enumeration, domain discovery), often a sign of attacker reconnaissance. |

### Cloud and Alert Tables

| Table | Stores |
|---|---|
| **CloudAppEvents** | Activity in Microsoft 365 and other connected cloud apps: logins, file sharing/downloads, app access, admin changes. |
| **AlertEvidence** | The objects **involved** in a Defender alert (files, users, devices, IP addresses, URLs), not the alert itself. |

### Frequently Confused Table Pairs

| Comparison | Table A | Table B | Memory Trick |
|---|---|---|---|
| Endpoint vs cloud authentication | **DeviceLogonEvents** — authentication on the device (Windows login, RDP) | **SigninLogs** — authentication in Microsoft Entra ID (Microsoft 365, Azure portal) | DeviceLogonEvents = device authentication, SigninLogs = cloud authentication |
| Delivery vs post delivery | **EmailEvents** — delivery and filtering decision | **EmailPostDeliveryEvents** — action taken after the email already arrived | Events = at delivery, PostDelivery = after delivery |
| Activity vs configuration | **DeviceNetworkEvents** — what the device did on the network | **DeviceNetworkInfo** — how the device is configured on the network | Events = activity, Info = configuration |

> **SC 200 Exam Tips**
> * `DeviceProcessEvents`, `DeviceNetworkEvents`, `DeviceFileEvents`, `EmailEvents`, and `IdentityLogonEvents` are the highest priority Defender XDR tables to know cold.
> * `AlertEvidence` stores the **objects tied to an alert**, not the alert record itself, that distinction is commonly tested.
> * Naming pattern: `Device` = endpoint, `Email` = mail flow, `Identity` = Active Directory / identity.
> * `IdentityQueryEvents` (enumeration/reconnaissance) is easy to confuse with `IdentityLogonEvents` (authentication), read the scenario carefully.


## Microsoft Sentinel vs Microsoft Defender XDR

There are really two categories of tables you will encounter.

**1. Microsoft Sentinel (Log Analytics) tables**, populated by Sentinel Data Connectors or Azure services: `SecurityEvent`, `SigninLogs`, `AuditLogs`, `AzureActivity`, `AzureDiagnostics`, `CommonSecurityLog`, `Syslog`, `OfficeActivity`, `SecurityAlert`, `SecurityIncident`, `ThreatIntelligenceIndicator`, `Watchlist`. Sources include Azure, Windows, Linux, firewalls, Microsoft Entra ID, Microsoft 365, and threat intelligence feeds.

```kql
SigninLogs
| where ResultType != 0
```

**2. Microsoft Defender XDR tables**, populated by Defender for Endpoint, Defender for Office 365, Defender for Identity, and Defender for Cloud Apps: `DeviceProcessEvents`, `DeviceNetworkEvents`, `DeviceFileEvents`, `DeviceRegistryEvents`, `DeviceLogonEvents`, `EmailEvents`, `EmailAttachmentInfo`, `EmailUrlInfo`, `CloudAppEvents`, `AlertEvidence`, `IdentityLogonEvents`.

```kql
DeviceProcessEvents
| where FileName == "powershell.exe"
```

### Product Roles

| Product | Role | Coverage |
|---|---|---|
| **Microsoft Sentinel** | SIEM | Brings together many sources: Windows, Linux, Azure, AWS, firewalls (Cisco, Fortinet, Palo Alto), Microsoft Defender, Microsoft 365, threat intelligence |
| **Microsoft Defender XDR** | XDR platform | Deep visibility limited to Microsoft's own security ecosystem (Endpoint, Office 365, Identity, Cloud Apps) |

### How the Data Connects

```text
Microsoft Defender XDR
         │
         │  Data Connector
         ▼
Log Analytics Workspace
         │
         ▼
   Microsoft Sentinel
```

Once the Defender XDR data connector is enabled, Defender telemetry is copied into the Log Analytics Workspace, and Microsoft Sentinel can then query it like any other table.

**Can Defender XDR query Sentinel tables?** Generally, **no**. Microsoft Defender XDR cannot query the full range of Microsoft Sentinel tables the way Sentinel can query Defender XDR data, because the products serve different roles: Sentinel is a SIEM that collects and correlates data broadly, while Defender XDR is an XDR platform focused specifically on Microsoft security product telemetry.

> **SC 200 Exam Tips**
> * The data flow is one directional in practice for the exam: **Defender XDR → Log Analytics Workspace → Sentinel**, enabled by the Defender XDR data connector.
> * If a question asks whether Defender XDR can natively query Sentinel only tables, the expected answer is **no**.
> * Know which table list belongs to Sentinel versus Defender XDR, this distinction is directly tested.


## Memory Techniques for Table Names

Five ways to recall which table to query, useful when the exam gives you a scenario instead of a table name.

### Method 1 (Best): Group by Data Source

* **Azure:** `AzureActivity` (administrator did something) vs `AzureDiagnostics` (Azure service did something).
* **Microsoft Entra ID:** `SigninLogs` (login) vs `AuditLogs` (changes).
* **Windows:** `SecurityEvent` (Windows) vs `Event` (Sysmon).
* **Linux:** only `Syslog`.
* **Third party security devices** (Palo Alto, Fortinet, Cisco, Check Point): `CommonSecurityLog`.
* **Microsoft 365** (Exchange, SharePoint, Teams, OneDrive): `OfficeActivity`.
* **Microsoft Sentinel objects** (not OS logs): `SecurityAlert` → alerts, `SecurityIncident` → incidents, `ThreatIntelligenceIndicator` → IOCs, `Watchlist` → custom lists.

Think of the Sentinel objects as a chain: **Alert → Incident → IOC → Watchlist**.

### Method 2: Follow the Investigation Flow

Think like a SOC analyst following an attack timeline rather than memorizing isolated names.

* User logs in → `SigninLogs`
* User/group modified → `AuditLogs`
* PowerShell starts → `SecurityEvent` or `DeviceProcessEvents`
* Malware calls out to an attacker → `CommonSecurityLog` or `DeviceNetworkEvents`
* Phishing email arrives → `EmailEvents`
* Malware creates/modifies files → `DeviceFileEvents`
* Malware sets persistence → `DeviceRegistryEvents`

### Method 3: Recognize the Defender XDR Naming Pattern

* Anything starting with **Device** = endpoint activity (`DeviceProcessEvents`, `DeviceFileEvents`, `DeviceNetworkEvents`, `DeviceRegistryEvents`, `DeviceLogonEvents`, `DeviceEvents`, `DeviceInfo`, `DeviceNetworkInfo`, `DeviceImageLoadEvents`). Formula: **Device + what happened**.
* Anything starting with **Email** = email activity (`EmailEvents`, `EmailAttachmentInfo`, `EmailUrlInfo`, `EmailPostDeliveryEvents`).
* Anything starting with **Identity** = Active Directory / identity activity (`IdentityLogonEvents`, `IdentityDirectoryEvents`, `IdentityQueryEvents`).

### Method 4: Ask "Where Did It Happen?"

* Logged into Microsoft 365 → `SigninLogs`
* PowerShell executed on a computer → `DeviceProcessEvents`
* Firewall blocked a connection → `CommonSecurityLog`
* VM deleted in Azure → `AzureActivity`
* Registry key modified → `DeviceRegistryEvents`
* SharePoint file deleted → `OfficeActivity`


## Supplementary: Core KQL Query Structure

*(Added for completeness: this is standard KQL syntax that supports every table discussed above, since the exam consistently pairs "which table" questions with "which query" questions.)*

Every KQL query follows the same basic shape, table first, then piped operators:

```text
TableName
     │
     ▼
| where ...        (filter rows)
     │
     ▼
| project ...       (choose columns)
     │
     ▼
| summarize ...     (aggregate, e.g. count(), by user or IP)
     │
     ▼
| order by ...      (sort results)
```

| Operator | Purpose | Example |
|---|---|---|
| `where` | Filter rows by a condition | `SecurityEvent \| where EventID == 4625` |
| `project` | Return only specific columns | `SigninLogs \| project TimeGenerated, UserPrincipalName` |
| `summarize` | Aggregate rows, often with `count()` | `DeviceProcessEvents \| summarize count() by FileName` |
| `extend` | Add a calculated column | `EmailEvents \| extend IsExternal = SenderFromDomain != RecipientDomain` |
| `distinct` | Return unique values | `SigninLogs \| distinct UserPrincipalName` |
| `order by` / `sort by` | Sort results, `desc` or `asc` | `DeviceNetworkEvents \| order by Timestamp desc` |
| `take` / `limit` | Return only N rows | `SecurityAlert \| take 20` |
| `ago()` | Relative time filter | `SigninLogs \| where TimeGenerated > ago(24h)` |
| `join` | Combine rows from two tables on a key | `DeviceProcessEvents \| join DeviceNetworkEvents on DeviceId` |

> **SC 200 Exam Tips**
> * A KQL query always starts with a table name, filtering (`where`) usually comes next.
> * `ago()` is the standard way to scope a query to a recent time window, common in hunting queries.
> * `join` across tables (for example `DeviceProcessEvents` joined to `DeviceNetworkEvents`) is how you connect "what ran" to "what it talked to" during an investigation.

### Final Memory Anchors

* Every query starts with a **table**.
* `Device*` = endpoint, `Email*` = mail, `Identity*` = Active Directory.
* `SecurityAlert` → `SecurityIncident` is one directional grouping, not the reverse.
* Defender XDR data flows **into** Sentinel through a data connector, not the other way around.

* When a scenario names Exchange, SharePoint, Teams, or OneDrive think `OfficeActivity`.
