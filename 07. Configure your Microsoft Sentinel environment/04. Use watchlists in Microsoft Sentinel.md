## What Is a Watchlist

A **Watchlist** is a table in Microsoft Sentinel that stores **custom, organization provided data**.

> Unlike log tables (SigninLogs, SecurityEvent, DeviceProcessEvents, etc.), a watchlist does **not** collect data automatically. You supply the data yourself, typically from a CSV file.

A watchlist is best understood as a **lookup table** that adds business context to raw security events. Sentinel knows *what* happened (a login, a process execution); the watchlist tells Sentinel *why it matters*.

### Common Watchlist Contents

| Category | Examples |
|---|---|
| Infrastructure | Critical servers, domain controllers, high value assets |
| People | VIP users, executive accounts |
| Network | Approved IP addresses, trusted domains |
| Applications | Authorized applications |
| Organizational | Sensitive departments, asset inventories |

### SC 200 Exam Tips

* A watchlist is a **custom reference dataset**, stored as **name value pairs** for fast lookups.
* Watchlists do **not** replace logs. They **enrich** existing log data with business context.
* Remember the core contrast: logs are collected automatically; watchlists are supplied by you.

## Why SOC Analysts Use Watchlists

### Worked Example: Critical Servers

A company has **500 servers**, but only **5** are business critical:

```text
DC01
DC02
SQL01
ERP01
PAYMENT01
```

These are placed into a watchlist named `CriticalServers` with a column `ComputerName`.

Microsoft Sentinel then detects PowerShell execution across many machines:

```text
WEB05     PowerShell.exe
DC01      PowerShell.exe
FILE02    PowerShell.exe
SQL01     PowerShell.exe
```

Without the watchlist, every alert looks equally important. With the watchlist, Sentinel can check membership and escalate appropriately:

```text
Alert: PowerShell execution on DC01
        │
        ▼
Is "DC01" present in CriticalServers watchlist?
        │
        ▼
       Yes
        │
        ▼
High Priority Alert
```

The SOC team can immediately focus on attacks against the servers that matter most, instead of triaging every PowerShell alert equally.

### Added Context

This pattern, "check event value against a watchlist to decide priority," is the single most tested watchlist use case on SC 200. Expect scenario questions describing a flood of similar alerts where the correct answer is "create a watchlist and reference it in the analytics rule or hunting query," rather than manually tuning each alert.

### SC 200 Exam Tips

* Watchlists let analysts distinguish **noise** from **business critical** activity.
* A flood of identical alerts across many hosts is a classic exam clue pointing toward watchlist enrichment as the solution.

## Watchlists for Business Data

Watchlists are not limited to servers. Microsoft Sentinel treats any organization supplied reference data the same way, whether it is threat intelligence or HR data.

### Real World Example: Threat Intelligence Feed

A threat intelligence provider sends a daily CSV of thousands of malicious IP addresses. You import this file into a watchlist. Firewall logs are then checked against the watchlist so traffic to a known malicious IP is immediately flagged as suspicious.

### Real World Example: Terminated Employees

HR provides a list of terminated employees. You import the list into a watchlist. If Sentinel detects a login attempt from one of those accounts, it becomes a **high priority investigation** automatically, since the account should no longer be active.

### Other Business Data Examples

* Privileged users
* Domain Admin accounts
* Service accounts
* Critical servers
* Terminated employees
* Approved devices

### SC 200 Exam Tips

* Watchlists combine **technical logs** with **business information** that Sentinel has no other way of knowing (who is terminated, who is a VIP, which IP ranges are trusted).
* Threat intelligence feeds delivered as CSV are a common watchlist source, distinct from the dedicated Threat Intelligence (TI) data connectors, but conceptually similar: both provide "known bad" indicators for matching.

## Allowlists and Blocklists

Watchlists can also implement two classic security patterns:

| Type | Contains | Effect |
|---|---|---|
| Allowlist | Trusted users, devices, IP addresses, or applications | Can be **excluded** from certain alerts |
| Blocklist | Known malicious or unauthorized objects | Any related activity can **generate alerts** or trigger investigations |

> Exam tip: if a question describes suppressing alerts for known good/trusted entities, think **allowlist**. If it describes generating alerts for known bad entities, think **blocklist**. Both are implemented as watchlists.

## Creating a Watchlist

Creating a watchlist lets you import external data (CSV files of IP addresses, privileged users, terminated employees, critical assets, etc.) into Microsoft Sentinel. Once created, a watchlist can be used in **analytics rules**, **threat hunting**, **KQL queries**, **workbooks**, and **investigation workflows**.

### Creation Workflow

```text
Open Microsoft Sentinel
        │
        ▼
Configuration
        │
        ▼
Watchlist
        │
        ▼
Add new
        │
        ▼
Configure general information (name, description, alias)
        │
        ▼
Upload the data source (CSV)
        │
        ▼
Review the configuration
        │
        ▼
Create the watchlist
```

### Example CSV: Privileged Users

```text
Username,Department,Role
admin01,IT,Domain Admin
admin02,IT,Enterprise Admin
backup01,IT,Backup Operator
```

After upload, Microsoft Sentinel stores these values so they can be used during investigations.

### SC 200 Exam Tips

* Path to memorize: **Microsoft Sentinel → Configuration → Watchlist → Add new**.
* Creation steps, in order: configure general information, upload data source, review configuration, create.
* During creation you provide: **Name, Description, Alias, Data source**.
* Most watchlists are imported from **CSV files**.
* **Watchlist uploads are limited to 3.8 MB per file.** This exact figure is a known exam fact; do not confuse it with other Sentinel size limits.
* Common watchlist data types tested on the exam: IP addresses, domains, file hashes, VIP users, privileged accounts, critical servers, terminated employees.

## Querying a Watchlist with KQL

Once created, a watchlist is queried using the built in KQL function:

```kql
_GetWatchlist('WatchlistName')
```

### Real World SOC Scenario

A company maintains a watchlist called `HighValueMachines` containing critical production servers. A ransomware alert fires for one endpoint. The analyst runs:

```kql
_GetWatchlist('HighValueMachines')
```

to check whether the affected endpoint is on the list. It is found, so the incident is immediately escalated because it affects a business critical asset.

### Added Context: Typical Join Pattern

The function returns a table, so it is normally combined with `where ... in` or a `join` against a log table, for example:

```kql
SecurityEvent
| where Computer in (_GetWatchlist('CriticalServers') | project ComputerName)
```

```kql
SigninLogs
| where UserPrincipalName in (_GetWatchlist('TerminatedEmployees') | project Username)
```

> Exam tip: if a question shows a KQL snippet and asks "what does `_GetWatchlist` do," the answer is always: it retrieves the rows of a named watchlist so they can be filtered or joined against log data in the same query.

### SC 200 Exam Tips

* Know the exact function name and syntax: `_GetWatchlist('WatchlistName')` (leading underscore, single quotes around the name).
* Watchlists are commonly joined with log tables such as **SigninLogs**, **SecurityEvent**, and **DeviceProcessEvents** to enrich investigations.
* This function can be used inside **hunting queries** and **analytics rules**, not only ad hoc investigation.

## Managing and Editing Watchlists

After creation, a watchlist must be kept accurate. Microsoft Sentinel supports:

* Editing existing watchlist items
* Adding new items
* Performing bulk updates using a CSV file

### Why Watchlists Need Maintenance

Business information changes constantly:

* New employees join.
* Employees leave.
* Servers are added or retired.
* New malicious IP addresses are discovered.
* VIP users change.
* Critical assets are updated.

If a watchlist is not kept current, detections and investigations built on it become inaccurate.

### Why Not Just Delete and Recreate?

> **Microsoft recommends editing an existing watchlist instead of deleting and recreating it.**

This is because **Log Analytics has approximately a five minute data ingestion delay**. If you delete a watchlist and immediately recreate it, you may temporarily see **both** the deleted and newly created entries during that ingestion window, producing duplicate data. If duplicates persist longer than expected, Microsoft recommends opening a support ticket.

### Editing a Single Item

Navigation path:

```text
Microsoft Sentinel
        │
        ▼
Configuration
        │
        ▼
Watchlist
        │
        ▼
Select Watchlist
        │
        ▼
Update Watchlist
        │
        ▼
Edit Watchlist Items
```

Steps:

1. Open the watchlist.
2. Select the checkbox next to the item.
3. Edit the information.
4. Select **Save**.
5. Confirm the changes by selecting **Yes**.

**Real world example:** a server named `WEB01` is renamed to `WEB-PROD01`. Instead of creating a new watchlist, you edit the existing record and save the updated hostname.

### Adding a Single New Item

If only one or two entries need to be added, add them manually:

1. Select **Add new**.
2. Enter the required information.
3. Select **Add**.

### SC 200 Exam Tips

* Memorize the rationale: **five minute Log Analytics ingestion delay** is *why* delete and recreate can cause temporary duplicates.
* Editing and adding single items is done directly from the watchlist UI: select the checkbox, edit, Save, confirm with Yes.
* If duplicates persist beyond the expected window, the recommended action is a **support ticket**, not deleting the watchlist again.

## Bulk Update and the Search Key

When many records need updating at once, use **Bulk Update** to upload a revised CSV instead of editing entries one by one.

### Critical Limitation: Bulk Update Does Not Delete

> **Bulk Update does not remove existing entries just because they are missing from the new CSV.**

Example:

| Original Watchlist | Updated CSV | Result After Bulk Update |
|---|---|---|
| ServerA | ServerA | ServerA |
| ServerB | ServerC | ServerB (still present) |
| ServerC | | ServerC |

**ServerB remains in the watchlist** even though it was left out of the updated CSV.

If individual entries must be removed, delete them manually. If **many** records must be removed, Microsoft recommends **deleting and recreating** the watchlist instead of manual deletion, accepting the temporary duplicate risk described above.

### The Search Key

Every watchlist has a **Search Key**, the column used to match rows during an update.

During a Bulk Update:

* The uploaded CSV **must contain the Search Key column**.
* The Search Key **cannot contain blank values**.

Without a valid Search Key, Sentinel cannot correctly match records, so the update will fail or behave unpredictably.

### Bulk Update Workflow

Navigation:

```text
Microsoft Sentinel
        │
        ▼
Configuration
        │
        ▼
Watchlist
        │
        ▼
Select Watchlist
        │
        ▼
Update Watchlist
        │
        ▼
Bulk Update
```

Steps:

1. Upload the updated CSV file.
2. Fix any validation errors if they occur.
3. Select **Reset** and upload the corrected file if necessary.
4. Select **Next: Review and update**.
5. Select **Update**.

### SC 200 Exam Tips

* The number one tested "gotcha": **Bulk Update adds and updates records but never deletes them**, even if a record is missing from the new CSV.
* A valid **Search Key with no blank values** is mandatory for Bulk Update to work.
* Large scale removals are handled by deleting and recreating the watchlist, small scale removals by manual deletion.

## SC 200 Last Minute Revision

### One Page Cheat Sheet

**Core definition**
A watchlist is a Sentinel table of organization supplied reference data, stored as name value pairs, used to enrich logs and detections with business context. It does not replace logs.

**Where to manage watchlists**

```text
Microsoft Sentinel → Configuration → Watchlist
```

**Create a watchlist**

```text
Watchlist → Add new → General info → Upload data source → Review → Create
```

**Query a watchlist in KQL**

```kql
_GetWatchlist('WatchlistName')
```

**Typical join fields:** SigninLogs, SecurityEvent, DeviceProcessEvents.

### Key Numbers to Memorize

| Fact | Value |
|---|---|
| Maximum watchlist upload size | 3.8 MB |
| Log Analytics ingestion delay | Approximately 5 minutes |
| Required field during creation | Name, Description, Alias, Data source |
| Required column during Bulk Update | Search Key (no blanks allowed) |

### Frequently Confused Concepts

| Question | Correct Answer |
|---|---|
| Does a watchlist collect data automatically? | No, it is manually supplied, unlike log tables. |
| Does Bulk Update remove entries missing from the new CSV? | No, it only adds and updates. Removal must be manual or via delete and recreate. |
| Should you delete and recreate a watchlist for small changes? | No, edit the existing watchlist to avoid ingestion delay duplicates. |
| What function retrieves watchlist data in KQL? | `_GetWatchlist('WatchlistName')` |
| What is required for Bulk Update to correctly match rows? | A populated Search Key column with no blanks. |

### Allowlist vs Blocklist Quick Recall

```text
Allowlist  → trusted objects → can suppress or exclude alerts
Blocklist  → malicious objects → can generate or trigger alerts
```

### End to End Watchlist Lifecycle Diagram

```text
Identify need for business context
        │
        ▼
Prepare CSV (with a valid Search Key column)
        │
        ▼
Create Watchlist (Configuration → Watchlist → Add new)
        │
        ▼
Reference watchlist in KQL, analytics rules, hunting queries
        │
        ▼
Alert or investigation enriched with business context
        │
        ▼
Maintain over time:
   Edit single items  OR  Bulk Update (add/update only, no delete)
        │
        ▼
Large scale change needed? → Delete and recreate (accept brief duplicate risk)
```

> Night before the exam: if you remember only five things, remember: (1) watchlists enrich, they do not replace logs, (2) `_GetWatchlist('Name')` is the KQL function, (3) 3.8 MB upload limit, (4) Bulk Update never deletes, and (5) prefer editing over delete and recreate because of the five minute ingestion delay.
