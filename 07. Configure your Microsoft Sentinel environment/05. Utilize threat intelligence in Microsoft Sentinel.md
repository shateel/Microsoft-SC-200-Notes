## 1. Introduction to Threat Intelligence

### 1.1 What Is Threat Intelligence

Threat Intelligence (also called **Cyber Threat Intelligence, CTI**) is **knowledge about cyber threats**. Instead of only collecting logs, security teams also collect information about attackers and their activity.

Threat intelligence typically answers questions such as:

* Who is attacking?
* What techniques are they using?
* Which IP addresses are malicious?
* Which domains are used for phishing?
* Which file hashes belong to malware?
* What infrastructure does the attacker control?

This information helps organizations recognize known threats before they cause damage.

### 1.2 Where Threat Intelligence Comes From

Common sources of CTI include:

* Open source intelligence (OSINT)
* Threat intelligence communities
* Commercial (paid) threat intelligence providers
* Internal security investigations
* Incident response teams

> **Exam Tip:** Know that CTI is aggregated from multiple external and internal sources, not just one feed.

**Example scenario:** A cybersecurity vendor discovers a new phishing campaign and publishes a report containing malicious IPs, fake domains, malware hashes, and phishing URLs. Organizations import these indicators into Microsoft Sentinel so the campaign can be detected if it targets their environment.

### 1.3 Tactical Threat Intelligence

The most commonly used form of threat intelligence inside Microsoft Sentinel is **Tactical Threat Intelligence**, which focuses on technical indicators that security tools can automatically consume, such as:

* Malicious IP addresses
* Malicious domains
* URLs
* File hashes

Unlike strategic intelligence (which supports long term, human level decision making), tactical intelligence is built for **automated detection and response**.

### 1.4 The Threat Intelligence Lifecycle in Microsoft Sentinel

The lifecycle has five stages, each covered in the source material:

```text
Step 1: Import Threat Intelligence
   (Data Connectors → TAXII servers, TIPs, custom solutions)
        │
        ▼
Step 2: Store and Manage Indicators
   (Threat Intelligence area, Logs)
        │
        ▼
Step 3: Generate Alerts
   (Analytics Rules compare logs to indicators)
        │
        ▼
Step 4: Visualize Threat Intelligence
   (Threat Intelligence Workbooks)
        │
        ▼
Step 5: Perform Threat Hunting
   (Analysts proactively search for indicator matches)
```

**Step 1, Import:** Indicators enter Sentinel through **Data Connectors**, which can connect to:

* TAXII servers (Trusted Automated Exchange of Intelligence Information, the standard protocol used to share STIX formatted indicators)
* Threat Intelligence Platforms (TIPs)
* Custom threat intelligence solutions

**Step 2, Store and Manage:** Analysts can view, search, manage, and review imported indicators. They are available in **Logs** and in the dedicated **Threat Intelligence** area of Sentinel.

**Step 3, Generate Alerts:** Once imported, **Analytics Rules** compare incoming logs against known malicious indicators. A match can trigger a security alert and, potentially, an incident.

**Step 4, Visualize:** **Threat Intelligence Workbooks** display the number of imported indicators, indicator categories, trends, statistics, and visual dashboards, giving analysts an at a glance view.

**Step 5, Threat Hunting:** Instead of waiting for an alert, analysts proactively search logs for known malicious indicators (IPs, domains, hashes) to catch attacks that automated detections may have missed.

**Example scenario:** Threat intelligence contains the malicious IP `185.45.22.18`. Firewall logs later show a connection to that same IP. An Analytics Rule detects the match and raises an alert for the SOC team.

### SC 200 Exam Tips — Section 1

* **CTI (Cyber Threat Intelligence)** is information about cyber threats that helps organizations detect and respond to attacks.
* CTI comes from multiple sources: open source feeds, commercial providers, communities, and internal investigations.
* **Indicators of Compromise (IOCs)** are the most common form of threat intelligence used inside Microsoft Sentinel.
* Common IOC types: IP addresses, domains, URLs, file hashes, email addresses.
* **Tactical Threat Intelligence** is built for automated detection, unlike strategic intelligence.
* Sentinel ingests threat intelligence through **Data Connectors** (TAXII, TIPs, custom feeds).
* Imported indicators are viewable in **Logs** and the **Threat Intelligence** section.
* **Analytics Rules** compare indicators against events to create alerts and incidents.
* **Workbooks** visualize imported threat intelligence.
* Threat hunting uses imported indicators to proactively search for malicious activity that alerts may have missed.

## 2. Managing Threat Indicators

### 2.1 What Are Threat Indicators

A **Threat Indicator** is an **Indicator of Compromise (IOC)** that identifies known malicious activity. Examples:

* Malicious IP addresses
* Malicious domains
* URLs
* File hashes
* Email addresses

Microsoft Sentinel automatically compares incoming security data against stored indicators, removing the need to manually search for known bad IPs or hashes.

### 2.2 Why Manage Threat Indicators

Threat intelligence changes constantly. New attacks appear daily and existing indicators can become obsolete. Managing indicators lets a team:

* Add newly discovered IOCs.
* Update existing indicators.
* Organize indicators using tags.
* Search and filter indicators quickly.
* Support investigations with current threat intelligence.

> **Exam Tip:** Outdated or unorganized indicators reduce detection effectiveness — this is the underlying reason indicator management exists as its own workflow.

### 2.3 The Threat Intelligence Management Area

Microsoft Sentinel provides a dedicated **Threat Intelligence** section where analysts can view, search, filter, sort, create, and manage indicators. This area is distinct from threat hunting: it focuses on **managing the intelligence itself**, not on searching security logs.

### 2.4 Tagging Threat Indicators

**Tagging** lets analysts organize indicators into logical groups instead of leaving thousands of unrelated indicators unsorted. Typical tag examples: `Ransomware`, `Phishing`, `APT29`, `FIN7`, `C2`, `Malware`, `Incident-2026-001`, `Campaign-X`.

Multiple tags can be applied to the same indicator. Because tags are free form text, organizations should agree on **consistent naming conventions**.

```text
15,000 Untagged Indicators
        │
        ▼
Hard to find related indicators

Tag Applied: "APT29"
        │
        ▼
Instant filtered view of only APT29 indicators
```

### 2.5 Intel Management

**Intel Management** is the central administration page for all threat intelligence in Sentinel. From here analysts can view, create, import, delete, tag, and search indicators. Think of it as the admin dashboard for Threat Intelligence.

### SC 200 Exam Tips — Section 2

* Threat Indicators are managed from the **Threat Intelligence** section.
* If prompted, select **Open Intel Management** to reach the newer management interface.
* Intel Management supports: view, search, filter, sort, import, create, delete, and tag indicators.
* To create a new indicator: select **Add New**, choose the indicator type, complete the required fields, then select **Apply**.
* Common indicator types: IP addresses, domains, URLs, file hashes, email addresses.
* Tags organize related indicators and multiple tags can apply to one indicator.
* Tag names are free form, so consistent naming conventions matter for the exam's "best practice" style questions.

## 3. Viewing Threat Indicators with KQL

### 3.1 Where Indicators Are Stored

After import, indicators are stored in a dedicated table queryable with **Kusto Query Language (KQL)**. Historically, this table has been:

```kql
ThreatIntelligenceIndicator
```

This table holds every imported IOC: IP addresses, domains, URLs, file hashes, and email addresses. Instead of using the Threat Intelligence interface only, analysts can query this table directly.

### 3.2 How to View Threat Indicators

```text
Microsoft Sentinel
        │
        ▼
General
        │
        ▼
Logs
        │
        ▼
Run KQL query against the Threat Intelligence table
```

The simplest possible query returns every indicator in the workspace:

```kql
ThreatIntelligenceIndicator
```

**Example scenario:** An organization imports a commercial feed containing 15,000 malicious IPs, 5,000 malicious domains, and 2,000 malware hashes. Running `ThreatIntelligenceIndicator` returns every imported IOC for review and investigation.

### 3.3 What Information Does the Table Contain

Each record represents one indicator and may include:

| Field | Purpose |
| --- | --- |
| Indicator value | The actual IOC (IP, domain, hash, and so on) |
| Indicator type | The category of the IOC |
| Description | Context about the indicator |
| Threat type | The type of threat it relates to (for example malware, phishing) |
| Confidence level | How reliable analysts consider the indicator to be |
| Source | Where the indicator originated |
| Expiration date | When the indicator is no longer considered current |
| Tags | Organizational labels applied to the indicator |

This helps analysts understand **why** an indicator exists and **how** it should be used.

### 3.4 New Threat Intelligence Tables (STIX Model)

Beginning in **2025**, Microsoft introduced two new tables to support the **STIX (Structured Threat Information Expression)** object model, alongside the legacy table:

| Table | Status | Notes |
| --- | --- | --- |
| `ThreatIntelligenceIndicator` | Legacy | Original schema; being phased out |
| `ThreatIntelIndicators` | New (2025 onward) | STIX based indicator storage |
| `ThreatIntelObjects` | New (2025 onward) | Supports additional STIX object types |

The new STIX based tables support richer threat intelligence data, additional object types, and better alignment with modern CTI standards. Microsoft recommends updating custom queries, Analytics Rules, Workbooks, Detection Rules, and Automation to use the new tables **before support for the legacy table ends**.

> **Exam Tip:** `ThreatIntelligenceIndicator` (legacy, singular) and `ThreatIntelIndicators` (new, plural) look alike and are an easy way for the exam to test attention to detail.

### 3.5 Example Investigation

```text
Firewall raises alert: connection to 185.45.22.18
        │
        ▼
Analyst queries the Threat Intelligence table
        │
        ▼
IP address confirmed as a known IOC
        │
        ▼
Alert / incident priority is increased
```

The Threat Intelligence table underpins multiple Sentinel capabilities:

```text
ThreatIntelligenceIndicator / ThreatIntelIndicators / ThreatIntelObjects
        │
        ├── Analytics Rules
        ├── Workbooks
        ├── Threat Hunting
        ├── Detection Rules
        └── Automation
```

### SC 200 Exam Tips — Section 3

* Imported indicators historically live in the **ThreatIntelligenceIndicator** table.
* Path to query: **Microsoft Sentinel → General → Logs**.
* The simplest query is just the table name: `ThreatIntelligenceIndicator`.
* The Threat Intelligence table feeds: Analytics Rules, Workbooks, Threat Hunting, Detection Rules, and Automation.
* New STIX based tables: **ThreatIntelIndicators** and **ThreatIntelObjects**.
* Expect exam questions on where imported IOCs are stored and how they are queried.

## 4. SC 200 Last Minute Revision

### One Page Cheat Sheet

| Concept | Quick Fact |
| --- | --- |
| CTI | Knowledge about cyber threats used to detect and respond to attacks |
| IOC | Indicator of Compromise; an IP, domain, URL, hash, or email address tied to known malicious activity |
| Tactical Threat Intelligence | Technical indicators built for automated detection |
| Data Connectors | Bring threat intelligence into Sentinel from TAXII servers, TIPs, or custom sources |
| Threat Intelligence section | Where indicators are viewed, searched, filtered, tagged, and managed |
| Intel Management | The central admin page for all threat intelligence |
| Tags | Free form labels used to group related indicators; multiple tags per indicator allowed |
| Legacy table | `ThreatIntelligenceIndicator` |
| New tables (2025+) | `ThreatIntelIndicators`, `ThreatIntelObjects` (STIX based) |
| Analytics Rules | Compare logs against indicators to create alerts and incidents |
| Workbooks | Visualize indicator counts, categories, and trends |
| Threat Hunting | Proactive, manual search for indicator matches in logs |

### Frequently Confused Concepts

| Concept A | Concept B | Key Difference |
| --- | --- | --- |
| Threat Intelligence section | Threat Hunting | The Threat Intelligence section manages the indicators themselves; Threat Hunting searches security logs using those indicators |
| `ThreatIntelligenceIndicator` | `ThreatIntelIndicators` | The first is the legacy table; the second is the new STIX based table. Names are nearly identical, read carefully |
| Tactical Threat Intelligence | Strategic Threat Intelligence | Tactical is technical and automated; strategic is higher level and supports human decision making |
| IOC | Threat Type | An IOC is the indicator itself (IP, hash, domain); Threat Type describes the category of threat it belongs to (for example phishing, malware) |

### Key Workflow to Memorize

```text
Import (Data Connectors)
        │
        ▼
Store and Manage (Threat Intelligence area / Logs)
        │
        ▼
Detect (Analytics Rules generate alerts)
        │
        ▼
Visualize (Workbooks)
        │
        ▼
Hunt (Proactive KQL search)
```

### Important KQL Syntax

```kql
// Return every imported indicator in the workspace
ThreatIntelligenceIndicator
```

Remember this is run from **Microsoft Sentinel → General → Logs**.

### Final Reminders Before the Exam

* Threat intelligence in Sentinel is mostly **tactical** (IPs, domains, URLs, hashes) and feeds **automated** detection.
* Indicators arrive through **Data Connectors** and are organized using **tags**.
* **Intel Management** is the admin hub; the **Threat Intelligence** section is where day to day viewing and searching happens.
* The exam favors precise table name recognition: legacy versus new STIX based tables.
* Analytics Rules, Workbooks, Threat Hunting, Detection Rules, and Automation all rely on the same underlying Threat Intelligence table.
