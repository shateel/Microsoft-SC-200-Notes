## Quick Overview

* **Microsoft Sentinel** is a cloud native **SIEM** (Security Information and Event Management) platform. It collects logs from Azure, multicloud, and third party sources.
* **Microsoft Defender XDR** is an **XDR** (Extended Detection and Response) platform. It provides deep visibility into Microsoft's own security products (Endpoint, Identity, Office 365, Cloud Apps).
* Integrating the two gives a single **unified SecOps experience**: one place to investigate alerts, incidents, vulnerabilities, and hunt for threats, instead of switching between the Azure portal and the Defender portal.

> **Exam framing:** the SC-200 exam frequently asks *which portal* a capability lives in, and *what changes* (and what does not change, such as RBAC) after onboarding. Memorize the portal boundaries carefully.

***

## Why Integrate Sentinel with Defender XDR

Individually, the two platforms serve different purposes:

| Product | Type | Primary Role |
|---|---|---|
| Microsoft Sentinel | SIEM | Broad log collection across Azure, multicloud, and third party systems; analytics, hunting, automation |
| Microsoft Defender XDR | XDR | Deep telemetry from Microsoft security products: Defender for Endpoint, Defender for Office 365, Defender for Identity, Defender for Cloud Apps |

Combining them gives analysts:

* Unified investigations across SIEM and XDR data
* Better overall visibility
* Improved alert and incident correlation
* Faster incident response
* Less time lost switching between portals

**Real world example:** an analyst investigating suspicious PowerShell activity would normally run two separate searches (Defender XDR for endpoint activity, Sentinel for firewall logs). After integration, one hunting query can search both datasets at once.

```text
Suspicious PowerShell Activity Detected
              │
              ▼
     Single Advanced Hunting Query
              │
      ┌───────┴────────┐
      │                 │
Defender XDR       Microsoft Sentinel
(Endpoint data)    (Firewall / SIEM logs)
      │                 │
      └───────┬─────────┘
              ▼
   Correlated Investigation Result
```

### SC-200 Exam Tips

* Sentinel = SIEM. Defender XDR = XDR. Know this pairing cold.
* Integration benefits to remember: unified investigation, better visibility, correlated alerts, faster response.
* Defender XDR telemetry sources: Endpoint, Identity, Email (Office 365), Cloud Apps.
* Sentinel data sources: Azure services, Microsoft Defender for Cloud, multicloud platforms, third party products.

## Two Integration Methods

Microsoft supports **two** distinct ways to connect the platforms.

### Method 1: Connect Defender XDR to Microsoft Sentinel

The Microsoft Defender XDR data connector is installed inside Sentinel. Defender XDR telemetry flows **into** Sentinel, and analysts keep working from the **Azure portal**.

```text
Microsoft Defender XDR
        │
        ▼
Defender XDR Connector
        │
        ▼
   Microsoft Sentinel
        │
        ▼
     Azure Portal
```

Best for SOCs where Microsoft Sentinel is already the primary SIEM.

### Method 2: Unified Experience in the Microsoft Defender Portal

Microsoft Sentinel is **onboarded into** the Microsoft Defender portal, so everything (Sentinel incidents, Defender incidents, alerts, vulnerabilities, threat intelligence, hunting, investigations) is available from **one interface**.

```text
        Microsoft Defender Portal
                    │
          ┌─────────┴─────────┐
          │                   │
   Microsoft Sentinel   Microsoft Defender XDR
```

### Method Comparison

| Aspect | Method 1 (Connector Only) | Method 2 (Onboarding / Unified) |
|---|---|---|
| Primary workspace | Azure Portal | Microsoft Defender Portal |
| What moves | Defender XDR telemetry into Sentinel | Sentinel itself into the Defender portal |
| Result | Sentinel gains Defender XDR data | Single portal for both SIEM and XDR |
| Best fit | Sentinel is your main SIEM | You want one unified SecOps experience |

> **Exam tip:** installing the **Microsoft Defender XDR connector** is required either way. Method 2 additionally requires **onboarding Sentinel into the Defender portal**.

### SC-200 Exam Tips

* Two methods: connect the connector and stay in Azure Portal, or onboard Sentinel into the Defender Portal for a single pane of glass.
* The Microsoft Defender XDR connector is a prerequisite for both approaches.
* Traditionally analysts had to switch between the Azure Portal (Sentinel) and the Defender Portal (Defender XDR); integration removes that friction.

## Capability Differences: Azure Portal vs Defender Portal

Most Sentinel capabilities exist in both portals, but some are portal specific. The exam tests this boundary directly.

| Portal | Best Suited For |
|---|---|
| **Azure Portal** | Workspace administration, configuration, automation, data connectors, advanced Sentinel management |
| **Microsoft Defender Portal** | Incident investigation, threat hunting, XDR investigations, unified incident management, day to day security operations |

**Simple memory rule:** *Azure Portal = Administration, Defender Portal = Operations.*

### Capabilities found only in the Azure Portal

* Advanced Hunting Bookmarks
* Data Connectors
* Threat Intelligence Entities
* Fusion Analytics Rule
* Edit Incident Comments
* Programmatic Incident Creation
* Reopen Closed Incidents
* Incident Tasks
* Multiple Workspace Management

### Capabilities found only in the Microsoft Defender Portal

* Unified Incident Management
* Advanced Hunting
* Attack Disruption for SAP
* Add / Remove Alerts from Incidents
* Unified SecOps Experience

> **Exam tip:** Notice that "Advanced Hunting Bookmarks" is Azure Portal only, while "Advanced Hunting" itself is Defender Portal only. This kind of near duplicate naming is a classic exam trap.

### SC-200 Exam Tips

* Most day to day SOC work happens in the Defender Portal once Sentinel is onboarded.
* Configuration heavy tasks (data connectors, multiple workspace management) remain in the Azure Portal.
* Memorize at least two or three items from each portal only list; the exam often gives a capability and asks which portal it belongs to.

## Onboarding Microsoft Sentinel into Defender XDR

Onboarding creates the **Unified SIEM + XDR** experience: one portal, one incident queue, one hunting experience, one investigation workflow.

```text
Before Onboarding

Microsoft Sentinel               Microsoft Defender XDR
        │                                 │
        ▼                                 ▼
 Investigate SIEM data            Investigate Defender alerts
   (Azure Portal)                    (Defender Portal)


After Onboarding

           Microsoft Defender Portal
                     │
                     ▼
           SIEM + XDR Together
   (Sentinel, Defender for Endpoint,
    Defender for Identity, Defender
    for Office 365, Defender for
    Cloud Apps all in one place)
```

What changes after onboarding:

* Microsoft Sentinel appears inside the Microsoft Defender portal navigation.
* Sentinel log tables, KQL queries, and saved functions become available inside **Advanced Hunting**.
* Incidents from Sentinel and Defender XDR are correlated together.
* Analysts investigate from a single interface, improving speed and simplicity.
* Microsoft security incident creation rules are disabled automatically, so the same event does not create duplicate incidents in both products.

### SC-200 Exam Tips

* Onboarding does not replace Sentinel data. It surfaces Sentinel content (tables, queries, functions) inside Defender XDR's Advanced Hunting.
* Duplicate incident creation is actively prevented by disabling Microsoft security incident creation rules once onboarded.

## Prerequisites and Required Roles

### Prerequisites Checklist

Before onboarding, all four of the following must already be in place:

1. **Microsoft Sentinel Workspace**: a Log Analytics Workspace with Microsoft Sentinel enabled on it.
2. **Microsoft Defender XDR Data Connector**: already enabled inside Sentinel, so it can collect Defender incidents and alerts.
3. **Microsoft Defender Portal Access**: the administrator performing onboarding needs access to this portal.
4. **Microsoft Defender XDR Tenant**: Defender XDR must already be deployed in the Microsoft Entra tenant. Sentinel cannot connect to a Defender environment that does not exist.

### Required Azure RBAC Roles

| Task | Required Role(s) |
|---|---|
| Connect or disconnect the workspace | Owner, User Access Administrator, or Microsoft Sentinel Contributor |
| View Microsoft Sentinel | Microsoft Sentinel Reader |
| Query Sentinel tables | Microsoft Sentinel Reader (or equivalent read permissions) |
| Investigate incidents | Microsoft Sentinel Contributor (or equivalent write permissions) |
| Create support requests | Owner, Contributor, or Support Request Contributor |

> **Critical exam point:** **Azure RBAC continues to control access to Microsoft Sentinel even after onboarding into the Defender portal.** Onboarding changes where you work, not the underlying authorization model.

### SC-200 Exam Tips

* A Sentinel enabled Log Analytics Workspace is a hard prerequisite; without it there is nothing to onboard.
* The Defender XDR connector must be enabled inside Sentinel *before* onboarding begins.
* RBAC roles do not change after onboarding, memorize this exact phrase style since it is a common exam distractor ("roles reset after onboarding" is a false statement).

## Offboarding Microsoft Sentinel

Organizations can disconnect Sentinel from the Defender portal at any time. Common reasons include migrating to another workspace, testing, or rebuilding an environment.

> **Rule to remember:** only **one** Microsoft Sentinel workspace can be connected to the Defender portal at a time. To connect a different workspace, the currently connected one must be disconnected first. Disconnecting removes the Sentinel experience from the portal; it does **not** delete the underlying workspace or its data.

## Sentinel Feature Categories Inside the Defender Portal

Once onboarded, Sentinel features inside the Defender portal are organized into four categories:

| Category | Purpose | Key Features |
|---|---|---|
| **Search** | Locate data quickly, including archived and long range data | Search across large datasets, long time ranges, restore archived logs |
| **Threat Management** | Investigate and proactively hunt for threats | Workbooks, Hunting, Bookmarks, Hunting Livestream, Jupyter Notebooks, Threat Intelligence, MITRE ATT&CK |
| **Content Management** | Install, organize, and maintain Sentinel content | Content Hub, Out of the Box content, Repository Integration |
| **Configuration** | Administer detection, automation, and data ingestion | Data Connectors, Analytics Rules, NRT Analytics Rules, Watchlists, Automation Rules, Playbooks |

### Search

Search lets analysts locate security information quickly, including across large datasets, long time ranges, and restored archived logs. Particularly useful for forensic investigations that need older data.

### Threat Management

**Workbooks** are interactive dashboards that display security metrics, charts, maps, and graphs, tracking things like incident trends and detection statistics. SOC managers rely on Workbooks heavily for reporting.

**Threat Hunting** is the proactive search for threats that have not yet triggered an alert. It assumes an attacker may already be inside the environment. Analysts use KQL to look for things such as suspicious PowerShell execution, credential theft, beaconing malware, lateral movement, and privilege escalation.

**Hunting Bookmarks** let analysts save important findings during a hunt, essentially "saved investigation notes" that can be revisited or shared with teammates later, instead of re running the same search.

**Hunting Livestream** shows events as they happen in near real time rather than searching historical logs. Useful for active attacks, red team exercises, penetration testing, and live incident response.

**Jupyter Notebooks** combine Python, KQL, data visualization, machine learning, and threat intelligence into a single investigation notebook. Typical uses include malware analysis, IOC enrichment, statistical analysis, and hunting automation.

**Threat Intelligence** features include bulk IOC import, indicator management and tagging, and IOC investigation. Indicators can be imported from CSV or JSON files and correlated against incoming logs.

**MITRE ATT&CK Coverage** maps Sentinel detections to the MITRE ATT&CK framework, showing which tactics and techniques are covered and which are not, helping identify detection gaps. Example: a credential dumping detection maps to the **Credential Access** tactic.

```text
Threat Management Workflow

  Hunt for Threats (KQL)
          │
          ▼
  Suspicious Finding
          │
          ▼
   Save as Bookmark
          │
          ▼
Correlate with MITRE ATT&CK Coverage
          │
          ▼
   Escalate to Incident
```

#### Search and Threat Management Exam Tips

* Workbooks visualize; Hunting discovers; Bookmarks preserve findings; Livestream monitors in near real time; Jupyter Notebooks add code driven analysis.
* MITRE ATT&CK mapping is used to find detection **gaps**, not just to label existing detections.

### Content Management

**Out of the Box Content**: prebuilt Analytics Rules, Hunting Queries, Workbooks, Parsers, and Playbooks created by Microsoft, so organizations do not need to build every detection from scratch (for example, installing a prebuilt brute force detection rule instead of writing one manually).

**Content Hub**: Sentinel's marketplace containing solutions, connectors, analytics rules, hunting queries, workbooks, and playbooks. Example: installing the Microsoft Defender XDR solution directly from the Content Hub.

**Repository Integration**: lets organizations store Sentinel content (such as Analytics Rules) inside source control systems like GitHub or Azure DevOps, enabling version control, change tracking, team collaboration, rollback, and automated deployment. Example: a SOC keeps all Analytics Rules in GitHub so every change is peer reviewed before deployment.

#### Content Management Exam Tips

* Content Hub = where you *get* prebuilt content. Repository Integration = where you *manage and version* your own content long term.
* Out of the Box content saves build time; it does not replace the need for custom rules tailored to the organization.

### Configuration

**Data Connectors** bring security data into Sentinel; without them, there is nothing to analyze. Examples: Microsoft Defender XDR, Azure Activity, Windows Security Events, Syslog, AWS, Cisco devices.

**Analytics Rules** analyze incoming data using KQL and generate alerts when suspicious patterns match, for example alerting when one user has more than twenty failed logins within five minutes.

**Near Real-Time (NRT) Analytics Rules** detect threats within seconds by continuously monitoring incoming events, rather than running on a schedule. Used when immediate detection matters, for example alerting instantly whenever Domain Admin privileges are assigned.

**Watchlists** are reference lists (VIP users, high value servers, approved applications, suspicious IP addresses) that can be used inside KQL queries to enrich detections. Analysts can add, remove, update, or fully replace entries; keeping watchlists current improves detection accuracy.

**Automation Rules** automatically respond when an incident is created: assigning it, changing severity, adding tags, closing false positives, or triggering a playbook. Example: every phishing incident is auto assigned to the Email Security Team.

**Playbooks** are automated response workflows built on **Azure Logic Apps**. They act without manual intervention: blocking IP addresses, disabling accounts, sending notifications, creating tickets, or collecting forensic evidence. Example: when ransomware is detected, a playbook isolates the infected device and notifies the SOC manager.

```text
Detection to Response Workflow

Data Connectors (Defender XDR, Azure, AWS, Syslog...)
              │
              ▼
       Microsoft Sentinel
              │
              ▼
  Analytics Rules / NRT Rules  ◄── enriched by Watchlists
              │
              ▼
            Alert
              │
              ▼
           Incident
              │
              ▼
      Automation Rule fires
              │
              ▼
     Playbook (Azure Logic Apps)
              │
              ▼
        Response Action
```

#### Configuration Exam Tips

* **Automation Rule vs Playbook**: an Automation Rule decides *when and what* should happen to an incident (assign, tag, close, or trigger something). A Playbook is the actual *workflow that performs* the action, built on Azure Logic Apps. Automation Rules can call Playbooks.
* **Analytics Rule vs NRT Rule**: both generate alerts from KQL logic; NRT rules run continuously for near instant detection instead of on a schedule.
* Data Connectors are the entry point for the entire pipeline. No connector, no data, no detections.

## SC-200 Last Minute Revision (Cheat Sheet)

### Core Definitions

| Term | One Line Definition |
|---|---|
| Microsoft Sentinel | Cloud SIEM; broad log collection and analytics across Azure, multicloud, third party sources |
| Microsoft Defender XDR | XDR platform; deep telemetry from Microsoft Endpoint, Identity, Office 365, Cloud Apps |
| Alert | A single signal of suspicious activity |
| Incident | A collection of correlated alerts representing one attack story |
| Analytics Rule | KQL based logic that turns raw data into alerts |
| NRT Rule | Analytics rule that runs continuously for near instant alerting |
| Automation Rule | Decides what happens automatically when an incident is created |
| Playbook | Azure Logic Apps workflow that performs the actual response action |
| Watchlist | Reference data (VIPs, IPs, servers) usable inside KQL for enrichment |
| Bookmark | Saved hunting finding for later reference or sharing |
| Content Hub | Marketplace for prebuilt Sentinel solutions and content |
| Advanced Hunting | Defender Portal only proactive query experience over Sentinel and Defender data |

### Frequently Confused Concepts

| Concept A | Concept B | Key Difference |
|---|---|---|
| Azure Portal | Microsoft Defender Portal | Administration and configuration vs day to day operations and investigation |
| Automation Rule | Playbook | Trigger and decision logic vs the actual executed workflow |
| Analytics Rule | NRT Analytics Rule | Scheduled detection vs continuous, near instant detection |
| Content Hub | Repository Integration | Getting Microsoft or partner content vs versioning your own content |
| Bookmark | Watchlist | A saved finding from one hunt vs a reusable reference dataset |
| Alert | Incident | One suspicious event vs a correlated group of related alerts |

### Two Integration Methods, Side by Side

| | Method 1 | Method 2 |
|---|---|---|
| Action | Install Defender XDR connector in Sentinel | Onboard Sentinel into the Defender Portal |
| Analyst home | Azure Portal | Microsoft Defender Portal |
| Outcome | Sentinel gains Defender XDR telemetry | Full unified SIEM + XDR experience |

### Portal Only Capabilities Quick List

| Azure Portal Only | Defender Portal Only |
|---|---|
| Data Connectors | Advanced Hunting |
| Multiple Workspace Management | Unified Incident Management |
| Fusion Analytics Rule | Unified SecOps Experience |
| Programmatic Incident Creation | Attack Disruption for SAP |
| Reopen Closed Incidents | Add / Remove Alerts from Incidents |

### Things That Do NOT Change After Onboarding

* Azure RBAC permissions and role assignments.
* The underlying Log Analytics Workspace and its retained data.
* The requirement to have the Defender XDR connector enabled first.

### Things That DO Change After Onboarding

* Sentinel appears inside the Defender Portal navigation.
* Sentinel tables, KQL queries, and functions surface inside Advanced Hunting.
* Microsoft security incident creation rules are disabled to prevent duplicate incidents.
* Only one Sentinel workspace can be connected at a time.

### One Page Cheat Sheet

```text
SIEM  = Microsoft Sentinel   (broad log collection, KQL analytics)
XDR   = Microsoft Defender XDR (deep Microsoft product telemetry)

Two ways to combine them:
  1) Connector only   → stay in Azure Portal
  2) Full onboarding  → work from Defender Portal (Unified SecOps)

Portal rule of thumb:
  Azure Portal      = Administration / Configuration
  Defender Portal   = Operations / Investigation

Detection pipeline:
  Connectors → Sentinel → Analytics/NRT Rules → Alert → Incident
      → Automation Rule → Playbook (Logic Apps) → Response

Four feature categories in Defender Portal:
  Search | Threat Management | Content Management | Configuration

Never forget:
  • RBAC does not change after onboarding
  • Only one Sentinel workspace connects at a time
  • Defender XDR connector is required before onboarding
  • Duplicate incident creation is auto disabled after onboarding
```

> **Final tip:** if an exam question describes analysts switching between two portals, wanting one incident queue, or wanting Sentinel data inside Advanced Hunting, the answer almost always points to **onboarding Sentinel into the Microsoft Defender Portal (Method 2)**.
