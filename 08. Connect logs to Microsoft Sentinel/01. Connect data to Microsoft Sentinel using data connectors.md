## 1. Introduction to Data Ingestion and Data Connectors

### What Is Data Ingestion?

**Data Ingestion** is the process of collecting security logs from various systems and sending them into Microsoft Sentinel. It is the foundation that everything else in Sentinel depends on.

Without data ingestion, there is:

1. No logs
2. No analytics
3. No threat hunting
4. No alerts
5. No incidents

> **Exam Tip:** If a Log Analytics table is empty, the root cause is almost always a missing or misconfigured Data Connector, not a broken analytics rule. Always confirm ingestion first.

### What Is a Data Connector?

A **Data Connector** is a built in integration that allows Microsoft Sentinel to **collect security data (logs, alerts, and events)** from a specific data source and send that data into a **Log Analytics Workspace**, where Microsoft Sentinel can analyze it.

Without a Data Connector, Microsoft Sentinel **cannot see or analyze** data from that source. Think of a Data Connector as a **bridge** between your systems and Microsoft Sentinel.

```text
Data Source
    │
    ▼
Data Connector
    │
    ▼
Log Analytics Workspace
    │
    ▼
Microsoft Sentinel
    │
    ▼
Analytics Rule
    │
    ▼
Alert
    │
    ▼
Incident
```

### Why Are Data Connectors Important?

Microsoft Sentinel cannot automatically collect data from every system. Each data source generally requires its own connector.

**Example 1**

```text
Microsoft Defender for Endpoint
    │
    ▼
Defender Connector
    │
    ▼
Microsoft Sentinel
```

**Example 2**

```text
Cisco ASA Firewall
    │
    ▼
CEF Connector
    │
    ▼
Microsoft Sentinel
```

If the connector is not configured, Microsoft Sentinel receives **no data** from that product, no matter how detailed the source logs are.

> ### SC-200 Exam Tips
> 1. Data ingestion is always the required first step before analytics, hunting, alerts, or incidents can exist.
> 2. A Data Connector moves data from a source system into the Log Analytics Workspace that backs Microsoft Sentinel.
> 3. No configured connector means no visibility into that source, even if the underlying product logs everything correctly.
> 4. Each data source generally needs its own connector unless a generic ingestion method (CEF, Syslog, Log Analytics API, Logstash) is used instead.

## 2. Microsoft Sentinel and Microsoft Defender XDR Relationship

Microsoft Sentinel and Microsoft Defender XDR can work together in two distinct ways. This relationship is a frequent SC-200 exam topic.

### Method 1: Send Defender XDR Data to Microsoft Sentinel

Security data from Microsoft Defender XDR is ingested into Microsoft Sentinel through a connector, and the SOC primarily works inside Microsoft Sentinel.

```text
Microsoft Defender XDR
    │
    ▼
Data Connector
    │
    ▼
Microsoft Sentinel
    │
    ▼
SOC Investigation
```

### Method 2: Use Microsoft Sentinel Inside the Microsoft Defender Portal

Microsoft Sentinel is integrated directly into the Microsoft Defender portal. Analysts investigate incidents, alerts, vulnerabilities, threat hunting, and security data from a single unified portal.

This delivers a combined **SIEM and XDR** experience rather than two separate tools.

| Method | Where the SOC Works | Data Flow |
|---|---|---|
| Method 1 | Microsoft Sentinel (Azure portal) | Defender XDR data flows into Sentinel via a connector |
| Method 2 | Microsoft Defender portal | Sentinel capabilities are surfaced natively inside Defender, no separate ingestion step needed for the unified experience |

> ### SC-200 Exam Tips
> 1. Know both integration models: Sentinel receiving Defender XDR data through a connector, and Sentinel running natively inside the Defender portal.
> 2. The unified Defender portal experience combines **SIEM (Sentinel)** and **XDR (Defender)** capabilities in one place.
> 3. Expect scenario questions asking which portal an analyst should use depending on how the environment is configured.

## 3. Real World Scenario: Building a New SOC

Imagine an organization with the following technology in place:

1. Microsoft 365
2. Microsoft Defender XDR
3. Azure Virtual Machines
4. VMware servers
5. Cisco firewalls
6. Palo Alto firewalls

Microsoft Sentinel cannot monitor any of these automatically. The correct first step is always to determine which connector is required for each source **before** ingestion begins.

| Data Source | Required Connector or Agent |
|---|---|
| Microsoft 365 | Microsoft 365 connector |
| Azure Virtual Machine | Azure Monitor Agent (AMA) |
| Cisco ASA | CEF connector |
| Palo Alto firewall | CEF or Syslog connector |
| VMware servers (on premises) | Azure Monitor Agent installed on a Linux forwarder, typically using Syslog or CEF |

> ### SC-200 Exam Tips
> 1. Always map each data source to its correct connector type before assuming Sentinel will "just work."
> 2. Native Microsoft products (Microsoft 365, Azure VMs) use purpose built connectors or agents.
> 3. Third party network and security appliances (Cisco, Palo Alto) typically rely on the generic **CEF** or **Syslog** connectors, usually via a Linux forwarder running the Azure Monitor Agent.

## 4. Installing Data Connectors Through the Content Hub

Most Data Connectors are installed through the **Content Hub**. Once installed, a solution allows Microsoft Sentinel to receive logs from Microsoft services, Azure resources, third party products, cloud platforms, and on premises systems.

The Content Hub contains full Microsoft solutions that typically bundle:

1. Data Connectors
2. Analytics Rules
3. Workbooks
4. Hunting Queries
5. Playbooks

```text
Content Hub
    │
    ▼
Install Solution (e.g. Azure Activity)
    │
    ▼
Microsoft Sentinel → Configuration
    │
    ▼
Data Connectors
    │
    ▼
Configure the Connector
```

### Real World Example

A company wants to collect Azure Activity logs. The administrator:

1. Opens the **Content Hub**.
2. Installs the **Azure Activity** solution.
3. Opens **Configuration → Data Connectors**.
4. Configures the Azure Activity connector.

After configuration, Azure Activity logs begin flowing into Microsoft Sentinel.

> ### SC-200 Exam Tips
> 1. The Content Hub is the primary place to discover and install new Microsoft Sentinel solutions, not just individual connectors.
> 2. Installing a solution can bring analytics rules, workbooks, hunting queries, and playbooks along with the connector, all in one package.
> 3. A connector only appears under **Configuration → Data Connectors** after its solution has been installed from the Content Hub.
> 4. Remember the order of operations: install from Content Hub first, then configure under Data Connectors.

## 5. Understanding Data Connector Providers

Microsoft Sentinel supports many different **Data Connector Providers**, allowing it to collect logs from Microsoft security products, Azure services, third party vendors, and custom applications.

Different providers use different connection methods depending on the type of product. When a native connector is not available, Microsoft Sentinel supports generic methods such as **Syslog**, **Common Event Format (CEF)**, **Logstash**, and the **Log Analytics API**.

| Provider Type | Example | Typical Use |
|---|---|---|
| Native Microsoft connector | Microsoft Defender XDR, Microsoft Entra ID, Azure Activity | First party services, direct API based ingestion |
| Agent based | Windows Security Events, VM based Syslog and CEF | Requires the Azure Monitor Agent on the host or forwarder |
| Generic / standards based | CEF, Syslog | Third party appliances with no native connector |
| Custom / API based | Log Analytics Data Collector API, Logstash plugin, Codeless Connector Platform | Products with no built in connector at all |

### Microsoft Defender XDR Connector

The Microsoft Defender XDR connector collects security data from multiple Defender products in a single integration. It can ingest **alerts**, **incidents**, and **raw security telemetry** from:

1. Microsoft Defender for Endpoint
2. Microsoft Defender for Identity
3. Microsoft Defender for Office 365
4. Microsoft Defender for Cloud Apps

Instead of configuring a separate connector for each Defender product, organizations enable the single **Microsoft Defender XDR** connector to receive alerts and incidents from every integrated Defender product at once.

### Check the Data Type

Every connector writes data into one or more Log Analytics tables. The connector page displays the **Data Type**, which tells you exactly which table receives the data.

> **Exam Tip:** Always confirm a connector's Data Type (destination table) before writing a KQL query. Querying the wrong table is a common mistake in both the exam and real investigations.

**Example:** Before writing a KQL query against Azure Firewall logs, an analyst opens the connector page to confirm which Log Analytics table stores that data, so the investigation targets the correct table from the start.

### Custom Connectors Using the Log Analytics API

When a product has **no built in Microsoft Sentinel connector**, organizations can send logs directly to the Log Analytics workspace using the **Log Analytics Data Collector API**. This lets custom applications or unsupported products upload log data into Sentinel.

### Logstash Plugin

Microsoft Sentinel supports **Logstash**, a widely used log collection and processing tool. Using the Microsoft Sentinel Logstash output plugin, organizations can send virtually any log already collected by Logstash into Microsoft Sentinel. Logs land in a **custom table** defined by the output plugin.

Organizations often already use Logstash to collect logs from Linux servers, applications, network devices, and databases, so rather than replacing Logstash they simply add Microsoft Sentinel as an output destination.

### Common Event Format (CEF) and Syslog Connector

If no vendor provided connector exists, Microsoft Sentinel recommends the **CEF** or **Syslog** connector.

**Syslog** is a standard logging protocol commonly used by Linux and Unix systems. Devices send log messages to a Syslog collector, which then forwards them to Microsoft Sentinel. Common Syslog devices include Linux servers, routers, switches, firewalls, and other network appliances.

| Feature | CEF | Syslog |
|---|---|---|
| Destination table | **CommonSecurityLog** (automatically parsed into structured fields) | **Syslog** (stores raw, mostly unstructured messages) |
| Parsing | Automatic, structured, easier to query | Often requires custom parsing before use |
| Preferred when available | Yes, generally preferred over plain Syslog | Used when the vendor only supports plain Syslog |
| Forwarder requirement | Linux server running the Azure Monitor Agent (AMA) | Linux server running the Azure Monitor Agent (AMA) |

> **Good to know (SC-200 relevant):** Microsoft Sentinel now also offers the **Codeless Connector Platform (CCP)**, a no code, JSON configuration based framework for building custom REST API connectors. It sits alongside Logstash and the Data Collector API as another option when no native connector exists, and is increasingly referenced in newer SC-200 content.

> ### SC-200 Exam Tips
> 1. Microsoft Sentinel supports connectors from Microsoft Defender XDR, Azure services, third party vendors, and custom applications.
> 2. The Microsoft Defender XDR connector collects alerts, incidents, and telemetry from multiple Defender products through one integration.
> 3. Common Azure connectors include Microsoft Entra ID, Azure Activity, Azure Firewall, Microsoft Defender for Cloud, Office 365, and Windows Security Events.
> 4. Always check a connector's **Data Type** to identify the correct Log Analytics table before writing KQL.
> 5. If no native connector exists, use the **Log Analytics Data Collector API**, **Logstash**, the **Codeless Connector Platform**, or a **CEF/Syslog** connector.
> 6. **CEF** is generally preferred over Syslog because it is automatically parsed into the structured **CommonSecurityLog** table.
> 7. **Syslog** stores raw messages in the **Syslog** table and often needs custom parsing.
> 8. CEF and Syslog connectors commonly rely on a Linux server running the **Azure Monitor Agent (AMA)** as the forwarder.

## 6. Viewing Connected Hosts

### What Is a Connected Host?

A **Connected Host** is a Windows or Linux computer that is successfully sending monitoring and security data to an Azure Log Analytics Workspace. Examples include Windows Server, Linux Server, Azure Virtual Machines, on premises servers, and virtual machines running in VMware or Hyper V.

Once connected, Microsoft Sentinel can receive logs from these systems through the Log Analytics Workspace.

```text
Windows Server
    │
    ▼
Azure Monitor Agent
    │
    ▼
Log Analytics Workspace
    │
    ▼
Microsoft Sentinel
    │
    ▼
Analytics Rules
    │
    ▼
Alerts
```

### Why View Connected Hosts?

Before Microsoft Sentinel can analyze security events from a device, that device must first be connected to the Log Analytics workspace. Viewing connected hosts helps confirm:

1. The agent is installed.
2. The agent is communicating successfully.
3. The host is connected to the correct workspace.
4. Windows and Linux devices are actively sending data.

This is often the **first troubleshooting step** whenever expected logs are missing.

### Why Do Some Connectors Need an Agent?

Some systems cannot send logs directly to Microsoft Sentinel. Windows Security Events is a good example: Sentinel cannot simply read the Windows Event Log on its own.

```text
Windows Server
    │
    ▼
Azure Monitor Agent
    │
    ▼
Log Analytics Workspace
    │
    ▼
SecurityEvent Table
```

The **Windows Security Events connector** tells Sentinel to use the logs that arrive through the Azure Monitor Agent.

> **Good to know (SC-200 relevant):** Microsoft has retired the legacy **Log Analytics Agent** (also called the MMA or OMS agent). The **Azure Monitor Agent (AMA)** is now the standard, current agent used across Sentinel data connectors. AMA works together with **Data Collection Rules (DCR)**, which define exactly what data is collected and where it is routed, giving finer control than the legacy agent allowed.

### Where to View Connected Hosts

Connected hosts are viewed in the **Log Analytics workspace**, not directly inside Microsoft Sentinel.

In the Microsoft Defender portal:

1. Navigate to **System → Settings → Microsoft Sentinel**.
2. Select the workspace.
3. Open **Log Analytics settings**.
4. Select **Configure Log Analytics workspace**.
5. Navigate to **Settings → Agents**.

The **Agents** page displays Windows hosts, Linux hosts, the number of connected machines, and agent status.

> **Exam Tip:** If a device does not appear on the Agents list, Microsoft Sentinel cannot ingest logs from that device. Checking connected hosts is one of the very first troubleshooting steps when expected log data is missing.

> ### SC-200 Exam Tips
> 1. Connected hosts are viewed in the **Log Analytics workspace**, not directly in Microsoft Sentinel.
> 2. Path: Microsoft Defender portal → **System → Settings → Microsoft Sentinel** → select workspace → **Log Analytics settings → Configure Log Analytics workspace** → **Settings → Agents**.
> 3. The Agents page shows connected Windows and Linux hosts, machine counts, and connection status.
> 4. A missing host on the Agents page means Sentinel is not receiving logs from that device until the connection issue is resolved.
> 5. Checking connected hosts is a standard first troubleshooting step for missing log data.
> 6. Know that AMA has replaced the legacy Log Analytics Agent (MMA/OMS), and that AMA relies on Data Collection Rules (DCR) to define what is collected.

## 7. SC-200 Last Minute Revision

### Must Memorize Facts

1. **Data Ingestion** must happen before analytics, hunting, alerting, or incident creation can occur.
2. A **Data Connector** is the bridge between a data source and the Log Analytics Workspace that Sentinel reads from.
3. Most connectors are installed from the **Content Hub**, then configured under **Configuration → Data Connectors**.
4. The **Microsoft Defender XDR** connector brings alerts, incidents, and telemetry from Defender for Endpoint, Identity, Office 365, and Cloud Apps in a single integration.
5. Always confirm a connector's **Data Type** (destination table) before writing a KQL query.
6. **CEF** logs land in **CommonSecurityLog** (structured, automatically parsed). **Syslog** logs land in the **Syslog** table (raw, often needs custom parsing).
7. Connected hosts are checked in the **Log Analytics workspace**, under **Settings → Agents**, not directly in Sentinel.
8. **Azure Monitor Agent (AMA)** is the current standard agent; the legacy Log Analytics Agent (MMA/OMS) has been retired.

### Frequently Confused Concepts

| Concept A | Concept B | Key Difference |
|---|---|---|
| Content Hub | Data Connectors blade | Content Hub is where solutions are **discovered and installed**; Data Connectors is where an installed connector is **configured** |
| CEF | Syslog | CEF is structured and auto parsed into CommonSecurityLog; Syslog is raw and often needs manual parsing |
| Microsoft Defender XDR connector | Individual Defender connectors | The XDR connector covers multiple Defender products at once; individual connectors cover a single product each |
| Azure Monitor Agent (AMA) | Legacy Log Analytics Agent (MMA/OMS) | AMA is current and uses Data Collection Rules; the legacy agent is retired |
| Sentinel in Azure portal | Sentinel inside Defender portal | Same underlying SIEM data, but Method 2 unifies SIEM and XDR investigation in one portal |

### Common Data Source to Connector Mapping

| Data Source | Connector / Agent |
|---|---|
| Microsoft 365 | Microsoft 365 connector |
| Microsoft Entra ID | Native Entra ID connector |
| Azure Activity | Azure Activity connector (Content Hub solution) |
| Windows Security Events | Windows Security Events connector, via Azure Monitor Agent |
| Cisco / Palo Alto firewalls | CEF or Syslog connector, via AMA on a Linux forwarder |
| Unsupported / custom product | Log Analytics Data Collector API, Logstash, or Codeless Connector Platform |

### Core Workflow to Remember

```text
Data Source
    │
    ▼
Data Connector (Content Hub → Configure)
    │
    ▼
Log Analytics Workspace
    │
    ▼
Microsoft Sentinel
    │
    ▼
Analytics Rule → Alert → Incident
```

### KQL Reminder

The document itself does not include specific KQL queries, but knowing the destination table lets you query it immediately using the standard pattern:

```kql
TableName
| where TimeGenerated > ago(1d)
| order by TimeGenerated desc
```

For CEF and Syslog sources specifically:

```kql
CommonSecurityLog
| where TimeGenerated > ago(1d)

Syslog
| where TimeGenerated > ago(1d)
```

### One Page Cheat Sheet

1. No connector configured, no data, no matter how good the source logs are.
2. Content Hub installs the solution, Data Connectors blade configures it.
3. Defender XDR connector equals one connector, many Defender products.
4. CEF is structured (CommonSecurityLog), Syslog is raw (Syslog table).
5. No native connector, fall back to API, Logstash, CCP, or CEF/Syslog.
6. Connected hosts live under Log Analytics workspace, Settings, Agents, not inside Sentinel itself.
7. AMA is current, the legacy MMA/OMS agent is retired.
8. Missing logs, check the Agents page first, then check the connector's Data Type.
