# SC 200 Revision Guide: Connect Microsoft Services to Microsoft Sentinel

> This guide condenses the "Connect Microsoft services to Microsoft Sentinel" study module into a fast, exam focused reference. It covers the four native connectors: **Microsoft 365**, **Microsoft Entra ID**, **Microsoft Entra ID Protection**, and **Azure Activity**. These connectors sit inside the **data collection** domain of the SC 200 exam, so knowing what each one ingests, and which table it lands in, is high value exam knowledge.

## 1. Overview: What Is a Sentinel Data Connector

A **data connector** is the mechanism Microsoft Sentinel uses to ingest logs, events, or alerts from a source system into a **Log Analytics workspace**. Once data lands in a table, it can be queried with **KQL (Kusto Query Language)**, used in **analytics rules**, and surfaced in **incidents**.

> **Exam Tip:** Almost every native Microsoft connector must first be installed as a **solution** from the **Content Hub** before it appears under **Configuration → Data Connectors**. Expect exam questions that test this exact order of operations.

General ingestion flow:

```text
Source Service (Microsoft 365, Entra ID, Azure, etc.)
        │
        ▼
Content Hub Solution Installed
        │
        ▼
Data Connector Configured
        │
        ▼
Log Analytics Table (e.g. OfficeActivity, SigninLogs)
        │
        ▼
KQL Queries / Analytics Rules
        │
        ▼
Alerts and Incidents in Microsoft Sentinel
```

Two categories of connector matter for this module:

| Category | What It Sends | Example |
|---|---|---|
| Raw log connector | Individual events (sign ins, audit actions) | Microsoft Entra ID Connector |
| Alert connector | Already analyzed security alerts, not raw events | Microsoft Entra ID Protection Connector |

Knowing which category a connector belongs to is a recurring exam pattern.

## 2. Microsoft 365 Connector

### What It Is

The **Microsoft 365 Connector** imports **audit activity logs** from Microsoft 365 services. It answers **"what did the user do"**, not **"was this an attack."** Threat detection is a separate function handled by Microsoft Defender products.

### What Microsoft 365 Covers

Microsoft 365 (formerly Office 365) is Microsoft's cloud productivity platform, providing email, file storage, document collaboration, team communication, calendars, and meetings through apps such as Outlook, SharePoint, Teams, and OneDrive. Every one of these everyday actions generates an audit event.

### Why Use It

SOC analysts use this connector to investigate suspicious user behavior, including:

* Sending emails
* Downloading files
* Creating Teams channels
* Sharing SharePoint documents
* Changing mailbox settings
* Creating Microsoft 365 groups

### Installation and Configuration

```text
Microsoft Sentinel
        │
        ▼
Content Management
        │
        ▼
Content Hub
        │
        ▼
Search "Microsoft 365"
        │
        ▼
Install
```

After installation, the connector appears under **Configuration → Data Connectors**. From there:

1. Review the connector's **Description** and **Data Types**.
2. Verify prerequisites (workspace read/write permissions, and **Global Administrator** or **Security Administrator** role).
3. Select the Microsoft 365 workloads to collect: **Exchange**, **SharePoint**, **Teams**.
4. Apply the configuration and wait for the connector status to change to **Disconnect**, which indicates a successful, already active connection (the button toggles to the action you would take next, so seeing "Disconnect" confirms the connector is currently connected).

### Where Data Lands

All collected events are written to the **`OfficeActivity`** table. This is one of the most frequently queried tables in Microsoft 365 investigations.

### Real World Example (Condensed)

A user reports missing confidential SharePoint files. An analyst queries `OfficeActivity` to determine who accessed the files, when they were deleted, and whether they were shared externally. This is a good template for how the exam frames investigation scenarios: identify the table first, then the fields that answer who, when, and what.

### SC-200 Exam Tips

> * Install the **Microsoft 365 Solution** from the **Content Hub** before the connector appears in **Data Connectors**.
> * Supported workloads: Exchange Online, SharePoint Online, Microsoft Teams.
> * All Microsoft 365 audit data lands in **`OfficeActivity`**, a single shared table (unlike Entra ID, which splits across many tables).
> * Required role: **Global Administrator** or **Security Administrator**, plus workspace read/write permissions.
> * This connector shows user activity, it does not by itself indicate malicious intent, that judgment comes from analytics rules or Defender alerts layered on top.

## 3. Microsoft Entra ID Connector

### What It Is

The **Microsoft Entra ID Connector** (Entra ID was formerly **Azure Active Directory**) collects **identity related logs**. Since many attacks begin with compromised credentials, this is one of the highest value connectors on the exam.

Microsoft Entra ID is Microsoft's cloud **Identity and Access Management (IAM)** service, answering: who are you, can you sign in, and what are you allowed to access. Organizations use it to authenticate users, manage accounts, control app access, enforce **Multi-Factor Authentication (MFA)**, apply **Conditional Access** policies, and manage admin roles.

Without this connector, Sentinel cannot see identity events at all, including suspicious sign ins, impossible travel, password spray attempts, privilege escalation, admin changes, application authentication, and provisioning activity.

### Key Difference From Microsoft 365 Connector

Unlike the single table Microsoft 365 connector, the Entra ID connector supports **multiple independent log types**, and **each log type writes to its own table**. Administrators choose which types to stream, which also controls ingestion cost.

### Available Log Types and Their Tables

| Log Type | Table Name | What It Captures |
|---|---|---|
| Interactive user sign in logs | `SigninLogs` | Sign ins where a user actively authenticates (Microsoft 365, Azure Portal, MFA prompts) |
| Non-interactive sign in logs | `AADNonInteractiveUserSignInLogs` | Sign ins without user action: refresh tokens, background auth, mobile apps |
| Service principal sign in logs | `AADServicePrincipalSignInLogs` | Authentication performed by applications (Azure Automation, Azure Functions, enterprise apps) |
| Managed identity sign in logs | `AADManagedIdentitySignInLogs` | Authentication by Azure managed identities (no stored passwords) |
| Provisioning logs | `AADProvisioningLogs` | Account lifecycle changes: user creation/deletion, group membership, sync events |
| AD FS sign in logs | `ADFSSignInLogs` | Federation authentication events for hybrid identity environments |
| Audit logs | `AuditLogs` | Administrative changes: user creation, password resets, Conditional Access changes, role assignments |

> **Exam Tip:** Interactive sign in logs help spot suspicious sign ins, impossible travel, and password spray attacks. Non-interactive logs help spot compromised tokens and unusual background activity. Service principal logs help detect compromised applications, not compromised users.

### Installation and Configuration

```text
Microsoft Sentinel
        │
        ▼
Content Management
        │
        ▼
Content Hub
        │
        ▼
Search "Microsoft Entra ID"
        │
        ▼
Install
```

Then, under **Configuration → Data Connectors**:

1. Select **Microsoft Entra ID**.
2. Open the connector page.
3. Select the log types to collect.
4. Select **Connect**.

### Prerequisites

* Workspace read and write permissions.
* Microsoft Entra ID diagnostic settings read and write permissions.
* **Global Administrator** or **Security Administrator** role in the tenant.

### SC-200 Exam Tips

> * Enable only the log types actually needed, each one adds Log Analytics ingestion cost.
> * Memorize the seven table names in the table above, table matching is a very common question format.
> * `SigninLogs` = interactive; `AADNonInteractiveUserSignInLogs` = background/token based; `AADServicePrincipalSignInLogs` = app identities; `AADManagedIdentitySignInLogs` = Azure managed identities; `AADProvisioningLogs` = lifecycle events; `ADFSSignInLogs` = hybrid federation; `AuditLogs` = admin actions.
> * This connector delivers **raw events**, not alerts. Compare with the Entra ID Protection connector below.

## 4. Microsoft Entra ID Protection Connector

### The Confusion Point (High Yield for the Exam)

Students frequently confuse **Microsoft Entra ID** with **Microsoft Entra ID Protection**. The exam tests this distinction directly.

| | Microsoft Entra ID | Microsoft Entra ID Protection |
|---|---|---|
| Answers | Who signed in, when, from where, what admin changes occurred | Is this sign in suspicious, is this user compromised, were leaked credentials detected |
| Data type | Raw identity logs | Security alerts and risk detections |
| Example tables | `SigninLogs`, `AuditLogs`, `AADProvisioningLogs` | `SecurityAlert` |

Relationship between the two:

```text
Microsoft Entra ID
        │
Collects Identity Logs
        │
        ▼
Microsoft Entra ID Protection
        │
Analyzes the Logs, Detects Risks, Creates Alerts
        │
        ▼
Microsoft Sentinel
```

### What It Detects

Microsoft Entra ID Protection analyzes authentication behavior for identity based attacks:

* Impossible travel
* Anonymous IP usage
* Password spray
* Leaked credentials
* Suspicious sign ins

### What Data It Sends

Unlike the plain Entra ID connector, this one sends **alerts**, not the underlying raw sign in events. Data is written to the **`SecurityAlert`** table, which stores the generated alert information only, not the full set of raw events that triggered it.

### Prerequisites

* Workspace read and write permissions.
* **Global Administrator** or **Security Administrator** role.
* **Microsoft Entra ID Premium P2 license.**

> **Exam Tip:** The **P2 license requirement** is an easy detail to forget and a common exam trap. Entra ID Protection specifically requires **Premium P2**, while the base Entra ID connector does not.

### Configuration Notes

Installed the same way, via **Content Hub**, then configured under **Configuration → Data Connectors**. Enable **Create incidents** to automatically generate Microsoft Sentinel incidents directly from Entra ID Protection alerts, skipping the need to build a separate analytics rule for that purpose.

### SC-200 Exam Tips

> * Entra ID Protection is an **identity threat detection** service, it detects at risk users, risk events, and identity vulnerabilities.
> * It imports **alerts**, not raw logs, stored in **`SecurityAlert`**.
> * Requires **Microsoft Entra ID Premium P2**.
> * **Create incidents** toggle turns alerts straight into Sentinel incidents automatically.
> * Remember the split: **Entra ID Connector = raw logs. Entra ID Protection Connector = security alerts.**

## 5. Azure Activity Connector

### What It Is

**Azure Activity** refers to management events occurring within an Azure subscription, essentially the **audit log for your Azure environment**. Any action affecting Azure resources is recorded.

Examples include creating a virtual machine, deleting a storage account, modifying a Network Security Group (NSG), creating an Azure Key Vault, assigning Azure roles, and changing Azure policies. These events answer who changed what, when, and where.

> **Important distinction:** Azure Activity records **management operations on resources** (the control plane), not activity happening **inside** a virtual machine or resource (the data plane). For inside the box telemetry you would instead rely on Defender for Cloud or agent based collection, which is outside the scope of this connector.

### Installation and Configuration

Install the **Azure Activity** solution from **Content Hub** first, same pattern as the other connectors. This connector is unique among the four in this module because it is configured through **Azure Policy** rather than a simple toggle.

In the **Azure Policy Assignment Wizard**:

1. Select the subscription.
2. Choose the target Log Analytics Workspace.
3. Enable **Create a remediation task**, so the policy also applies retroactively to existing resources, not just future ones.

### Prerequisites

* Azure subscription **Owner** role is required (a stricter requirement than the Global/Security Administrator role used by the identity connectors).

### Where Data Lands

Azure Activity Logs are stored in the **`AzureActivity`** table, covering Azure Resource Manager operations, Service Health events, write operations, and subscription level administrative actions.

### SC-200 Exam Tips

> * Requires **Owner** role on the subscription, this is the one connector in the module that is not satisfied by Global/Security Administrator alone.
> * Uses **Azure Policy**, not a simple connect toggle, to configure log collection.
> * Always enable **Create a remediation task** so existing resources are covered retroactively.
> * Data lands in **`AzureActivity`**.
> * Know the distinction: **`AzureActivity`** = subscription management events (control plane). **Azure Resource Logs** = detailed events generated by individual resources (data plane), a separate diagnostic setting.

## 6. Connector to Table Quick Reference

This mapping is one of the single most tested facts in this module.

| Connector | Log Analytics Table(s) | Data Type |
|---|---|---|
| Microsoft 365 | `OfficeActivity` | Raw audit events (Exchange, SharePoint, Teams) |
| Microsoft Entra ID | `SigninLogs` | Raw: interactive sign ins |
| Microsoft Entra ID | `AADNonInteractiveUserSignInLogs` | Raw: non interactive sign ins |
| Microsoft Entra ID | `AADServicePrincipalSignInLogs` | Raw: application sign ins |
| Microsoft Entra ID | `AADManagedIdentitySignInLogs` | Raw: managed identity sign ins |
| Microsoft Entra ID | `AADProvisioningLogs` | Raw: account lifecycle changes |
| Microsoft Entra ID | `ADFSSignInLogs` | Raw: AD FS federation sign ins |
| Microsoft Entra ID | `AuditLogs` | Raw: admin/tenant changes |
| Microsoft Entra ID Protection | `SecurityAlert` | Alerts (not raw events) |
| Azure Activity | `AzureActivity` | Raw: subscription management events |

Required role by connector:

| Connector | Minimum Required Role |
|---|---|
| Microsoft 365 | Global Administrator or Security Administrator |
| Microsoft Entra ID | Global Administrator or Security Administrator |
| Microsoft Entra ID Protection | Global Administrator or Security Administrator, plus Entra ID Premium P2 |
| Azure Activity | Subscription Owner |

## 7. Starter KQL Queries

These are simple, standard query patterns that build directly on the tables above and are worth being comfortable with for scenario style exam questions.

```kql
// Microsoft 365: who accessed or deleted a SharePoint file
OfficeActivity
| where Operation in ("FileAccessed", "FileDeleted")
| project TimeGenerated, UserId, Operation, SiteUrl, SourceFileName

// Entra ID: interactive sign ins that failed
SigninLogs
| where ResultType != "0"
| project TimeGenerated, UserPrincipalName, AppDisplayName, IPAddress, ResultType

// Entra ID: admin role assignments from AuditLogs
AuditLogs
| where OperationName == "Add member to role"
| project TimeGenerated, InitiatedBy, TargetResources

// Entra ID Protection: recent identity risk alerts
SecurityAlert
| where ProviderName == "IPC" // Identity Protection Center
| project TimeGenerated, AlertName, AlertSeverity, Description

// Azure Activity: resource deletions in the last 24 hours
AzureActivity
| where OperationNameValue has "delete"
| where TimeGenerated > ago(24h)
| project TimeGenerated, Caller, ResourceGroup, OperationNameValue
```

> **Exam Tip:** You are not usually expected to write complex KQL from memory for this module, but you should recognize which table a scenario points to and understand basic filtering with `where` and field selection with `project`.

## 8. SC-200 Last Minute Revision

### One Page Cheat Sheet

| Connector | Installed From | Configured Under | Table(s) | Role Needed | Data Type |
|---|---|---|---|---|---|
| Microsoft 365 | Content Hub | Configuration → Data Connectors | `OfficeActivity` | Global/Security Admin | Raw logs |
| Microsoft Entra ID | Content Hub | Configuration → Data Connectors | 7 tables (see section 3) | Global/Security Admin | Raw logs |
| Microsoft Entra ID Protection | Content Hub | Configuration → Data Connectors | `SecurityAlert` | Global/Security Admin + Entra ID Premium P2 | Alerts |
| Azure Activity | Content Hub | Azure Policy Assignment Wizard | `AzureActivity` | Subscription Owner | Raw logs |

### Frequently Confused Pairs

> **Microsoft Entra ID vs Microsoft Entra ID Protection**
> Entra ID = raw identity logs (who signed in, what changed). Entra ID Protection = analyzed alerts (is this sign in risky). Entra ID Protection needs a **Premium P2** license; plain Entra ID does not.

> **`AzureActivity` vs Azure Resource Logs**
> `AzureActivity` = subscription level control plane events (who created/deleted/changed a resource). Azure Resource Logs = detailed diagnostic events emitted from inside individual resources, configured separately per resource.

> **Interactive vs Non-interactive Sign in Logs**
> Interactive = a human actively typed credentials or approved an MFA prompt. Non-interactive = the sign in happened silently in the background (refresh token renewal, mobile app polling), no human action involved.

### Facts to Memorize Before the Exam

1. Every native connector in this module is installed as a **solution from Content Hub** before it can be configured.
2. Microsoft 365 connector, one connector, one table: **`OfficeActivity`**.
3. Entra ID connector, one connector, **seven possible tables**, each log type is independent and billed separately.
4. Entra ID Protection sends **alerts only**, to **`SecurityAlert`**, and needs **Premium P2**.
5. Azure Activity is configured through **Azure Policy**, not a simple connect button, and needs **Owner** at the subscription scope.
6. **Create incidents** is a toggle available on alert generating connectors (such as Entra ID Protection) to auto generate Sentinel incidents.
7. **Create a remediation task** during Azure Activity policy assignment ensures existing resources, not just new ones, are covered.

### Quick Workflow to Remember

```text
Identify the data source needed for an investigation
        │
        ▼
Confirm the matching Content Hub solution is installed
        │
        ▼
Configure the connector (toggle, or Azure Policy for Azure Activity)
        │
        ▼
Data lands in its Log Analytics table
        │
        ▼
Query with KQL, or build an analytics rule
        │
        ▼
Alerts and incidents appear in Microsoft Sentinel
```

> **Final Tip:** If an exam question describes a scenario and asks "which table would you query," first decide whether the scenario involves Microsoft 365 activity, identity sign ins/admin actions, identity risk alerts, or Azure subscription management, then match it to the single relevant table from Section 6. This connector to table mapping is the highest value, fastest to review fact in this entire module.
