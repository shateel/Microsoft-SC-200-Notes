## Quick Overview

Microsoft Sentinel is a cloud native **SIEM** (Security Information and Event Management) and **SOAR** (Security Orchestration, Automation, and Response) platform. It cannot analyze what it cannot see, so the first job of a Security Operations Analyst is to **connect data sources**.

This module covers three connector families:

* Microsoft Defender XDR connector, which unifies Endpoint, Identity, Office 365, Cloud Apps, Purview, and Entra signals.
* Microsoft Defender for Cloud connector, which brings in cloud resource security posture and workload protection alerts.
* Microsoft Defender for IoT connector, which brings in IoT and OT device security alerts.

> **Exam Tip:** SC-200 frequently tests *which product detects a threat* versus *which product investigates and responds to it*. As a rule, the Defender family of products **detects**, and Microsoft Sentinel **investigates, correlates, and automates the response**.

## Microsoft Defender XDR Overview

Microsoft Defender XDR (Extended Detection and Response) combines several Microsoft security products into a single investigation experience. Each product protects a different layer of the environment, and Defender XDR fuses their signals together.

| Product | Protects |
|---|---|
| Microsoft Defender for Endpoint | Devices and endpoints |
| Microsoft Defender for Identity | On premises Active Directory identity signals |
| Microsoft Defender for Office 365 | Email and collaboration tools |
| Microsoft Defender for Cloud Apps | SaaS and cloud application usage |

> **Key Definition:** **XDR** stands for **Extended Detection and Response**. It correlates signals across multiple security layers (endpoint, identity, email, cloud apps) rather than looking at each one in isolation, which is what separates it from a single point product.

## Connecting the Microsoft Defender XDR Connector

### What the Connector Is

The **Microsoft Defender XDR Connector** is a **Microsoft Sentinel Data Connector** that imports Microsoft Defender XDR security data into Microsoft Sentinel. Instead of connecting each Defender product one at a time, a single connector imports:

* Incidents
* Alerts
* Advanced Hunting Events

It also keeps incidents synchronized between Microsoft Sentinel and Microsoft Defender XDR in both directions.

### What Data It Collects

```text
Microsoft Defender for Endpoint
Microsoft Defender for Identity
Microsoft Defender for Office 365
Microsoft Defender for Cloud Apps
Microsoft Defender for Cloud
Microsoft Purview Data Loss Prevention (DLP)
Microsoft Entra ID Protection
Microsoft Purview Insider Risk Management
        │
        ▼
Microsoft Defender XDR Connector
        │
        ▼
Microsoft Sentinel (Incidents, Alerts, Advanced Hunting Events)
```

This single connector lets Sentinel investigate threats across endpoints, identities, email, cloud applications, cloud resources, and insider risk from one place.

### Two Integration Methods

There are **two ways** to integrate Microsoft Defender XDR with Microsoft Sentinel.

#### Method 1: Defender Portal Integration

If Microsoft Sentinel is onboarded to the **Microsoft Defender portal** and the organization is licensed for Microsoft Defender XDR, integration happens automatically:

* Microsoft Sentinel is automatically connected to Microsoft Defender XDR.
* The Microsoft Defender XDR connector is automatically configured.
* Supported legacy Defender connectors are automatically disconnected (see table below).
* Analysts work directly from the **Microsoft Defender portal**, using a unified SIEM and XDR experience.

Legacy connectors automatically disconnected during Defender portal integration:

| Legacy Connector |
|---|
| Microsoft Defender for Cloud Apps (alerts) |
| Microsoft Defender for Endpoint |
| Microsoft Defender for Identity |
| Microsoft Defender for Office 365 |
| Microsoft Entra ID Protection |

> **Exam Tip:** Disconnecting these legacy connectors is intentional. It prevents duplicate data collection and simplifies management once the unified connector is active.

#### Method 2: Azure Portal Integration (Manual Setup)

If the organization continues managing Microsoft Sentinel from the **Azure portal**, the Microsoft Defender XDR connector must be configured manually.

> **Exam Tip:** This manual Azure portal workflow is **the configuration process most commonly tested in the SC-200 exam**. Memorize the exact click path below.

```text
Step 1: Install the Microsoft Defender XDR Solution from the Content Hub
        │
        ▼
Step 2: Open Data Connectors and select the Microsoft Defender XDR connector page
        │
        ▼
Step 3: Verify prerequisites (workspace, connector, and tenant permissions, plus license)
        │
        ▼
Step 4: Select "Connect incidents & alerts"
        │
        ▼
Step 5: Connect UEBA entities and Advanced Hunting events, then "Apply Changes"
```

**Step 1 navigation path (Content Hub):**

```text
Microsoft Sentinel
        │
        ▼
Content Management
        │
        ▼
Content Hub
        │
        ▼
Search "Microsoft Defender XDR"
        │
        ▼
Install
```

**Step 2 navigation path (Data Connectors):**

```text
Microsoft Sentinel
        │
        ▼
Configuration
        │
        ▼
Data Connectors
        │
        ▼
Select "Microsoft Defender XDR" → Open connector page
```

**Step 3, prerequisites to verify before connecting:**

* Workspace permissions.
* Connector access permissions.
* Tenant permissions.
* A supported Microsoft Defender XDR license.

**Step 4, connect incidents and alerts:** Under **Configuration**, select **Connect incidents & alerts**. Under normal conditions, incidents appear in Microsoft Sentinel within a few minutes, though data ingestion into backend tables can take slightly longer.

**Step 5, connect UEBA entities and events:** The connector can also ingest:

* **UEBA Entities**, User and Entity Behavior Analytics data used to detect abnormal behavior.
* **Advanced Hunting Events**, raw telemetry used for threat hunting queries.

Select **Connect entities** and **Connect events**, choose the event types needed, then select **Apply Changes**.

> **Exam Tip:** Organizations typically enable only the event types required for threat hunting, to reduce unnecessary data ingestion and control cost.

### Important Considerations

Microsoft Defender XDR already has its own incident creation engine. To avoid duplicate incidents in Microsoft Sentinel, keep the following option **enabled**:

> **"Turn off all Microsoft incident creation rules for these products"**

If this setting is disabled, duplicate incidents may appear in Microsoft Sentinel because both Defender XDR and Sentinel would try to create incidents from the same alerts.

The following incident fields synchronize between Microsoft Defender XDR and Microsoft Sentinel:

| Synchronized Fields |
|---|
| Title |
| Severity |
| Description |
| Comments |

### SC-200 Exam Tips (Defender XDR Connector)

* The Microsoft Defender XDR Connector imports **Incidents**, **Alerts**, and **Advanced Hunting Events**.
* It collects data from Defender for Endpoint, Defender for Identity, Defender for Office 365, Defender for Cloud Apps, and Defender for Cloud.
* It also includes alerts from Purview DLP, Entra ID Protection, and Purview Insider Risk Management.
* There are **two integration methods**: Defender portal integration (automatic) and Azure portal integration (manual).
* Azure portal integration requires installing the Microsoft Defender XDR Solution, opening **Configuration → Data Connectors**, and selecting **Connect incidents & alerts**.
* UEBA collects user and entity behavioral information; Advanced Hunting events provide raw telemetry for threat hunting.
* Keep **"Turn off all Microsoft incident creation rules for these products"** enabled to avoid duplicate incidents.
* Title, Severity, Description, and Comments synchronize between the two platforms.

## Connecting Microsoft Defender for Cloud

### What It Is

Microsoft Defender for Cloud is Microsoft's **Cloud Security Posture Management (CSPM)** and **Cloud Workload Protection Platform (CWPP)** solution. It continuously monitors cloud resources for:

* Security misconfigurations
* Vulnerabilities
* Active attacks
* Compliance issues
* Suspicious behavior

It protects workloads running in:

* Microsoft Azure
* Amazon Web Services (AWS)
* Google Cloud Platform (GCP)
* Hybrid environments
* Servers hosted locally and connected through Azure Arc

Its primary goal is to improve an organization's security posture while detecting attacks against cloud resources.

### What Is a Workload

A **workload** is any application, service, or computing resource that performs work for a business or user. Think of it as **anything that runs and processes data**.

| Example Workload | Type |
|---|---|
| Windows Server running Active Directory | Identity infrastructure |
| Linux web server hosting a website | Web hosting |
| SQL database storing customer records | Data storage |
| Kubernetes cluster running containers | Container orchestration |
| Azure Virtual Machine (VM) | Compute |
| Docker container | Application packaging |
| Azure App Service hosting a web application | Platform as a service |

### How It Connects to Sentinel

```text
Cloud Resources (Azure, AWS, GCP, Hybrid, locally hosted via Azure Arc)
        │
        ▼
Microsoft Defender for Cloud (detects misconfigurations, vulnerabilities, attacks)
        │
        ▼
Microsoft Sentinel (investigates, correlates, automates response)
```

### SC-200 Exam Tips (Defender for Cloud)

* Microsoft Defender for Cloud primarily protects Azure, hybrid, and multicloud resources.
* The connector streams Defender for Cloud security alerts into Microsoft Sentinel.
* Sentinel becomes the central investigation platform once the connector is configured.
* Defender for Cloud is responsible for cloud security monitoring, while Sentinel performs SIEM and SOAR functions.
* Bidirectional sync keeps incident status synchronized between Defender for Cloud and Sentinel.
* Cloud alerts can be correlated with identity, endpoint, and email telemetry inside Sentinel.
* Automation Rules and Logic Apps are commonly used once alerts are ingested.
* Defender for Cloud combines two roles: security posture (CSPM) and workload protection (CWPP).
* Expect exam questions asking which product **detects** the threat (Defender for Cloud) versus which product **investigates and automates response** (Microsoft Sentinel).

## Connecting Microsoft Defender for IoT

### What It Is

Microsoft Defender for IoT discovers, monitors, and protects **Internet of Things (IoT)** and **Operational Technology (OT)** devices. Unlike traditional computers, IoT devices usually have limited security features and cannot always run antivirus software, so Defender for IoT monitors network traffic and device behavior to detect threats without requiring an agent on every device.

| Category | Example Devices |
|---|---|
| Physical security | Smart cameras, smart sensors |
| Healthcare | Medical devices |
| Industrial and OT | Industrial controllers (PLCs), manufacturing robots |
| Building systems | HVAC systems, smart lighting, building management systems |
| Network equipment | Network printers, IP phones |

### Why Connect It to Sentinel

Organizations often have thousands of IoT devices spread across offices, factories, hospitals, and remote sites. Connecting Defender for IoT to Microsoft Sentinel lets a SOC:

* Centralize IoT security alerts.
* Investigate IoT incidents alongside other security data.
* Correlate IoT attacks with identity and endpoint events.
* Perform threat hunting using KQL.
* Create automated response workflows.
* Monitor IoT security from a single SIEM platform.

The connector also provides ready to use access to IoT alert metrics, trends, top alerts, severity breakdowns, and recommendations.

### How to Connect It

```text
Open Microsoft Sentinel
        │
        ▼
Navigate to Data Connectors
        │
        ▼
Select Microsoft Defender for IoT
        │
        ▼
Open the connector page
        │
        ▼
Enable the Connect toggle for the Azure subscription
        │
        ▼
IoT alerts begin flowing into Microsoft Sentinel
```

### SC-200 Exam Tips (Defender for IoT)

* Defender for IoT is agentless: it monitors network traffic and device behavior rather than installing software on every device.
* It covers both **IoT** (consumer and enterprise connected devices) and **OT** (industrial control systems).
* Connecting it to Sentinel centralizes IoT and OT alerts alongside identity, endpoint, email, and cloud data for correlation and hunting.
* The connection is enabled per Azure subscription using a simple **Connect** toggle on the connector page, unlike the multi step Defender XDR setup.

## Legacy Defender Connectors

> **Note on this section:** the source study material's "Legacy Defender Connectors" module heading did not contain any body text. The content below is compiled from information already presented earlier in this same document (the list of legacy connectors that Defender portal integration automatically disconnects), so no new facts have been introduced.

Before the unified Microsoft Defender XDR connector existed, each Defender product had its own **individual, product specific data connector** in Microsoft Sentinel. These are commonly referred to as legacy connectors.

| Legacy Connector | Replaced By |
|---|---|
| Microsoft Defender for Cloud Apps (alerts) | Microsoft Defender XDR Connector |
| Microsoft Defender for Endpoint | Microsoft Defender XDR Connector |
| Microsoft Defender for Identity | Microsoft Defender XDR Connector |
| Microsoft Defender for Office 365 | Microsoft Defender XDR Connector |
| Microsoft Entra ID Protection | Microsoft Defender XDR Connector |

### SC-200 Exam Tips (Legacy Connectors)

* Running a legacy connector alongside the unified Defender XDR connector for the same product causes duplicate data ingestion.
* Microsoft's guidance is to migrate to the unified Microsoft Defender XDR connector rather than maintaining individual legacy connectors.
* During Defender portal integration, supported legacy connectors are disconnected automatically. During Azure portal integration, an analyst should verify and remove redundant legacy connectors manually.

## Querying Connected Data with KQL

> **Added for exam preparation:** the source module covers connector setup only and does not contain KQL examples. Since SC-200 also tests querying the data these connectors ingest, this section adds the standard table names and a sample query for revision purposes.

Once the connectors above are active, their data lands in specific tables that can be queried with **KQL (Kusto Query Language)** inside Microsoft Sentinel or Defender Advanced Hunting.

| Table | Populated By | Contains |
|---|---|---|
| SecurityIncident | Microsoft Defender XDR Connector | Incident level records (title, severity, status, owner) |
| SecurityAlert | Microsoft Defender XDR Connector and other connectors | Individual alerts feeding into incidents |
| DeviceProcessEvents / DeviceEvents | Advanced Hunting Events (Defender for Endpoint) | Endpoint process and activity telemetry |
| IdentityLogonEvents | Advanced Hunting Events (Defender for Identity) | Authentication and identity activity |
| EmailEvents | Advanced Hunting Events (Defender for Office 365) | Email delivery and threat data |
| CloudAppEvents | Advanced Hunting Events (Defender for Cloud Apps) | SaaS and cloud application activity |

Example query to review the last day of high severity incidents:

```kql
SecurityIncident
| where TimeGenerated > ago(24h)
| where Severity == "High"
| project TimeGenerated, Title, Severity, Status, Owner
```

> **Exam Tip:** The **Advanced Hunting Events** you enable in Step 5 of the Defender XDR connector determine which raw telemetry tables (like `DeviceProcessEvents`, `IdentityLogonEvents`, `EmailEvents`, `CloudAppEvents`) become queryable in Sentinel. Enabling fewer event types reduces ingestion cost but also reduces hunting visibility.

## SC-200 Last Minute Revision

### One Page Cheat Sheet

* Microsoft Defender XDR combines Defender for Endpoint, Identity, Office 365, and Cloud Apps signals into one investigation.
* The Microsoft Defender XDR Connector imports Incidents, Alerts, and Advanced Hunting Events into Sentinel.
* Two integration methods exist: Defender portal integration (automatic) and Azure portal integration (manual, most tested).
* Azure portal path: Content Hub install, then Data Connectors, then Connect incidents & alerts, then connect UEBA entities and events.
* Keep **"Turn off all Microsoft incident creation rules for these products"** enabled to prevent duplicate incidents.
* Synchronized incident fields: Title, Severity, Description, Comments.
* Defender for Cloud is CSPM plus CWPP: it finds misconfigurations, vulnerabilities, and attacks across Azure, AWS, GCP, hybrid, and locally hosted resources connected through Azure Arc.
* A workload is anything that runs and processes data (VM, container, database, app service, and similar).
* Defender for IoT is agentless and protects IoT and OT devices by monitoring network traffic and device behavior.
* Connecting Defender for IoT to Sentinel is a simple toggle per Azure subscription, unlike the multi step Defender XDR setup.
* Legacy, product specific connectors should be migrated to the unified Defender XDR connector to avoid duplicate data.
* General rule for the exam: Defender products **detect**; Microsoft Sentinel **investigates, correlates, and automates response**.

### Frequently Confused Terms

| Term | Meaning | Do Not Confuse With |
|---|---|---|
| XDR | Extended Detection and Response, correlates signals across endpoint, identity, email, cloud apps | SIEM, which is Sentinel's broader log platform role |
| SIEM | Security Information and Event Management, Sentinel's log collection and correlation role | SOAR, which is the automation role |
| SOAR | Security Orchestration, Automation, and Response, Sentinel's automation and playbook role | SIEM |
| CSPM | Cloud Security Posture Management, finds misconfigurations before an attack | CWPP, which protects the running workload itself |
| CWPP | Cloud Workload Protection Platform, protects running cloud workloads | CSPM |
| UEBA | User and Entity Behavior Analytics, detects abnormal behavior patterns | Advanced Hunting Events, which is raw telemetry rather than behavior analytics |

### Common Exam Traps

* Assuming Defender for Cloud protects endpoints. It does not; that is Defender for Endpoint's job. Defender for Cloud protects cloud resource posture and workloads.
* Forgetting that disabling **"Turn off all Microsoft incident creation rules for these products"** causes duplicate incidents.
* Mixing up CSPM (finding weaknesses before an attack) with CWPP (protecting the workload while it runs).
* Assuming the Defender XDR connector is a single toggle like the IoT connector. It is a multi step process: install the solution, verify prerequisites, connect incidents and alerts, then connect UEBA entities and events.
* Forgetting that Advanced Hunting Events selected during setup control which raw telemetry tables (DeviceProcessEvents, IdentityLogonEvents, EmailEvents, CloudAppEvents) are available for KQL hunting in Sentinel.
