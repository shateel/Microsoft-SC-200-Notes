## Overview of the Windows Hosts Security Events Connector

A Windows Hosts Security Events Connector sends Windows Security Event Logs into Microsoft Sentinel for monitoring, detection, hunting, investigation, and incident response.

> Without a connector, Sentinel cannot analyze Windows logon events, correlate alerts with Windows activity, support meaningful threat hunting, or build a complete investigation timeline.

Sources of Windows Security Events include Windows Servers, Domain Controllers, Windows 10/11 clients, Azure Virtual Machines, on premises Windows Servers, and hybrid Windows devices.

Common Security Events tested on the exam:

1. User logon and failed logon
2. Account lockout
3. Privilege changes and group membership changes
4. Process creation
5. Service installation
6. Scheduled task creation

Once ingested, these events become searchable with KQL inside Microsoft Sentinel.

### Exam Tips: Overview

> **SC-200 Exam Tips**
1. Know that the connector's job is simply to move Windows Event Logs into Sentinel; detection and investigation happen afterward inside Sentinel.
2. Be able to recognize common Security Event categories (logon, privilege change, process creation) from a scenario description.

## Planning Windows Security Event Collection

Microsoft provides two primary collection methods. Choosing between them is a recurring exam scenario.

### Content Hub Solution: AMA vs Legacy Agent

This is Microsoft's recommended approach. Installing the **Windows Security Events** solution from the Content Hub provides two possible connectors:

1. **Windows Security Events via AMA Connector** (recommended)
2. **Security Events via Legacy Agent Connector** (deprecated, uses the Log Analytics Agent / MMA)

```text
Windows Device
      │
      ▼
Azure Monitor Agent (AMA)
      │
      ▼
Data Collection Rule (DCR)
      │
      ▼
Azure Monitor
      │
      ▼
Microsoft Sentinel
```

| Aspect | Windows Security Events via AMA | Security Events via Legacy Agent |
|---|---|---|
| Underlying agent | Azure Monitor Agent (AMA) | Log Analytics Agent (MMA) |
| Status | Current, recommended | Deprecated |
| Filtering | At the source, using a DCR | Limited, workspace level |
| Management | Centralized, DCR based | Per workspace configuration |

### Windows Forwarded Events Method

Instead of installing an agent on every computer, Windows devices send events to a centralized **Windows Event Collector (WEC)**. The collector forwards all events to Microsoft Sentinel using the **Windows Forwarded Events** connector.

```text
Windows PC 1
      │
Windows PC 2
      │
Domain Controller
      │
      ▼
Windows Event Collector (WEC)
      │
      ▼
Windows Forwarded Events Connector
      │
      ▼
Microsoft Sentinel
```

This approach fits scenarios where:

1. A large enterprise already uses Windows Event Forwarding.
2. The organization wants centralized event collection.
3. Agents cannot be installed on every endpoint.

### Exam Tips: Planning Collection

> **SC-200 Exam Tips**
1. Given a scenario, pick AMA for direct, per machine collection and Windows Forwarded Events for centralized, agentless endpoint scenarios.
2. Remember that Windows Forwarded Events still relies on AMA, just installed on the WEC server rather than every endpoint.

## Windows Security Events via AMA Connector

The **Windows Security Events via Azure Monitor Agent (AMA) Connector** is the recommended method for collecting Windows Security Event Logs into Microsoft Sentinel. Administrators create **Data Collection Rules (DCRs)** to specify exactly which events are collected and from which machines, instead of collecting everything from every computer. Machines outside Azure must first be onboarded to **Azure Arc** before they can use the AMA connector.

### What Is Azure Monitor Agent

**AMA (Azure Monitor Agent)** is Microsoft's modern monitoring agent that replaces the older Log Analytics Agent (MMA). It securely collects:

1. Security Events
2. Performance data
3. Event Logs
4. Syslog
5. Custom Logs

and sends them into Azure Monitor. AMA performs filtering at the source, so unnecessary events never leave the endpoint, which reduces bandwidth usage, storage consumption, and ingestion costs.

### Data Collection Rules

A **Data Collection Rule (DCR)** is a configuration object that controls what data AMA collects from monitored devices. Think of it as a policy: one DCR can be applied to many computers instead of configuring each machine individually.

A DCR defines:

1. Which Windows computers collect logs
2. Which event logs and Event IDs are collected
3. Which Log Analytics Workspace receives the data
4. Filtering rules (which events to keep or ignore)

Example: a DCR could collect only Event ID 4624, Event ID 4625, and Event ID 4688, and ignore everything else, which lowers ingestion costs, reduces noise, and improves query performance.

> **Important:** A DCR can be reused across different resource groups and subscriptions as long as they belong to the same Microsoft Entra tenant.

### Azure Arc for Machines Outside Azure

**Azure Arc** allows machines that are not Azure virtual machines, such as on premises servers or Windows VMs hosted in other clouds, to be managed as if they were Azure resources. Azure Arc installs the **Azure Connected Machine Agent (azcmagent)** on the device, which then enables Azure native management, including AMA deployment.

```text
Machine Outside Azure
      │
      ▼
Azure Arc (azcmagent)
      │
      ▼
Azure Monitor Agent (AMA)
      │
      ▼
Data Collection Rule (DCR)
      │
      ▼
Azure Monitor
      │
      ▼
Log Analytics Workspace
      │
      ▼
Microsoft Sentinel
```

### Prerequisites

Before configuring the connector:

1. **Microsoft Sentinel permissions.** You need permission to read the Sentinel workspace and write configuration changes, otherwise you cannot create or modify DCRs.
2. **Azure Arc requirement.** Any monitored system that is not an Azure virtual machine (physical servers, on premises VMs, VMs in non Azure clouds) must have Azure Arc installed and enabled before it can use the AMA based connector.

### Event Collection Levels

There are four event collection levels, and matching the right level to a scenario is a common exam question.

| Level | What It Collects | Visibility | Cost |
|---|---|---|---|
| All Security Events | Every Security Event | Highest | Highest |
| Common | Commonly used security events | Balanced | Moderate |
| Minimal | Only essential events | Limited | Lowest |
| Custom | Defined by XPath queries | Fully controlled | Depends on filter |

> Choose **All Security Events** for critical servers and deep investigations, **Common** for most production environments, **Minimal** when cost control is the priority, and **Custom** when only specific Event IDs matter.

### XPath Custom Filtering

XPath is used inside a Custom DCR when you need to:

1. Collect only specific Event IDs.
2. Reduce ingestion costs by excluding everything else.
3. Apply advanced filtering logic that the built in levels cannot express.

Example: collect Event ID 4624 and Event ID 4625, and ignore everything else.

> Always validate an XPath query before deploying it in a production DCR.

### Connecting Azure Virtual Machines

Azure Windows Virtual Machines connect directly using the AMA connector.

```text
Azure Windows VM
      │
      ▼
Azure Monitor Agent (AMA)
      │
      ▼
Data Collection Rule (DCR)
      │
      ▼
Azure Monitor
      │
      ▼
Log Analytics Workspace
      │
      ▼
Microsoft Sentinel
```

Steps:

1. Open Microsoft Sentinel, go to **Data Connectors**, and select the **Windows Security Events via AMA** connector.
2. Select **Create Data Collection Rule** and enter the rule name, subscription, and resource group.
3. Select the Azure Windows VMs to monitor.
4. If AMA is not already installed, Azure installs it automatically on the selected VMs.
5. Choose an Event Collection Level: All Security Events, Common, Minimal, or Custom (XPath).
6. Save the DCR. The VMs begin sending Windows Security Events to Microsoft Sentinel.

### Connecting Machines Outside Azure

Machines outside Azure, such as physical servers, on premises virtual machines, or Windows VMs hosted in other clouds, must first be onboarded to Azure Arc.

```text
Machine Outside Azure
      │
      ▼
Azure Arc (Connected Machine Agent)
      │
      ▼
Azure Monitor Agent (AMA)
      │
      ▼
Data Collection Rule (DCR)
      │
      ▼
Azure Monitor
      │
      ▼
Log Analytics Workspace
      │
      ▼
Microsoft Sentinel
```

Steps:

1. Onboard the Windows machine to Azure Arc by installing the Azure Connected Machine Agent and registering the server.
2. Verify the machine appears as an Azure Arc resource.
3. Open Microsoft Sentinel, go to **Data Connectors**, and select the **Windows Security Events via AMA** connector.
4. Create a Data Collection Rule with the required settings.
5. Assign the DCR to the Azure Arc enabled machine.
6. If AMA is not already installed, Azure installs it automatically during DCR assignment.
7. Choose an Event Collection Level: All Security Events, Common, Minimal, or Custom (XPath).
8. Save the DCR. The machine starts sending Windows Security Events to Microsoft Sentinel.

Quick role summary:

1. **Azure Monitor Agent** collects logs.
2. **Data Collection Rule** filters logs.
3. **Azure Monitor** receives telemetry.
4. **Log Analytics Workspace** stores logs.
5. **Microsoft Sentinel** detects, investigates, and automates responses.

### Exam Tips: AMA Connector

> **SC-200 Exam Tips**
1. Use **Windows Security Events via AMA** for new deployments; it is Microsoft's recommended connector.
2. **Security Events via Legacy Agent (MMA)** is deprecated; prefer AMA whenever possible.
3. DCRs determine which machines collect data, which events are collected, and where the data is sent, filtering happens before data leaves the endpoint.
4. One DCR can be assigned to multiple machines, and reused across resource groups and subscriptions within the same Microsoft Entra tenant.
5. Azure VMs use AMA directly; machines outside Azure need Azure Arc first.
6. Azure automatically installs AMA on selected resources if it is not already present.
7. Memorize the four event collection levels and when to use each one.
8. Memorize the data flow: **Windows Host → AMA → DCR → Azure Monitor → Log Analytics Workspace → Microsoft Sentinel → Analytics Rule → Incident.**
9. AMA collects data; Microsoft Sentinel detects threats, these are separate responsibilities.

## Collecting Sysmon Event Logs

This module covers Sysmon telemetry delivered through the **Windows Forwarded Events** connector, a separate scenario from the direct Security Events via AMA connector above.

### What Is Sysmon

**Sysmon (System Monitor)** is a Windows system service and device driver from the Microsoft Sysinternals suite. It continuously monitors system activity and writes detailed events to the Windows Event Log, and it stays active across reboots for persistent visibility.

Sysmon records detail that helps analysts detect malicious behavior, including:

1. Process creation and network connections
2. File creation and file creation time changes
3. Driver and image loading
4. Registry modifications and process injection
5. DNS queries, depending on configuration

These events help analysts identify attacker behavior, malware execution, lateral movement, and persistence techniques.

### Windows Event Forwarding and Windows Event Collector

**Windows Event Forwarding (WEF)** is a Windows feature that forwards Windows Event Logs from one Windows computer to another. The destination computer is called a **Windows Event Collector (WEC)**.

> WEF does **not** send logs to Microsoft Sentinel. Its only job is moving Windows Event Logs between Windows computers.

```text
Windows PC (Sysmon Event)
      │
      ▼
Windows Event Forwarding (WEF)
      │
      ▼
Windows Event Collector (WEC)
```

When WEF sends logs to a WEC, those logs land in another Windows Event Log called **Forwarded Events**:

```text
Windows Event Collector
Windows Logs
      │
      ├── Application
      ├── Security
      ├── System
      └── Forwarded Events
```

### Why Azure Monitor Agent Is Needed

WEF only moves logs between Windows machines, and Microsoft Sentinel cannot read Windows Event Logs directly. Something must collect those logs and upload them into Azure, and that component is **Azure Monitor Agent (AMA)**. AMA reads the Windows Event Logs, including the Forwarded Events log, and uploads them to Azure Monitor.

> Think of AMA as the bridge between Windows and Azure.

```text
Windows Event Collector
      │
      ▼
Forwarded Events Log
      │
      ▼
Azure Monitor Agent (AMA)
      │
      ▼
Azure Monitor
```

Example at scale: with 500 Windows PCs, all 500 forward their Sysmon events to one WEC server (or a small number of WEC servers for scalability). The WEC server stores all forwarded events in its Forwarded Events log. AMA is installed only on the WEC server, reads the Forwarded Events log, and uploads it to Microsoft Sentinel, so 500 separate AMA installations are not required.

### Two Architecture Options

**Option 1, AMA directly on every endpoint (most common in modern deployments):** AMA reads the Microsoft-Windows-Sysmon/Operational event log directly on each computer and uploads events to Azure, provided the DCR includes that log. There is no Windows Event Forwarding, no Windows Event Collector, and no Forwarded Events log involved.

```text
Windows PC (Sysmon)
      │
      ▼
Microsoft-Windows-Sysmon/Operational
      │
      ▼
Azure Monitor Agent (AMA)
      │
      ▼
Data Collection Rule (Collect Sysmon Log)
      │
      ▼
Azure Monitor
      │
      ▼
Log Analytics Workspace
      │
      ▼
Microsoft Sentinel
```

**Option 2, WEF architecture:** AMA is installed only on the WEC server, not on every endpoint.

```text
Windows PC (Sysmon)
      │
      ▼
Microsoft-Windows-Sysmon/Operational
      │
      ▼
Windows Event Forwarding (WEF)
      │
      ▼
Windows Event Collector (WEC)
      │
      ▼
Forwarded Events
      │
      ▼
Azure Monitor Agent (AMA, on WEC server only)
      │
      ▼
Azure Monitor
      │
      ▼
Microsoft Sentinel
```

| Option | AMA Installed On | WEC Required | Best For |
|---|---|---|---|
| Option 1: AMA per endpoint | Every endpoint | No | Modern deployments, simpler architecture |
| Option 2: WEF and WEC | WEC server only | Yes | Large environments that already use Windows Event Forwarding |

### Complete End to End Data Flow

```text
1. Sysmon monitors Windows activity
      │
      ▼
2. Sysmon writes events to
   Microsoft-Windows-Sysmon/Operational
      │
      ▼
3. Windows Event Forwarding (WEF)
   forwards the Sysmon events
      │
      ▼
4. Windows Event Collector (WEC)
   stores them in the Forwarded Events log
      │
      ▼
5. Azure Monitor Agent (AMA)
   reads the Forwarded Events log
   according to the Data Collection Rule (DCR)
      │
      ▼
6. AMA uploads the events to Azure Monitor
      │
      ▼
7. Azure Monitor stores them in the
   Log Analytics Workspace
      │
      ▼
8. Microsoft Sentinel analyzes the logs and
   creates alerts, incidents, and hunting results
```

### Key Terminology Recap

| Term | Role |
|---|---|
| Sysmon | Generates detailed endpoint telemetry |
| Windows Event Forwarding (WEF) | Moves Windows Event Logs from one Windows computer to another |
| Windows Event Collector (WEC) | Receives forwarded Windows Event Logs |
| Azure Monitor Agent (AMA) | Reads Windows Event Logs and sends them to Azure |
| Azure Monitor | Receives monitoring data |
| Log Analytics Workspace | Stores the logs |
| Microsoft Sentinel | Detects threats and investigates incidents |
| ASIM | Normalizes security data across different data sources so KQL queries and analytics rules work consistently regardless of the original log format |

> **Remember:** Sysmon equals endpoint telemetry. Windows Forwarded Events equals the log that holds forwarded Windows Event Logs. AMA equals the component that collects and sends logs. DCR equals the rule that controls what is collected. ASIM equals normalization across data sources.

### Installing the Windows Forwarded Events Solution

Before collecting Sysmon events, install the **Windows Forwarded Events** solution, which contains the Windows Forwarded Events data connector.

1. Open Microsoft Sentinel.
2. Navigate to **Content management** then **Content hub**.
3. Search for **Windows Forwarded Events**.
4. Select the solution and click **Install**.

> The Content Hub is used to install Microsoft Sentinel solutions in general, including data connectors, analytics rules, hunting queries, workbooks, and playbooks, not just this one connector.

Once installed, the **Windows Forwarded Events** connector becomes available inside Microsoft Sentinel so it can receive forwarded Windows Event logs.

### Configuring the Windows Forwarded Events Connector

After installing the solution, configure the connector to collect Sysmon logs.

```text
Install Sysmon
      │
      ▼
Install Windows Forwarded Events Solution
      │
      ▼
Configure Windows Forwarded Events Connector
      │
      ▼
Create Data Collection Rule
      │
      ▼
Select Custom
      │
      ▼
Microsoft-Windows-Sysmon/Operational!*
      │
      ▼
Azure Monitor Agent
      │
      ▼
Microsoft Sentinel
```

**Step 1, open the connector:**

1. Open Microsoft Sentinel.
2. Expand **Configuration**.
3. Select **Data connectors**.
4. Open **Windows Forwarded Events**.
5. Select **+ Create data collection rule**.

**Step 2, configure the Basic tab:**

1. **Rule Name**: a descriptive name for the DCR.
2. **Subscription**: the Azure subscription where the DCR is stored.
3. **Resource Group**: the Azure resource group where the DCR is stored.

> The subscription and resource group used to store the DCR do not need to match those of the monitored virtual machines.

**Step 3, select resources:**

1. Select **Next: Resources**.
2. Expand the Azure subscription, then the resource group.
3. Select the virtual machines that will send Sysmon logs to Microsoft Sentinel.

**Step 4, configure event collection:**

1. Select **Next: Collect**.
2. Choose the **Custom** radio button instead of **All Forwarded Events**.

**Step 5, add the Sysmon event log:**

Enter this exact event log location: `Microsoft-Windows-Sysmon/Operational!*`

Click **Add** to include it in the DCR. This is the Windows Event Log channel where Sysmon writes its events.

**Step 6, create the DCR:**

1. Select **Next: Review + Create**.
2. Wait for validation to complete.
3. Select **Create**.
4. Select **Refresh** afterward to see the new rule. Existing DCRs can also be edited or deleted from the connector configuration.

### Exam Tips: Sysmon and Windows Forwarded Events

> **SC-200 Exam Tips**
1. Sysmon provides detailed endpoint telemetry that goes beyond standard Windows Security logs.
2. Install the Windows Forwarded Events solution before configuring the connector.
3. Use the Windows Forwarded Events data connector, not the Security Events via AMA connector, to collect Sysmon events.
4. Create a DCR and select **Custom**, not **All Forwarded Events**, when only Sysmon logs are needed.
5. Memorize the exact event log path: `Microsoft-Windows-Sysmon/Operational!*`.
6. Azure automatically installs AMA if it is not already installed.
7. Enable ASIM normalization for standardized log fields and improved analytics.
8. The ingested Sysmon and forwarded events land in the **Event** table, this is a frequently tested fact.

## SC-200 Last Minute Revision

A one page cheat sheet for the day before the exam.

### Core Facts to Memorize

1. **AMA (Azure Monitor Agent)** is the current, recommended agent. The **Log Analytics Agent (MMA)** is deprecated.
2. A **Data Collection Rule (DCR)** defines what is collected, from which machines, and where it is sent. One DCR can serve many machines and can be reused across subscriptions within the same Microsoft Entra tenant.
3. **Azure Arc** is required before any machine that is not an Azure virtual machine can use the AMA connector.
4. There are four Event Collection Levels: All Security Events, Common, Minimal, and Custom (XPath).
5. **Windows Event Forwarding (WEF)** only moves logs between Windows machines; it never talks to Sentinel directly. **AMA** is what actually uploads data to Azure.
6. Sysmon telemetry reaches Sentinel through the **Windows Forwarded Events** connector, either directly (AMA on every endpoint) or via a **Windows Event Collector (WEC)**.

### Frequently Confused Concepts

| Easily Confused | Clarification |
|---|---|
| AMA vs Azure Arc | AMA collects and uploads log data. Azure Arc makes a non Azure machine manageable as an Azure resource so AMA can be deployed on it. |
| WEF vs Forwarded Events vs WEC | WEF is the forwarding mechanism. WEC is the destination server. Forwarded Events is the Windows Event Log on the WEC that stores the forwarded data. |
| Windows Security Events via AMA vs Windows Forwarded Events connector | The AMA connector collects Security Events (logons, privilege changes) typically into the **SecurityEvent** table. The Windows Forwarded Events connector collects forwarded logs, including Sysmon, into the **Event** table. |
| DCR vs Content Hub solution | The Content Hub solution installs the connector and related content. The DCR is the configuration object that decides what data that connector actually collects. |
| Common vs Custom collection level | Common is a Microsoft curated preset. Custom uses your own XPath query for exact control. |

### Quick Comparison: Connector Choice by Scenario

| Scenario | Connector to Use |
|---|---|
| Azure VM needs Windows Security Events | Windows Security Events via AMA |
| On premises server needs Windows Security Events | Windows Security Events via AMA, after Azure Arc onboarding |
| Large enterprise already using Windows Event Forwarding | Windows Forwarded Events |
| Need Sysmon telemetry from many endpoints | Windows Forwarded Events, either AMA per endpoint or via WEC |
| Legacy environment still on Log Analytics Agent | Migrate to AMA where possible; Legacy Agent is deprecated |

### Important KQL and Configuration Syntax to Remember

1. Sysmon event log path used in a Custom DCR: `Microsoft-Windows-Sysmon/Operational!*`
2. Example illustrative query against ingested events:

```kql
Event
| where EventID in (4624, 4625, 4688)
| project TimeGenerated, Computer, EventID, Account
```

3. Common Event IDs worth recognizing on the exam:

| Event ID | Meaning |
|---|---|
| 4624 | Successful logon |
| 4625 | Failed logon |
| 4688 | Process creation |

```text

      │
      ▼
Azure Monitor Agent (AMA)
      │
      ▼
Data Collection Rule (DCR)
      │
      ▼
Azure Monitor
      │
      ▼
Log Analytics Workspace
      │
      ▼
Microsoft Sentinel
      │
      ▼
Analytics Rule
      │
      ▼
Incident
```

> **Last check before the exam:** if a question asks which agent to use, answer AMA. If it asks which table Sysmon or forwarded events land in, answer Event. If it asks what makes a non Azure machine eligible for AMA, answer Azure Arc. If it asks what filters events before ingestion, answer the Data Collection Rule.
