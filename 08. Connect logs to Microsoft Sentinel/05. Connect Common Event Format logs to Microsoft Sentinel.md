## 1. Overview: CEF and Syslog Fundamentals

### What is CEF?

**Common Event Format (CEF)** is a vendor neutral, standardized log format originally developed by ArcSight. It gives security products a shared structure for writing log events, so Microsoft Sentinel does not need a custom parser for every vendor.

Devices that typically generate CEF logs include:

* Firewalls
* Intrusion Detection Systems (IDS)
* Intrusion Prevention Systems (IPS)
* Web Application Firewalls (WAF)
* Proxy servers
* VPN appliances
* Routers and switches
* Security gateways

### What is Syslog?

**Syslog** is the standard transport protocol that network and security devices use to send log messages. Most security appliances support it natively.

> **Core exam distinction**
>
> | Term | Role |
> |---|---|
> | **CEF** | Log **format** (the content and structure of the message) |
> | **Syslog** | Transport **protocol** (how the message is sent) |

Common Syslog transport methods:

* UDP
* TCP
* TLS (preferred for secure transmission)

Default Syslog port: **514**

### SC-200 Exam Tips

> * CEF and Syslog are frequently tested as a pair. Remember: **CEF describes what the log looks like, Syslog describes how it travels.**
> * A device can send plain Syslog or Syslog carrying a CEF payload. Both use the same transport, but they are ingested into different Sentinel tables (see Section 6).
> * Know the default Syslog port (**514**) and that it can run over UDP, TCP, or TLS.

## 2. Why a Linux Log Forwarder Is Required

Most network appliances (firewalls, proxies, gateways) run proprietary, closed operating systems and **cannot install the Azure Monitor Agent (AMA) directly**. Examples include:

* Cisco ASA
* Palo Alto Networks Firewall
* Fortinet FortiGate
* Check Point Firewall
* F5 BIG IP
* Sophos Firewall

Because these devices cannot run AMA themselves, they instead send Syslog messages to an intermediary: a **Linux Syslog Forwarder**. This is simply a Linux server (physical, on premises virtual machine, Azure virtual machine, or a virtual machine in another cloud) that:

1. Receives Syslog messages from multiple devices.
2. Processes them using a Syslog daemon.
3. Hosts the Azure Monitor Agent, which reads the collected messages.
4. Forwards the logs securely to Microsoft Sentinel.

Without a forwarder, each device would need its own direct connection to Sentinel, which is not possible for appliances that cannot run AMA. The forwarder centralizes collection instead:

```text
Firewall 1     Firewall 2     Firewall 3
     │              │              │
     └──────────────┼──────────────┘
                     ▼
          Linux Syslog Forwarder
                     │
                     ▼
           Azure Monitor Agent
                     │
                     ▼
             Microsoft Sentinel
```

The Linux forwarder does **not** generate security events itself. It only receives and relays them.

### What is a Syslog Daemon?

A **Syslog daemon** is the software on the Linux forwarder that listens on the Syslog port and receives incoming messages. Supported daemons:

* **rsyslog** (version 8 or later)
* **syslog-ng**

Its responsibilities:

1. Listen on the configured Syslog port.
2. Receive logs from external devices.
3. Store or process the incoming logs.
4. Make the logs available for Azure Monitor Agent to collect.

### SC-200 Exam Tips

> * Know **why** a forwarder is needed: proprietary appliance operating systems cannot run AMA.
> * The forwarder runs a **Syslog daemon** (rsyslog or syslog-ng), which is a separate component from AMA itself. The daemon receives the logs; AMA reads and uploads them.
> * AMA requires a **64 bit Linux** operating system on the forwarder.

## 3. CEF via AMA Architecture

### What is the CEF via AMA connector?

The **Common Event Format (CEF) via Azure Monitor Agent (AMA) connector** collects CEF formatted logs from third party security devices and delivers them into Microsoft Sentinel. The Azure Monitor Agent is installed on the Linux forwarder and configured through a **Data Collection Rule (DCR)**. AMA reads the CEF messages that the Syslog daemon has received and forwards them to the Sentinel workspace, where they are parsed and enriched.

A common misconception is that devices send logs **directly** to Microsoft Sentinel. They do not. Sentinel cannot read Syslog files on a Linux machine directly; AMA is the required bridge between Linux and Azure.

```text
Firewall
   │
   ▼
CEF Log
   │
   ▼
Syslog (UDP / TCP / TLS, Port 514)
   │
   ▼
Linux Forwarder
   │
   ▼
Syslog Daemon (rsyslog / syslog-ng)
   │
   ▼
Azure Monitor Agent (AMA)
   │
   ▼
Azure Monitor
   │
   ▼
Log Analytics Workspace
   │
   ▼
Microsoft Sentinel
```

### SC-200 Exam Tips

> * **Think of AMA as the bridge between Linux and Azure.** It is the only component that actually uploads data to the cloud.
> * The connector is configured through a **Data Collection Rule (DCR)**, not through agent side configuration files.
> * Network prerequisite: the machine running AMA needs **outbound port 443** open so it can reach Azure Monitor.

## 4. Setting Up the CEF via AMA Connector

Follow these steps in the Microsoft Sentinel portal:

1. **Open Data Connectors.** In Microsoft Sentinel, select **Data connectors**.
2. **Open the CEF Connector.** Search for **Common Event Format (CEF) via AMA**, select it, then open the connector page.
3. **Create a Data Collection Rule.** Under **Configuration**, select **+ Create data collection rule**.
4. **Configure Basic Settings.** Set the **Rule Name**, **Subscription**, and **Resource Group**. These determine where the DCR itself is stored.
5. **Select the Linux Log Forwarder.** On the **Resources** tab, choose the Linux machine that will act as the forwarder.
6. **Configure Collection Settings.** On the **Collect** tab, confirm the **CEF Facility** and **Log Level**.
7. **Deploy.** Select **Review + Create**, then **Create**. If AMA is not already present on the forwarder, it is installed automatically.
8. **Configure the Security Devices.** Point each firewall or appliance at the Linux forwarder, sending Syslog on **UDP 514** or **TCP 514**, depending on the device.

### Facility and log level, explained

| Setting | What it means | Exam relevance |
|---|---|---|
| **Facility** | Identifies the source or category of a Syslog message (for example `local0` or `auth`) | Used to filter which messages the DCR collects |
| **Log Level** | Indicates severity (Informational, Warning, Error, and so on) | Choosing the right level reduces unnecessary ingestion and cost |

### SC-200 Exam Tips

> * The DCR is created **from inside the connector page**, not as a separate, disconnected resource.
> * If AMA is missing from the forwarder, Sentinel installs it automatically during DCR deployment; you do not need to install it manually first.
> * Choosing a narrow **facility** and **log level** is a cost and noise control technique the exam may test as a "how do you reduce unnecessary log ingestion" scenario.
> * If a forwarder runs **both** the plain Syslog connector and the CEF connector, the same message can be ingested twice. Prevent duplication by adjusting the Syslog daemon configuration (for example, excluding the CEF sourced facility from the plain Syslog stream) or by adding an ingestion time transformation in the DCR.

## 5. The Complete Log to Incident Pipeline

This is the single most exam relevant diagram in this module. Memorize the order of components.

```text
Security Device (Firewall / IDS / IPS / WAF)
                    │
                    ▼
        Device detects a security event
                    │
                    ▼
      Device formats the event as a CEF message
                    │
                    ▼
   Sends the CEF message using Syslog
   (UDP / TCP / TLS, default Port 514)
                    │
                    ▼
             Linux Log Forwarder
                    │
                    ▼
      Syslog Daemon (rsyslog or syslog-ng)
                    │
                    ▼
           Azure Monitor Agent (AMA)
                    │
                    ▼
                Azure Monitor
                    │
                    ▼
           Log Analytics Workspace
                    │
                    ▼
             Microsoft Sentinel
      (log parsed and enriched into CommonSecurityLog)
                    │
                    ▼
   Analytics Rules / Hunting Queries / Workbooks
                    │
                    ▼
                 Incident
```

### Worked example

1. A firewall blocks a connection from source `10.10.10.5` to destination `192.168.1.20`.
2. The firewall formats this as a CEF message, structured like:

   ```text
   CEF:0|Vendor|Firewall|Version|100|Connection Denied|8|src=10.10.10.5 dst=192.168.1.20 act=deny
   ```

3. The firewall sends this CEF message over Syslog to the Linux forwarder.
4. The Syslog daemon on the forwarder receives it.
5. AMA reads it from the daemon and uploads it to Azure Monitor.
6. It lands in the Log Analytics Workspace, becomes visible in Microsoft Sentinel, and is available to Analytics Rules, Hunting Queries, Incidents, and Workbooks.

> **Remember the split:** *Event* is what happened. *CEF* is how that event is formatted for transport. Do not confuse the two when a question asks "what does the device generate first?" (Answer: the event; CEF formatting happens next.)

### SC-200 Exam Tips

> * Be able to reproduce this pipeline from memory, in order, including which component performs each step (device generates, device formats, Syslog transports, daemon receives, AMA uploads, Sentinel analyzes).
> * The Linux forwarder and its Syslog daemon **never talk to Sentinel directly**. Only AMA uploads data to Azure Monitor.
> * Once data reaches Sentinel it becomes available to Analytics Rules, Hunting Queries, Workbooks, and Investigations, which can then generate an Incident.

## 6. Where the Data Lands: Tables and KQL

CEF and plain Syslog messages are ingested into **different tables** in the Log Analytics workspace:

| Message type | Destination table |
|---|---|
| CEF formatted messages | **CommonSecurityLog** |
| Plain Syslog messages | **Syslog** |

> **Exam trap:** A question may ask "which table does the CEF connector write to?" The answer is **CommonSecurityLog**, not "Syslog," even though CEF is transported using the Syslog protocol. Format determines the table, not transport.

A simple KQL query to confirm CEF ingestion from a specific vendor:

```kql
CommonSecurityLog
| where TimeGenerated > ago(1d)
| where DeviceVendor == "Palo Alto Networks"
| where DeviceProduct == "PAN-OS"
| project TimeGenerated, DeviceVendor, DeviceProduct, SourceIP, DestinationIP, DeviceAction
```

Useful `CommonSecurityLog` fields to recognize for the exam:

* `DeviceVendor`, `DeviceProduct`, `DeviceVersion`
* `SourceIP`, `DestinationIP`
* `DeviceAction`
* `Activity`
* `LogSeverity`

### A note on the legacy Log Analytics agent

Older Sentinel documentation and some exam material may reference the legacy **Log Analytics agent** (also called the MMA or OMS agent) for CEF collection. That agent has been retired in favor of the **Azure Monitor Agent (AMA)** based connector covered in this guide. For current exam content, assume **AMA is the supported path**; if you see "Log Analytics agent" in an older question, treat it as the deprecated predecessor to AMA, not the recommended solution.

### SC-200 Exam Tips

> * Memorize: **CEF logs land in CommonSecurityLog; plain Syslog messages land in Syslog.**
> * `DeviceVendor` and `DeviceProduct` are the standard fields for filtering `CommonSecurityLog` by appliance type.
> * AMA based connectors need **outbound port 443** to reach Azure Monitor. This is a common prerequisite question.

## 7. Key Terms and Relationships

| Term | Definition |
|---|---|
| **CEF** | Standardized, vendor neutral log **format** |
| **Syslog** | Protocol that **transports** logs (UDP, TCP, or TLS, port 514 by default) |
| **Linux Log Forwarder** | Linux machine that receives Syslog/CEF messages and hosts AMA |
| **Syslog Daemon** | Software (rsyslog or syslog-ng) that listens for and receives Syslog messages on the forwarder |
| **Azure Monitor Agent (AMA)** | Agent that reads logs from the forwarder and uploads them to Azure Monitor |
| **Data Collection Rule (DCR)** | Configuration object that defines what AMA collects and how it is filtered |
| **Azure Monitor** | Ingestion service that receives data from AMA |
| **Log Analytics Workspace** | Storage location for ingested logs |
| **Microsoft Sentinel** | SIEM/SOAR layer that detects, investigates, hunts, and automates responses using workspace data |
| **CommonSecurityLog** | Table that stores parsed CEF messages |
| **Syslog table** | Table that stores plain (non CEF) Syslog messages |

### SC-200 Exam Tips

> * If a question describes a chain of components and asks "what comes next," walk the chain in this exact order: **Device → CEF → Syslog → Linux Forwarder → Syslog Daemon → AMA → Azure Monitor → Log Analytics Workspace → Sentinel.**
> * Do not swap AMA and the Syslog daemon. The daemon **receives**; AMA **uploads**.

### Frequently confused concepts

| Confusion | Clarification |
|---|---|
| "CEF is a protocol" | No. CEF is a **format**. Syslog is the **protocol** that carries it. |
| "Devices send logs straight to Sentinel" | No. Sentinel cannot read Syslog files directly; **AMA** must upload them via Azure Monitor. |
| "CEF messages go into the Syslog table" | No. CEF messages are parsed into **CommonSecurityLog**. Only plain Syslog messages go into the **Syslog** table. |
| "The Syslog daemon uploads to Azure" | No. The daemon only **receives** messages locally. **AMA** performs the upload. |
| "Any Linux forwarder works regardless of architecture" | AMA requires a **64 bit** Linux operating system. |
| "Log Analytics agent (MMA) is still the way to connect CEF" | That agent is retired. Use the **AMA based CEF connector**. |

### Quick facts to memorize

* Default Syslog port: **514** (UDP, TCP, or TLS).
* Supported Syslog daemons: **rsyslog** (v8+) and **syslog-ng**.
* CEF connector destination table: **CommonSecurityLog**.
* Plain Syslog destination table: **Syslog**.
* AMA is configured through a **Data Collection Rule (DCR)**.
* AMA needs **outbound port 443** to reach Azure Monitor.
* AMA requires a **64 bit** Linux forwarder.
* Prevent duplicate ingestion when running both Syslog and CEF connectors on one forwarder by adjusting the Syslog daemon configuration or adding a DCR ingestion time transformation.

### Component order, one more time

```text
Security Device → CEF → Syslog → Linux Forwarder → Syslog Daemon → AMA → Azure Monitor → Log Analytics Workspace → Microsoft Sentinel → Incident
```

> Walk this chain out loud until you can say it without looking. It is the backbone of nearly every question this module can produce.
