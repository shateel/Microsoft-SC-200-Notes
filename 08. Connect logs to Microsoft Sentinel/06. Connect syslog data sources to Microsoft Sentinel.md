## Overview

Microsoft Sentinel collects Linux Syslog data through the **Azure Monitor Agent (AMA)**, driven by a **Data Collection Rule (DCR)**. The onboarding path differs depending on where the Linux machine lives:

| Machine Location | Path to Sentinel |
|---|---|
| Already an Azure Virtual Machine | Configure a DCR directly. AMA installs automatically. |
| Outside Azure (on premises, VMware, Hyper-V, AWS, Google Cloud) | Onboard to **Azure Arc** first, then add the machine to a DCR. |

> **Exam tip:** the destination for both paths is the same, an **Azure Monitor Logs (Log Analytics) workspace** that Microsoft Sentinel is connected to. Only the onboarding route changes.

## Connecting an Azure Linux VM

When a Linux machine already runs as an **Azure VM**, Azure Arc is **not** required. You only need a **Data Collection Rule (DCR)** that targets the VM. Azure installs the **Azure Monitor Linux Agent (AMA)** extension automatically once the DCR is assigned.

### Configuration Steps

1. Open the Azure portal and search for **Monitor**, then open **Azure Monitor**.
2. In Azure Monitor, select **Data Collection Rules**, then select **+ Create**.
3. On the Basics tab, enter the rule name, subscription, resource group, region, and set **Platform Type = Linux**.
4. Select **Next: Resources**, then **+ Add resources**, expand the subscription and resource group, select the target Linux VM, and select **Apply**.
5. Select **Next: Collect and deliver**, then **+ Add data source**, and choose **Linux Syslog** as the data source. Confirm the destination is the Log Analytics workspace.
6. Select **Review + Create**, wait for validation, then select **Create**.
7. Azure automatically installs the **AzureMonitorLinuxAgent** extension on the VM.
8. To verify, open **Virtual Machines**, select the VM, open **Extensions + applications**, and confirm **AzureMonitorLinuxAgent** is listed.

> **Note:** if Microsoft Defender for Cloud automatic provisioning is enabled, AMA may already be present through Azure Policy before you even finish the DCR.

### Workflow Diagram

```text

      ▼

      │
      ▼

      │

installs automatically as a VM extension
      │

```

### SC-200 Exam Tips

* Azure Linux VMs do **not** need Azure Arc for Syslog collection.
* Syslog collection is configured through a **Data Collection Rule (DCR)**.
* Set **Platform Type = Linux** when creating the DCR.
* The Linux VM is added to the DCR as a **Resource**.
* The data source selected is **Linux Syslog**; the destination is the **Log Analytics workspace**.
* Assigning the DCR triggers automatic installation of the **Azure Monitor Linux Agent (AMA)**.
* Verify installation at **Virtual Machine → Extensions + applications**.
* Microsoft Defender for Cloud can pre install AMA through **Azure Policy** based automatic provisioning.

## Connecting a Linux Machine That Is Not Hosted in Azure

A Linux machine that is **not an Azure VM** (a physical server, a VMware or Hyper-V VM, an AWS EC2 instance, a Google Cloud instance, or any on premises server) cannot be targeted by a DCR directly. It must first be registered with Azure through **Azure Arc**.

> **Exam tip:** Azure Arc only makes the machine **visible and manageable** inside Azure. It does **not** collect or forward logs by itself.

### Onboarding to Azure Arc

1. Open the Azure portal, search for **Arc**, open **Azure Arc**, then select **Machines**.
2. Select **+ Add/Create**, then **Add a machine**, then choose **Generate script** for a single server.
3. Enter subscription, resource group, Azure region, and set **Operating System = Linux**.
4. Choose a connectivity method: public endpoint, proxy server, or private endpoint, depending on the network design.
5. Go to **Download and run script** and download or copy the generated Bash script.
6. On the Linux server, open a Bash terminal as **root** and run the script. It downloads and configures the Microsoft package repository, installs the **Azure Connected Machine Agent**, and creates the Azure Arc server resource.
7. Run **azcmagent connect**, which associates the server with the subscription, resource group, region, and tenant, and verifies connectivity to Azure.
8. The script displays the URL `https://microsoft.com/devicelogin`. Open it, enter the device code shown, and sign in with an administrator account to complete authentication.
9. Back in **Azure Arc → Machines**, confirm the server status shows **Connected**.

### Adding the Arc Machine to the Syslog DCR

Being connected to Azure Arc does **not** turn on Syslog collection by itself. The machine still has to be added to the existing DCR.

1. Search for **DCR** and open the previously created Syslog Data Collection Rule.
2. Open **Resources**, select **+ Add**, choose the Azure Arc Linux server, and select **Apply**.
3. Azure installs the **Azure Monitor Agent (AMA)** on the Arc enabled machine.
4. From this point, the native Linux service (**rsyslog** or **syslog-ng**) collects events locally, AMA receives them, AMA uploads them to Azure Monitor, and Microsoft Sentinel can analyze them.

### SC-200 Exam Tips

* A machine outside Azure must be onboarded to **Azure Arc** before Azure can manage it.
* Azure Arc installs the **Azure Connected Machine Agent (azcmagent)**.
* The Connected Machine Agent registers and manages the server; it does **not** collect logs.
* Server details required: subscription, resource group, region, and Operating System = Linux.
* Run the generated script as **root**.
* Authentication uses `https://microsoft.com/devicelogin` plus a device code.
* Confirm status is **Connected** under **Azure Arc → Machines** before assigning a DCR.
* After onboarding, the Arc machine must still be **added to the existing Syslog DCR** as a Resource.
* Assigning the DCR is what actually installs **AMA**, which is the component that collects the Syslog events.

## Configuring the DCR: Facility and Severity Filtering

A DCR does not collect every Syslog message by default. Two settings control what is captured: **Facility** and **Minimum Log Level**.

### Syslog Facility

A **Facility** identifies where a log message came from, essentially the category of the log. Different Linux services and processes write to different facilities.

| Example Event Source | Typical Facility |
|---|---|
| SSH login | LOG_AUTH |
| Kernel event | LOG_KERN |
| Mail server activity | LOG_MAIL |

Common facilities available when configuring the Linux Syslog data source:

* LOG_AUTH
* LOG_AUTHPRIV
* LOG_CRON
* LOG_DAEMON
* LOG_KERN
* LOG_MAIL
* LOG_NEWS
* LOG_SYSLOG
* LOG_USER
* LOG_LOCAL0 through LOG_LOCAL7

### Minimum Log Level

The **Minimum Log Level** sets the lowest severity AMA will collect for a given facility. Selecting a level collects that level **and every level below it in the ladder** (i.e. every more severe level). This reduces storage cost and noise.

### Syslog Severity Ladder (Least to Most Severe)

```text
LOG_DEBUG      (least severe, default minimum)
      │
      ▼
LOG_INFO
      │
      ▼
LOG_NOTICE
      │
      ▼
LOG_WARNING
      │
      ▼
LOG_ERR
      │
      ▼
LOG_CRIT
      │
      ▼
LOG_ALERT
      │
      ▼
LOG_EMERG      (most severe)
```

Example: setting the minimum level to **LOG_WARNING** collects LOG_WARNING, LOG_ERR, LOG_CRIT, LOG_ALERT, and LOG_EMERG. Everything above LOG_WARNING in the ladder (LOG_DEBUG, LOG_INFO, LOG_NOTICE) is dropped.

### SC-200 Exam Tips

* A DCR filters Syslog events using **Facility** and **Minimum Log Level**, one severity setting per facility.
* Facility = category/source of the message. Minimum Log Level = the lowest severity collected.
* Choosing **LOG_WARNING** collects LOG_WARNING, LOG_ERR, LOG_CRIT, LOG_ALERT, and LOG_EMERG.
* Events below the configured minimum severity are not collected at all, they are filtered before ingestion.
* Every facility in the same DCR can have its own independent minimum severity.
* The default minimum log level for every facility is **LOG_DEBUG**, meaning everything is collected until you tighten it.
* Saving the DCR immediately applies the new filtering to every Linux resource assigned to that rule, no per machine redeployment needed.

## Additional Exam Context

The following points are not spelled out in the source module but are commonly tested alongside it.

### AMA vs the Legacy Log Analytics Agent

Microsoft Sentinel now standardizes on the **Azure Monitor Agent (AMA)**. The older **Log Analytics Agent (also called MMA or OMS agent)** used a different configuration model, Syslog facilities were set directly on the Log Analytics workspace rather than in a DCR. The legacy agent has been retired industry wide, so for SC-200 purposes assume **AMA plus DCR** is the current and only method you should configure.

> **Exam tip:** if a question describes configuring facilities "on the workspace" rather than in a Data Collection Rule, it is describing the legacy agent, a strong signal that the described approach is outdated versus the AMA/DCR model in this module.

### Where the Data Lands

Syslog events collected by AMA are stored in the **Syslog** table inside the Log Analytics workspace, and Microsoft Sentinel queries that table using KQL. A representative query:

```kql
Syslog
| where Facility == "auth"
| where SeverityLevel in ("warning", "err", "crit", "alert", "emerg")
| project TimeGenerated, Computer, ProcessName, SeverityLevel, SyslogMessage
| order by TimeGenerated desc
```

### End to End Data Flow (Both Paths Combined)

      │

## SC-200 Last Minute Revision

### Must Remember Facts

* Azure VM Syslog onboarding needs only a **DCR**. No Azure Arc involved.
* A machine outside Azure needs **Azure Arc first**, then must still be added to a **DCR**, Arc alone changes nothing about log collection.
* The agent that actually ships log data is the **Azure Monitor Agent (AMA)**, installed as a side effect of assigning a DCR.
* The **Azure Connected Machine Agent (azcmagent)** only registers and manages the server in Azure; it is not a log shipper.
* Authentication for Arc onboarding uses the device code flow at `https://microsoft.com/devicelogin`.
* Filtering happens in the DCR through **Facility** (source/category) and **Minimum Log Level** (severity floor).
* Default minimum severity per facility is **LOG_DEBUG** (collects everything) unless tightened.

### Frequently Confused Concepts

| Term | What It Actually Does | Common Mix Up |
|---|---|---|
| Azure Arc / azcmagent | Registers and manages a non Azure server in Azure | Mistaken for the log collector itself |
| Azure Monitor Agent (AMA) | Collects and uploads telemetry, including Syslog | Confused with Azure Arc, but Arc is a prerequisite, not the collector |
| Data Collection Rule (DCR) | Defines what data is collected, from which resources, and where it goes | Confused with the agent; the DCR is configuration, AMA is the executable that follows it |
| Facility | Category/source of a Syslog message | Confused with severity |
| Minimum Log Level | Severity floor for collection | Confused with facility; severity and facility are independent, per facility settings |

### Quick Comparison: Azure VM vs Machine Outside Azure

| Aspect | Azure Linux VM | Linux Machine Outside Azure |
|---|---|---|
| Needs Azure Arc | No | Yes |
| First real step | Create a DCR | Onboard to Azure Arc |
| Agent installation trigger | Assigning the DCR | Being added as a Resource to a DCR, after Arc onboarding |
| Manual authentication required | No | Yes, device code sign in |
| Resource type added to DCR | Azure VM resource | Azure Arc enabled server resource |

### Important KQL Syntax to Remember

```kql
// Table that stores Syslog data
Syslog

// Common filter fields
Facility          // e.g. "auth", "kern", "mail"
SeverityLevel     // e.g. "warning", "err", "crit"

// Typical shape of a Syslog query
Syslog
| where Facility == "auth"
| where SeverityLevel == "err"
| project TimeGenerated, Computer, ProcessName, SyslogMessage
```

### Key Terminology Cheat Sheet

| Term | One Line Definition |
|---|---|
| DCR | Data Collection Rule, defines what is collected and where it goes |
| AMA | Azure Monitor Agent, the modern log and metrics collector |
| Azure Arc | Service that extends Azure management to machines outside Azure |
| azcmagent | Azure Connected Machine Agent, installed by Azure Arc onboarding |
| Facility | Category or origin of a Syslog message (auth, kern, mail, etc.) |
| Severity | How serious a Syslog message is, from LOG_DEBUG to LOG_EMERG |
| Syslog table | Log Analytics table that stores ingested Syslog events |
