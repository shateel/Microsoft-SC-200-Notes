## 1. What Is Microsoft Sentinel Analytics

**Microsoft Sentinel Analytics** is the detection engine of Microsoft Sentinel. It continuously analyzes collected security data to identify potential threats, suspicious activity, and vulnerabilities across the environment, instead of an analyst manually reviewing thousands of raw log entries every day.

Sentinel Analytics automatically:

* Correlates events across data sources.
* Detects attack patterns.
* Generates **alerts**.
* Groups related alerts into **incidents** for investigation.

> **Key distinction (exam favorite):** An **Alert** is a single detection produced by a rule. An **Incident** is the case Sentinel creates to group one or more related alerts together for a SOC analyst to investigate.

### SC-200 Exam Tips

* Sentinel Analytics is the **core detection engine**, not the SIEM itself, Sentinel is the SIEM; Analytics is the component that inspects the data.
* Remember the direction of the pipeline: **Data → Analytics Rule → Alert → Incident → Investigation**.

```text
      │                              All Required Resources
      ▼

      │
      ▼

      │
      ▼

```

Benefits of ARM templates:

* Consistent deployments.
* Faster setup.
* Reduced configuration mistakes.
* Repeatable environments.

### SC-200 Exam Tips

* ARM templates are an **IaC** concept, expect the exam to test the acronym and the "deploy everything together" benefit.
* Know that ARM templates can provision the **entire lab environment**, not just a single resource.

A **Rule Template** is a prebuilt Analytics Rule created by Microsoft, so administrators do not need to write complex KQL detection logic manually. Templates are commonly based on:

* Microsoft Defender products.
* Microsoft Entra ID.
* Microsoft 365.
* Common attacker techniques.
* MITRE ATT&CK tactics.

### Details Pane

The **Details Pane** shows extra information about the currently selected rule or template so analysts understand what a rule detects before enabling it. Typical information includes:

* Description.
* Detection logic.
* Severity.
* MITRE tactics and techniques.
* Required data connectors.

### SC-200 Exam Tips

* **Active** means enabled and running; a disabled rule does not evaluate any data.
* Rule Templates exist so analysts do not need to author KQL from scratch for common detections.
* The Details Pane is where you check **required data connectors before enabling a rule**, this is a common exam scenario (rule enabled but not detecting anything because the connector is missing).

## 5. Types of Analytics Rules

Microsoft Sentinel provides several built in Analytics Rule types. Each uses a different detection method depending on the attack type, available telemetry, and how quickly detection is needed.

```text
Connected Data Sources
      │
      ▼
Analytics Rule
      │
      ▼
Detection Logic Matches
      │
      ▼
Alert
      │
      ▼
Incident
      │
      ▼
SOC Investigation
```

| Rule Type | Detection Method | Editable? | Typical Use |
|---|---|---|---|
| Anomaly | Establishes a behavior baseline, flags deviations | Yes (settings), logic is Microsoft defined | Unusual behavior, informational alerts |
| Fusion | Correlation engine + machine learning across products | No, hidden logic, enabled by default | Combines several low confidence alerts into one high confidence incident |
| Microsoft Security | Imports alerts already generated by Microsoft security products | No custom KQL needed | Auto creates incidents from Defender product alerts |
| ML Behavior Analytics | Built in Microsoft machine learning on user/entity behavior | No, cannot edit or view logic | Abnormal sign in location, impossible travel, unusual mailbox activity |
| Scheduled | Custom KQL query run on a defined schedule | Yes, fully customizable | Most common, custom organization specific detections |
| NRT (Near real-time) | Runs almost immediately after logs arrive | Limited customization | Fast moving threats: ransomware, brute force, privileged account abuse |
| Threat Intelligence | Matches indicators of compromise (IOCs) against logs | Template based | IOC matching (IP, domain, file hash) |

### 5.1 Anomaly

**Anomaly** rules detect activity that **deviates from normal behavior**, rather than matching a fixed attack pattern. They establish a baseline of normal activity and flag unusual deviations.

> **Note:** Anomaly alerts are **informational** and identify anomalous behaviors, they are not automatically treated as confirmed threats.

Example: A user normally signs in 3 times a day; today they sign in 300 times, the deviation is flagged as an anomaly.

### 5.2 Fusion

**Fusion** is an advanced rule type that uses Microsoft's correlation engine and machine learning to combine multiple **low confidence** alerts into a single **high confidence** incident. It examines relationships between alerts across users, devices, IP addresses, time, and attack sequence.

```text
Impossible Travel
      +
PowerShell Execution
      +
Credential Dumping
      =
Fusion Incident
```

> **Exam tip:** Fusion is **enabled by default**, and its detection logic is **hidden and not customizable**. Fusion can correlate alerts from Scheduled Analytics Rules with alerts from other systems.

### 5.3 Microsoft Security

**Microsoft Security** rules allow Sentinel to **automatically create incidents from alerts generated by connected Microsoft security products** (for example Defender for Endpoint detecting malware, Defender for Identity detecting identity attacks, Defender for Office 365 detecting phishing). Instead of writing new KQL, Sentinel imports the existing alert and creates an incident.

```text
Microsoft Security Product
      │
      ▼
Generates Alert
      │
      ▼
Microsoft Sentinel (Microsoft Security Rule)
      │
      ▼
Incident
      │
      ▼
SOC Investigation
```

### 5.4 ML Behavior Analytics

**Machine Learning (ML) Behavior Analytics** uses Microsoft's native machine learning algorithms to detect suspicious user and entity behavior. Unlike Scheduled rules, these are built into Sentinel:

* You **cannot edit** these rules.
* You **cannot review** their internal settings.
* Microsoft manages and updates them automatically.

Examples: abnormal sign in location, impossible travel, unusual mailbox activity, abnormal privilege escalation.

### 5.5 Scheduled Alerts

**Scheduled Analytics Rules** are the **most customizable** rule type. You define your own detection logic using **Kusto Query Language (KQL)** and configure when the rule runs.

Example (runs every 5 minutes):

```kql
SigninLogs
| where ResultType != 0
| summarize count() by UserPrincipalName
```

### 5.6 NRT (Near Real-Time)

**NRT** rules run almost immediately after logs arrive, used for rapid detections such as ransomware, suspicious PowerShell, brute force attacks, and privileged account abuse.

### 5.7 Threat Intelligence

**Threat Intelligence** rules match indicators of compromise against incoming logs.

> **Memory Trick**
> * **Anomaly** = Unusual behavior
> * **Fusion** = Many alerts → One incident
> * **Microsoft Security** = Import Microsoft product alerts
> * **ML Behavior Analytics** = Microsoft managed AI detections
> * **Scheduled Alerts** = Your KQL, your schedule
> * **NRT** = Fast detections
> * **Threat Intelligence** = IOC matching

### SC-200 Exam Tips

* Know which rule types are **editable** versus **fixed by Microsoft**: Fusion and ML Behavior Analytics are **not customizable**; Scheduled is **fully customizable**.
* Fusion works on **alerts**; ML Behavior Analytics works on **raw behavior/entity data**, this is a commonly confused pair.
* Expect scenario questions describing a behavior (for example "combines several unrelated low severity alerts into one incident") and asking you to name the rule type (**Fusion**).

## 7. Creating a Custom Scheduled Analytics Rule (Wizard Walkthrough)

A **Custom Scheduled Analytics Rule** provides the **highest level of customization**. You define what to detect, which logs to search, how often the query runs, when an alert is generated, how incidents are created, and whether automated response should run.

```text
Collected Logs
      │
      ▼
Scheduled KQL Query
      │
      ▼
Runs Every X Minutes
      │
      ▼
Query Returns Results
      │
      ▼
Alert
      │
      ▼
Incident
      │
      ▼
SOC Investigation
```

Common reasons to build a custom rule: organization specific threats, insider threats, custom applications, business specific attack patterns, compliance violations.

### 7.1 General Tab

Defines the rule's identity and classification.

| Field | Purpose | Example |
|---|---|---|
| Name | Descriptive name of the detected activity | "Multiple Failed Logons from Same IP" |
| Description | What it detects, why it exists, how to investigate | Helps analysts understand the rule during an investigation |
| Tactics | MITRE ATT&CK tactic that matches the behavior | Initial Access, Execution, Persistence, Privilege Escalation, Defense Evasion, Credential Access, Discovery, Lateral Movement, Collection, Command and Control, Exfiltration, Impact |
| Severity | Business impact of the alert | Ransomware → High; Multiple failed logons → Medium; Successful admin login → Informational |
| Status | Whether the rule is active | Enabled / Disabled |

### 7.2 Set Rule Logic Tab

This is where you write the **KQL query** that searches the Sentinel workspace and determines when alerts fire. A **Results Simulation (Preview)** lets you test the query before saving.

```kql
SigninLogs
| where ResultType != 0
| summarize FailedAttempts = count() by IPAddress
| where FailedAttempts > 20
```

If the query returns results, Sentinel creates alerts.

Additional configuration on this tab:

* **Query Scheduling**: configures how often the query runs and how far back it searches.
  > **Exam tip:** Do **not** search further back than the query frequency, or duplicate alerts may be generated.
* **Alert Threshold** operators: greater than, fewer than, equal to, not equal to.
* **Event Grouping**: group all events into a single alert (default), or trigger an alert for each event.
* **Suppression**: temporarily stops the query from generating further alerts after one has fired.
* **Incident Settings**: can group alerts into a single incident, and can reopen matching closed incidents if related alerts occur later.
  > **Recommended alert grouping option:** Group alerts into a single incident **if all entities match**.
* **Entity Mapping**: maps up to **five entities** from the query results (for example User/Account, Host, IP Address) so Sentinel can link related alerts and drive investigation graphs.
* **Custom Details**: adds key value pairs to alerts.
* **Alert Details**: allows dynamic alert names, descriptions, tactics, and severity for each alert instance.

### 7.3 Automated Response Tab

Select an existing **Automation Rule**, or create a new one, to run **Playbooks** based on triggers and conditions (see Section 8).

### 7.4 Review and Create Tab

Final step to verify all rule settings before the analytics rule is created.

### SC-200 Exam Tips

* Memorize the wizard tab order: **General → Set Rule Logic → Automated Response → Review and Create**.
* **Severity, Status, Tactics** live on the **General** tab, the **KQL query** lives on **Set Rule Logic**.
* **Entity Mapping supports a maximum of five entities.**
* Know the recommended **grouping option**: single incident if all entities match, this exact phrase is likely to appear as a distractor question.
* Do not let the query lookback period exceed the schedule frequency, this causes duplicate alerts.

## 8. Automation Rules and Playbooks

The **Automated Response** feature lets you associate one or more **Automation Rules** with an Analytics Rule, so Sentinel can automatically execute predefined actions after an incident is created, instead of requiring an analyst to do repetitive tasks manually.

> An **Automation Rule** is an incident management feature that performs predefined actions **after an incident has been created**. Its purpose is to **automate the SOC response process**, not to detect threats, detection is the job of the Analytics Rule.

A **Playbook** is the workflow that an Automation Rule triggers to actually perform actions, such as changing an incident's status or adding a comment. (Supporting context: Playbooks in Sentinel are built on **Azure Logic Apps**.)

```text
Analytics Rule
      │
      ▼
Incident Created
      │
      ▼
Automation Rule Triggered
      │
      ▼
Evaluate Conditions
      │
      ▼
Conditions Match?
      │
   ┌──┴──┐
   │     │
  Yes    No
   │      │
   ▼      ▼
Execute   No Action
Actions
   │
   ▼
SOC Investigation Continues
```

### SC-200 Exam Tips

* **Analytics Rule = detects.** **Automation Rule = responds.** **Playbook = performs the action.** Keep this chain straight, it is a very common exam distinction.
* Automation happens **immediately after incident creation**, so analysts start investigating with administrative work already completed.
* Editing an existing Analytics Rule is a common way to **add an Automated Response (Playbook)** after the fact.

## 9. Managing Existing Analytics Rules

Rule management is about maintaining detections **after** they are created, as the environment, applications, infrastructure, and users change over time. Without maintenance, rules may generate excessive false positives, miss new techniques, watch systems that no longer exist, or need automated response added.

Microsoft Sentinel provides **four** management actions:

| Action | Effect | Reversible | Typical Reason |
|---|---|---|---|
| Edit | Opens the same wizard used at creation, preserves existing settings | Yes | Reduce false positives, add an Automated Response (Playbook), tune thresholds |
| Disable | Stops alert generation, keeps configuration intact | Yes, can be enabled again later | Activity is expected to trigger alerts intentionally, or the rule is being tuned |
| Duplicate | Creates a new rule with all settings copied from the original | N/A (creates a new object) | Build similar detections quickly; default name has "Copy" appended, rename it |
| Delete | Permanently removes the rule | **No**, no undo | Remove obsolete detections |

Example of editing to reduce noise:

| | Condition |
|---|---|
| Originally | Alert if Failed Login > 5 |
| Later (tuned) | Alert if Failed Login > 20 |

> **Best practice:** Disable a rule for a period of time before permanently deleting it, to confirm it is truly no longer needed. Sentinel also asks for **confirmation** before deletion since the action cannot be undone.

### SC-200 Exam Tips

* Memorize all **four** actions: **Edit, Disable, Duplicate, Delete.**
* **Disable is temporary and reversible; Delete is permanent and irreversible.**
* Duplicated rules keep the same name with **"Copy"** appended by default.
* Microsoft's recommended order before permanent removal is: **Disable first, then Delete.**

## 10. Hands On Lab: Detecting Azure VM Deletion

**Scenario:** A company experienced multiple Azure Virtual Machine deletions. The SOC wants Sentinel to automatically detect future VM deletion events and generate incidents.

```text
Azure Activity Logs
      │
      ▼
Log Analytics Workspace
      │
      ▼
Scheduled Analytics Rule
      │
      ▼
KQL Query Executes
      │
      ▼
Alert Generated
      │
      ▼
Incident Created
      │
      ▼
SOC Investigation
      │
      ▼
(Optional) Automation Rule
      │
      ▼
Playbook
```

**Azure Activity Log** records every management operation performed on Azure resources, for example: create VM, delete VM, start VM, stop VM, modify Network Security Group, create storage account, delete resource group. It is one of the most common data sources used by Sentinel scheduled rules.

### Task 1: Build the Rule via the Analytics Rule Wizard

**General tab**

| Field | Value | Why |
|---|---|---|
| Rule Name | Azure VM Deletion | Clearly describes the detected activity |
| Description | Alert when someone deletes an Azure Virtual Machine | Helps other analysts during investigation |
| MITRE ATT&CK Tactic | Impact | Deleting production VMs affects service availability, MITRE classifies destructive actions under **Impact** |
| Severity | Medium | Reflects business impact (see Section 6.1 severity guide) |
| Status | Enabled | Only enabled rules continuously monitor data |

**Set Rule Logic tab**

```kql
AzureActivity
| where OperationNameValue == "MICROSOFT.COMPUTE/VIRTUALMACHINES/DELETE"
| where ActivityStatusValue == "Success"
```

Query breakdown:

| Line | Meaning |
|---|---|
| `AzureActivity` | Searches Azure Activity Logs (Azure management events) |
| `where OperationNameValue == "MICROSOFT.COMPUTE/VIRTUALMACHINES/DELETE"` | Filters only VM delete operations, all other operations are ignored |
| `where ActivityStatusValue == "Success"` | Keeps only successful deletions, failed attempts are ignored |

**Results Simulation**: before enabling the rule, Sentinel lets you test it against current workspace data to validate syntax, verify matching events, reduce false positives, and confirm expected behavior.

> **Best practice:** Always test custom KQL using Results Simulation before deploying a rule to production.

### SC-200 Exam Tips

* Recognize `AzureActivity` as the table for **Azure management/control plane operations**, distinct from resource level diagnostic logs.
* `OperationNameValue` filters the specific operation performed; `ActivityStatusValue == "Success"` filters only completed actions.
* This exact scenario (VM deletion → Impact tactic → Medium severity) is a strong candidate for a scenario based exam question.

### Frequently Confused Concepts

| Concept A | Concept B | Key Difference |
|---|---|---|
| Alert | Incident | Alert = single detection; Incident = grouped case for investigation |
| Analytics Rule | Automation Rule | Analytics Rule detects; Automation Rule responds after the incident exists |
| Automation Rule | Playbook | Automation Rule decides "what should run and when"; Playbook is the actual workflow that runs |
| Fusion | ML Behavior Analytics | Fusion correlates existing **alerts**; ML Behavior Analytics analyzes raw **behavior/entity data** directly |
| Disable | Delete | Disable is temporary and reversible; Delete is permanent with no undo |
| Rule Template | Custom Scheduled Rule | Template = Microsoft prebuilt blueprint; Custom rule = fully authored KQL from scratch |
| Anomaly rule | ML Behavior Analytics | Anomaly rules are informational baseline deviations; ML Behavior Analytics are Microsoft managed AI models you cannot view or edit at all |

### KQL Quick Reference (used in this module, plus common companions)

| Operator | Purpose | Example |
|---|---|---|
| `\|` | Pipes results into the next operator | `TableName \| where ...` |
| `where` | Filters rows by condition | `where ResultType != 0` |
| `summarize` | Aggregates rows into groups | `summarize count() by UserPrincipalName` |
| `count()` | Counts rows in a group | `summarize count() by IPAddress` |
| `by` | Defines the grouping column(s) for summarize | `by UserPrincipalName` |
| `project` | Selects specific columns (supporting reference) | `project TimeGenerated, UserPrincipalName` |
| `extend` | Adds a calculated column (supporting reference) | `extend Country = tostring(LocationDetails.countryOrRegion)` |
| `order by` | Sorts results (supporting reference) | `order by TimeGenerated desc` |

> Rows marked "supporting reference" are common KQL operators tested broadly on SC-200 that were not explicit examples in this source module, included here because KQL fluency is required across the exam.

### One Page Cheat Sheet

* Sentinel Analytics = detection engine; runs on data already inside the **Log Analytics workspace**.
* **Seven** rule types: Anomaly, Fusion, Microsoft Security, ML Behavior Analytics, Scheduled, NRT, Threat Intelligence.
* Only **Scheduled** rules give full custom KQL control; **Fusion** and **ML Behavior Analytics** cannot be edited or viewed at all.
* **Entity Mapping** supports a maximum of **five** entities.
* Recommended grouping: **single incident if all entities match**.
* Do not set the query lookback longer than the schedule frequency, prevents duplicate alerts.
* Four rule management actions: **Edit, Disable, Duplicate, Delete**; disable before deleting.
* **Automation Rule** triggers a **Playbook** (Azure Logic App) after an incident is created, this is response automation, not detection.
* ARM templates deploy full lab environments as **Infrastructure as Code**.
* `AzureActivity` table holds Azure management operations; filter with `OperationNameValue` and `ActivityStatusValue == "Success"` for confirmed actions.
* Always validate a new custom rule with **Results Simulation** before production deployment.
