## Overview of Sentinel Automation

**Microsoft Sentinel Automation** is the ability to automatically carry out security operations tasks after an alert or incident is generated, removing the need for an analyst to do them by hand.

Manual tasks that automation replaces include:

* Assigning incidents
* Changing severity
* Adding tags
* Sending notifications
* Blocking users
* Isolating devices
* Creating tickets

Two building blocks deliver this automation:

* **Automation Rules**, the decision layer
* **Playbooks**, the action layer (built on Azure Logic Apps)

> **Exam Tip:** Automation reduces manual work, human error, response time, and alert fatigue. Any exam question describing "less manual effort and faster, consistent response" is pointing at Sentinel Automation.

```text
Alert or Incident Created
        │
        ▼
Microsoft Sentinel
        │
        ▼
Automation Rule (decides IF and WHEN)
        │
        ▼
Playbook (decides WHAT actions run)
        │
        ▼
Response Actions Completed
```

## Automation Rules

### What Is an Automation Rule

An **Automation Rule** is a rule based workflow in Microsoft Sentinel that automatically performs actions when predefined conditions are met. It centrally manages incident handling and can tag, assign, or close incidents **without needing a Playbook**, and it can also launch one or more Playbooks when advanced action is required.

Logic pattern to memorize:

```text
IF Condition Matches
        │
        ▼
THEN Perform Action
```

Automation Rules also let an analyst:

* Automate responses across **multiple analytics rules at once**
* Control the **order** in which automated actions execute
* Simplify complex incident orchestration workflows

> **Key distinction:** Automation Rules decide **WHEN** automation should occur. Playbooks decide **WHAT** actions are executed.

### Why Automation Rules Matter

SOC analysts repeatedly perform the same low value tasks, such as assigning incidents, changing severity, adding an owner, adding tags, closing false positives, and launching Playbooks. Automation Rules remove this repetition.

**Benefits:**

* Faster response
* Consistent incident handling
* Standardized SOC workflow
* Reduced analyst workload

### Creating and Managing Automation Rules

Automation Rules can be created and managed from three locations, each suited to a different scope.

| Location | Scope | Best Used For |
|---|---|---|
| **Automation page** | Entire workspace | Central management, reordering, enabling and disabling rules, applying rules broadly (including to future analytics rules) |
| **Analytics Rule Wizard** ("Automated response" tab) | A single analytics rule | Automation that should apply only to that specific analytics rule; the analytics rule condition is auto linked to the automation rule |
| **Incidents blade** | A single recurring incident | Quickly building **suppression rules** for noisy, repeating incidents; Sentinel pre fills values from the incident and suggests a suppression action and expiration date |

> **Exam Tip:** If a question describes managing automation across the **whole workspace**, the answer is the **Automation page**. If it describes automation tied to **one specific analytics rule**, the answer is the **Analytics Rule Wizard**. If it describes silencing a **recurring, noisy incident**, the answer is the **Incidents blade**.

### Components of an Automation Rule

Every Automation Rule is built from five components:

1. **Trigger** – when the rule starts
2. **Conditions** – whether the rule should act
3. **Actions** – what the rule does
4. **Expiration Date** – when the rule stops applying
5. **Execution Order** – the sequence relative to other rules

### Trigger Types

A **Trigger** determines **when** an Automation Rule starts. Without a trigger, the rule never runs. Microsoft Sentinel supports three trigger types.

#### Trigger 1: When an Incident Is Created

The most commonly used trigger. It fires immediately after Microsoft Sentinel creates an incident.

Typical uses: initial triage, assigning an owner, adding tags, changing severity, launching a Playbook.

```text
Incident Created
        │
        ▼
Automation Rule
        │
        ▼
SOC Actions
```

#### Trigger 2: When an Incident Is Updated

Fires whenever incident properties change, for example severity, status, or owner changes. Useful for escalation workflows, synchronization with external systems, and follow up automation.

```text
Incident Updated
        │
        ▼
Automation Rule
        │
        ▼
Reevaluate Conditions
        │
        ▼
Execute Actions
```

#### Trigger 3: When an Alert Is Created

Fires immediately after an Analytics Rule generates an alert, **before** incident processing occurs (where applicable). Useful for Scheduled Analytics Rules, Near real-time (NRT) Analytics Rules, alert only workflows, and Defender portal scenarios where Microsoft Defender XDR handles incident creation instead of Sentinel.

```text
Alert Created
        │
        ▼
Automation Rule
        │
        ▼
Response Actions
```

> **Exam Tip:** In the unified **Defender portal**, incident trigger rules apply to both Microsoft Sentinel and Microsoft Defender XDR incidents, while alert trigger rules apply **only** to Microsoft Sentinel alerts. This distinction is a favorite exam trap.

### Conditions

**Conditions** determine **whether** an Automation Rule should execute once it has been triggered. A rule can define one or many conditions, and Sentinel evaluates them using logical operators.

> **Exam Tip:** Automation Rules support logical operators such as **AND**, **OR**, **NOT**, and **CONTAINS** when building condition logic. Conditions are what let one rule apply narrowly, for example only to incidents tagged "Phishing" with severity "High."

### Actions

**Actions** are the operations Microsoft Sentinel performs once all conditions evaluate to true. Multiple actions can be chained, and the analyst controls the order in which they run.

| Action | What It Does | Typical Use Case |
|---|---|---|
| **Change Incident Status** | Updates status, and lets the analyst set a closing reason and comment when closing | Reduces false positives, improves reporting quality |
| **Change Severity** | Reprioritizes an incident, for example Medium to High | Critical assets, high value users, or sensitive servers are involved |
| **Assign Incident Owner** | Routes the incident to the right analyst or team | Malware to Tier 1 Analyst, credential theft to Identity Team, cloud attack to Cloud Security Team |
| **Add Tags** | Classifies the incident, for example Malware, Phishing, Insider Threat, Ransomware, VIP User, Critical Server | Improves searching, filtering, reporting, and downstream automation |
| **Run Playbook** | Launches one or more Playbooks for advanced remediation | High severity incident triggers notifications, ticketing, disabling a user, and isolating a device |

Example escalation chain for the **Run Playbook** action:

```text
High Severity Incident
        │
        ▼
Automation Rule
        │
        ▼
Playbook
        │
        ▼
Notify Teams
        │
        ▼
Open ServiceNow Ticket
        │
        ▼
Disable User
        │
        ▼
Isolate Device
```

### Expiration Date

An Automation Rule can be given an **expiration date**. Once that date passes, Sentinel automatically **disables** the rule.

Common use cases:

* Penetration tests
* Security assessments
* Planned maintenance
* Temporary suppression of expected noisy alerts

> **Exam Tip:** Expiration Date is the go to answer whenever a scenario says automation is needed only "temporarily" or "for the duration of" an event.

### Execution Order

**Execution Order** controls the sequence in which multiple Automation Rules run. Rules execute top to bottom, and a later rule evaluates the incident **after** earlier rules have already modified it.

```text
Rule 1: Change Severity
        │
        ▼
Rule 2: Check Severity (condition)
        │
        ▼
Rule 3: Launch Playbook
```

**Worked example:** if Rule 1 changes an incident from **Medium** to **Low**, and Rule 2 only acts on incidents that are **Medium or higher**, then Rule 2 will **not** execute, because Rule 1 already altered the state Rule 2 depends on.

> **Exam Tip:** Execution order questions almost always test whether you understand that earlier rules can silently disqualify later rules from running. Always trace the incident state rule by rule.

### Exam Tips: Automation Rules

* The **Automation page** is the centralized console for creating, editing, enabling, disabling, and reordering rules across the workspace, and it can apply rules to future analytics rules too.
* Use the **Analytics Rule Wizard** when a rule should apply to one specific analytics rule only.
* Use the **Incidents blade** to build **suppression rules** for recurring, noisy incidents; Sentinel auto suggests the suppression action and expiration date.
* Memorize the **three trigger types**: incident created, incident updated, alert created.
* **Conditions** gate whether actions run; they support AND, OR, NOT, and CONTAINS logic.
* Know the five **actions**: change status, change severity, assign owner, add tags, run Playbook.
* **Playbooks** provide advanced orchestration through Azure Logic Apps and can be launched from an Automation Rule.
* **Expiration Date** equals temporary automation.
* **Execution Order** equals sequence dependency; earlier rules can change the outcome of later rules.
* In the **Defender portal**: incident triggers cover both Sentinel and Defender XDR incidents; alert triggers cover Sentinel alerts only.

## Playbooks and Azure Logic Apps

### What Is a Playbook

A **Playbook** is a collection of automated response and remediation actions that Microsoft Sentinel can execute. Unlike an Automation Rule, which only decides and orchestrates, a Playbook performs the **actual response actions**.

```text
Incident
        │
        ▼
Workflow
        │
        ▼
Multiple Automated Actions
```

Playbooks can:

* Integrate with internal and external systems
* Run automatically when triggered by an Analytics Rule or an Automation Rule
* Be run manually from the incident page

### Azure Logic Apps Foundation

Microsoft Sentinel Playbooks are built on **Azure Logic Apps**, Microsoft's cloud workflow automation platform for orchestrating tasks across systems. This gives Playbooks scalability, reliability, and broad integration coverage.

Azure Logic Apps provides:

* Hundreds of prebuilt connectors
* Low code workflow design
* Enterprise grade integrations
* Cloud scalability

> **Exam Tip:** Whenever a question asks which component orchestrates a workflow with **external, third party services** (Teams, ServiceNow, Jira, email, etc.), the answer is **Playbooks, built on Azure Logic Apps**. Whenever a question asks which feature can tag, assign, or close incidents **without needing a Playbook**, the answer is **Automation Rules**.

### How Playbooks Run

Playbooks can start from either an **alert trigger** or an **incident trigger**, and each behaves differently.

| Trigger Type | Fires On | Data Available to the Playbook |
|---|---|---|
| **Microsoft Sentinel alert trigger** | A single alert | Only that alert's details |
| **Microsoft Sentinel incident trigger** | A full incident | The incident plus its related alerts, entities, and bookmarks |

> This is supplementary context beyond the source document, added because it is a frequently tested SC-200 distinction: incident triggered Playbooks see the full incident context (entities, alerts, bookmarks), while alert triggered Playbooks only see the single alert that fired them. Modern Sentinel deployments favor incident triggered Playbooks launched from Automation Rules for this reason.

### Playbook Permissions and Managed Identity

> This subsection is supplementary, added for exam completeness, since Playbook permissions are a commonly tested SC-200 detail closely tied to this module.

To run a Playbook, whether manually or automatically through an Automation Rule, Microsoft Sentinel needs permission to trigger the underlying Logic App. This is handled through:

* A **managed identity** assigned to the Automation Rule or user context
* The **Microsoft Sentinel Automation Contributor** role, granted on the resource group containing the Playbook, which allows Sentinel to run the Playbook without granting rights to edit it
* Analysts who need to run Playbooks manually from the incident page require the **Microsoft Sentinel Playbook Operator** role

> **Exam Tip:** If a Playbook is not appearing as runnable or an Automation Rule fails to trigger one, the likely cause tested on the exam is a **missing role assignment** (Automation Contributor or Playbook Operator), not a broken trigger.

### Consumption vs Standard Logic Apps

> Supplementary comparison, included because Logic Apps plan type is relevant background for the Playbooks topic.

| Plan Type | Billing Model | Typical Fit |
|---|---|---|
| **Consumption** | Pay per execution | Most standard Sentinel Playbooks, simpler workflows |
| **Standard** | Fixed pricing, runs in a dedicated App Service style plan | High volume, stateful, or performance sensitive automation |

### Exam Tips: Playbooks

* Playbooks perform the **actual response and remediation** work; Automation Rules only decide when that work should start.
* Playbooks are built on **Azure Logic Apps**.
* Playbooks can run **automatically** (from an Analytics Rule or Automation Rule) or **manually** (from the incident page).
* Playbooks support Microsoft and third party integrations through Logic Apps connectors.
* Know the difference between **alert triggered** Playbooks (single alert scope) and **incident triggered** Playbooks (full incident scope).
* Running Playbooks requires the correct role assignment: **Microsoft Sentinel Automation Contributor** for automated execution, **Microsoft Sentinel Playbook Operator** for manual execution.

## Automation Rules vs Playbooks

This comparison is one of the most heavily tested concepts in this module.

| Aspect | Automation Rule | Playbook |
|---|---|---|
| Purpose | Decides **when** and **whether** automation runs | Performs the **actual** response actions |
| Built on | Native Microsoft Sentinel engine | Azure Logic Apps |
| Can tag, assign, close incidents alone | Yes, no Playbook required | Not applicable, it is the execution layer |
| External system integration | No, delegates to a Playbook | Yes, via Logic Apps connectors |
| Ordering control | Controls order of multiple rules and actions | Executes the steps defined inside its own workflow |
| Common trigger | Incident created, incident updated, alert created | Alert trigger or incident trigger |
| Expiration support | Yes, expiration date | Not applicable |

```text
Automation Rule                         Playbook
────────────────                        ────────
Decides WHEN / WHETHER      ──launches──▶   Decides WHAT actions run
(tag, assign, close, order)                  (notify, ticket, disable, isolate)
```

## Supplementary Exam Focused Notes

The following points are not restated from the source document; they are added because they directly extend the automation topic and are commonly tested alongside it. They are technically accurate, standard Microsoft Sentinel product behavior.

* **Analytics Rule Wizard legacy behavior:** Older Sentinel experiences allowed a Playbook to be attached directly to an Analytics Rule. In the current experience, this is implemented behind the scenes as an Automation Rule, which is why the exam objective groups Playbook attachment under Automation Rules management.
* **Suppression versus closing:** A suppression rule created from the Incidents blade typically sets status to closed with an expiration date, so it is a **temporary** closure, not a permanent one. Once the expiration date passes, new matching incidents are created and processed normally again.
* **Order matters across the whole rule set, not just within one rule:** Execution order applies to the full list of Automation Rules in the workspace. A broad rule created early (for example, "tag all incidents") can affect the conditions evaluated by every rule that runs after it.
* **NRT and automation:** Near real-time (NRT) analytics rules generate alerts with very low latency and pair naturally with the **alert created** trigger, since they are designed for near immediate automated response, unlike scheduled analytics rules that run on a fixed interval.
* **Defender portal convergence:** As Microsoft Sentinel and Microsoft Defender XDR converge in the unified Defender portal, incident trigger Automation Rules become the more universal choice because they operate across both Sentinel and Defender XDR incidents, while alert trigger rules remain Sentinel specific.

## SC-200 Last Minute Revision

### One Page Cheat Sheet

```text
SECURITY EVENT
        │
        ▼
Analytics Rule generates an ALERT
        │
        ▼
Sentinel groups alerts into an INCIDENT (or Defender XDR does, in unified portal)
        │
        ▼
AUTOMATION RULE evaluates Trigger + Conditions
        │
        ▼
ACTIONS run directly (status, severity, owner, tags)
        │              │
        │              ▼
        │        PLAYBOOK launched (Azure Logic Apps)
        │              │
        │              ▼
        │        External systems act: notify, ticket, disable, isolate
        ▼
INCIDENT RESOLVED / TRACKED
```

### Core Definitions to Memorize

| Term | One Line Definition |
|---|---|
| **Automation Rule** | Decision engine: if condition matches, then perform action; can act without a Playbook |
| **Playbook** | Automated workflow that performs real response actions, built on Azure Logic Apps |
| **Trigger** | Defines WHEN an Automation Rule starts: incident created, incident updated, or alert created |
| **Condition** | Defines WHETHER the rule proceeds after the trigger fires |
| **Action** | Defines WHAT the rule does: status, severity, owner, tags, run Playbook |
| **Expiration Date** | Automatically disables a rule after a set date, ideal for temporary automation |
| **Execution Order** | Sequence in which multiple Automation Rules run; earlier rules can change what later rules see |
| **Azure Logic Apps** | Low code workflow platform that powers Playbooks with hundreds of connectors |
| **Automation Contributor role** | Lets Sentinel trigger a Playbook automatically without granting edit rights |
| **Playbook Operator role** | Lets an analyst run a Playbook manually from the incident page |

### Frequently Confused Concepts

| Confusion | Clarification |
|---|---|
| "Automation Rule" vs "Playbook" | Rule decides WHEN and WHETHER; Playbook decides and performs WHAT |
| "Alert" vs "Incident" trigger | Alert trigger fires per alert, before incident grouping in some flows; Incident trigger fires on the grouped incident and, in the Defender portal, covers both Sentinel and Defender XDR |
| Suppression vs permanent closure | Suppression from the Incidents blade is typically temporary and expires |
| Automation page vs Analytics Rule Wizard | Automation page manages rules workspace wide; Analytics Rule Wizard scopes a rule to one analytics rule only |
| Automation Contributor vs Playbook Operator | Contributor lets Sentinel run the Playbook automatically; Operator lets a human run it manually |

### Quick Trigger Reference

| Trigger | Fires When | Best For |
|---|---|---|
| Incident Created | A new incident appears | Initial triage, assign owner, tag, launch Playbook |
| Incident Updated | Incident properties change | Escalation, sync, follow up automation |
| Alert Created | An analytics rule generates an alert | Scheduled and Near real-time (NRT) rules, alert only workflows, Defender portal scenarios |

### Quick Action Reference

```text
Change Status   → close, reduce false positives, add reason and comment
Change Severity → reprioritize, e.g. Medium → High for critical assets
Assign Owner    → route to correct team, e.g. Malware → Tier 1
Add Tags        → classify, e.g. Phishing, Ransomware, VIP User
Run Playbook    → escalate to Azure Logic Apps for real remediation
```

> **Final Reminder:** If the exam question is about deciding, tagging, assigning, or closing without external systems, think **Automation Rule**. If the question is about notifying, ticketing, disabling accounts, isolating devices, or talking to third party systems, think **Playbook, powered by Azure Logic Apps**.
