## 2. Module 1: What Are Microsoft Sentinel Playbooks

### Microsoft Sentinel Overview

Microsoft Sentinel is Microsoft's cloud native **SIEM** (Security Information and Event Management) and **SOAR** (Security Orchestration, Automation, and Response) platform. It detects, investigates, and responds to threats across hybrid and cloud environments by collecting logs, analyzing them, generating alerts and incidents, and supporting automated response.

### SIEM vs SOAR

| Aspect | SIEM | SOAR |
|---|---|---|
| Focus | Visibility and threat detection | Response and orchestration |
| Typical tasks | Collecting logs, correlating events, detecting threats, generating alerts, supporting investigations | Creating tickets, sending notifications, disabling accounts, isolating endpoints, blocking IPs, updating incidents, calling APIs |
| Common log sources | Windows Event Logs, Linux Syslog, Defender products, Microsoft Entra ID, Azure Activity Logs, Azure Firewall, third party firewalls, network devices | N/A |

> **Easy way to remember:** SIEM = **Detect**. SOAR = **Respond**.

Microsoft Sentinel combines both roles:

* SIEM functions: log collection, threat detection, alert generation, incident creation
* SOAR functions: Playbooks, Automation Rules, Azure Logic Apps, automated remediation

### The Full Detection To Response Pipeline

```text
Data Sources (Defender XDR, Entra ID, Azure
Activity, Windows Events, Syslog, third party)
        │
        ▼
Microsoft Sentinel (SIEM)
        │
        ▼
Analytics Rules (detection)
        │
        ▼
Automation Rules (orchestration logic)
        │
        ▼
Playbooks (Azure Logic Apps)
        │
        ▼
Automated Response Actions
```

### Azure Logic Apps: The Engine Behind Playbooks

A Microsoft Sentinel **Playbook** is a collection of automated procedures built on **Azure Logic Apps**. It can run manually during an investigation, or automatically when triggered by an alert or an incident creation rule.

Azure Logic Apps provides:

* Low code workflow design
* Enterprise automation
* Cloud scalability
* Hundreds of integrations

> **Formula to memorize:** Azure Logic App + Microsoft Sentinel Connector = Microsoft Sentinel Playbook

Workflows are built in the graphical **Logic Apps Designer** (or edited directly in JSON for advanced customization):

```text
Trigger
   │
   ▼
Condition
   │
   ▼
Action
   │
   ▼
Action
   │
   ▼
Complete
```

### Connectors: Two Very Different Things

The exam frequently tests whether you can tell these apart.

| | Microsoft Sentinel Data Connector | Logic Apps Connector |
|---|---|---|
| Purpose | Collects security logs into Sentinel | Lets a Playbook communicate with external services through APIs |
| Examples | Defender for Endpoint, Azure Activity, Syslog, CEF, Windows Security Events | Microsoft Teams, Outlook, Defender, ServiceNow, Jira, Azure Functions, SQL Server, REST APIs, SharePoint, GitHub |
| Easy label | **Collect Data** | **Perform Actions** |

```text
Security Product
      │
      ▼
Data Connector
      │
      ▼
Microsoft Sentinel
```

```text
Playbook
      │
      ▼
Logic Apps Connector
      │
      ▼
External Service
```

> **Exam Tip:** These connectors are explicitly *not* the same thing. A Data Connector brings logs **in**. A Logic Apps Connector lets a Playbook act **out**.

### Triggers And Actions

Logic Apps workflows are built from **Triggers** and **Actions**.

* **Trigger:** starts the workflow when a specified event occurs. Without a trigger, the workflow never begins.
* **Action:** performs a task after the trigger, or after another action, completes. One Playbook can contain many actions in sequence.

```text
Incident Created
      │
      ▼
Trigger Activated
      │
      ▼
Playbook Starts
```

### The Microsoft Sentinel Logic Apps Connector

Every Sentinel Playbook uses the **Microsoft Sentinel Logic Apps connector**, which supplies Sentinel specific triggers and actions. Memorize the two supported triggers:

1. **When a response to a Microsoft Sentinel alert is triggered**
2. **When a Microsoft Sentinel incident creation rule is triggered**

Common actions provided by this connector:

| Category | Example Actions |
|---|---|
| Incident management | Add comment to incident, add labels to incident, remove labels from incident, change incident title, change incident description, change incident severity, change incident status, get incident |
| Entity retrieval | Get Accounts, Get Hosts, Get IPs, Get URLs, Get File Hashes |

### Entities And Entity Actions

An **entity** is simply something involved in the attack: a User, Computer, IP Address, File, URL, Hash, or Process.

Example: Sentinel detects malware. The incident contains a User (John), a Computer (WIN10 01), an IP (192.168.1.50), and a Hash (ABC123). All four are entities.

```text
Incident: Malware Detected
      │
      ▼
Retrieve Host Entity (Get Hosts)
      │
      ▼
Host Identified: WIN10 01
      │
      ▼
Isolate WIN10 01
```

> **Exam Tip:** Entity retrieval actions (Get Accounts, Get Hosts, and so on) return **collections**. When an action can return more than one result, pair it with a **For each** loop so the Playbook processes every returned entity individually.

### The Four Concept Exam Trick

Candidates frequently confuse Data Connectors, Logic Apps Connectors, Triggers, and Actions. Memorize this mapping:

```text
Data Connector          →  Brings logs INTO Sentinel
Logic Apps Connector    →  Lets Playbooks TALK to Sentinel
Trigger                 →  Starts the Playbook
Action                  →  Does the work
```

### Module 1 SC-200 Exam Tips

* Microsoft Sentinel = SIEM + SOAR. SIEM detects, SOAR responds.
* Playbooks are built on **Azure Logic Apps**.
* Playbooks can run manually or automatically.
* Do not confuse **Data Connectors** (collect logs) with **Logic Apps Connectors** (execute automated actions).
* Memorize the two Sentinel Playbook triggers word for word.
* Entity retrieval actions almost always pair with a **For each** loop.
* Know the common connector actions: changing incident severity, adding comments or labels, retrieving entities, updating status.

## 3. Module 2: Trigger A Playbook In Real Time

### Real Time vs Manual Execution

A **Real Time Playbook** starts automatically the instant a specific Sentinel event occurs, cutting response time compared to manual execution.

```text
Threat Detected
      │
      ▼
Alert
      │
      ▼
Trigger Fires
      │
      ▼
Playbook Runs Automatically
```

```text
SOC Analyst
      │
      ▼
Open Incident
      │
      ▼
Run Playbook Manually
```

### The Playbooks Page

The **Playbooks** page is the central management dashboard for all Playbooks created from Azure Logic Apps. From here analysts can:

* Create Playbooks
* View existing Playbooks and their execution status
* Enable or disable Playbooks
* Delete Playbooks
* Open a Playbook in the Logic Apps Designer

### Creating A Playbook

Creating a Playbook actually creates a new **Azure Logic App**. During creation you specify the subscription, resource group, Logic App name, region, and optional Log Analytics integration. You are then redirected to the Logic Apps Designer to build the workflow. Microsoft recommends starting from a **Blank Logic App**, then adding a Sentinel trigger followed by actions.

### Automating Response To An Incident

A Playbook only becomes fully automated once it is attached to an **Analytics Rule** through that rule's **Automated Response** section. When the Analytics Rule fires and generates an alert or incident, Sentinel automatically launches the linked Playbook.

### Dynamic Content

**Dynamic Content** is information produced by one step in a workflow that becomes available for later steps to reuse, without manual re entry.

```text
Sentinel Trigger Fires
      │
      ▼
Alert Name
      │
      ▼
Account
      │
      ▼
IP Address
      │
      ▼
Host
      │
      ▼
Entities Available To Later Actions
```

### Module 2 SC-200 Exam Tips

* Every Playbook begins with a **Microsoft Sentinel trigger**.
* A Playbook is only "fully automated" once linked to an Analytics Rule's **Automated Response** section; otherwise it must be run manually.
* **Dynamic Content** is output from earlier steps (for example, alert display name and entities) that later actions can reuse.
* **Conditions** implement IF/ELSE logic, producing **True** and **False** branches.
* Know the Playbooks page management options: Run Trigger, Edit, Clone, Export, Disable, Delete.
* A typical designer flow to recognize: Trigger → Entity Action → For each → Get User → Approval → Condition → True/False actions.

## 4. Module 3: Run Playbooks On Demand

Running a Playbook **on demand** means a SOC analyst manually executes it from an existing incident, typically after investigating first.

### Automatic vs On Demand

| | Automatic Execution | On Demand Execution |
|---|---|---|
| Started by | Microsoft Sentinel (via Analytics Rule or Automation Rule) | SOC Analyst, from an existing incident |
| Best for | Repetitive, well defined, low risk responses | Actions needing analyst judgment or approval first |
| Example actions | Send Teams notification, create ServiceNow ticket, add incident labels, notify SOC | Disable user account, remove risky user status, reset passwords, block production resources |

> **Easy way to remember:** Automatic → Sentinel decides. On Demand → the analyst decides.

### Why Investigate Before Automating

Some incidents should not trigger an automatic response because the action could affect legitimate users or business operations. Typical cases:

* Suspected false positives
* Insider threat investigations
* Privileged account investigations
* High value assets
* Incidents requiring manager approval
* Actions that could disrupt users (disable account, isolate device, block IP)

### Worked Example: Atypical Travel False Positive

Microsoft Defender for Cloud Apps raises an **Atypical Travel** alert because a user appears to sign in from two distant locations within a short time. Investigation shows the user was on a corporate VPN, working remotely, and the activity was legitimate. Instead of disabling the account, the analyst manually runs a Playbook that dismisses the risky user flag in Microsoft Entra ID.

> **Takeaway:** This is the classic SC-200 pattern for On Demand Playbooks: investigate first, then run a targeted corrective Playbook rather than letting automation act blindly.

### The Microsoft Sentinel GitHub Repository

Microsoft maintains a public GitHub repository of ready to use security content so organizations do not have to build everything from scratch. It includes:

* Playbooks
* Analytics Rules
* Hunting Queries
* Workbooks
* Parsers
* Automation content

Many Playbooks in the repository ship as **Azure Resource Manager (ARM) templates**.

### ARM Templates

An **ARM Template** is an Infrastructure as Code (IaC) file that defines Azure resources. For a Playbook, an ARM template can deploy the Logic App, its workflow, triggers, actions, connections, and configuration, so Azure builds the Playbook from the template instead of it being built manually.

### API Connections

A Playbook talks to Microsoft services through **API connections**. When deploying from a template, these connections must be authorized before the Playbook can reach Sentinel, Microsoft Entra ID, Outlook, Teams, or other services.

| Before Authorization | After Authorization |
|---|---|
| Cannot read incidents | Can retrieve incidents |
| Cannot update incidents | Can update Sentinel |
| Cannot send emails | Can send Teams messages |
| Cannot modify Entra ID users | Can modify users and interact with Microsoft services |

> **Naming note:** API connections created by Sentinel Playbooks commonly use an **azuresentinel** prefix, which makes them easier to spot and manage.

### Manual Investigation Workflow

```text
Open The Incident
      │
      ▼
Review Alert Details
      │
      ▼
Examine Related Entities (accounts, hosts, IPs)
      │
      ▼
Determine If The Incident Is Genuine
      │
      ▼
Run The Playbook If Remediation Is Appropriate
      │
      ▼
Verify The Outcome
      │
      ▼
Continue Or Close The Investigation
```

### Module 3 SC-200 Exam Tips

* **On Demand** Playbooks are started manually by an analyst; **Automatic** Playbooks are started by Sentinel.
* Use Automatic Playbooks for repetitive, predictable, low risk responses.
* Use On Demand Playbooks when investigation or human approval must happen first.
* The **Sentinel GitHub repository** provides prebuilt Playbooks, Analytics Rules, Hunting Queries, and Workbooks.
* ARM templates deploy Playbooks as Infrastructure as Code.
* API connections must be **authorized** before a templated Playbook can talk to Microsoft services.
* Classic exam scenario: a false positive investigated manually, then resolved with an On Demand Playbook.

## 5. Module 4: Create A Microsoft Sentinel Playbook (Playbook Permissions)

Before Microsoft Sentinel can execute a Playbook, it needs permission to run Logic Apps inside the Azure Resource Group that contains them. Without this, Automation Rules and analysts cannot execute Playbooks from within Sentinel.

**Why is this required?** Sentinel and Azure Logic Apps are separate Azure services. Sentinel does not own the Logic App directly, so it must request Azure to execute it on Sentinel's behalf.

```text
Microsoft Sentinel
      │
      │  Request to run Playbook
      ▼
Azure Resource Group
      │
      ▼
Azure Logic App
      │
      ▼
Playbook Executes
```

### Module 4 SC-200 Exam Tips

* A **Playbook** is implemented as an **Azure Logic App**.
* Sentinel needs **Playbook Permissions** to execute Logic Apps in a Resource Group, and these are commonly assigned at the Resource Group level.
* The **Microsoft Sentinel connector** lets Logic Apps interact with Sentinel incidents.
* An **API Connection** authenticates the Playbook to Microsoft services.
* **Get Incident** retrieves incident details for later steps; **Update Incident** modifies an existing incident rather than creating a new one.
* **Dynamic Content** passes values such as the Incident ARM ID, owner, and severity between actions.
* The **Incident ARM ID** uniquely identifies which incident the Playbook updates.

## 6. Additional Clarifications For The Exam

These points are not spelled out at length in the source material but are useful context for answering scenario style questions correctly.

### Automation Rules vs Playbooks (Do Not Mix These Up)

An **Automation Rule** is a native Sentinel object that decides **when**, **in what order**, and **under what conditions** actions happen after an incident or alert is created. It can assign an owner, change severity, add tags, suppress noisy incidents, or call one or more Playbooks. A **Playbook** is the actual automated workflow (the Azure Logic App) that performs the work, such as isolating a host or sending a notification.

> **Simple distinction:** the Automation Rule is the traffic controller. The Playbook is the vehicle that does the driving.

### Quick Relationship Map

```text
Incident Or Alert Created
      │
      ▼
Automation Rule Evaluates Conditions
      │
      ▼
Automation Rule Runs Actions (assign owner,
change severity, run a Playbook, and so on)
      │
      ▼
Playbook (Azure Logic App) Executes If Called
```

### Why This Matters On The Exam

Questions often describe a scenario ("an incident should automatically get a severity change and notify a Teams channel") and ask which object to configure. If no code automation or external system call is needed, an **Automation Rule alone** may be enough. If the scenario needs to call an external API, isolate a device, or perform multi step logic, a **Playbook** is required, typically invoked through an Automation Rule.

### Frequently Confused Pairs

| Concept A | Concept B | How To Tell Them Apart |
|---|---|---|
| Data Connector | Logic Apps Connector | Data Connector = logs in. Logic Apps Connector = actions out. |
| Automatic Playbook | On Demand Playbook | Automatic = Sentinel starts it. On Demand = analyst starts it. |
| Automation Rule | Playbook | Automation Rule = decision logic and sequencing. Playbook = the workflow that does the work. |
| Trigger | Action | Trigger = starts the workflow. Action = does the work after it starts. |
| SIEM | SOAR | SIEM = detect and alert. SOAR = orchestrate and respond. |

2. When Microsoft Sentinel incident creation rule was triggered
