## Part 1: Incident Fundamentals

### 1.1 What Is an Incident

An **incident** represents a potential security attack or suspicious activity that requires investigation. Think of it as a **case file** in a Security Operations Center (SOC).

Instead of forcing an analyst to review dozens of separate alerts, Microsoft Sentinel groups related alerts into a single incident so everything can be investigated from one place.

An incident typically contains:

1. One or more alerts
2. Related entities (users, hosts, IP addresses, URLs, file hashes)
3. Incident severity
4. Incident status
5. Owner
6. Investigation timeline
7. Comments and notes

An incident stays open until the analyst classifies it as a **true positive**, **false positive**, or **benign** activity.

> **Exam tip:** Microsoft Sentinel is both a SIEM (Security Information and Event Management) and a SOAR style incident management platform. Analysts use it to review incidents, assign owners, change status, add comments, investigate related entities, and track incidents through to resolution.

### 1.2 The Building Blocks of an Incident

| Component | Role | Key Idea |
|---|---|---|
| **Data Connectors** | Collect security data from sources and send it to Sentinel | The data collection layer; without them, Sentinel has nothing to analyze |
| **Events** | A single recorded activity | Not inherently suspicious; just a record of something that happened |
| **Analytics Rules** | Analyze events for suspicious activity | Their job is **detection**, not investigation |
| **Alerts** | Generated when an Analytics Rule detects suspicious activity | A notification, not the full investigation |
| **Incidents** | Created from one or more related alerts | The case file used for investigation |

**Data Connectors** commonly bring in data from Microsoft Defender products, Windows Event Logs, Linux Syslog, Azure Activity Logs, Azure Firewall, third party firewalls, and proxy servers.

**Events** are raw activity records, for example a user signing in, a file being deleted, a firewall allowing a connection, a process starting, an account being locked, or a virtual machine being deleted. Events are stored in the **Log Analytics Workspace**.

**Analytics Rules** contain the detection logic. They can use built in Microsoft templates or custom **Kusto Query Language (KQL)** queries to decide whether an event, or a combination of events, represents a threat.

**Alerts** are examples of what an Analytics Rule might flag: malware detected, password spraying, impossible travel, or suspicious PowerShell execution. An alert says "this deserves attention," it is not itself the investigation.

> **Exam tip:** This is one of the most tested distinctions on SC-200. Many candidates confuse alerts with incidents. An alert is a single detection; an incident is the grouped case file built from one or more alerts.

### 1.3 From Event to Incident

```text
Events
  │
  ▼
Analytics Rule
  │
  ▼
One or More Alerts
  │
  ▼
Single Incident
```

This grouping of related alerts into one incident is what gives an analyst a single investigation case instead of many disconnected alerts.

### 1.4 Microsoft Sentinel Overview Page

The **Overview** page is the SOC dashboard. It gives a high level snapshot of the environment before an analyst starts investigating, showing:

* Number of events
* Number of alerts
* Number of incidents
* Incident status
* Recent incidents
* Events and alerts over time

This lets analysts quickly spot unusual activity and prioritize what to investigate first.

### 1.5 How It All Connects

Microsoft Sentinel acts as the central platform receiving data from Microsoft and third party sources.

```text
Microsoft Defender, Microsoft Entra ID, Azure Firewall,
Azure Activity, Windows Events, Linux Syslog, Third Party Solutions
        │
        ▼
Data Connectors
        │
        ▼
Log Analytics Workspace
        │
        ▼
Analytics Rules
        │
        ▼
Alerts
        │
        ▼
Incidents
        │
        ▼
SOC Investigation
```

Each layer has one job: Data Connectors collect data, the Log Analytics Workspace stores it, Analytics Rules analyze it, Alerts flag suspicious activity, and Incidents organize the investigation.

### SC-200 Exam Tips (Part 1)

> * An **Event** is a single recorded activity, stored in the **Log Analytics Workspace**.
> * **Data Connectors** collect logs and forward them to Sentinel.
> * **Analytics Rules** analyze events and generate alerts, they use built in templates or custom **KQL**.
> * An **Alert** indicates suspicious activity detected by an Analytics Rule.
> * An **Incident** is created from one or more related alerts.
> * Memorize the full flow: **Data Connector → Event → Analytics Rule → Alert → Incident → Investigation**.
> * The **Overview** page provides a high level summary; use it at the start of a SOC shift.

## Part 2: Incident Evidence and Entities

### 2.1 What Is Incident Evidence

**Incident Evidence** is the security information Sentinel attaches to an incident to explain **why the incident was created**. Evidence answers questions such as what triggered the incident, which alerts contributed, which events support the detection, and what resources were involved.

Without evidence you only know "an attack may have happened." With evidence you know exactly which logs, alerts, and related information explain the detection.

> **Important:** Evidence does not create the incident. It is attached **after** the incident already exists, to support the investigation.

### 2.2 Incident Investigation Workflow

```text
Security Activity
        │
        ▼
Events Generated
        │
        ▼
Analytics Rule
        │
        ▼
Alert Created
        │
        ▼
Incident Created
        │
        ▼
Evidence Attached
        │
        ▼
SOC Investigation
```

### 2.3 Events as Evidence

Events are single activities recorded in the Log Analytics Workspace, for example a sign in, a deleted file, a PowerShell execution, an allowed firewall connection, a process start, or a locked account. Organizations generate thousands, even millions, of events daily, most of them completely normal.

When an Analytics Rule detects suspicious activity, it attaches the **matching events** to the incident as evidence. For example, if a rule detects "more than 10 failed logins followed by one successful login," Sentinel attaches the actual login events, letting the analyst immediately verify the number of failed attempts, the time of each attempt, the source IP address, and the target account. This makes the investigation faster because the analyst is not searching for the raw logs separately.

### 2.4 Alerts as Evidence and Alert Grouping

Alerts represent suspicious activity detected by Analytics Rules, for example suspicious file detection, suspicious user activity, privilege escalation attempts, malware detection, or impossible travel. Most Sentinel incidents originate from one or more alerts. An alert says "this deserves attention," it does not contain the complete investigation, that is the purpose of the incident.

Sentinel can group multiple related alerts into a single incident. This process is called **Alert Grouping**.

```text
Alert 1: Password Spray
Alert 2: Successful Login
Alert 3: Privilege Escalation
        │
        ▼
Single Incident (Alert Grouping)
```

Instead of investigating three separate alerts, the analyst investigates one incident containing all the related evidence.

### 2.5 Bookmarks

A **Bookmark** lets an analyst save an important finding during an investigation. While reviewing large volumes of events, an analyst may find activity that looks useful but is not yet actionable. Rather than searching for it again later, the analyst bookmarks it.

Bookmarks can include interesting events, notes, tags, and investigation comments. They can be shared with other SOC analysts and referenced later during threat hunting, without modifying the original event data.

> **Exam tip:** Bookmarks improve investigation efficiency and support collaboration and threat hunting. They do not alter the underlying logs.

### 2.6 Incident Entities

An **Entity** is any identifiable object involved in an incident. While evidence explains **why** an incident exists, entities identify **the objects involved**, helping analysts understand who, what, or where the attack affected.

Common entity types mentioned for incident investigation:

| Entity Type | Example |
|---|---|
| Account | A user or service account involved in the activity |
| Host | A device or machine involved in the activity |
| IP Address | Source or destination address of network traffic |
| URL | A web address linked to the activity |
| File Hash | A unique identifier for a file, often malware |

> **Good to know:** Microsoft Sentinel supports additional entity types beyond the core five above, including Azure resource, cloud application, mailbox, mail message, process, registry key, DNS resolution, and security group. Selecting an entity in the Investigation Graph reveals its connections to other entities.

### SC-200 Exam Tips (Part 2)

> * **Incident Evidence** supports the investigation, it is attached after the incident is created, it does not create it.
> * **Events** are raw activity; matching events become evidence when an Analytics Rule triggers.
> * **Alerts** are detections that often become incident evidence.
> * **Alert Grouping** combines multiple related alerts into a single incident.
> * **Bookmarks** save findings for later review, collaboration, and threat hunting.
> * **Entities** are the objects (accounts, hosts, IPs, URLs, file hashes, and more) involved in an attack.
> * Know the distinction: **Events = raw activity**, **Alerts = detection**, **Evidence = investigation support**, **Entities = objects involved**.

## Part 3: Incident Management

### 3.1 Reviewing Incidents: Overview Page vs Incidents Page

Reviewing incidents is the first task a SOC analyst performs after Sentinel detects suspicious activity. There are two primary places to do this.

| Page | Purpose |
|---|---|
| **Overview page** | High level summary snapshot: how many incidents exist, how many are active, severity distribution, recent activity. Best used at the start of a shift. |
| **Incidents page** | Complete list of every incident in the workspace, where analysts spend most of their investigation time. Supports search, sort, and filter. |

Each incident on the Incidents page shows its Incident ID, title, severity, alert count, product source, creation time, last updated time, owner, and status. Filtering is available by severity, status, owner, product, and incident name.

Selecting an incident opens the **Incident Details** pane, which includes description, evidence, entities, the triggering Analytics Rule, related alerts, and **MITRE ATT&CK** tactics. Choosing **View Full Details** opens a deeper investigation experience, including associated workbooks and Analytics Rule details.

> **Exam tip:** Microsoft Entra identity investigations from within an incident may require the **Directory Reader** role.

### 3.2 Incident Metadata: Ownership, Status, Severity

Every incident carries metadata so SOC teams can organize and manage investigations without duplicating effort.

| Property | Answers the Question | Values |
|---|---|---|
| **Ownership** | Who is responsible for the incident? | An assigned analyst (can be reassigned or escalated) |
| **Status** | Where does the investigation currently stand? | New, Active, Closed |
| **Severity** | How much impact could this incident have, and how urgently should it be worked? | Informational, Low, Medium, High |

**Ownership** provides accountability, investigation tracking, easier collaboration, and a clear escalation path. Without it, multiple analysts might duplicate work on one incident while others go unattended.

**Status** progresses through a simple lifecycle:

```text
New
  │
  ▼
Active
  │
  ▼
Closed
```

* **New** — not yet investigated
* **Active** — investigation in progress
* **Closed** — investigation completed

**Severity** determines investigation priority. It is usually set automatically by the Analytics Rule or Microsoft security product that generated the incident, but analysts can raise or lower it as new evidence emerges.

### 3.3 Closing an Incident: Resolution Classification

Closing an incident requires selecting a **Resolution Classification**:

| Classification | Meaning |
|---|---|
| **True Positive** | Confirmed malicious activity |
| **Benign Positive** | Detection was correct, but the activity was expected or authorized |
| **False Positive** | The detection should not have occurred |

> **Exam tip:** "Benign Positive" is easy to confuse with "False Positive." Benign Positive means the detection logic worked correctly, the activity really happened, it just was not malicious. False Positive means the detection itself was wrong.

### 3.4 Investigation Graph

The **Investigation Graph** is one of Sentinel's most powerful tools. Instead of showing information as lists, it visually maps the **relationships between entities** involved in an incident, helping answer questions such as which user logged onto which computer, which IP address communicated with which server, which alerts are related, and how different entities connect.

Selecting an entity in the graph reveals additional context, including related alerts, account activity, and connected entities. The graph correlates information from Microsoft Entra ID, Microsoft Defender products, Azure Activity Logs, and other connected sources.

### SC-200 Exam Tips (Part 3)

> * **Overview page** = summary snapshot. **Incidents page** = full incident list with filtering.
> * The **Incident Details** pane shows description, evidence, entities, the Analytics Rule, related alerts, and **MITRE ATT&CK** tactics.
> * **Ownership** = who. **Status** = where the investigation stands (New, Active, Closed). **Severity** = how urgent (Informational, Low, Medium, High).
> * Closing an incident always requires a **Resolution Classification**: True Positive, Benign Positive, or False Positive.
> * The **Investigation Graph** visualizes entity relationships and correlates data from Entra ID, Defender products, and Azure Activity Logs.
> * Microsoft Entra identity investigations may require the **Directory Reader** role.

### Quick Definitions Table

| Term | One Line Definition |
|---|---|
| Event | A single raw recorded activity, stored in the Log Analytics Workspace |
| Analytics Rule | Detection logic (template or KQL) that scans events for threats |
| Alert | A notification that an Analytics Rule found suspicious activity |
| Incident | A case file grouping one or more related alerts for investigation |
| Evidence | Supporting information attached to an incident, explains why it exists |
| Entity | An object (account, host, IP, URL, file hash, etc.) involved in an incident |
| Bookmark | A saved finding from an investigation, shareable for collaboration or hunting |
| Alert Grouping | Combining multiple related alerts into one incident |
| Investigation Graph | Visual map of entity relationships within an incident |

### Frequently Confused Concepts

| Concept A | Concept B | The Difference |
|---|---|---|
| Alert | Incident | An alert is one detection; an incident groups related alerts into one case |
| Evidence | Entities | Evidence explains **why** the incident exists; entities identify **what/who** was involved |
| Ownership | Status | Ownership is **who** is responsible; status is **where** the investigation stands |
| Benign Positive | False Positive | Benign Positive: correct detection, expected activity. False Positive: incorrect detection |
| Overview page | Incidents page | Overview is a summary snapshot; Incidents page lists and lets you filter every incident |

### Key KQL Concepts for Analytics Rules

Analytics Rules can run custom **Kusto Query Language (KQL)** queries against the Log Analytics Workspace. You are not expected to master KQL for this module, but recognizing the core syntax helps with detection focused SC-200 questions.

| Operator | Purpose |
|---|---|
| `where` | Filters rows based on a condition |
| `project` | Selects specific columns to return |
| `summarize` | Aggregates data, often with `count()` |
| `extend` | Adds a calculated column |
| `join` | Combines rows from two tables on a matching key |
| `ago()` | Refers to a relative time in the past, for example `ago(1d)` |
| `TimeGenerated` | The standard timestamp column used for time filtering |

Example, modeled on the "more than 10 failed logins followed by a success" scenario from this module:

```kql
SigninLogs
| where TimeGenerated > ago(1d)
| where ResultType != "0"
| summarize FailedCount = count() by UserPrincipalName, IPAddress
| where FailedCount > 10
```

> **Exam tip:** You will not need to write complex KQL for the incident management objectives, but you should recognize that Analytics Rules can be template based or fully custom KQL, and that the Log Analytics Workspace is the data source being queried.

### Final Checklist Before the Exam

1. Be able to state the full pipeline from memory: **Data Connector → Event → Analytics Rule → Alert → Incident → Investigation**.
2. Know that evidence is attached **after** incident creation, not before.
3. Know the three Status values (New, Active, Closed) and the three Resolution Classifications (True Positive, Benign Positive, False Positive), and do not mix them up.
4. Know that Severity can be changed by an analyst, it is not fixed once set.
5. Know what lives in the Incident Details pane: description, evidence, entities, Analytics Rule, related alerts, MITRE ATT&CK tactics.
6. Know that the Investigation Graph shows entity relationships and pulls data from Entra ID, Defender products, and Azure Activity Logs.
7. Remember Alert Grouping combines related alerts into one incident, reducing duplicate investigation work.
8. Remember Bookmarks save findings without modifying original event data, useful for collaboration and threat hunting.
