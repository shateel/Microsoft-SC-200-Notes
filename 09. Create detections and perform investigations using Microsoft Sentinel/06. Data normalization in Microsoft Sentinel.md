## 1. Introduction to Data Normalization

**Data normalization** is the process of converting security logs from different vendors into a **common format** so Microsoft Sentinel can process them consistently.

Every vendor names the same concept differently. For example, the field that stores a username looks completely different across products:

| Source | Field Name Used |
|---|---|
| Microsoft Defender | `AccountName` |
| Windows Event | `TargetUserName` |
| Sysmon | `User` |

All three represent the same concept, **Username**. Normalization maps every vendor variant into one standardized field, so an analyst queries a single common field instead of memorizing dozens of vendor specific names.

> **Exam tip:** If a question describes different products using different field names for the same concept, and asks how Sentinel solves this, the answer is **data normalization using ASIM**.

## 2. ASIM: Advanced Security Information Model

**ASIM** stands for **Advanced Security Information Model**. It is Microsoft Sentinel's data normalization framework, acting as a translation layer that sits between raw data sources and everything an analyst or Sentinel feature does with that data.

```text
Different Security Products
        │
        ▼
       ASIM
(Translates to a Common Format)
        │
        ▼
   Normalized Data
        │
        ▼
 Analytics · Hunting · Workbooks · Investigations
```

ASIM converts inconsistent security telemetry into standardized, user friendly data, and it sits between the data sources and Microsoft Sentinel users.

> **Exam tip, Robustness Principle:** ASIM follows the classic networking robustness principle: **be strict in what you send, be flexible in what you accept.** This phrase shows up in SC-200 style questions about ASIM's design philosophy.

### Benefits of ASIM

#### Cross Source Detection

A **single analytics rule** written against a normalized schema can detect the same attack pattern across many different products, instead of needing a separate rule per vendor.

```text
WITHOUT ASIM                    WITH ASIM
Windows Rule                    One ASIM Rule
Linux Rule                            │
Azure Rule                            ▼
AWS Rule              Windows · Linux · Azure · AWS · Okta
Okta Rule
(5 separate rules)          (1 rule covers all sources)
```

**Example:** An organization using Windows Servers, AWS, Azure, and Okta wants to detect **impossible travel**. Without ASIM, this needs a separate rule per platform. With ASIM, one normalized Authentication rule covers all four sources.

#### Source Agnostic Content

**Source agnostic** means Sentinel content does not depend on a specific vendor. Instead of asking "did Windows generate this event," the analytics rule asks "is this an authentication event." ASIM determines which source actually produced the event.

Both built in and custom content automatically work with any source that supports ASIM, including Microsoft Defender for Endpoint, Windows Events, and Sysmon.

> **Why it matters:** If an organization collects Windows Event Logs today and deploys Sysmon next year, and both sources support ASIM, existing analytics rules keep working with no rewriting required.

#### Support for Custom Sources

Custom applications, third party firewalls, and proprietary software normally cannot use Microsoft's built in analytics rules. ASIM lets administrators normalize these custom logs into the same schema Sentinel already understands. Once normalized, custom logs can be used in Analytics Rules, Hunting Queries, Workbooks, and Investigations exactly like Microsoft native logs.

### ASIM and OSSEM

ASIM aligns with the **Open Source Security Events Metadata (OSSEM)** project, a community driven initiative that standardizes security event documentation across vendors and operating systems. OSSEM provides a **Common Information Model (CIM)** used to help normalize data from different sources.

> **Exam tip:** You are **not** expected to know OSSEM in depth for SC-200. Just remember three facts: it is an open, community driven project; it provides a Common Information Model (CIM); and ASIM aligns with it to improve standardization and interoperability.

### SC-200 Exam Tips

* **Data Normalization** converts vendor specific logs into a common format.
* **ASIM** = **Advanced Security Information Model**, Sentinel's normalization framework.
* ASIM sits between **data sources** and **Microsoft Sentinel**.
* Remember the **Robustness Principle**: be strict in what you send, be flexible in what you accept.
* Three ASIM benefits: **cross source detection**, **source agnostic content**, **support for custom sources**.
* **OSSEM** provides a Common Information Model (CIM); ASIM aligns with it.
* **Reporting Device** is the system that sent the record, it is **not necessarily** where the event actually occurred.
* **Record** = one unit of data (a log, event, or alert).

## 3. ASIM Components

The ASIM architecture is built from three components that work together to turn raw vendor logs into standardized, usable data.

| Component | Role |
|---|---|
| **Normalized Schemas** | Define the standard structure (template) for one event type |
| **Parsers** | Translate vendor specific logs into the normalized schema |
| **Content** | Analytics Rules, Hunting Queries, Workbooks, Investigations that consume normalized data |

### 1. Normalized Schemas

A **Normalized Schema** is a template that defines standard field names, column names, event format, and values for one category of event, regardless of the original source.

**Example, Authentication Schema fields:** `Username`, `SourceIP`, `DestinationHost`, `Result`, `TimeGenerated`. Whether the raw data came from Windows, Linux, Azure, or Okta, these same standardized fields are used after normalization.

Schemas referenced in this module include: **Authentication**, **DNS**, **Network Session**, **Process Event**, **Registry Event**, and **File Event**.

> **Good to know (supplementary):** Microsoft's ASIM documentation also defines additional normalized schemas beyond those above, such as Web Session, Audit Event, DHCP Event, and User Management. You do not need every schema memorized, just recognize that ASIM covers many event categories, not only authentication.

### 2. Parsers

A **Parser** is a translator that converts vendor specific logs into the normalized schema, implemented as a **KQL function**.

| Vendor Field | Parser Output (ASIM Field) |
|---|---|
| Windows: `TargetUserName` | `Username` |
| Linux: `User` | `Username` |

```text
Vendor Log
    │
    ▼
  Parser
(KQL Function)
    │
    ▼
Normalized Schema
    │
    ▼
Microsoft Sentinel
```

### 3. Content for Each Normalized Schema

Once data is normalized, the same content, Analytics Rules, Hunting Queries, Workbooks, and Investigations, works across every normalized source without building separate, source specific versions of each item.

### ASIM Architecture (the most important diagram in this module)

```text
Connectors
    │
    ▼
Raw Vendor Logs
    │
    ▼
Source Specific Parsers
    │
    ▼
Source Specific Normalized Data
    │
    ▼
Unifying Parsers
    │
    ▼
Multi Source Normalized Data
    │
    ▼
Microsoft Sentinel Features
    ├── Analytics Rules
    ├── Hunting Queries
    ├── Workbooks
    ├── UEBA
    ├── Fusion
    ├── Threat Intelligence
    └── Customer Content
```

**Step by step explanation:**

1. **Connectors** ingest logs from different security products.
2. Logs initially remain in their original vendor specific format.
3. **Source Specific Parsers** convert vendor specific logs into a standardized schema for that particular source.
4. **Unifying Parsers** combine normalized data from multiple vendors into one common ASIM schema.
5. Sentinel features (Analytics, Hunting, Workbooks, UEBA, Fusion, Threat Intelligence, and customer content) consume the unified normalized data, so the same logic works across many vendors without rewriting anything.

### SC-200 Exam Tips

* Three core ASIM components: **Normalized Schemas**, **Parsers**, **Content**.
* **Parsers use KQL functions** to map raw data into normalized schemas.
* **Content Items** (Analytics Rules, Hunting Queries, Workbooks) consume normalized data, they do not create it.
* Memorize the ASIM architecture flow: **Connectors → Raw Logs → Source Specific Parsers → Unifying Parsers → Sentinel Features.**
* Normalization = convert different log formats into one common schema.
* One normalized rule can work across multiple vendors at once.

## 4. Using ASIM Parsers

An **ASIM Parser** is a **Kusto Query Language (KQL) user defined function** that translates raw security logs into a standardized ASIM schema. Microsoft Sentinel recommends querying the **parser**, not the raw table directly.

```text
WITHOUT A PARSER              WITH A PARSER
   Raw Log                       Raw Log
     │                              │
     ▼                              ▼
Vendor Specific Fields         ASIM Parser
(different per source)              │
                                     ▼
                            Normalized Fields
                          (same regardless of source)
```

### Query Time Normalization

One of the most important SC-200 concepts is **when** normalization happens.

> Unlike some SIEMs that normalize data during ingestion, **Microsoft Sentinel performs parsing and normalization at query time.** The original stored logs are never rewritten, only the query results are normalized.

```text
Logs Stored
    │
    ▼
User Runs Query
    │
    ▼
ASIM Parser Executes
    │
    ▼
Normalized Results Returned
```

**Why normalize at query time?**

* Original data remains unchanged.
* Microsoft can improve parsers without re importing historical logs.
* Organizations can add new parsers without modifying stored data.

### Built in vs Workspace Deployed Parsers

| Aspect | Built in Parsers | Workspace Deployed Parsers |
|---|---|---|
| Availability | Present automatically in every Sentinel workspace | Deployed manually, e.g. from GitHub or an ARM template |
| Support | Fully supported by Microsoft, integrated with built in content | Functionally equivalent, but not used automatically by Microsoft's built in content |
| Modification | Cannot be directly modified by users | New parsers often appear here first, before becoming built in |
| Naming | `_Im_Authentication` style | `imAuthentication` style |
| Recommendation | Use whenever an equivalent exists | Use when no built in equivalent exists yet |

Both parser types can exist in the same workspace at the same time because their naming conventions differ.

### Parser Hierarchy

ASIM uses **two levels of parsers** that work together:

```text
Windows Parser ─┐
Linux Parser ───┤
Cisco Parser ───┼──▶  Unifying Parser  ──▶  One Normalized Dataset
Palo Alto Parser┘
```

* **Source Specific Parser:** Understands the log format of one particular product only, for example Palo Alto, Cisco, Infoblox, or Microsoft Defender. Keeps parsing logic accurate and easy to maintain per vendor.
* **Unifying Parser:** Combines the outputs of multiple source specific parsers into one normalized schema. Analysts should usually query the **Unifying Parser**, not individual vendor parsers.

### Naming Convention

| Parser Type | Naming Pattern | Example |
|---|---|---|
| Built in Unifying Parser | `_Im_<Schema>` | `_Im_Authentication`, `_Im_Dns`, `_Im_ProcessEvent` |
| Workspace Deployed Unifying Parser | `im<Schema>` | `imAuthentication` |

### Optimizing Parser Performance

Because parsing happens at query time, performance matters. Use available filtering parameters (such as `starttime` and `endtime`) to filter **before** parsing occurs.

```text
WITHOUT FILTERING                WITH FILTERING
1 Million Logs                   1 Million Logs
     │                                │
     ▼                                ▼
Parse Everything                 Filter First
     │                                │
     ▼                                ▼
Filter Results                  Parse Only Matching Logs
                                       │
                                       ▼
                                 Return Results
```

Parsing fewer records is significantly faster than parsing everything and filtering afterward.

### SC-200 Exam Tips

* **ASIM Parsers are KQL user defined functions.**
* Sentinel performs **parsing and normalization at query time**, not at ingestion time.
* Query the **ASIM parser** instead of raw tables such as `CommonSecurityLog` or `Syslog`.
* Two parser types: **Built in** and **Workspace Deployed**. Prefer built in whenever an equivalent exists.
* Two parser levels: **Source Specific** (one vendor) and **Unifying** (combines many vendors); most rules and hunts should query the **Unifying Parser**.
* Filtering **before** parsing (using parameters like `starttime`/`endtime`) improves performance.

## 5. Parameterized KQL Functions

A **Parameterized KQL Function** is a saved KQL query that accepts one or more input parameters, similar to a function in a programming language. Instead of hardcoding values such as dates, usernames, IP addresses, or categories, you pass them in when the function runs.

> **Why they matter for the exam:** Parameterized functions are the mechanism used to build **ASIM parsers**. They let the parser filter data dynamically instead of returning every record.

### Converting a Hardcoded Query into a Function

**Original (hardcoded) query:**

```kql
AzureActivity
| where CategoryValue == "Administrative"
| where TimeGenerated > todatetime("2021/04/05 5:40:01 PM")
```

**Parameterized version:**

```kql
AzureActivity
| where CategoryValue == CategoryParam
| where TimeGenerated > DateParam
```

The function is then saved with a name, for example `AzureActivityByCategory`, and each parameter is defined with a **Name**, a **Data Type**, and an optional **Default Value**.

| Parameter | Type | Default Value |
|---|---|---|
| `CategoryParam` | string | `"Administrative"` |
| `DateParam` | datetime | none shown |

### How Parameterized Functions Support ASIM Parsers

```text
Authentication Parser
        │
        ▼
starttime = Yesterday
endtime   = Today
Username  = Alice
        │
        ▼
Return Matching Records Only
```

Without parameters, the parser would return every authentication event in the table, which wastes performance. Parameters improve both flexibility and query speed.

### SC-200 Exam Tips

* Parameterized functions **replace hardcoded values with reusable inputs**.
* Typical workflow: verify the original query, replace hardcoded values with parameters, save the query as a function, define parameter names/types/defaults, then call the function with real values.
* Common parameter data types: `string`, `datetime`, `int`, `bool`.
* Parameters make functions reusable, flexible, easier to maintain, and more efficient.
* **ASIM parsers are implemented as parameterized KQL functions.**

## 6. Creating a Custom ASIM Parser

Build a custom parser when **built in parsers cannot correctly normalize a data source** (unsupported devices, custom log formats, firmware differences, or modified logs).

### Custom Parser Development Workflow

```text
Collect Sample Logs
        │
        ▼
Identify ASIM Schema
        │
        ▼
Map Source Fields
        │
        ▼
Develop Parser
        │
        ▼
Test Parser
        │
        ▼
Deploy Parser
        │
        ▼
Update Unifying Parser
```

**Step 1, Collect Sample Logs.** Gather representative logs covering successful events, failed events, different action types, usernames, hostname formats, IP addresses, and event IDs. Testing only the "happy path" (e.g. only successful logins) risks the parser breaking later when a different event format arrives (e.g. a failed login).

**Step 2, Identify the Correct ASIM Schema.** Match the source events to an existing schema.

| Log Type | Usually Belongs To Schema |
|---|---|
| Firewall Logs | Network Session |
| Authentication Logs | Authentication |
| DNS Logs | DNS |

Choosing the wrong schema makes the parser incompatible with Microsoft's built in content.

**Step 3, Map Source Fields.** Every vendor uses different field names; the parser maps them to ASIM field names.

| Vendor Field | ASIM Field |
|---|---|
| `Src_IP` | `SrcIpAddr` |
| `UserName` | `Username` |
| `ResultCode` | `EventResult` |

If a field has no equivalent in the chosen schema, check whether another ASIM schema has a matching normalized field.

**Value Mapping is also required**, not just field names. Vendor specific values must map to the values ASIM expects.

| Vendor Value | ASIM Value |
|---|---|
| `Allow` | `Success` |
| `Deny` | `Failure` |

**Step 4, Develop the Parser.** Microsoft recommends building **two parsers per schema**:

* **Filtering Parser:** Accepts parameters (time, source values) and is optimized for performance.
* **Parameterless Parser:** Returns normalized results without requiring parameters; typically used internally by the filtering parser.

**Parser internal structure**, three logical stages:

```text
Filter Records
      │
      ▼
Parse Fields
      │
      ▼
Prepare Output Fields
```

**Stage 1 example, filter first:** A single table like `Syslog` may hold DNS, Authentication, Firewall, and Linux Service logs all mixed together. A DNS parser should filter to DNS records **before** parsing them, which improves performance.

```text
All Syslog
    │
    ▼
Filter DNS Records
    │
    ▼
Parse DNS Data
```

### Testing the Parser

Before deployment, verify:

* Correct records are selected.
* Every required field is populated.
* Values are correctly normalized.
* Filtering parameters work correctly.
* Performance is acceptable.

Test against multiple event types to catch parsing errors before production use.

### Deploying the Parser

* Deploy the parser to the Sentinel workspace.
* Update the relevant **ASIM Unifying Parser** so it references the new custom parser.
* Optionally contribute the parser back to the ASIM open source project for wider reuse.

Once linked to the Unifying Parser, Sentinel treats the new custom source exactly like any officially supported source.

### SC-200 Exam Tips

* Build a custom ASIM parser when built in parsers cannot correctly normalize a source (unsupported device, custom log format, firmware differences, modified logs).
* Development workflow (memorize the order): **collect samples → identify schema → map fields → develop filtering and parameterless parsers → test → deploy → update the Unifying Parser.**
* **Do not filter by time inside the parser itself**, let the calling query define the time range.
* Filter records **before** parsing, for better performance.
* Use the **ASimSourceType Watchlist** when filtering by source type is difficult.
* Prefer efficient parsing operators; minimize regular expressions.
* Normalize both **field names** and **field values** before returning results.

## 7. Azure Monitor and Data Collection Rules

### What is Azure Monitor?

**Azure Monitor** is Microsoft's cloud native monitoring service. It collects, analyzes, stores, and visualizes telemetry from Azure resources, on premises servers, virtual machines, applications, containers, and other cloud services. It helps answer questions such as "is my server healthy," "is there suspicious activity," and "what logs should Sentinel analyze."

> **In one line:** Azure Monitor collects the data, while Microsoft Sentinel analyzes that data for security threats.

```text
Azure Resources / VMs / Applications / Azure Services
On Prem Servers / Containers / Network Devices
        │
        ▼
   Azure Monitor
        │
        ├── Metrics
        ├── Logs
        ├── Events
        └── Alerts
        │
        ▼
Log Analytics Workspace
        │
        ▼
Microsoft Sentinel
        │
        ▼
Threat Detection
```

### Data Collection Rules (DCRs)

A **Data Collection Rule (DCR)** is an Azure Monitor resource that defines **what** data to collect, **which** machines to collect it from, **how** to transform it, and **where** to send it. Think of a DCR as a processing pipeline sitting between the data source and Azure Monitor.

```text
Data Source
    │
    ▼
Data Collection Rule (DCR)
    │
    ├── Collect Data
    ├── Filter Data
    ├── Transform Data
    └── Route Data
              │
              ▼
     Azure Monitor Logs
              │
              ▼
     Microsoft Sentinel
```

**Without a DCR:** Device → Raw Logs → Log Analytics Workspace (everything is stored exactly as received).

**With a DCR:** Device → Data Collection Rule (Filter, Modify, Rename, Route) → Log Analytics Workspace (stored data is already optimized for analysis).

### DCR vs ASIM Parser (a key SC-200 comparison)

| Aspect | ASIM Parser | Data Collection Rule (DCR) |
|---|---|---|
| When transformation happens | At **query time** | **Before storage**, at ingestion |
| Original logs | Remain unchanged | Transformed data is what gets stored |
| Technology | KQL functions | Ingestion time transformations (also written in KQL) |
| Main purpose | Normalization | Improves query performance and reduces storage |

```text
ASIM PARSER PIPELINE           DCR PIPELINE
Store Raw Logs                 Receive Logs
      │                              │
      ▼                              ▼
  Run Query                     Transform
      │                              │
      ▼                              ▼
  Transform                   Store Clean Data
```

> **Exam tip, direct question format:**
> "Which technology transforms data **before** it is stored?" → **Data Collection Rules (DCRs).**
> "Which technology normalizes data **during query execution**?" → **ASIM Parsers.**

### ETL Pipeline

The source material describes a DCR as an **ETL style pipeline**: **Extract, Transform, Load.**

| Stage | What Happens |
|---|---|
| **Extract** | Azure Monitor collects data from the source (Azure Monitor Agent, virtual machines, custom logs) |
| **Transform** | The DCR filters records, modifies fields, renames columns, or parses values |
| **Load** | The transformed data is stored in Azure Monitor Logs / Log Analytics Workspace |

### Types of Data Collection Rules

**1. Standard DCR:** The most common type, used with workflows that send data directly to Azure Monitor, for example via the **Azure Monitor Agent (AMA)** or custom log ingestion.

```text
Azure Monitor Agent
        │
        ▼
    Standard DCR
        │
        ▼
    Azure Monitor
```

**2. Workspace Transformation DCR:** Performs ingestion time transformations for data that does not currently support standard DCR processing directly. Instead of modifying data at collection, it transforms data as it enters the Log Analytics workspace.

```text
Incoming Data
        │
        ▼
Workspace Transformation DCR
        │
        ▼
   Transform Data
        │
        ▼
Log Analytics Workspace
```

### Transformations and the "source" Table

**Transformations** let Sentinel modify incoming records before they are stored, written in **Kusto Query Language (KQL)**. Rather than editing existing data, a transformation creates a new version of the incoming record that matches the target table, and this happens once at ingestion instead of every time a query runs.

**Example:** An original log has `Severity = Informational`, but the organization only wants to keep `Severity = Critical` records. The DCR can discard everything else before storage, reducing storage costs, query time, and unnecessary noise.

The **`source`** identifier used inside a transformation is **not a real table**. It is a **virtual table** representing the incoming records currently being processed by the DCR.

```text
Incoming Records
       │
       ▼
 Virtual Table (source)
       │
       ▼
  Transformation
       │
       ▼
 Destination Table
```

### SC-200 Exam Tips

* **DCRs provide an ETL style pipeline:** Extract, Transform, Load.
* A DCR defines what to collect, how to transform it, and where to send it.
* **Transformations occur at ingestion time**, before data is stored; **ASIM parsers normalize at query time.**
* Two DCR types to remember: **Standard DCR** and **Workspace Transformation DCR**.
* DCR transformations are written using **KQL**.
* Every transformation begins from the virtual **`source`** table.
* Common KQL operators in DCR transformations: `where` (filter records), `extend` (create new columns), `project` (select final output columns).
* `parse_json()` converts text into structured data that queries more efficiently.

## 8. SC-200 Last Minute Revision

### Must Memorize Facts

* **ASIM** = Advanced Security Information Model = Sentinel's normalization framework.
* Sentinel normalizes **at query time**, not at ingestion (that is what makes ASIM different from many other SIEM approaches).
* **DCRs** transform **at ingestion time**, before storage.
* **Parsers = KQL functions.** **DCR transformations = also KQL, but ingestion time.**
* Query the **Unifying Parser**, not raw tables like `CommonSecurityLog` or `Syslog`, whenever possible.
* Built in parser naming: `_Im_<Schema>` (example `_Im_Authentication`). Workspace deployed naming: `im<Schema>` (example `imAuthentication`).
* Filter **before** you parse, and filter **before** you transform, for best performance.
* **Reporting Device** = system that sent the record, not necessarily where the event happened.

### Frequently Confused Concepts

| Concept A | Concept B | How to Tell Them Apart |
|---|---|---|
| ASIM Parser | Data Collection Rule (DCR) | Parser = normalizes at query time, logs untouched. DCR = transforms at ingestion time, stored data is changed. |
| Source Specific Parser | Unifying Parser | Source specific = one vendor only. Unifying = combines many source specific parsers into one dataset; query this one for hunting/analytics. |
| Built in Parser | Workspace Deployed Parser | Built in = automatic in every workspace, Microsoft supported, used by default content. Workspace deployed = manually installed (GitHub/ARM), often newer, not used automatically by built in content. |
| Standard DCR | Workspace Transformation DCR | Standard = works with sources sending data directly (e.g. AMA). Workspace Transformation = transforms data as it lands in the Log Analytics workspace, for sources that cannot use a Standard DCR directly. |
| Normalized Schema | Parser | Schema = the template/structure (the "what"). Parser = the KQL function that performs the conversion (the "how"). |
| Field Mapping | Value Mapping | Field mapping = renaming columns (e.g. `Src_IP` to `SrcIpAddr`). Value mapping = translating the data inside a field (e.g. `Allow` to `Success`). |

### Important KQL Syntax to Recognize

```kql
// Basic filter and transform pattern used in DCRs and parsers
source
| where Severity == "Critical"
| extend NewField = strcat(FieldA, FieldB)
| project TimeGenerated, NewField, Severity
```

* `where` → filters records.
* `extend` → creates new computed columns.
* `project` → selects which columns appear in the final output.
* `parse_json()` → converts a text/string field into structured, queryable data.
* `datetime()` / `todatetime()` → converts text into a KQL datetime value for time comparisons.
