## Log Analytics Workspace and the Sentinel Logs Page

### What Is the Log Analytics Workspace?

The **Log Analytics Workspace** is the centralized repository, essentially the **database behind Microsoft Sentinel**, that stores:

* Security logs
* Configuration information
* Collected telemetry

It allows analysts to:

* Search logs
* Aggregate data
* Filter events
* Correlate events from multiple sources
* Create analytics rules
* Detect threats

> **Key idea:** Every KQL query you run in Microsoft Sentinel executes against the Log Analytics Workspace. Sentinel itself does not store its own separate copy of the data; it queries the workspace.

### The Sentinel Logs Page

The **Logs** page is the primary interface analysts use to write and run KQL queries. It is made up of four main areas:

| Area | Purpose |
| --- | --- |
| Page Header | Toolbar with run, save, time range, export, share, and alert creation controls |
| Tables Pane | Lists all available log tables, grouped by solution |
| Query Pane | Where KQL is written and executed |
| Query Results | Displays output as a table or a chart |

The **Header Toolbar** specifically allows analysts to:

* Run queries
* Save queries
* Change the time range
* Export results
* Share queries
* Create an Azure Monitor or Microsoft Sentinel alert directly from a query

> **Exam tip:** Creating a **Microsoft Sentinel Alert** from a query in the Logs page is the starting point for building an **Analytics Rule**. This connection (query → alert → analytics rule) is a common exam concept.

### Data Flow: From Raw Data to an Alert

```text
Data Sources (Azure, Defender, firewalls, endpoints, etc.)
      │
      ▼
Log Analytics Workspace
      │
      ▼
Sentinel Logs Page (KQL Query)
      │
      ▼
Query Results (Table or Chart)
      │
      ▼
Create Alert from Query
      │
      ▼
Analytics Rule
```

### Key Definitions Recap

| Term | Definition |
| --- | --- |
| Log Analytics Workspace | Database that stores Microsoft Sentinel logs |
| Tables Pane | List of available log tables |
| Query Pane | Area to write and run KQL |
| Query Explorer | Saved queries and Microsoft provided Solution Queries |
| Results Pane | Displays results as a table or chart |
| `extend` | Commonly used to create Microsoft Sentinel entity fields, such as `AccountCustomEntity` and `IPCustomEntity` |

### SC-200 Exam Tips

> * Microsoft **Sentinel Logs** is the primary interface for querying security data.
> * The **Log Analytics Workspace** stores the data that Microsoft Sentinel queries; think of it as the underlying database.
> * Every KQL query starts from a **table**, for example `SecurityEvent`, `AzureActivity`, `SigninLogs`, `CommonSecurityLog`.
> * **Query Explorer** stores saved queries and gives access to Solution Queries.
> * `extend` creates new columns and is commonly used to map entity fields, such as `AccountCustomEntity` and `IPCustomEntity`, which Sentinel uses to identify the account or IP address involved in an incident.
> * Query results can be displayed as either **tables** or **charts**.
> * Creating an alert from a Logs page query is the first step toward building an **Analytics Rule**.

## Kusto Query Language (KQL) Fundamentals

### Microsoft Sentinel GitHub Repository

Microsoft maintains a public **GitHub repository** containing:

* Hunting queries
* Analytics queries
* Workbooks

SOC analysts use these as starting points for investigations instead of writing every query from scratch. One example described in the source material is a query that detects suspicious Azure role assignment activity. Conceptually, it:

1. Filters the `AzureActivity` table for role assignment write operations.
2. Projects only the relevant fields (time, caller, resource group, status).
3. Maps the caller field to a Sentinel entity so it can be tracked across investigations.

```kql
// Illustrative pattern only, not an exact reproduction of the source query
AzureActivity
| where OperationNameValue == "MICROSOFT.AUTHORIZATION/ROLEASSIGNMENTS/WRITE"
| where ActivityStatusValue == "Success"
| project TimeGenerated, Caller, ResourceGroup, ActivityStatusValue
| extend AccountCustomEntity = Caller
```

> **Takeaway:** You rarely need to memorize a specific query for the exam. Instead, understand the **pattern**: filter with `where`, keep only needed columns with `project`, and map fields to entities with `extend`.

### Core KQL Concepts

* KQL is the primary query language for **Microsoft Sentinel** and **Log Analytics**.
* KQL queries are **read only**; they never modify the underlying data.
* Every query begins with a **table** name or a `search` command.
* The **pipe** (`|`) passes the output of one operator into the next operator.

### Common KQL Operators

| Operator | Purpose |
| --- | --- |
| `where` | Filters rows based on a condition |
| `count` | Counts rows |
| `take` | Returns the first N rows |
| `project` | Selects specific columns |
| `sort` | Orders rows |
| `top` | Returns the top N sorted rows |
| `extend` | Creates a new calculated column |
| `summarize` | Groups and aggregates data |
| `render` | Displays results as a chart |
| `join` | Combines related records from multiple tables |
| `union` | Appends rows from multiple tables into one result set |

> **Exam tip:** `ago()` is commonly paired with the `TimeGenerated` column to filter for recent events, for example `where TimeGenerated > ago(24h)`.

### `join` vs `union`

| Feature | `join` | `union` |
| --- | --- | --- |
| What it does | Combines **columns** from two tables based on a matching key | Stacks **rows** from two or more tables together |
| Typical use | Correlating an event in one table with related data in another (for example, matching a sign in event to a device record) | Searching across multiple similar tables at once (for example, searching several security log tables together) |
| Result shape | Wider (more columns) | Taller (more rows) |

> **Exam tip:** Microsoft Sentinel supports KQL but **does not support every KQL feature available in Azure Data Explorer**, so some advanced syntax available in Azure Data Explorer may not work identically inside Sentinel.

### SC-200 Exam Tips

> * KQL is **read only**, case sensitive for string comparisons, and always begins with a table or `search` command.
> * The pipe `|` chains operators together, and each operator processes the output of the one before it.
> * Memorize the operator table above: `where`, `count`, `take`, `project`, `sort`, `top`, `extend`, `summarize`, `render`.
> * `summarize ... by` is the standard way to aggregate and group data, for example counting failed sign ins per account.
> * `render` turns query results directly into a chart inside the Logs page.
> * The Microsoft Sentinel **GitHub repository** is a real source of prebuilt hunting queries, analytics rules, and workbooks that SOC teams reuse.

## Microsoft Sentinel Workbooks (Built In Templates)

### What Is a Workbook?

A **Workbook** is an interactive dashboard used to visualize and analyze security data stored in Microsoft Sentinel. Instead of reading thousands of raw log entries, analysts can view:

* Charts
* Tables
* Maps
* Metrics
* Interactive filters
* Trend graphs

A workbook turns raw security data into meaningful visual information.

### Why Workbooks Matter

Imagine an organization receives:

* 2 million sign in events
* 500 malware alerts
* 10,000 firewall events

Reviewing this volume as raw logs is impractical. A workbook condenses it into insight an analyst can act on quickly.

```text
Security Logs
      │
      ▼
Workbook
      │
      ├── Charts
      ├── Tables
      ├── Maps
      ├── Trends
      └── Metrics
             │
             ▼
Quick Security Insights
```

### How Workbooks Actually Work

A common misconception is that workbooks store their own data. **They do not.** Each tile in a workbook runs one or more KQL queries in the background against the Log Analytics Workspace, every time the workbook is opened or refreshed.

```text
User Opens Workbook
      │
      ▼
Workbook Tile
      │
      ▼
Run KQL Query
      │
      ▼
Log Analytics Workspace
      │
      ▼
Return Results
      │
      ▼
Display Chart
```

> **Key idea:** A workbook is essentially a **collection of visualized KQL queries**, not a separate database. This is one of the most frequently tested distinctions on the SC-200 exam.

### Workbook Templates

Microsoft provides many built in workbook templates that already contain preconfigured:

* Queries
* Charts
* Tables
* Visualizations

Analysts can customize these templates for their own environment instead of building dashboards from scratch.

The **Microsoft Entra Sign-in Workbook** is a commonly referenced built in template. It surfaces:

* Sign in locations
* Devices
* Failed sign ins
* Conditional Access status
* MFA (Multifactor Authentication) requirements

### The Advanced Editor

The **Advanced Editor** displays the workbook definition as **JSON**, since every workbook is stored as a JSON based Azure resource. SOC engineers can use it to:

* Modify queries
* Change parameters
* Add visualizations
* Adjust layout

This allows changes that are not always exposed in the graphical editor.

### Key Points to Remember

| Concept | Meaning |
| --- | --- |
| Workbook | Interactive visualization dashboard |
| Templates tab | Microsoft provided workbook designs |
| My Workbooks tab | Saved and customized workbooks |
| Each tile | Runs one or more KQL queries |
| Data source | Log Analytics Workspace (workbooks never store their own data) |
| Filters (Time Range, Application, User) | Automatically update all visualizations in the workbook |
| Drill down | Selecting a chart or row reveals more detailed information |
| Refresh | Reruns all KQL queries in the workbook |
| Advanced Editor | Exposes the workbook's JSON definition |
| Pinning | Frequently used tiles can be pinned to Azure dashboards |

### SC-200 Exam Tips

> * Workbooks are **visualization only**; they never store data themselves, they run KQL against the **Log Analytics Workspace**.
> * The **Templates** tab holds predefined workbooks, while **My Workbooks** holds saved and customized ones.
> * Interactive **filters** (Time Range, Application, User) update every visualization in the workbook at once.
> * The **Microsoft Entra Sign-in Workbook** is a good example to remember: sign in locations, devices, failed sign ins, Conditional Access status, and MFA requirements.
> * **Refresh** reruns the underlying KQL, it does not pull from a cached workbook database because none exists.
> * The **Advanced Editor** is JSON based, since workbooks are Azure JSON resources under the hood.
> * The Microsoft Sentinel **GitHub repository** also supplies reusable workbooks alongside hunting queries and playbooks.

## Creating a Custom Microsoft Sentinel Workbook

### What Is a Custom Workbook?

A **custom workbook** is one you build yourself instead of starting from a Microsoft template. It gives complete control over:

* Layout
* Queries
* Visualizations
* Parameters
* Navigation
* Metrics

Think of it as building your own SOC dashboard from a blank canvas.

### Creation Workflow

```text
Workbooks Page
      │
      ▼
Select "+ Add workbook"
      │
      ▼
Basic Analytics Query Loaded Automatically
      │
      ▼
Select "Edit" (Enter Edit Mode)
      │
      ▼
Add and Configure Components
      │
      ▼
Save (Stored as an Azure Resource in the Sentinel Resource Group)
```

A new workbook always starts with a basic query already in place to help you get going, and every workbook you save becomes an **Azure resource** inside the Microsoft Sentinel resource group. You can only build or modify a workbook while in **Edit Mode**.

### Markdown Formatting Inside Workbooks

Microsoft Sentinel uses **Markdown**, the same lightweight markup language used to format this guide, to format text inside workbooks. It supports:

* Headings
* Bold text
* Italics
* Hyperlinks
* Tables

You can preview the formatted content before saving it.

### Visualization Options

The **Visualization** setting determines how query results are displayed. Options include:

* Grid
* Line Chart
* Bar Chart
* Pie Chart
* Time Chart
* Tiles

You can let the KQL query itself decide the visualization using the `render` operator, or override it manually using the workbook's Visualization setting.

| Visualization Type | Best Used For |
| --- | --- |
| Grid | Detailed, row level records |
| Line / Bar / Pie / Time Chart | Trends and summarized patterns |
| Tiles | At a glance metric style summaries |

### Parameters

**Parameters** make a workbook interactive. Without them, an analyst has to edit the underlying KQL query every time they want different results. With parameters, an analyst simply changes a selection, such as:

* User
* Time range
* Subscription
* Resource

...and every connected visualization updates automatically, with no query editing required.

### SC-200 Exam Tips

> * A custom workbook is created from **Workbooks → + Add workbook**.
> * Every workbook, template based or custom, is saved as an **Azure resource** inside the Sentinel resource group.
> * Workbook text uses **Markdown** formatting.
> * **Query Items** are the building blocks that execute KQL and display results.
> * **Run Query** lets you test a query before saving the workbook.
> * **Grid** suits detailed record level review, while **charts** suit trend and summary review.
> * **Parameters** remove the need to edit KQL for common changes like user, time range, subscription, or resource.
> * **Links/Tabs** improve navigation across a large workbook.
> * **Metric Steps** combine native Azure metrics with workbook content.
> * No matter how a workbook looks, every dynamic visualization ultimately depends on a **KQL query against the Log Analytics Workspace**.

## SC-200 Last Minute Revision

### One Page Cheat Sheet

| Concept | One Line Memory Hook |
| --- | --- |
| Log Analytics Workspace | The database behind Sentinel; every KQL query runs here |
| Sentinel Logs Page | Where you write and run KQL, with Tables Pane, Query Pane, and Results |
| KQL | Read only query language; pipe `\|` chains operators |
| Workbook | Interactive dashboard; never stores data, only runs KQL |
| Custom Workbook | Blank canvas workbook; full control of layout, queries, parameters |
| Advanced Editor | JSON view of a workbook, since workbooks are Azure JSON resources |
| Parameters | Turn a static query into an interactive control (user, time range, etc.) |
| Analytics Rule | Created starting from a saved alert built off a Logs page query |

### Frequently Confused Concepts

| Term | What It Actually Is | Common Mistake |
| --- | --- | --- |
| Log Analytics Workspace | The data store (database) | Confusing it with Sentinel itself; Sentinel is the analytics layer on top of the workspace |
| Workbook | A visualization dashboard that runs live KQL queries | Thinking it stores its own data separately from the workspace |
| Analytics Rule | Detection logic that generates **alerts**, which can become **incidents** | Confusing it with a Workbook, which only visualizes and never generates alerts |
| Playbook | An automated response workflow, typically built on Azure Logic Apps, triggered by an alert or incident | Confusing it with a Workbook because the names sound similar; a Playbook automates response, a Workbook only visualizes data |
| `join` | Combines **columns** from two tables using a matching key | Using it when you actually just want to stack rows, which calls for `union` |
| `union` | Combines **rows** from multiple tables | Using it when you actually want to match related records across tables, which calls for `join` |

> **Exam tip:** Remember the chain: **Query → Alert → Analytics Rule → Incident → (optional) Playbook for automated response.** Workbooks sit outside this chain entirely; they only visualize.

### Relationship Diagram: How It All Connects

```text
Data Sources
      │
      ▼
Log Analytics Workspace
      │
      ▼
KQL Query (Logs Page)
      │
      ├── Workbook Tile ──► Visualization (Charts, Tables, Maps, Metrics)
      │
      └── Saved as Alert ──► Analytics Rule ──► Incident
```

### Quick KQL Syntax Reference

```kql
TableName
| where TimeGenerated > ago(24h)
| where ColumnName == "Value"
| project TimeGenerated, ColumnA, ColumnB
| extend AccountCustomEntity = ColumnA
| summarize Count = count() by ColumnB
| sort by Count desc
| top 10 by Count
| render barchart
```

| Clause | Quick Meaning |
| --- | --- |
| `where TimeGenerated > ago(24h)` | Limit results to the last 24 hours |
| `project` | Keep only the listed columns |
| `extend` | Add a new computed or mapped column |
| `summarize ... by` | Aggregate and group rows |
| `sort by ... desc` | Order results, largest first |
| `top N by` | Return the N highest ranked rows |
| `render` | Draw the results as a chart type |

### Key Terminology Glossary

| Term | Definition |
| --- | --- |
| Log Analytics Workspace | Central data store for Sentinel logs and telemetry |
| KQL | Kusto Query Language, the read only query language used across Sentinel and Azure Monitor |
| Entity | A mapped field (account, IP, host, etc.) that Sentinel uses to correlate activity across an investigation |
| Workbook | Visualization dashboard built on live KQL queries |
| Template | A prebuilt, Microsoft supplied workbook or query |
| Advanced Editor | JSON level editor for a workbook |
| Parameter | An interactive input that changes workbook query results without editing KQL |
| Analytics Rule | Detection logic that converts query results into alerts |
| Alert | A single triggered detection, typically the seed of an analytics rule or an incident |
| Playbook | Automated, Logic Apps based response workflow |

> **Day before the exam:** Focus on three memory anchors: (1) the **Workspace is the database**, (2) a **Workbook never stores data, it only runs KQL**, and (3) the chain **Query → Alert → Analytics Rule → Incident**, with Playbooks handling automation and Workbooks handling visualization as two separate, non overlapping concepts.
