## 1. Foundations: Behavioral Analytics and UEBA

### 1.1 What Is Behavioral Analytics

Behavioral Analytics is a detection technique that identifies threats by comparing current behavior with expected or normal behavior.

Traditional detection asks: **"Did this event match a detection rule?"**
Behavioral Analytics asks: **"Is this behavior unusual for this user, device, or entity?"**

This makes Behavioral Analytics effective for detecting:

* Insider threats
* Compromised accounts
* Advanced Persistent Threats (APTs)
* Zero day attacks
* Targeted attacks

> These attacks often use legitimate credentials and normal tools, so signature based detection alone will not catch them. Behavioral Analytics looks for abnormal behavior instead of known attack patterns.

### 1.2 Why Behavioral Analytics Matters

Modern attackers often avoid malware and instead abuse legitimate accounts. Example scenario: an attacker steals an employee's credentials and logs in successfully with the correct username and password.

From a traditional logging perspective, nothing looks wrong:

* Login succeeded.
* Password is correct.
* MFA may even be completed.

Behavioral Analytics instead asks:

* Does this user normally log in from this country?
* Does this user normally access these servers?
* Does this user usually download this amount of data?
* Does this activity match the user's historical behavior?

Instead of focusing only on **what happened**, UEBA focuses on **whether the behavior is normal**.

### 1.3 UEBA: User and Entity Behavior Analytics

UEBA is the Microsoft Sentinel capability that builds behavioral profiles for users and entities, then continuously analyzes activity to detect anomalies.

Its goal is to reduce analyst workload by automatically highlighting activity most likely to represent a compromised account or malicious behavior. It also helps identify sensitive assets, peer groups, and the potential impact, or **blast radius**, of a compromise.

#### What Is an Entity

An **Entity** is any object whose behavior can be analyzed. Common entity types:

* Users
* Hosts
* IP addresses
* Applications
* Devices

Microsoft Sentinel builds behavioral profiles for all of these entity types, not just users.

#### How UEBA Works

UEBA continuously collects security data, builds behavioral baselines, compares new activity against those baselines, and identifies anomalies.

```text
Security Logs
      │
      ▼
Build Baseline
      │
      ▼
Learn Normal Behavior
      │
      ▼
Compare New Activity
      │
      ▼
Detect Anomalies
      │
      ▼
Prioritize Investigation
```

### 1.4 Baseline Behavior

A **Baseline** is Microsoft's understanding of what "normal" looks like for an entity, learned automatically over time.

Example baseline for a user, who normally:

* Logs in between 8:00 AM and 5:00 PM.
* Uses a Windows laptop.
* Connects from Bangladesh.
* Accesses Finance applications.
* Downloads approximately 20 MB of data each day.

### 1.5 UEBA Architecture

Microsoft Sentinel collects logs from connected data sources, synchronizes identity information, builds behavioral datasets, and applies machine learning to identify anomalies.

```text
Data Sources
      │
      ▼
Microsoft Sentinel
      │
      ▼
UEBA Engine
      │
      ├── Behavioral Analytics
      ├── User Peer Analytics
      └── Identity Information
             │
             ▼
      Machine Learning
             │
             ▼
      Detected Anomalies
```

> Note that Machine Learning runs **after** Microsoft Sentinel has already collected and organized behavioral information, not before.

### 1.6 Security Driven Analytics (the "Outside In" Model)

Microsoft Sentinel's UEBA design is based on a model adapted from Gartner, using three reference frames:

| Frame | What It Means |
|---|---|
| **Use Cases** | Sentinel prioritizes attack vectors and scenarios based on security research aligned to the MITRE ATT&CK framework of tactics, techniques, and subtechniques. Entities are identified as victims, perpetrators, or pivot points in the kill chain. |
| **Data Sources** | Sentinel primarily supports Azure data sources, while also selecting third party data sources that match relevant threat scenarios. |
| **Analytics** | Sentinel uses machine learning to identify anomalous activity and present the evidence clearly through contextual enrichments. |

### 1.7 Peer Comparison

A unique UEBA capability is comparing a user with **similar users (peers)** rather than the entire organization.

Example: Alice works in Finance. Instead of comparing Alice to every employee, Sentinel compares her only to other Finance employees. If Alice starts performing activity that no other Finance employee performs, that behavior becomes more suspicious. Comparing within a relevant peer group significantly improves anomaly detection accuracy.

### SC-200 Exam Tips: Foundations

* **Behavioral Analytics** uses **UEBA** to detect abnormal behavior instead of relying only on static detection rules.
* UEBA builds **behavioral baselines** automatically over time; a baseline represents normal behavior for a user or entity.
* Entities analyzed by UEBA include: Users, Hosts, IP addresses, Applications, and other objects.
* Memorize the general analytics pipeline: **Ingestion → Filter → Enrich → Profile → Correlate → Trigger.**
* UEBA compares behavior against: historical behavior, peer groups, organization wide behavior, geographic locations, devices, and time patterns.
* **Investigation Priority Score** ranges from **0 to 10**. A high score means **higher priority for investigation**, not automatic confirmation of compromise.
* Peer comparison narrows the comparison group (for example, Finance employees only), which improves detection accuracy over comparing against the whole organization.

## 2. Exploring Entities

### 2.1 Entity Resolution

Entity Resolution is the process of determining whether different identifiers actually represent the same object.

```text
john@contoso.com
      │
CONTOSO\john
      │
Microsoft Entra Object ID
      │
      ▼
Single User Entity
```

This simplifies investigations: analysts see one unified identity instead of several fragmented identities scattered across log sources.

### 2.2 Entity Pages

An **Entity Page** is a dedicated investigation page for an entity, think of it as a profile page. It shows more than the entity name; it shows a timeline and behavioral insights. Entity Pages are currently available for **users and hosts**.

The Entity Page layout:

| Panel | Content |
|---|---|
| Left Panel | Identity information |
| Center Panel | Timeline |
| Right Panel | Behavioral Insights |

The Timeline displays: Alerts, Bookmarks, and Activities.

Entity Pages can be opened from:

* Incident Management
* Investigation Graph
* Bookmarks
* Entity Search (under Entity Behavior Analytics)

Entity Search lets analysts investigate a user or host even **without an active incident**.

### SC-200 Exam Tips: Exploring Entities

* Entities provide investigation context for alerts and incidents.
* Microsoft Sentinel attempts to **merge different identifiers into a single entity**; poor or incomplete log data can prevent successful resolution.
* Synchronizing identities with **Microsoft Entra ID** improves user entity resolution.
* Entity Pages currently exist for **users and hosts only**.
* Ensure **Entity Mapping** is configured correctly in custom Analytics Rules so alerts are properly associated with entities. This is a very common exam scenario question.
* **Entity Insights** are prebuilt investigation queries created by Microsoft security researchers, drawing on data from Syslog, SecurityEvent, Audit Logs, Sign in Logs, Office Activity, and BehaviorAnalytics (UEBA).
* Entity Behavior centralizes information from multiple Microsoft security features, reducing the need to switch between portals during an investigation.

## 3. Entity Behavior Information

Entity Behavior Information is the collection of security data, historical activity, alerts, and behavioral insights associated with a specific entity. Instead of separately investigating raw logs, multiple alerts, and separate incidents, Microsoft Sentinel consolidates everything about an entity into one place.

For a user account, the Entity Page can show:

* User identity
* Login history
* Security alerts
* Timeline of activities
* Behavioral anomalies
* Related incidents

### SC-200 Exam Tips: Entity Behavior Information

* The **Entity Behavior Page** is the primary investigation page for an entity, showing identity information, timeline, alerts, activities, and behavioral insights.
* The **Investigation Graph** focuses on **relationships between entities**.
* The **Insights** option inside the Investigation Graph displays behavioral information from the Entity Behavior dataset.

## 4. Anomaly Detection Analytical Rule Templates

### 4.1 What Is an Anomaly Detection Analytical Rule

An Anomaly Detection Analytical Rule is a special type of **Analytics Rule** that uses machine learning instead of static conditions.

Traditional Analytics Rule logic:

```text
IF
User logs in from blocked country
THEN
Create Alert
```

Anomaly Rule logic:

```text
Learn Normal Behavior
      │
      ▼
Compare Current Activity
      │
      ▼
Is Behavior Unusual?
      │
     Yes
      │
      ▼
Generate Anomaly
```

Instead of searching for a known attack pattern, the ML model identifies **behavior that is statistically unusual**.

### 4.2 Why Anomaly Detection Rules Are Important

Attackers constantly change technique to avoid detection. Even when they evade traditional signatures, they usually leave behind unusual behavior such as:

* Logging in at unusual hours
* Accessing systems never accessed before
* Downloading abnormal amounts of data
* Using administrative tools unexpectedly

Machine learning is what catches these unusual behaviors.

### 4.3 Built In Templates vs Custom Templates

Building machine learning models from scratch is difficult, so Microsoft provides pretrained, tested, production ready **Anomaly Detection Templates**, built using thousands of data sources and millions of events.

| Built In Templates | Custom Templates |
|---|---|
| Created by Microsoft | Built by the organization |
| Ready to use | Require additional tuning |
| Already trained | Used for organization specific scenarios |
| Recommended for most organizations | Recommended once built in coverage is insufficient |

> Exam tip: For SC-200, remember Microsoft recommends **starting with the built in templates** before building custom ones.

### 4.4 Understanding Anomaly Rule Properties

When you open an anomaly rule template, Sentinel shows several properties you must understand for the exam.

| Property | What It Tells You |
|---|---|
| **Description** | What the anomaly detects, how it works, and what data it requires. Always review before enabling a rule. |
| **Data Sources** | Which logs are required, for example Microsoft Entra Sign in Logs, Azure Activity Logs, or Windows Security Events. If required logs are missing, the rule cannot work properly. |
| **Tactics and Techniques** | Each anomaly is mapped to the **MITRE ATT&CK Framework** (for example Initial Access, Persistence, Credential Access, Discovery), showing where it fits in the attack lifecycle. |
| **Parameters** | Configurable settings that control the anomaly model, such as time windows, entity types, and behavioral limits. |
| **Threshold** | How unusual behavior must be before Sentinel raises an anomaly. Covered in detail below. |
| **Rule Frequency** | How often the anomaly detection algorithm runs, for example hourly, daily, or on a custom schedule. More frequent runs mean faster detection but higher processing cost. |
| **Anomaly Version** | Which version of the ML template the rule uses. New Microsoft versions do **not** automatically upgrade existing rules; you must recreate the rule using the updated template. |
| **Template Last Updated** | When Microsoft last modified the template, helping you know if newer improvements are available. |

### 4.5 Threshold: Tuning Sensitivity

The Threshold determines how unusual behavior must be before Sentinel creates an anomaly.

```text
Lower Threshold
      │
      ▼
More Sensitive
      │
      ▼
More Anomalies
      │
      ▼
More False Positives
```

```text
Higher Threshold
      │
      ▼
Less Sensitive
      │
      ▼
Fewer Anomalies
      │
      ▼
May Miss Attacks
```

> Finding the right threshold, balancing noise against missed detections, is one of the most important tuning tasks and a frequent SC-200 exam scenario.

### 4.6 Activating an Anomaly Rule

```text
Analytics
      │
      ▼
Rule Templates
      │
      ▼
Filter: Rule Type = Anomaly
      │
      ▼
Choose Template
      │
      ▼
Create Rule
      │
      ▼
Validation Passed
      │
      ▼
Select Create
      │
      ▼
Rule Becomes Active
```

Key rules:

* Choose a template that is **not already marked "IN USE."**
* The rule creation wizard has three steps: **General**, **Configuration**, and **Review and create**.
* After validation succeeds, selecting **Create** activates the rule.
* Only **one active rule** can exist per anomaly template. Once activated, the template is marked **IN USE**.

### 4.7 Training Period

Anomaly rules require a **training period** because the machine learning model must first learn normal behavior.

| Phase | What Happens |
|---|---|
| During training | No anomalies are generated. |
| After training completes | Detection begins. |

> This training period concept is a favorite SC-200 exam topic: do not expect anomalies immediately after activating a rule.

### 4.8 Where Detected Anomalies Are Stored

After activation and training, Microsoft Sentinel stores detected anomalies in the **Anomalies** table inside the **Logs** section of the Sentinel workspace.

### 4.9 Assessing Anomaly Quality

Enabling a rule is only the beginning. SOC analysts must review whether generated anomalies are actually useful.

```text
Active Rule
      │
      ▼
Logs
      │
      ▼
Anomalies Table
      │
      ▼
Review Results
      │
      ▼
Assess Quality
```

Because active anomaly rules **cannot be edited directly**, the tuning workflow is:

1. Duplicate the rule.
2. Customize the duplicate.
3. Test it in **Flighting** mode.
4. Promote the tuned rule to **Production**.

Only **one production version** of an anomaly rule can exist at a time.

### SC-200 Exam Tips: Anomaly Detection Rules

* Anomaly Detection Rules use **Machine Learning**, not static conditions.
* An anomaly is **unusual behavior**, not proof of malicious activity.
* Microsoft provides built in anomaly templates that are production ready and customizable through duplication.
* Primary uses of anomalies: improve detections, support investigations, enable proactive threat hunting.
* Required logs must be ingested before an anomaly rule can function correctly.
* Rule properties to memorize: Description, Data Sources, MITRE ATT&CK Tactics and Techniques, Parameters, Threshold, Rule Frequency, Anomaly Version, Template Last Updated.
* **Lower threshold = more anomalies and more false positives. Higher threshold = fewer anomalies but possible missed attacks.**
* Anomaly rules require a **training period** before producing results.
* Generated anomalies are stored in the **Anomalies** table; review the **AnomalyReasons** field to understand why an anomaly fired.
* **You cannot directly edit an active anomaly rule.** Duplicate it, customize it, test in **Flighting**, then promote to **Production**.
* Only **one production version** of an anomaly rule can exist at a time; only **one active rule per template** overall.

## 5. Added Context: Other Sentinel Analytics Rule Types

*This section is not from the source module. It is added because the exam expects you to place Anomaly rules correctly among the other Microsoft Sentinel analytics rule types.*

| Rule Type | Logic | Customizable | Typical Use |
|---|---|---|---|
| **Scheduled** | KQL query you write or edit, runs on a timer | Fully customizable | Known attack patterns, custom detections |
| **NRT (Near Real Time)** | Same idea as Scheduled, but runs roughly every minute | Mostly customizable, some scheduled features unavailable | Time critical detections needing very low latency |
| **Anomaly** | Machine learning model observes behavior against a learned baseline | Only via duplicate, then tune Threshold and Parameters | Unknown or unusual behavior without a signature |
| **Fusion** | Machine learning correlation engine combining alerts across products using kill chain and entity mapping data | Not customizable (only one instance exists) | Multistage attack detection across signals |
| **Microsoft Security / ML Behavior Analytics** | Built in, Microsoft managed detection logic | Not customizable | Specific known scenarios such as unusual SSH or RDP sign ins |
| **Threat Intelligence (TI Map)** | Matches indicators of compromise against ingested threat intelligence feeds | Limited configuration | Known bad indicators (IPs, domains, hashes) |

> Frequently confused on the exam: an **Anomaly** rule produces rows in the **Anomalies** table, not an alert by default. A **Fusion** rule produces an **incident** directly by correlating other alerts. Know the difference.

## 6. Added Context: Practical KQL for UEBA Tables

*Also added for exam relevance. Field names below match Microsoft's published UEBA reference schema.*

Key UEBA related tables:

* **BehaviorAnalytics**: the main table holding UEBA anomaly detections, one row per anomalous activity.
* **IdentityInfo**: identity data synchronized from Microsoft Entra ID (and on premises Active Directory via Microsoft Defender for Identity).
* **UserPeerAnalytics**: peer group information used for peer comparison.

Example query pattern to review high priority behavioral anomalies for a user:

```kql
BehaviorAnalytics
| where TimeGenerated > ago(30d)
| where InvestigationPriority > 0
| project TimeGenerated, UserName, ActivityType, ActionType,
          SourceIPAddress, InvestigationPriority, UsersInsights, DevicesInsights
| order by InvestigationPriority desc
```

> Exam tip: the `UsersInsights` and `DevicesInsights` fields are **dynamic** fields enriched from Microsoft Entra ID and threat intelligence. The `ActivityInsights` field is built from Sentinel's own behavioral profiles. You are not expected to memorize every field, but you should recognize that `BehaviorAnalytics` and `InvestigationPriority` are the terms the exam associates with UEBA output.

### Frequently Confused Concepts

* **Anomaly vs Alert**: An anomaly lands in the Anomalies table; it does not automatically become an alert or incident on its own.
* **Baseline vs Threshold**: Baseline defines what normal looks like. Threshold defines how far from normal triggers a flag.
* **Entity Resolution vs Entity Mapping**: Entity Resolution is Sentinel automatically merging identifiers into one entity. Entity Mapping is a setting **you configure** in a custom Analytics Rule so query results map correctly to entity types.
* **Anomaly rule vs Fusion rule**: Anomaly rules flag unusual single entity behavior. Fusion rules correlate multiple alerts across products into one incident.
* **Production vs Flighting**: Production is the live rule version. Flighting is a parallel test version you tune before promoting.
* **Built In vs Custom templates**: Built in templates are Microsoft trained and ready to use. Custom templates require your own tuning for organization specific scenarios.

### Must Remember Numbers and Rules

* Only **one production version** of an anomaly rule at a time.
* Entity Pages exist for **users and hosts** only (per this module).
* Anomaly rule wizard steps: **General → Configuration → Review and create**.
* You **cannot edit** an active anomaly rule directly; duplicate, tune, flight, then promote.
