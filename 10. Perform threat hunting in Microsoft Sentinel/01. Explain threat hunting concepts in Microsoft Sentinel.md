## 1. Threat Hunting Fundamentals

### 1.1 What Is Threat Hunting?

Threat hunting is the **proactive search for threats or malicious activity that existing security controls have not yet detected**. It assumes an attacker may already be inside the environment without having triggered any alert.

> **Key exam point:** Threat hunting looks for **unknown threats**. Investigating an alert that a tool already raised is not threat hunting, it is alert triage or incident response.

### 1.2 Threat Hunting Using Known Indicators (IOC Search)

Sometimes a team receives a new Indicator of Compromise (IOC), such as:

* A malicious IP address
* A malicious domain
* A file hash
* A URL
* A malicious email address

The analyst then searches historical logs to see whether that IOC ever appeared in the environment.

Example: Threat intelligence reports IP address `185.10.55.23`. The analyst checks firewall, proxy, and endpoint logs for any device that communicated with it.

> This is technically an **IOC search**, not true hunting, because the analyst already knows exactly what to look for. True hunting starts from a hypothesis about unknown activity.

### 1.3 KQL: The Language of Hunting

Threat hunting depends heavily on **Kusto Query Language (KQL)**. Almost every hunting activity in Microsoft security products involves writing or running a KQL query, for example to:

* Search endpoint activity
* Investigate authentication logs
* Find process execution
* Detect suspicious PowerShell commands
* Identify failed logons
* Find uncommon network connections

Example query:

```kql
DeviceProcessEvents
| where ProcessCommandLine contains "powershell"
```

### 1.4 Microsoft Defender XDR and Advanced Hunting

Microsoft Defender XDR focuses on endpoint, identity, email, cloud app, and Office security. Its **Advanced Hunting** feature lets analysts query telemetry across connected workloads.

| Workload | Source Product |
|---|---|
| Endpoint | Defender for Endpoint |
| Identity | Defender for Identity |
| Email | Defender for Office 365 |
| Cloud Apps | Defender for Cloud Apps |
| Directory (selected telemetry) | Microsoft Entra ID |

Typical Advanced Hunting tables:

* `DeviceProcessEvents`
* `DeviceNetworkEvents`
* `DeviceFileEvents`
* `DeviceLogonEvents`
* `EmailEvents`
* `IdentityLogonEvents`

### 1.5 Proactive Hunting

Proactive hunting means searching for attacks **before any alert exists**, to catch attackers as early as possible and reduce the impact of a compromise. Rather than starting from a known indicator, the analyst starts from a **hypothesis**.

### 1.6 The Threat Hunting Process

```text
1. Develop Hypothesis
       │
       ▼
2. Data Review
       │
       ▼
3. Plan Hunt
       │
       ▼
4. Execute Hunt
       │
       ▼
5. Respond
       │
       ▼
6. Monitor
       │
       ▼
7. Improve
```

| Step | What Happens |
|---|---|
| 1. Develop Hypothesis | Define the suspicious behavior to investigate, e.g. "Attackers may be abusing scheduled tasks for persistence." |
| 2. Data Review | Confirm the telemetry needed to test the hypothesis exists (endpoint, authentication, firewall, network, cloud, email logs). |
| 3. Plan Hunt | Decide on data sources, KQL queries, time range, scope, and expected evidence. |
| 4. Execute Hunt | Run the queries, analyze results, pivot into related events, gather evidence. |
| 5. Respond | If activity is confirmed malicious: raise or update an incident, contain systems, isolate endpoints, disable accounts, escalate. |
| 6. Monitor | Keep watching to confirm mitigations worked and to catch recurring activity. |
| 7. Improve | Turn findings into new analytics rules, updated hunting queries, refined playbooks, and better monitoring coverage. |

### 1.7 SC-200 Exam Tips

> * Threat hunting is **proactive**; incident response is **reactive**.
> * An IOC search (hunting from a known indicator) is different from hypothesis based hunting (searching for unknown threats).
> * KQL is the primary language for hunting in both Microsoft Sentinel and Microsoft Defender XDR.
> * Microsoft Sentinel is a SIEM and SOAR platform that supports hunting across the whole organization and many data sources.
> * Microsoft Defender XDR provides Advanced Hunting across Microsoft security telemetry specifically.
> * A hunting hypothesis is usually based on attacker techniques (for example MITRE ATT&CK), not only on a single indicator.
> * The hunting lifecycle is continuous: it includes documentation and feeding results back into future detections.

### 1.8 SC-200 Quick Memorization

| Term | Meaning |
|---|---|
| Threat Hunting | Proactive search for **unknown** threats |
| Incident Response | Reactive investigation after an alert |
| IOC Hunt | Search using a known indicator |
| Hypothesis Hunt | Search based on suspected attacker behavior |
| KQL | Primary hunting language |
| Microsoft Sentinel | SIEM + SOAR + hunting across the organization |
| Microsoft Defender XDR | XDR + Advanced Hunting |

## 2. Building a Threat Hunting Hypothesis

### 2.1 What Is a Threat Hunting Hypothesis?

A **threat hunting hypothesis** is an educated guess about what malicious activity might exist in the environment and how to go looking for it. It sets the focus of the hunt and guides what data to collect, what queries to run, and what evidence to look for.

Example hypotheses:

* "An attacker may be abusing PowerShell to download malware."
* "A compromised account may be using Remote Desktop outside business hours."
* "Attackers may be using `cmd.exe` for automated execution."

> **Exam point:** A hypothesis must be specific enough that it can either be confirmed or disproved through investigation, not just a vague hunch.

### 2.2 What Makes a Good Hypothesis?

**Achievable**

The required data must actually exist and logging must be enabled. Do not start a hunt if:

* The needed data does not exist
* Logging is not enabled
* The SOC lacks enough knowledge of the threat
* There is no realistic chance of finding evidence

**Narrow in Scope**

A hypothesis should target a specific behavior, not a broad idea, so results are easy to interpret.

**Time Bound**

Every hunt should state the time period under investigation. This avoids repeated analysis of the same data and improves documentation. Good documentation records the start time, end time, data sources searched, and time zone if relevant.

**Useful and Efficient**

Hunts are most valuable when they target detection gaps, areas where existing rules are weak or attacks may have been missed, for example Living off the Land techniques, credential dumping, scheduled task persistence, or PowerShell abuse.

**Aligned to the Organization's Threat Model**

A threat model considers industry, business type, technologies used, geographic footprint, common attacker groups, and known attack techniques.

| Organization Type | Likely Threats |
|---|---|
| Financial | Banking malware, credential theft, Business Email Compromise (BEC), ransomware |
| Healthcare | Patient data theft, ransomware, insider threats |
| Cloud Service Provider | Cloud credential theft, privilege escalation, API abuse |

### 2.3 Example Comparison: Poor Hypothesis vs Good Hypothesis

| Quality Being Tested | Poor Hypothesis | Better Hypothesis |
|---|---|---|
| Achievability | "Search for firmware level malware." (telemetry usually unavailable) | "Search Windows Security Event logs for failed administrator logons during the last 24 hours." |
| Narrow scope | "I'm going to hunt for strange logons." (undefined user, system, location, time) | "Investigate administrator accounts authenticating from countries where the organization has no offices during the last seven days." |

Example KQL for the narrow, time bound hypothesis above:

```kql
SigninLogs
| where TimeGenerated > ago(7d)
| where UserPrincipalName contains "admin"
| where Country != "Bangladesh"
```

### 2.4 SC-200 Exam Tips

> * Every hunt should start with a **well defined hypothesis**.
> * A good hypothesis is: achievable, narrow in scope, time bound, useful and efficient, and relevant to the organization's threat model.
> * Confirm required telemetry is actually available before starting a hunt.
> * Focus hunting on detection gaps, not on areas already well covered.
> * Start simple, then increase complexity as the hunt matures.
> * A successful hunt often becomes a new analytics rule in Microsoft Sentinel, this is how hunting feeds back into automated detection.

## 3. MITRE ATT&CK in Microsoft Sentinel

### 3.1 Why MITRE ATT&CK Matters for Microsoft Sentinel

Microsoft Sentinel uses the MITRE ATT&CK framework to show analysts **which attacker techniques are already detected and which still lack detection coverage**, instead of only listing raw alerts.

```text
Data Connectors
      │
      ▼
Log Analytics Workspace
      │
      ▼
Microsoft Sentinel
      │
      ▼
Analytics Rules
      │
      ▼
MITRE ATT&CK Mapping
      │
      ▼
Alerts and Incidents
```

This lets analysts answer questions such as: which techniques can we detect, which techniques have no detections, and which tactics need more monitoring.

### 3.2 The MITRE Coverage Matrix

**MITRE coverage** shows how well the organization's existing detections cover the ATT&CK framework. It is based on active detections in the workspace, including:

* Scheduled analytics rules
* Near real time (NRT) rules
* Anomaly rules

Two useful matrix features:

| Feature | Purpose |
|---|---|
| Legend | Shows coverage level per technique (high coverage, partial coverage, no coverage) so gaps can be prioritized. |
| Search | Locates a specific technique by name or by technique ID, for example `T1059`. |

### 3.3 Viewing MITRE by Threat Scenarios

Instead of showing the entire matrix, Sentinel can filter it to only the techniques associated with a specific attack scenario, such as Business Email Compromise (BEC), financial fraud, ransomware, credential theft, insider threat, or cloud attacks.

```text
Scenario: Business Email Compromise
      │
      ▼
Matrix filters to BEC related techniques only
      │
      ▼
Analyst reviews missing detections
      │
      ▼
New Analytics Rules created
```

Large organizations may have hundreds of detections, so threat scenarios help analysts focus investigations, spot gaps for a specific threat, and prioritize improvements.

### 3.4 MITRE ATT&CK in Analytics Rules

Analytics rules continuously analyze log data to find suspicious activity, and each rule can be mapped to one or more MITRE tactics and techniques.

```text
KQL Analytics Rule
      │
      ▼
Assign MITRE Techniques
      │
      ▼
Rule Executes
      │
      ▼
Alert Generated
      │
      ▼
Incident Created
      │
      ▼
MITRE Coverage Updated
```

Example: a KQL rule detects suspicious PowerShell execution and is mapped to tactic **Execution**, technique **T1059, Command and Scripting Interpreter**. Every alert the rule raises is then linked to that mapped technique.

Mapping rules to MITRE improves detection organization, enables coverage reporting, simplifies investigations, helps find detection gaps, and aligns detections with real attacker behavior.

### 3.5 MITRE ATT&CK in Incidents

Because analytics rules carry MITRE mappings, the incidents they create inherit those mappings automatically, so analysts immediately see which tactics and techniques are involved without working it out manually.

```text
Incident
    │
    ▼
Execution
    │
    ▼
PowerShell
    │
    ▼
Credential Access
```

This helps analysts understand the attack lifecycle, prioritize investigations, and spot additional techniques that may also be in play.

### 3.6 MITRE ATT&CK in Threat Hunting

Hunters can assign MITRE tactics and techniques to hunting queries. Queries can be filtered by tactic, and **bookmarks** can inherit or include technique mappings to preserve investigation context.

```text
Threat Intelligence
      │
      ▼
Identify MITRE Technique
      │
      ▼
Develop Hunting Hypothesis
      │
      ▼
Write KQL Query
      │
      ▼
Analyze Results
      │
      ▼
Create Bookmark
      │
      ▼
Improve Detection
```

Using MITRE this way organizes hunts around attacker **behavior** rather than isolated indicators, which makes hunts more structured and repeatable.

### 3.7 Tactic, Technique, Procedure (TTP): Quick Definitions

| Term | Definition |
|---|---|
| Tactic | **Why** the attacker performs an action (the goal). |
| Technique | **How** the attacker achieves that goal. |
| Procedure | The **specific implementation** a particular threat actor uses. |

### 3.8 SC-200 Exam Tips

> * MITRE ATT&CK organizes attacker behavior into Tactics, Techniques, and Procedures (TTPs).
> * Microsoft Sentinel uses MITRE mappings in four places: Analytics Rules, Incidents, Hunting Queries, and the Coverage Matrix.
> * The Coverage Matrix's job is to reveal **detection gaps**.
> * Simulated coverage in the matrix shows detections that are available but not yet enabled, not detections already firing.
> * Threat scenarios filter the matrix to just the techniques relevant to one type of attack.
> * Bookmarks and hunting queries can carry MITRE mappings forward to keep investigation context.

### 3.9 SC-200 Quick Memorization

| Term | Meaning |
|---|---|
| MITRE ATT&CK | Real world attacker behavior framework |
| Tactic | Why |
| Technique | How |
| Procedure | Actual implementation used |

## 4. Additional Context for the Exam

The points below are not repeated verbatim from the source material. They are added because they are standard SC-200 exam content that connects directly to the hunting and MITRE topics above.

### 4.1 Microsoft Sentinel's Hunting Workspace, at a Glance

Microsoft Sentinel groups hunting tools under one workspace:

| Feature | What It Does |
|---|---|
| Hunting queries | Prebuilt and custom KQL queries organized by MITRE tactic, used to run a hunt manually. |
| Livestream | Runs a query on a short interval so new matching events surface in near real time while a hunt is active. |
| Bookmarks | Save interesting events found during a hunt, with notes and optional MITRE mapping, so they can be revisited or escalated to an incident. |
| Notebooks | Jupyter based notebooks for deeper, code driven investigation and automation beyond what KQL alone can do. |

> **Exam point:** If a question asks how to preserve evidence found mid hunt for later escalation, the answer is usually **Bookmarks**, not the raw query results.

### 4.2 Microsoft Sentinel Hunting vs Defender XDR Advanced Hunting

| Aspect | Microsoft Sentinel Hunting | Defender XDR Advanced Hunting |
|---|---|---|
| Scope | Any data source connected to the Log Analytics workspace (firewalls, cloud, on premises, third party) | Microsoft 365 Defender workloads: endpoint, identity, email, cloud apps |
| Query language | KQL | KQL (Advanced Hunting schema) |
| Typical use | Enterprise wide, cross source hunting and SIEM correlation | Deep, native investigation within Microsoft security products |
| Output | Bookmarks, incidents, new analytics rules | Custom detection rules, incidents |

### 4.3 MITRE ATT&CK Enterprise Tactics (Reference Order)

Knowing the tactic order helps when a question describes attacker behavior and asks which tactic it maps to:

Reconnaissance, Resource Development, Initial Access, Execution, Persistence, Privilege Escalation, Defense Evasion, Credential Access, Discovery, Lateral Movement, Collection, Command and Control, Exfiltration, Impact.

> **Exam point:** "Suspicious PowerShell execution" maps to **Execution**, technique T1059. "An attacker stealing a password hash" maps to **Credential Access**. "An attacker moving from one workstation to a server" maps to **Lateral Movement**.

### 5.2 Frequently Confused Concepts

| Often Confused | Clarification |
|---|---|
| Threat hunting vs incident response | Hunting is proactive and looks for the unknown; incident response is reactive and starts from a known alert. |
| IOC search vs hypothesis hunt | An IOC search starts from a known indicator; a hypothesis hunt starts from an idea about unknown activity. |
| Sentinel hunting vs Defender XDR Advanced Hunting | Sentinel spans every connected data source; Advanced Hunting is scoped to Microsoft 365 Defender workloads. |
| Tactic vs Technique vs Procedure | Tactic is the why, Technique is the how, Procedure is the specific real world implementation. |
| Analytics rule coverage vs simulated coverage | Analytics rule coverage means the detection is active; simulated coverage means it is available but not yet enabled. |

### 5.3 Important KQL Syntax to Remember

```kql
// Filter by time window
| where TimeGenerated > ago(7d)

// Filter text fields
| where ProcessCommandLine contains "powershell"

// Exclude a value
| where Country != "Bangladesh"

// Common hunting tables
DeviceProcessEvents, DeviceNetworkEvents, DeviceFileEvents,
DeviceLogonEvents, EmailEvents, IdentityLogonEvents, SigninLogs
```
