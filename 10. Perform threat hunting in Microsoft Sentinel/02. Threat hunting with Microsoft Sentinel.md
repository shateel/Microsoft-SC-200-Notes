## Threat Hunting Overview

Threat hunting in Microsoft Sentinel is a **proactive**, analyst driven activity. Instead of waiting for an alert to fire, the analyst actively searches collected security data for indicators of compromise (IOCs), attacker techniques, and unusual behavior.

```text
Predefined or Custom KQL Query
        │
        ▼
Run Interactively Against Data
        │
        ▼
Review Results
        │
        ▼
Bookmark Key Findings
        │
        ▼
Create or Update an Incident
```

> **Exam Tip:** Threat hunting is fundamentally **manual and investigator led**. Whenever a question describes an analyst actively searching data without an alert already existing, think **Hunting**, not **Analytics Rules**.

## Hunting with Predefined Queries

Microsoft Sentinel ships with a large set of **predefined hunting queries** so SOC analysts do not need to write KQL from scratch for common scenarios.

Key facts:

* Predefined queries are written in **Kusto Query Language (KQL)**.
* They do **not** continuously monitor the environment and do **not** automatically raise alerts. They must be run interactively.
* They are found on the **Hunting** page in Microsoft Sentinel.
* Queries can be searched, filtered, and organized to quickly find the right investigation.

### Common Filters on the Hunting Page

| Filter | Purpose |
|---|---|
| Query name | Locate a specific query |
| Provider | Filter by the content source (Microsoft or partner) |
| Data source | Match queries to connected data tables |
| MITRE tactic | Filter by attacker stage |
| Results | Show queries that already returned results |
| Category | Group queries by scenario type |

### SC-200 Exam Tips

* **Hunting queries are manual; Analytics Rules are automatic.** This is one of the most tested distinctions in the exam.
* All hunting activity in Sentinel uses **KQL**.
* Predefined queries can be filtered, modified, saved, favorited, and run interactively.

## Hunting by MITRE ATT&CK Tactics

Microsoft Sentinel maps every hunting query to one or more **MITRE ATT&CK tactics**. This lets an analyst search by attacker stage rather than scanning the entire query catalog.

Instead of asking "which query should I run," the analyst asks "what stage of the attack am I investigating."

```text
Credential Theft Investigation
        │
        ▼
Credential Access Tactic (MITRE ATT&CK)
        │
        ▼
Relevant Hunting Queries
        │
        ▼
Run Investigation
```

> **Exam Tip:** Expect scenario questions naming a tactic (for example Credential Access, Lateral Movement, Exfiltration) and asking how an analyst would locate the right queries. The answer is filtering the Hunting page by **MITRE tactic**.

## Custom Hunting Queries

When predefined queries do not cover a scenario, analysts write **custom hunting queries** in KQL. These can be modified, saved, and reused inside the Sentinel workspace.

Organizations create custom queries to tailor hunting to:

* Their own environment
* Internal policies
* Known attacker behavior specific to their industry
* Devices, users, applications, and logging that are unique to them

### A Well Formed Custom Query Should Include

| Element | Why It Matters |
|---|---|
| Name | Identifies the query for reuse |
| Description | Explains investigative purpose |
| KQL query | The actual detection logic |
| Entity mapping | Links results to users, hosts, IPs, and so on |
| MITRE tactics and techniques | Aligns the query with the ATT&CK framework |

> **Exam Tip:** If a question asks what a custom hunting query needs in order to be useful for later automation or incident creation, remember **entity mapping** and **MITRE tactic and technique** tagging. These are the details examiners like to test.

## Threat Hunting Bookmarks

A **bookmark** lets an analyst **save important findings** discovered during a hunt, including the query, its results, notes, tags, and investigative context, so the work is preserved and shareable.

Threat hunting frequently involves reviewing huge volumes of log data. Individual events may look harmless in isolation but become significant evidence once combined with other findings. Bookmarks capture that evidence so it is never lost between sessions.

> **Exam Tip:** A bookmark by itself does **not** mean malicious activity has been confirmed. It is evidence storage, not a verdict.

### What a Bookmark Preserves

* The KQL query that produced the result
* The query results themselves
* Investigation notes
* Analyst observations
* Tags
* Security context

### Where Bookmarks Live

* Accessible from the **Bookmarks** tab on the **Hunting** page
* Can be searched, filtered, reopened, and continued by another analyst
* Stored in the **HuntingBookmark** table inside the Log Analytics workspace, so bookmark data itself can be queried with KQL

## Bookmarks and Incidents

Bookmarks are the bridge between **threat hunting** and **incident response**. When a hunt confirms malicious activity, the analyst does not need to rebuild the investigation manually. The bookmarked evidence can be turned directly into an incident.

```text
Threat Hunt
     │
     ▼
Bookmark Created
     │
     ▼
Incident Action Selected
     │
     ├──▶ Create New Incident
     │
     └──▶ Add to Existing Incident
```

### Incident Actions Available From a Bookmark

| Action | When to Use |
|---|---|
| Create Incident | No incident currently exists and the hunt uncovered a new attack |
| Add to Existing Incident | The bookmark relates to an active incident and adds new evidence |
| Remove from Incident | The evidence turned out to be a false positive or was linked incorrectly |

### Bookmarks vs Incidents

> **Exam Tip:** This comparison is one of the most frequently tested concept pairs in the SC-200 hunting domain.

| Aspect | Bookmark | Incident |
|---|---|---|
| Purpose | Saves investigation findings | Represents a security investigation |
| Confirms an attack? | No | Represents a tracked, actionable case |
| Scope | Preserves individual pieces of evidence | Groups related alerts and evidence |
| Ownership | Not assigned to an analyst | Assigned to an analyst for handling |
| Tracks status? | No | Yes, tracks investigation status |
| Used during | Threat hunting | Incident response |

## Investigation Graph and Entity Details

Bookmarks can be explored using the **Investigation Graph**, the same visual tool used for incidents. It shows how entities such as users, devices, IP addresses, Azure resources, domains, URLs, and files relate to one another, instead of forcing the analyst to read isolated log rows one at a time.

```text
Bookmarked Evidence
        │
        ▼
Investigation Graph
        │
        ▼
Connected Entities
(Users, Devices, IPs, Azure Resources, Domains, URLs, Files)
        │
        ▼
Reveal Broader Attack Path
```

Each entity node carries contextual details that help the analyst pivot without starting a new search, including:

* Relationships with other entities
* Account activity
* Device information
* Network connections
* Data flow
* Related events in Log Analytics

> **Exam Tip:** Investigation Graph = **relationships**. Entity Details = **context on a single entity**. Questions often ask which feature to use to "see how entities connect" (Investigation Graph) versus "see more about one entity" (Entity Details).

## Real World SOC Scenario

A short walkthrough that mirrors how SC-200 scenario questions are usually written:

1. An analyst is hunting for signs of credential theft and notices unusual login attempts from foreign locations.
2. The analyst runs a KQL hunting query in Microsoft Sentinel.
3. Suspicious authentication events are identified.
4. Bookmarks are created for the most relevant results.
5. Notes are added explaining why the events are suspicious.
6. The bookmarks are tagged with **Credential Access** and **MITRE ATT&CK technique T1003**.
7. The Investigation Graph is used to review related accounts, devices, and IP addresses.
8. Malicious activity is confirmed, and a new incident is created directly from the bookmarked evidence.
9. The incident is assigned to the Incident Response team for containment.

> **Exam Takeaway:** Notice the full chain: **Query → Findings → Bookmark → Tag with MITRE technique → Investigation Graph → Incident → Assignment**. SC-200 loves testing whether you know the correct order of this workflow.

## Livestream: Observing Threats Over Time

**Livestream** runs a KQL query **continuously** against incoming data so an analyst can watch events as they happen, instead of searching historical logs after the fact.

Traditional hunting answers questions like "what happened yesterday" or "what happened in the last 24 hours." Livestream answers a different question: **"what is happening right now?"**

### How Livestream Works

```text
Incoming Security Logs
        │
        ▼
Log Analytics Workspace
        │
        ▼
Microsoft Sentinel
        │
        ▼
Livestream Query (Runs Continuously)
        │
        ▼
Matching Events
        │
        ▼
SOC Analyst Investigation
```

### Livestream Behavior

* Continuously evaluates newly arriving events rather than executing once
* Refreshes approximately **every 30 seconds**
* Can generate Azure portal notifications when a matching event occurs
* **Cannot use time parameters** in the query, since it always processes new incoming events rather than a fixed time range
* Sessions can be played, saved, deleted, or elevated to an alert
* A validated Livestream query can be promoted into an **Analytics Rule** for automated, ongoing detection

> **Exam Tip:** If a question mentions a query that "cannot include a time filter" and must show results "as they happen," the answer is **Livestream**. If the same validated query needs to run permanently and generate alerts automatically, the next step is converting it into an **Analytics Rule**.

### SC-200 Quick Memorization

* **Livestream** = live threat hunting against incoming data
* **Hunting Query** = investigation against historical data
* **Analytics Rule** = automated, ongoing detection that generates alerts
* **Livestream refresh** = approximately 30 seconds
* **No time parameters** allowed in a Livestream query
* **Elevate to Alert** = turn an observed Livestream event into an alert
* **Validated Livestream query → promote to Analytics Rule**

## KQL Syntax Refresher

The source module references KQL repeatedly without listing syntax, and the exam expects familiarity with the basics. This is general Kusto Query Language knowledge added for context, not specific to the source document.

| Operator | Purpose | Example Pattern |
|---|---|---|
| `where` | Filters rows | `SigninLogs \| where ResultType != 0` |
| `project` | Selects specific columns | `SigninLogs \| project UserPrincipalName, IPAddress` |
| `summarize` | Aggregates data | `SigninLogs \| summarize count() by UserPrincipalName` |
| `extend` | Adds a computed column | `SigninLogs \| extend RiskFlag = iff(RiskLevel == "high", true, false)` |
| `join` | Combines data from two tables | `Table1 \| join kind=inner Table2 on CommonColumn` |
| `ago()` | Relative time filter | `TimeGenerated > ago(24h)` |

> **Exam Tip:** `ago()` and other time filters are valid in ordinary hunting queries but are **not** valid in Livestream queries, since Livestream always evaluates newly arriving data rather than a fixed lookback window.

## SC-200 Last Minute Revision

A single page cheat sheet for the day before the exam.

### Core Concept Map

```text
Threat Hunting (Manual)
        │
        ▼
Findings Worth Saving
        │
        ▼
Bookmark
        │
        ▼
Investigation Graph (Entity Relationships)
        │
        ▼
Incident (Tracked, Assigned, Actioned)
        │
        ▼
Incident Response Team
```

### Fastest Way to Tell These Apart

| Term | One Line Definition |
|---|---|
| Hunting Query | A manual KQL search across historical data; does not alert automatically |
| Analytics Rule | Automated, continuously running detection that generates alerts and incidents |
| Livestream | A KQL query that runs continuously against new incoming data, refreshing about every 30 seconds |
| Bookmark | Saved evidence from a hunt: query, results, notes, tags, and context |
| Incident | A tracked, assignable security investigation grouping related alerts and evidence |
| Investigation Graph | Visual map of how entities (users, hosts, IPs, files, and so on) relate to each other |
| Entity Details | Contextual data about a single entity (activity, connections, related events) |

### Frequently Confused Pairs

> **Hunting Query vs Analytics Rule:** Hunting is manual and interactive. Analytics Rules run automatically and generate alerts on their own.

> **Bookmark vs Incident:** A bookmark preserves evidence and implies nothing about confirmed compromise. An incident is a tracked, assigned case built from confirmed or suspected evidence.

> **Livestream vs Hunting Query:** Both use KQL, but Livestream runs continuously against new data with no time filter allowed, while a hunting query runs once against a chosen historical range.

> **Investigation Graph vs Entity Details:** The graph shows relationships between many entities. Entity Details show context about one specific entity.

### Storage Locations to Memorize

* Bookmark data → **HuntingBookmark** table (Log Analytics workspace, queryable with KQL)

### Numbers to Remember

* Livestream refresh interval: approximately **30 seconds**
* Livestream queries: **no time parameters allowed**

### MITRE ATT&CK Quick Reference (From the Scenario)

* Tactic used in the walkthrough: **Credential Access**
* Technique referenced: **T1003**
* Hunting queries and custom queries can both be tagged with MITRE tactics and techniques for organization and later automation

### One Page Workflow to Memorize

```text
1. Analyst runs a hunting query (KQL) or watches Livestream
        │
        ▼
2. Suspicious results identified
        │
        ▼
3. Analyst bookmarks findings (query, notes, tags, MITRE mapping)
        │
        ▼
4. Investigation Graph used to explore entity relationships
        │
        ▼
5. Confirmed activity → Create Incident or Add to Existing Incident
        │
        ▼
6. Incident assigned to Incident Response team
        │
        ▼
7. Optional: validated Livestream query promoted to an Analytics Rule for future automated detection
```

> **Final Reminder:** Hunting proves a threat exists using manual investigation. Bookmarks preserve that proof. The Investigation Graph shows how the proof connects. Incidents turn that proof into a tracked response. Analytics Rules and Livestream exist to catch the same kind of activity automatically going forward.
