## Overview

Microsoft Sentinel gives analysts two tools for working with data that is too large or too old for a normal interactive query: **Search Jobs** and **Restore**. Both exist because standard KQL queries are optimized for **hot, recent data**, not for scanning enormous volumes of history or true archived logs.

> **Exam framing:** if a question describes searching months or years of log history, think Search Job or Restore, not a plain KQL query.

## Part 1: Search Jobs

### What Is a Search Job

A **Search Job** is a Microsoft Sentinel feature that lets an analyst search **very large datasets and archived logs** without slowing down or overloading the workspace. Rather than returning results instantly like a normal query, a Search Job runs **asynchronously in the background** and, once finished, writes only the matching records into a **new search results table**.

Search Jobs are the right tool when you need to:

* Investigate historical security events.
* Search archived logs.
* Look through many months of telemetry.
* Query datasets containing millions of records.

### Why Search Jobs Exist

SOC analysts often need to look far beyond "right now." Typical scenarios include:

* Investigating a breach that happened six months ago.
* Searching historical authentication logs.
* Finding evidence tied to an Advanced Persistent Threat (APT).
* Performing forensic work after an incident has already been contained.

Running a normal KQL query across an extremely large dataset can be slow and can consume workspace resources. Search Jobs solve this by running in the background, processing large volumes asynchronously, writing results to a separate table, and keeping the impact on the workspace low.

### How a Search Job Works

```text
Large Dataset or Archived Logs
          │
          ▼
     Search Job Starts
          │
          ▼
 Asynchronous Background Processing
          │
          ▼
    Matching Records Found
          │
          ▼
 Search Results Table Created
        (_SRCH suffix)
          │
          ▼
   SOC Analyst Queries Results
```

### Asynchronous Processing Explained

**Asynchronous** means you do **not** have to wait for the task to finish before continuing other work. When a Search Job is submitted, Sentinel does not search immediately and return results on screen. It effectively queues the request, processes it in the background, and notifies the analyst when it is done.

Example: searching 500 GB of logs covering the last 10 months.

```text
Step 1: Submit the Search Job
          │
          ▼
Step 2: Sentinel Acknowledges
        (status shows "Running")
          │
          ▼
Step 3: Background Processing
   (analyst is free to hunt, review
    alerts, work incidents, or close
    other cases while it runs)
          │
          ▼
Step 4: Notification Received
          │
          ▼
    _SRCH Table Is Ready to Query
```

> **Exam tip:** the analyst is never blocked during a Search Job. That "not blocked" behavior is exactly what "asynchronous" means in this context.

### Search Jobs vs Standard KQL Queries

| Aspect | Standard KQL Query | Search Job |
|---|---|---|
| Execution style | Interactive | Asynchronous |
| Results | Returned immediately | Delivered when the job finishes |
| Best suited for | Recent or smaller datasets | Very large datasets, long time ranges |
| Data queried | Hot data | Includes archived data |
| Where it runs | Directly against the selected table | Writes results into a brand new table |

### What Happens After a Search Job Completes

Once a Search Job finishes:

* A new table is created in the Log Analytics workspace.
* The table contains only the matching records, not the full source dataset.
* The table name always ends with the **`_SRCH`** suffix.

Example: a search over `SecurityEvent` produces `SecurityEvent_SRCH`.

### Supported Log Types

Search Jobs can run against three Log Analytics tiers:

| Log Type | Used For | Key Trait |
|---|---|---|
| **Analytics Logs** | Analytics rules, threat hunting, investigations, dashboards, workbooks | Full Sentinel capability, highest cost tier |
| **Basic Logs** | High volume, low priority sources (for example firewall or network logs) | Lower ingestion cost, reduced analytics capability |
| **Auxiliary Logs** | Specialized or supplementary data that does not need full analytics | Additional low cost storage option |

> **Exam tip:** Auxiliary Logs can be searched with a Search Job but, as covered later, they **cannot** be restored.

### Search Job Limitations

| Limit | Value |
|---|---|
| Tables searched per job | 1 (one table at a time) |
| Maximum search period | Up to 1 year |
| Maximum run time | Up to 24 hours |
| Maximum records returned | 1,000,000 records |
| Concurrent Search Jobs per workspace | 5 |
| Search Results tables per workspace | 100 |
| Search Job executions per workspace per day | 100 |

If an investigation needs to cover more than a year, it must be split into multiple Search Jobs. If more than a million matching records exist, tighter filtering is required.

### SC-200 Exam Tips (Search Jobs)

> * Search Jobs are **asynchronous** and run in the background, freeing the analyst to keep working.
> * They are built for **large datasets** and **archived logs**, not everyday queries.
> * Results always land in a new table ending in **`_SRCH`**.
> * They support Analytics, Basic, and Auxiliary Logs.
> * Memorize the numbers: 1 table, up to 1 year, up to 24 hours, 1,000,000 records, 5 concurrent jobs, 100 result tables, 100 executions per day.
> * A Search Job only ever returns matching records, it does not restore the full underlying dataset for open ended analysis, that is what Restore is for.

## Part 2: Restore Historical Data

### What Is Restore

Sometimes the evidence needed for an investigation lives in **archived logs**. Archived logs are cheap to store but are not built for fast, full KQL investigation. **Restore** solves this by copying the needed data into a temporary, high performance table inside the Log Analytics workspace. Once restored, that data can be queried with the **full power of KQL**, just like any normal table.

### Why Restore Data

Imagine investigating an attack that happened eight months ago, and the relevant logs are already archived. Without restoring them, queries are slower and investigation capability is limited. By restoring the logs, the data becomes available in a temporary table, full KQL queries become possible, and the restored data behaves exactly like a normal Log Analytics table.

### How Restoration Works

```text
Archived Log Table
          │
          ▼
Select Table and Time Range
          │
          ▼
      Restore Job Runs
     (in the background)
          │
          ▼
 Temporary Restored Table
        (_RST suffix)
          │
          ▼
   Run Full KQL Queries
```

The restored table is separate and temporary. Example: restoring `SecurityEvent` produces `SecurityEvent_RST`. Deleting the restored table does **not** delete the original archived source data, since it is only a copy.

### Restoring Data (Step by Step)

1. Open **Search & Restore**.
2. Choose the table to restore.
3. Specify the start and end time.
4. Start the restore operation.

You can also restore data directly from a previously saved search result if the relevant records have already been identified through a Search Job.

### Monitoring the Restore

Restoration is not immediate, the restore job runs in the background and progress can be tracked from the **Restoration** section. When the status changes to **Data Available**, the restored table is ready to query.

### SC-200 Exam Tips (Restore)

> * Archived logs are restored into a temporary table ending in **`_RST`**.
> * Restored tables support **full KQL**, unlike a `_SRCH` table which only holds matching records.
> * Restoration is temporary and never modifies the original archived data.
> * Delete restored tables once you are finished with them to reduce cost.
> * **Auxiliary tables cannot be restored,** use a Search Job for them instead.

## Search Job vs Restore vs Direct Query

This comparison is a common source of exam confusion, keep it clear:

| Feature | Direct Query (hot data) | Search Job | Restore |
|---|---|---|---|
| Data scope | Interactive retention only | Archived and large datasets | Archived data |
| Speed | Immediate | Asynchronous, up to 24 hours | Asynchronous, runs in background |
| Output | Query results on screen | New `_SRCH` table with matches only | New `_RST` table with full data |
| Query power on results | Full KQL | Limited to what the search matched | Full KQL |
| Works on Auxiliary Logs | N/A | Yes | No |
| Typical use case | Everyday investigation | Finding specific records across huge ranges | Deep, open ended analysis of a past period |

## Data Tiers in Microsoft Sentinel

Understanding why Search Jobs and Restore exist is easier once the underlying data tiers are clear. Log Analytics tables generally move through an **interactive retention period** first, and older data can then move to lower cost storage.

```text
Data Ingested into Sentinel
          │
          ▼
 Interactive Retention Period
 (Analytics, Basic, or Auxiliary Logs)
          │
          ▼
   Retention Period Ends
          │
          ▼
       Archived Logs
          │
          ▼
   Search Job or Restore
```

* **Analytics Logs**: full featured, used by analytics rules and workbooks, highest cost.
* **Basic Logs**: cheaper ingestion, reduced analytics features, good for high volume sources that are rarely queried.
* **Auxiliary Logs**: lowest cost option for supplementary data, searchable but not restorable.
* **Archived Logs**: data past its interactive retention window, cheap to keep, not directly queryable, accessed only through a Search Job or Restore.

> **Exam tip:** if a question mentions data that is "past its retention period" or "archived," the answer almost always involves either a Search Job or a Restore operation, not a normal query.

## Querying Results with KQL

Search Jobs and Restore are started through the Sentinel **Search & Restore** experience in the portal, not by typing a special KQL command. Once the resulting table exists, though, it is queried with ordinary KQL, exactly like any other table.

```kql
// Example: querying a Search Job results table
SecurityEvent_SRCH
| where TimeGenerated > ago(180d)
| where Account == "contoso\\jdoe"
| project TimeGenerated, Account, Computer, EventID
```

```kql
// Example: querying a Restored table with full KQL power
SecurityEvent_RST
| where TimeGenerated between (datetime(2025-01-01) .. datetime(2025-03-01))
| summarize EventCount = count() by Account, EventID
| order by EventCount desc
```

> **Exam tip:** a `_SRCH` table only contains the records that matched the search criteria, so aggregation across it is limited to that subset. A `_RST` table contains the full restored range, so it supports open ended analysis like the summarize example above.

## SC-200 Last Minute Revision

### Must Memorize Facts

| Item | Value |
|---|---|
| Search Job result suffix | `_SRCH` |
| Restore result suffix | `_RST` |
| Max tables per Search Job | 1 |
| Max search period | 1 year |
| Max Search Job run time | 24 hours |
| Max records per Search Job | 1,000,000 |
| Max concurrent Search Jobs | 5 per workspace |
| Max search result tables | 100 per workspace |
| Max Search Job executions | 100 per workspace per day |
| Log types Search Jobs support | Analytics, Basic, Auxiliary |
| Log types Restore supports | Analytics, Basic (not Auxiliary) |

### Frequently Confused Concepts

* **`_SRCH` vs `_RST`**: `_SRCH` holds only matching records from a search, `_RST` holds the full restored dataset for a time range.
* **Search Job vs Restore**: a Search Job filters and finds, a Restore brings back the entire slice of archived data for deep analysis.
* **Auxiliary Logs**: can be searched, cannot be restored, this exception is a favorite exam trap.
* **Basic vs Auxiliary Logs**: both are lower cost than Analytics Logs, but only Basic Logs can be restored.
* **Asynchronous**: means the analyst is not blocked, work continues while the job runs in the background.

### One Page Cheat Sheet

```text
NEED TO SEARCH HUGE OR OLD DATA?
          │
          ▼
   Is it just a normal recent query?
          │
   ┌──────┴──────┐
  Yes            No
   │              │
   ▼              ▼
Run KQL      Do you need full KQL power
directly     on the results afterward?
                   │
            ┌──────┴──────┐
           Yes            No
            │              │
            ▼              ▼
        RESTORE        SEARCH JOB
      (creates _RST) (creates _SRCH)
      Full KQL after  Matches only
      Not for          Works on Analytics,
      Auxiliary Logs   Basic, Auxiliary
```

Final reminders before the exam:

* Both features are asynchronous, background operations, the analyst is never forced to wait.
* Both create a **new, separate table**, the original data (archived or otherwise) is never modified.
* Restore is temporary storage, delete the `_RST` table when finished to control cost.
* If the scenario says "Auxiliary Logs" and "restore" in the same sentence, the correct answer is that this is **not possible**, use a Search Job instead.
* Search Jobs are capped at a one year lookback and a 24 hour run time, remember both numbers precisely, they are easy to swap by mistake.
